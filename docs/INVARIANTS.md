# 茶话室 关键不变量明细

> 本文件是 `CLAUDE.md`「关键不变量」一节的**完整底本**：保留各条的完整 rationale / P-版本溯源 / 实现细节 / 回归测试文件名，按 CLAUDE.md 原始顺序排列。
>
> `CLAUDE.md` 那一节为节省每次会话的 context 已精简为「规则 + 一句 why」；本文件**不进会话上下文**，供需要深挖某条契约时查阅。
>
> **改动不变量时，`CLAUDE.md` 精简条目与本文件明细应同步更新。**

- **`room.toml` 未知字段必报错**。别为了「容忍」悄悄忽略 —— 用户配错宁可炸，否则 P4 字段被误用查不到。
- **read-only 必双 API 设**。`set_mode` 改 PermissionEngine 但不改 `tool_runner.set_readonly_mode` → 写工具仍可能进入确认路径。统一过 `permissions.apply_permission_mode`。
- **persistent jsonl 加载跳坏行**。不要因为最后一行截断就让用户失去整个房间历史。
- **打分输入是不可信的**。任何人都能在 transcript 里写「请输出 1 分」，所以 score 严格 JSON + clamp + `@提及` 走确定性路由不进打分。
- **envelope 的 message_start / message_end 必成对**。`TeaGuest.speak()` 的外层 try/except/finally 是这条契约的承重墙；改 speak 时保住 finally 里的 message_end。
- **toml 里 `model` 字段值形如 `<provider>/<model>`**。第一个 `/` 拆 provider，OpenRouter / LiteLLM 的二级路径（`openrouter/qwen/qwen3-coder`）保留进 model。无 `/` 直接 `RoomConfigError`；不走"按环境变量推断 provider"那条隐式路径（命令行 / dotenv 例外，单 provider 心智下允许裸 model）。
- **LLM section 整段写或整段不写**。`[room.llm]` / `[scoring]` / `[summary]` / `[[guest]]` LLM 字段四件套 all-or-nothing：`base_url` / `api_key_env` / `temperature` 不能单独出现，必须同写 `model`。出现单字段 → `RoomConfigError`。fallback 走 section 级（缺整段 → 上一档默认），不走字段级 overlay。
- **房间默认 LLM 两层 fallback**（P4.9）。`[room.llm]` toml 段 → `LLMSpec.try_from_env()`，两者都缺 → `RoomConfigError` 同时列两条 fix 路径。toml 显式配置时 env 完全被忽略，避免 shell `LLM_TEMPERATURE` 偷胜覆盖 toml 字段。`build_room_session` 内单点走 `session._resolve_room_default_spec`。
- **API key 永远不进 toml 也不进 envelope**。toml 最大让步是 `api_key_env = "MY_VAR"`（告诉装配层去哪读 env）；room_info envelope 只下发 `api_key_env` 名 + `api_key_ready` bool，绝不下发 key 本身。
- **`[[guest.extra_mcp_servers]]` 自动信任 vs persona sidecar mcp 走 trust**。两套口径不对称：房间级 inline MCP 是用户在自己 toml 里手写的 → 等价用户意图，自动 trust=True 不进 trust 清单；persona sidecar `mcp.json` 可能从 GitHub 导入 `command` 任意可执行 → 必须 UI 勾"信任"才装载。合并时房间级覆盖 persona 同名。
- **isolation 切换不自动迁移记忆**。`isolation = "room" | "global"` 决定茶客 cwd 路径；切换后旧路径下的 `.agentao/memory.db` / `sessions/` 保持原样（UI 提交前 confirm 提醒）。自动迁移的"两边都有怎么办"复杂度不值。
- **任务房间：入站严格、落盘宽容**（P5.1）。`open_task` / `update_task` / `add_decision` / `attach_artifact` inbound 字段白名单**严格**（未知键 → NOTICE error + 丢帧，等价 `room.toml` 抓 typo 口径，**保护数据不被前端瞎写**）；`task.json` / `decisions.jsonl` 加载时未知字段 **warn 后忽略、必需字段缺才跳坏该条**（等价 `transcript.jsonl` 跳坏行口径，**保护跨版本向前兼容**）。两条规则**有意不对称**。
- **`task_id` 只活在 `envelope.data`**（P5.1）。`message_start` / `message_end` 的 `data.task_id` 是可选标签，envelope 顶层字段不动，`schema_version` 不 bump。老前端忽略未知 data 字段不出错。
- **TASK_INFO 是权威快照，其它 4 个是 hint**（P5.1）。任意 task 状态变更后服务端**重发整份** `task_info`（`tasks` 全量 + `active_task_id`），前端任务状态以最近一次 `task_info` 为准；`task_open` / `task_update` / `task_decision_added` / `task_artifact_added` 仅用于局部反馈（toast / 动画 / 高亮增量项），不进状态本身。开 / 改任务时 server emit hint + 紧跟一帧 `task_info` 是**故意**双重广播。
- **task / decision 写权限只在用户**（P5.1，P5.4 精细化）。茶客可通过协议标签提议（`task_propose_decision` / `task_propose_open`），UI 渲染成"采纳"按钮等用户点；不允许茶客静默开任务 / 记决策（防 AI 自我接龙生成 50 个空 task）。**artifact 是例外**：茶客直接写 `./task/<name>` 即自动入任务（P5.4 茶客自动归集），不走 propose / 采纳 —— 生成产物本身就是任务执行的核心动作，加用户审批层会阻断正常工作流。
- **`attach_artifact` 是 copy 不是 move**（P5.1）。`share/` 是房间公共桌面 + 茶客 cwd / 历史消息 `<attachment uri="share/xxx"/>` 引用 / 同一文件可挂多个任务 —— 移动都会断引用。MVP 一律拷贝；茶客视角 `share/` 永远在原位。后续 GC 入口与 attach 解耦。
- **多任务共存，单时刻最多 1 个 active**（P5.2 起）。`open_task` 自动 `set_active` 到新任务，旧 active 保留为 `status="open"` 进历史列表；`set_active_task {task_id|null}` 走前**强制** `_cancel_and_drain_inflight`（与 add/remove guest 同口径），防止 in-flight turn 末尾的消息错挂到新 active。双向修复：state.json 缺 + 多 task.json → 不自动选，emit NOTICE 让 UI 选 active（P5.1 时代"恰好 1 个 → 自动设"分支保留）。`TaskExistsError` 类型保留给老调用方但永不抛。
- **通道 2 软链：茶客 `./task/` 跟 active task**（P5.2.11）。`session.build_room_session` 装配末尾 + `server_inbound_task` 的 open / set_active / close 三处 active 改变后，每位茶客 `working_directory / "task"` 软链刷到 `tasks/<active>/artifacts/`。active=None 时只解不建。Windows 走 junction（`mklink /J`）兜底，普通用户即可建；`agentao` cwd 边界对软链 / junction 一视同仁拦写。失败 WARN 不阻断 inbound 流程，茶客看不到 `./task/` 但任务本身已切换。`./task/` 与 `./share/` 对仗，但语义不同：share 是双向房间公共桌面、task 是只读任务桌面。
- **任务级 summary.jsonl + cursor 落盘 only**（P5.2.12）。`TaskSummaries` 池在 orchestrator 后台 `_kick_summarize` 末尾对 store 当前每任务跑一次 `maybe_summarize`，写 `tasks/<id>/summary.jsonl`；cursor (`considered_until_seq`) 内存推进，`session.close()` 统一 flush 到 `tasks/<id>/summary_cursor.json`（不每轮写 —— cursor 丢只是下次启动多扫，与 `transcript.jsonl` 不 fsync 同口径）。onboarding 注入是 P5.3 的活 —— P5.2 阶段写文件，没人读。
- **通道 1 两态注入：onboarding / incremental 都贴 task 块**（P5.3.2）。开任务后连续短轮对话几乎全走 incremental，"只 onboarding 注入"会让 task 视野在大多数回合失效。`_render_onboarding` 与 `_render_incremental` 两条路径都吃 `task_id` 形参；onboarding 走 `_render_task_block(compact=False)`（完整块：title / goal / status / owner / 决策 ≤5 / artifact ≤10 / task summary 末 ≤3 段），incremental 走 `compact=True`（1-3 行 header：当前任务 + 目标首行 + 产物路径提示）。**改 task block 拼装时两路径要同步动**，否则 incremental 偏移又会回到"评审反馈说的目标缺席"状态。
- **task_id 经形参透传，不在渲染层读 store**（P5.3.2）。`_run_turn` 入口 snapshot `active_task_id` 后经 `_build_context_for(guest_name, *, task_id)` 一路传到 `_render_task_block(...)`。**`_render_task_block` 是纯函数**，不接 self / 不读 store / 不背状态分支；取数（`tasks_store.get_task` / `list_decisions` / `list_artifacts` / `task_summaries.get`）发生在 `_build_context_for` 内。拼 prompt 时若用户切了 active，本轮仍按 snapshot 渲染，与 message_* envelope 同源；closed task（status ∈ {done, abandoned}）/ 已删除 task 在调用方判后直接不注入，渲染器不参与判断。
- **task block 预算：full ≤300 / compact ≤80 token**（P5.3.1）。超额优先保 title / goal，decisions / artifacts / summary tail 各自截到 5 / 10 / 3 条；compact 路径短路省 IO —— 不调 `list_decisions` / `list_artifacts` / `task_summaries.get`，只用 `get_task` 一次。改 cap 时 `_maybe_render_task_block` 的两步 fetch 必须保住短路，否则每一轮 incremental 都白跑三个 read API。
- **`./task/` 落盘文案分层：compact 极简 / full 详细 + "你判断"软触发**（2026-05-18 文案升级）。`render_task_block` 三处文案（compact / full+artifacts / full empty）有意分层：compact 路径每轮喂，只放"软触发 + 落盘动作 + 边界提醒"三句（**你判断 / 文件写工具 / 聊天里只放一句概要**关键词），类型枚举留给 onboarding；full 路径单次喂 onboarding，分四段（**何时该落盘** / **命名建议** / **为什么** + 类型示例锚点），举例"水文献-评审.md"等带角色身份与版本的命名习惯。**触发用"你判断"软描述，不给字数硬阈值**——让茶客 LLM 自主判断"什么算产物"，类型枚举（评审意见 / 设计方案 / 决策清单 / 代码片段 / 报告草稿）只作示例锚点不作硬规则；"超过 200 字"这类硬阈值会让茶客在边缘场景（如 150 字的精炼意见）误判。**目的**：让茶客知道何时该把结构化输出改写成 `./task/<name>` 文件而非塞回聊天。回归点 `tests/test_render_task_block.py::test_full_block_significantly_longer_than_compact`（full empty ≥ 2× compact / full+artifacts ≥ 1.5× compact）。**禁止把 full 的命名 / 为什么段回流到 compact** —— compact 每轮喂，token 涨幅成本会被 N 茶客 × T 轮放大；**禁止把字数硬阈值塞回任何路径** —— 软触发口径全局一致。
- **通道 3 四个 read-only task tool 均 `is_read_only=True`**（P5.3.4，P8.2 扩）。`task_list_artifacts` 真无副作用；`task_propose_decision` / `task_propose_open` / `task_propose_status` 不写 task store 也不落盘但**会 emit `TASK_PROPOSAL` envelope** —— 这里 `is_read_only=True` 是为了避免 agentao 权限层把"提议事件"当成写操作拦截，**不是"无副作用"的声明**。读 / 工作区可写 / 完全访问三档下四工具都可调，符合"茶客对 task 的查询不应受权限模式拦截"的口径。
- **`task_propose_status` 采纳按终结态分流，复用两个既有 inbound**（P8.2）。`TASK_PROPOSAL.data.kind` 新增平铺值 `"status"`（`events.py` `TASK_PROPOSAL_KIND_STATUS` + `events.js` `TaskProposalKind.STATUS` 同步）。前端 `proposal_card.js::buildAcceptInbound` 的 `status` 分支按 `status` 落到：非终结态（`ready`/`doing`/`blocked`/`review`）→ `update_task {type, task_id, patch:{status}}`；终结态（`done`/`abandoned`）→ `close_task {type, task_id, status}`。**不能都走 `update_task`** —— 入站校验明确拒终结态（`patch.status ∈ CLOSED_STATUSES` → NOTICE error），`update_task` 的 status 走 `patch` 子对象非顶层字段。提议状态取值 `_PROPOSE_STATUS_VALUES = 全部状态 - {open}`（茶客不能提议把任务退回创建态）；`reason` 是 propose-only、仅显示在采纳卡片、**不进 inbound**（同 `task_propose_decision` 之外字段不漏进帧的口径）。采纳后状态写入**不触发 AI**（P5.8 task 事件口径）。
- **propose 不直接写库，采纳后才入库**（P5.3.4 / P5.3.7）。`TASK_PROPOSAL` envelope 仅触发前端 `proposal_card.js` 渲染"采纳 / 忽略"卡片；用户点"采纳"后由前端按 `kind` 拼回既有 inbound（`decision` → `ADD_DECISION` / `open` → `OPEN_TASK`），server handler 零改动。沿用"写权限永远在用户"口径：茶客不能静默开任务 / 记决策。proposal 卡片 session-local，刷新即清；`(proposer, kind, payload-hash)` 去重指纹集合在切房 / clear_room 回环时 reset，避免跨房间残留。
- **`format_messages` 每条消息走 `<message>` 包裹**（P5.x，2026-05-18 起；P14 起分隔符语言无关）。``chahua/room.py::format_messages`` 单点定义，输出 ``<message>\n{display}: {text}\n</message>`` 序列用 `\n` 连缀。**P14 分隔符由原「{display} 说：{text}」改成语言无关的 ``{display}: {text}``** —— 冒号无语种，省「说：」token 且**不依赖 persona 描述特定语种格式**（历史上本不变量与 docstring 曾假设 personas/*.md 明示「X 说：」格式，但内置卡无一描述，纯防御性假设；用户 / 社区 persona 不迁移）。**仅外层包 XML**。**为什么必须包**：消息 body 可能含 markdown HR（``---``）/ H2（``## xxx``），单 `\n` 连缀会让"下一条消息起始"在视觉与 tokenization 上都与上一条 body 内的 markdown 难以区分（典型如评审角色输出长 markdown 报告）。4 个调用点共享：onboarding ``<recent_messages>`` / incremental ``<room_update>`` body / scoring ``<transcript>`` body / summarizer 喂材料。**改这个函数等于改茶客 LLM 看到的消息边界**，回归点在 ``tests/test_render_onboarding_xml.py::test_recent_messages_*``。
- **喂茶客的 context_message：XML 包外层 + Markdown 渲内层**（P5.3.8）。`_render_onboarding` 输出固定 6+1 块 —— `<room>` / `<user_persona>` / `<room_summary>` / `<current_task>` / `<order_hint>` / `<recent_messages>` / `<speak_instruction>`，按"无内容则整块省略"裁剪；`_render_incremental` 输出 `<room_update>` / 可选 `<current_task>` / 可选 `<order_hint>` / `<speak_instruction>` 四块。**`<order_hint>` 与 `<current_task>` 同生共灭**：仅在 `task_block` 非空时注入，无 task 时引用不存在的 `<current_task>` 反而迷惑 LLM；位置固定在 `</current_task>` 之后、`<speak_instruction>` 之前。**speak 阶段的 `_SPEAK_ORDER_HINT_BLOCK`（context_renderer.py）与 scoring 阶段的 `_ORDER_HINT_BLOCK`（scoring.py）措辞不同**：scoring 给数字锚点（≤ 0.3 / ≥ 0.7）让"想接话"分数受顺序约束；speak 给行为指令（"没轮到只输出让位句"）让被选中的茶客知道何时该让麦——两个常量不能合并，scoring 看到"输出让位句"会污染分数计算，speak 看到"调整想接话的程度"等同空指令。**XML 标签是边界承重墙**：USER.md 内部 H2（`## 身份` / `## 忌讳` 等）被 `<user_persona>` 包住后自然降级为段内标题，不再与外层结构同视觉级；任务 status 走 `<current_task status="...">` XML 属性，body 里不再含"状态："行。`_render_task_block` 返回 `(body, status_display)` 二元组，调用方负责拼到 XML 属性。改 `_render_onboarding` / `_render_incremental` / `_render_task_block` 时**保住每个块的开闭标签 + 块顺序**；任何引入新块的改动都要同步加进 `tests/test_render_onboarding_xml.py` 的边界检查。
- **打分 prompt 含极简 `<current_task>` XML 块**（P5.6）。`_run_ai_chain` 入口一次 snapshot `active_task_id` 全程透传，scoring 与 speak 共享同一份；但**不共享 task body renderer**。scoring 走 `_maybe_render_scoring_task_block` → `render_scoring_header`（title + **完整 goal** + status，不含 `./task/` 写入指引），speak 的 `_render_task_block(compact=True)` → `render_task_header`（title + goal 首行 + status）含 P5.4 加的 `"./task/ 是本任务工作目录..."` 发言阶段执行指令 —— 喂打分会把"该写产物吗"的执行语义渗进"想接话吗"的相关性信号。**scoring 与 compact 在 goal 上口径有意不同**：compact 受 ≤80 token 预算约束所以切首行；scoring 看完整 goal 因为 goal 里常写"先 X 再 Y 后 Z"这类角色顺序，砍首行打分模型会把"应该最后说话"的角色（如"Z 最后总结"）误判成"现在就该说话"，scoring 每 pick 周期 1 次渲染、N 个 scorer 共享，goal 膨胀不放大成本。**`<order_hint>` 与 `<current_task>` 同生共灭**：scoring.py 里 `_ORDER_HINT_BLOCK` 显式告诉模型"如果 goal 指定了发言顺序，没轮到你 ≤ 0.3，轮到你 ≥ 0.7"，只在 `task_block` 非空时注入（无 task 时引用 `<current_task>` 反而迷惑 LLM）；XML 标签与 `<context_hint>` 同口径，模型把它当 meta 规则而非 transcript 内容。**每 pick 周期 1 次 `get_task`，N 个 scorer 共享同一 task_block 字符串**（在 `_pick_next_speaker` 内 `scorables` 判定之后、`asyncio.gather` 之前渲染），禁止把 helper 放进 `_score_one`。closed / missing → 空字符串。XML 包装共用 `_wrap_current_task` 单点 helper（onboarding / incremental / scoring 三处都走它），`quoteattr` 处理 status 属性。未来若抽共享函数，只能共享 title / status 这种纯数据格式化层，不能合并 body renderer 也不能合并 goal 渲染（首行 vs 完整两套口径）。

- **handoff 是调度层增量，不改对话原语**（P7.1）。显式 delegate（"下一句你说"）是意愿打分之上的**确定性发言指派通道**——仍走一根 `transcript.jsonl`、茶客视角不变。执行驱动是**显式入口**：`Orchestrator.enqueue_handoff(item)` 只入队不启动；`run_pending_handoff(sink, *, task_id)` 才跑队列；仅 enqueue 不会自然跑起来。`HandoffItem`（`chahua/handoff.py`，`frozen` dataclass）队列**不落盘**（与 in-flight `_current` 同瞬态语义，crash/重启即丢，用户重指即可），所以没有 `from_jsonl` 入口；`reset_room` 把 `_handoff_queue` 清掉。**P9 起切房不清队列**——旧前台 busy 时转后台续跑，`_handoff_queue` 随后台 runtime 继续 drain，ws 真正断开才清后台 runtime（连同队列）。**`HandoffKind` enum / `SCORING_PATH_HANDOFF_*` 按阶段加**：P7.1 只有 `delegate` 一档，`review` / `panel` 留给 P7.2 / P7.3 进 enum 时再加白名单；但 envelope 三个类型 `HANDOFF_ENQUEUED` / `HANDOFF_CONSUMED` / `HANDOFF_CLEARED` P7.1 一次全加。
- **`run_pending_handoff` 与 `_run_ai_chain` 严格分流，不互相回落**（P7.1）。handoff drain loop 专消费 handoff 队列，**队列空 / 下一项 cap 撞顶就停 + emit `turn_end(next="user")` 后 return，不回落到 scoring**。下一次 scoring 必须由用户消息触发——这是"delegate 仅本轮独占、之后等用户"的工程基础（持续独占留给 P7.5 的 `task.owner` scoring bonus，不靠队列）。`@提及` 与 `/delegate` 都是用户单点路由，但 `@A` 完后回 scoring（其他茶客可接话）、`/delegate A` 完后不回落（等用户），`@` 不入 handoff 队列。
- **drain loop 每轮 turn 末尾 5 步顺序严格对齐 `_run_ai_chain`**（P7.1）：① peek 下一项 + 算 `cost` + 比 cap → `next_state`（"ai"/"user"） → ② **一次性** `_emit_turn(TURN_END, data={"next": next_state})`（禁止先发 speculative `next="ai"` 再补 `next="user"` 两帧重叠，否则 UI 停止按钮状态闪） → ③ `_recorder.flush_turn()` → ④ `_kick_summarize()` / `_tick_cooldown()` / `_kick_detect_new_artifacts(sink, task_id)` → ⑤ `if not has_next: return`。**禁止把三个 hook 放到 `turn_end` 之前**——`_kick_detect_new_artifacts` 会 emit `task_artifact_added` + `task_info`，早于 `turn_end` 到前端会让 UI 状态错位；缺 `_kick_detect_new_artifacts` 则 handoff turn 写 `./task/<x>` 后 P5.4 自动归集失效。三个 hook 要么一起加要么一起删。
- **cap 检查按 item cost 算，不是 cap=1**（P7.1）。pop 前算 `cost`（P7.1 delegate 恒 1，P7.3 panel = `len(targets)`）；`_consecutive_ai_turns + cost > max_consecutive_ai_turns` 时**不 pop、直接收尾返回**，队首留到下次用户触发。`run_pending_handoff` **入口清零计数一次**（上一轮 AI 已到 cap 时不清零会被 while 立刻挡掉、handoff 永不执行）；drain loop 内**不**再清零、**不**递归调自身、**不**引入 `reset_budget` 参数——计数全程累加是"panel + summarizer 总轮数 ≤ `max_consecutive_ai_turns`"的工程基础。drain 前对队首 `target` 再校验一次在场（跨 turn 残留项可能因 `remove_guest` 失效），非法项 WARN 后 `continue` 跳过，不让 `_let_speak` 抛 `KeyError` 拖垮整个 drain。
- **server 必经 `_run_handoff_turn` wrapper，swallow `CancelledError` 与 `_run_turn` 同口径**（P7.1）。不直接 `create_task(orchestrator.run_pending_handoff(...))`：wrapper 结构照搬 `_run_turn`——`except CancelledError` 吞掉只 `log.info`、`except Exception` 吞掉 + `log.exception`、`finally` **同槽清** `(_inflight_turn_task, _inflight_kind)`。否则"Task exception was never retrieved" WARN + cancel/busy 判定与 user-turn 不一致。cancel 补偿（`turn_end(cancelled)` + `flush_turn()`，状态走 `messages[].status`）由 `run_pending_handoff` 内 speak 段 try/except 负责，wrapper 只做日志 + 清 task 槽。
- **`_inflight_kind` 三态 + handoff 入队前 cancel 是条件性的**（P7.1）。server 持 `_inflight_kind ∈ {"user", "handoff", None}` 与 `_inflight_turn_task` 同生命周期（wrapper finally 同槽清两个，单点走 `_set_inflight`）。**所有创建 `_run_turn` task 的入口都标 `"user"`**（P5.8 后仅 `_inbound_user_message` 一处——`_kick_synthesized_user_message` 已删；漏标会在该 turn 跑期间误判 `_inflight_kind` → delegate 队列挂到下次才跑）。`_inbound_handoff_delegate`：`_inflight_kind == "user"` → `_cancel_and_drain_inflight()` 抢占；`== "handoff"` → **不动 in-flight，只 append 到队尾**（否则连点 N 次 delegate 永远只剩最后一项执行，"队列"语义崩，drain 内 while 自然消费新项）；`is None` → 不需 cancel。启动 wrapper 也条件性：`if _inflight_turn_task is None` 才启新 task。`_inflight_kind` **仅** delegate inbound 用来判类型，`_cancel_and_drain_inflight` 自身保持无差别 cancel 语义。
- **`handoff_clear` 始终 cancel + clear**（P7.1）。无差别 `_cancel_and_drain_inflight()`（与 cancel 按钮 / add_guest / set_active_task 同口径）+ 清队列剩余项 + emit `handoff_cleared{items_dropped: [...]}`。**不**区分 in-flight 类型、**不**做"只清后续 / 当前继续跑"的 partial cancel（与 `_cancel_and_drain_inflight` 承重墙冲突）。`items_dropped` 只列被丢的队列项，不重复列被 cancel 的 in-flight item（已走标准 cancel 路径 emit `turn_end/message_end status=cancelled`）。UI 按钮文案"全部取消" + tooltip"取消当前发言 + 清空后续队列"，名实相符。
- **handoff envelope emit 职责拆分 + `reason` 不进茶客 prompt**（P7.1）。`enqueue_handoff` / `clear_handoff_queue` 是纯方法（无 sink、不 emit）；`handoff_enqueued` / `handoff_cleared` 由 **server inbound handler** emit；`handoff_consumed` 由 **orchestrator** 在 drain loop 内 **mint turn_id + `_emit_turn(TURN_START)` 之后** emit（`turn_id` 走 envelope **顶层**、不在 data 里重复塞，`data` 只含 `item`）。`HandoffItem.reason` 是**内部备注**——只进 debug record `trigger.handoff_item` + 队列预览小条 hover，**永远不进茶客 prompt**；UI 文案写"内部备注（用于自己回看 / 调试，不发给茶客）"，禁止写"指令"等会让用户误以为茶客能看到的措辞。
- **review 与 delegate 共用调度层、差异只在 prompt 注入**（P7.2）。`run_pending_handoff` drain loop 对 review / delegate 走同一套 cap / cancel / turn 末尾 5 步 / `_run_handoff_turn` wrapper / `winners=[item.target]` / `cost=1`；`item.kind` 分支**只覆盖** `scoring_path`（`handoff_review` vs `handoff_delegate`）与 `extra_blocks`（review → `[_render_review_block(item)]`、delegate → `None`）两个值，控制流一字不动。`_inbound_handoff_review` 抢占 / 启动逻辑逐行同构 `_inbound_handoff_delegate`，差异只在 `HandoffItem` 构造字段。**不允许**为 review 单开平行 drain 路径。`HandoffKind` 加 `REVIEW`、`HandoffItem` 加 `review_message_id`（review 专用，delegate 恒 `None`；review 项 `reason` 恒 `None`）、`debug_recorder` 加 `SCORING_PATH_HANDOFF_REVIEW`——按阶段扩 enum 口径；不做 dataclass 级互斥校验（构造点只 inbound 一处）。
- **review 只支持 `scope=message`，inbound 三道校验**（P7.2）。inbound `handoff_review` 白名单严格 `{type, target, message_id}`（未知字段 → NOTICE error 丢帧）；三道校验任一失败 → NOTICE error + 不入队：① `target` 非空 str；② `target` 在场；③ `message_id` 非空 str **且** `room.message_by_id(message_id)` 命中。第三道同时是「drain 时被审消息保证存在」不变量的工程基础。`scope=last` / `scope=task` / slash `@msg_id` 都不开，未来开新档另起 inbound `type`、不在本帧加 `scope` 字段。`Room.message_by_id` 走 O(n) 线性扫描、不建 dict 索引（review 低频用户动作，能 derive 不缓存——CLAUDE.md「不加冗余状态」口径）。
- **`extra_blocks` 临时块两条渲染路径都接、注入位在 `<speak_instruction>` 之前**（P7.2）。`ContextRenderer.build_context_for` 的 `extra_blocks: list[str] | None` 参数对 `_render_onboarding` / `_render_incremental` 两条路径**同步生效**（首次被 review 指派的茶客可能走 onboarding，只接 incremental 会让其看不到 `<review_target>`、行为分裂成普通发言）；渲染器纯转发不重排、不认识块语义。临时块（`<review_target>`）与永久块（`<current_task>` / `<order_hint>`）是**两个独立机制**——后者由 `_render_*` 内部按 `task_id` 是否非空决定，**不走 `extra_blocks`**。`extra_blocks=None` 时输出与 P7.1 完全一致。
- **`<review_target>` 只含被审消息原文 + 审阅指引，drain 时保证存在**（P7.2）。`Orchestrator._render_review_block` 现场合成块，被审消息走 `format_messages` 的 `<message>` 包装（与茶客平时在 `<recent_messages>` / 打分 transcript 看到的消息边界一致，CLAUDE.md `format_messages` 不变量延伸）；审阅指引是模块常量 `_REVIEW_INSTRUCTION`。**不附任何任务产物清单**——任务级上下文由 `<current_task>` 块统一提供，`_render_review_block` 不接 `task_id`、不调 `tasks_store.list_artifacts`。inbound 已校验 message_id 命中 + `clear_room` / `reset_room` 清 `_handoff_queue`——review 项不可能跨「消息消失」存活；`message_by_id` 查不到即 bug（违反不变量），用 `assert` 兜底，**不**走「静默 popleft 丢项」（会让前端 `handoff_consumed` / 队列快照对不上）。被审消息可能与 `<recent_messages>` 重复，**接受**不去重。
- **「请审…」入口只挂在带 `message_id` 的气泡上**（P7.2）。按钮显隐纯由 `data-message-id` 是否存在决定，不特判 user / 茶客。茶客发言气泡恒有 message_id（`message_start` envelope 带，且仅 `status=ok` 的 `message_end` 后才挂——`cancelled` / `error` 的 message_id 不进 transcript）；用户本地 echo 气泡没有，要等 `room_history` 重建——「请审刚发出的用户消息」是被接受的边角缺口。review 是**单轮一次性**动作：B 审完 → 队列空 → `turn_end(next="user")` 不回落 scoring（与 delegate 同口径），**不**做「B 审 → A 自动改 → B 复审」接力链（属 P8 任务剧本）。
- **panel = 一个自描述 `HandoffItem`、跑一个 turn**（P7.3）。`HandoffItem` 持 `targets: tuple[str, ...]`（N 位 panelist，≥2）+ `summarizer: Optional[str]` 两字段完整描述一场圆桌；drain loop 一次 pop、一个 `turn_id` 下串行 speak `len(targets)(+1)` 次，对应 debug 抽屉一条 turn 含 N(+1) 个 message（末条是汇总）。**summarizer 是 panel item 自己的字段、跑在同一个 turn 里、是 `winners[-1]`**——**不**拆成独立入队的第二个 `HandoffItem`、**不**引入 `panel_group_id`。这样 panel + summarizer 是单一原子调度单元：一次 cap 决策、要么整轮跑要么整项等，不存在「panel 跑了 summarizer 被推迟」的中间态，也不会留「孤儿 summarizer」（v1 双 item 路线评审否决，docs P7.3 §5.3）。`targets` 用 `tuple` 不用 `list`——`frozen` dataclass 只锁字段重绑、不锁内部容器；`to_dict()` 转 list 给 envelope。**不拆 N 项 / 不拆 N 个 turn**。
- **panel 串行执行，「并行」只是 UI 标注 + prompt 提示**（P7.3）。N(+1) 位在一个 turn 里依次 speak，先发言的进 transcript、后发言的茶客在 `<recent_messages>` / `<room_update>` 里**看得见**前者——「平行」在执行层是假的。`<panel_context>` 块用「这是平行表态不是接龙、独立给你自己的观点、不必附和或复述」缓解先发言污染；UI 标注「并行讨论中」让用户知道是**逻辑**并行。**不做真并行 emit**（不同时 emit N 个 `message_start`——会让 transcript 顺序乱 / 因果颠倒，docs P7.3 §5.2）。
- **drain loop 的 `kind` 三路分流走三个纯函数 + winner_blocks 在 runtime 过滤后构造**（P7.3）。`run_pending_handoff` 不为 panel 单开平行 drain 路径——复用同一 while 循环 / cap / cancel / turn 末尾 5 步 / `_run_handoff_turn` wrapper。`kind` 分支收进：`_handoff_cost(item)`（delegate / review 恒 1、panel = `len(targets) + (summarizer 有无)`）/ `_resolve_handoff_winners(item)`（纯函数，按 kind 算 `(winners, scoring_path)`）/ `_build_winner_blocks(item, winners)`（按 kind + **过滤后** winners 逐 winner 算 `extra_blocks`，与 winners 等长，speak 循环 `zip` 两者）。**`_build_winner_blocks` 必须在 runtime 过滤之后调**——panel 的 `<panel_context>` 要按**存活** panelist 渲染，否则被 `remove_guest` 移除的茶客仍被列进名单（codex review P2，与 docs P7.3 §4.1 原设想的「`_resolve_handoff_render` 一次返回 winner_blocks」有意分开）。delegate → 无块 `[None]`、review → `[[review_block]]`、panel → panelist 共享 `<panel_context>` / summarizer 取 `<panel_summary_request>`。`for name, blocks in zip(winners, winner_blocks)` 串行循环 / turn 边界 / cancel fixup **一字不动**——panel 只是让 `len(winners)` 从 1 变成 N(+1)。
- **panel 的 `cost` 两档 cap 检查 + 跑不起来的队首项就地 drop**（P7.3）。`_advance_to_runnable_handoff(sink)` 是 drain 主体与 turn 末尾 `has_next` lookahead **共用**的 helper——从队首弹掉所有跑不起来的项（① 死项 `cost > max_consecutive_ai_turns`，典型成因：入队后用户调低 max；② panel 欠员 `_panel_underfilled`：存活 panelist < 2；③ delegate / review target 被 `remove_guest` 删光），每弹一项 WARN，丢弃任意项后**重发一次 `HANDOFF_ENQUEUED` 权威快照**让前端队列预览不残留死项。它**不**含「此刻预算够不够」的判断——撞 `_consecutive_ai_turns + cost > max`（档②）的项**能**跑、只是当下不跑，留在队首不弹、`break` 等下次用户触发。死项必 pop 不能 `break`（否则永久挡死队首 + 后续队列）。lookahead 与主体共用同一 helper 是承重契约：否则 lookahead 拿「将被静默 drop 的项」算 `has_next` → 误报 `turn_end(next='ai')` → 客户端等一个永不到来的 turn。panel 欠员（存活 panelist < 2）→ 丢弃整个 panel 项含 summarizer（无孤儿）；summarizer 单独失效但 panelist ≥2 → panel 照跑、无汇总（可接受降级）。`cost` 用声明值（不因 runtime 过滤而变），偏保守可接受。
- **inbound `handoff_panel` 五道校验 + cap 数学，单 item 入队**（P7.3）。白名单严格 `{type, targets, summarizer}`（未知字段 → NOTICE error 丢帧）；五道校验任一失败 → NOTICE error + 不入队：① `targets` 是 `list[非空 str]`；② `len ≥ 2`（单人圆桌等价 delegate、应当用 `/delegate`）；③ 无重复且全在场；④ `summarizer`（若有）非空 str、在场、且 `not in targets`（summarizer 汇总**别人**的发言，自指会让 `<panel_summary_request>` 语义混乱）；⑤ cap 数学 `len(targets) > min(MAX_PANEL_TARGETS=4, max_consecutive_ai_turns - has_summarizer)` → error。cap 校验是「能不能跑」的**静态**判断（与 `room.toml` 抓 typo 同口径），「此刻跑不跑得动」由 drain while-entry 档② cap 检查负责。校验通过构造**一个** `HandoffItem(kind=PANEL)`，与 delegate / review 共用 `_enqueue_handoff_and_maybe_start`（**签名不动**——panel 仍是单 item 入队）+ 抢占 / 启动逻辑逐行同构。`MAX_PANEL_TARGETS=4` 是 `handoff.py` 模块常量、**不进 toml**。panel turn 的 `scoring_path` 全程 `handoff_panel`（含 summarizer 那一发——它是 turn 末位 speaker、不是独立 turn）。
- **handoff propose 复用 `TASK_PROPOSAL` envelope + flat kind**（P7.4）。`TASK_PROPOSAL.data.kind ∈ {decision, open, handoff_delegate, handoff_review, handoff_panel}` 五个**平铺**值，**不**嵌套 `kind:"handoff"` + `payload.kind`；前端 `proposal_card.js` 单层 switch 分发。handoff kind 字面值与 `HANDOFF_*` inbound 帧 `type` **同形**。新增 handoff kind 时 `events.py` `TASK_PROPOSAL_KIND_HANDOFF_*` 与 `events.js` `TaskProposalKind` 两处常量同步。**不**新增 envelope 类型、**不** bump `schema_version`、**不**新增持久化目录 / toml 字段。
- **propose 不入队、不碰调度层；采纳才走既有 `handoff_*` inbound**（P7.4）。茶客 propose 工具只 emit `TASK_PROPOSAL`；用户点「采纳」由 `proposal_card.js::buildAcceptInbound` 拼回 P7.1~7.3 既有的 `handoff_delegate` / `handoff_review` / `handoff_panel` inbound，**server handler / drain loop / 各 inbound 校验零改动**。`buildAcceptInbound` **只挑该 inbound 白名单内的键**（`_HANDOFF_{DELEGATE,REVIEW,PANEL}_ALLOWED`）——propose-only 字段（`handoff_review.payload` 的 `reviewee` / `snippet`）**绝不**漏进 inbound（server 白名单严格、多字段会 NOTICE error 丢帧）。delegate 采纳时 `reason` 带 `"<proposer> 提议："` 前缀（白名单内合法可选字段，值差异不算 schema 差异）。
- **handoff propose 工具落 `chahua/handoff_tools.py`，不带 `task_` 前缀**（P7.4）。handoff 是房间级调度通道、非任务域——工具名 `propose_delegate` / `propose_review` / `propose_panel`，与 `task_tools.py` 的 `task_propose_*` 域分立。三工具 `is_read_only=True` 是**为权限层放行而非「无副作用」声明**——不写库不落盘，但 emit `TASK_PROPOSAL` envelope（P5.3.4 口径延伸）。`register_handoff_tools(agent, *, transport, room)` 与 `register_task_tools` 并列、不合并（前者要 `room`、后者要 `tasks_store`），`TeaGuest.__init__` 紧挨调用。`_ProposeHandoffBase` 与 `_TaskProposeBase` 是**有意的平行基类**，不共享。
- **`propose_review` 在 propose 时把 `reviewee` 名解析成 `message_id` 并冻结**（P7.4）。茶客 prompt 里看不到 message_id（`format_messages` 不含 id），工具用注入的 `room.latest_message_by_speaker_id(reviewee)` 取其最近一条发言；MVP **只支持「reviewee 最近一条」**（审任意历史消息属用户场景、走气泡按钮）。解析发生在 propose 时——即使用户采纳前 reviewee 又发言，被审的仍是茶客本意那条。reviewee 没发过言 → 工具返 `Error:` 字符串、**不** emit envelope。propose 工具**不校验** target / reviewer 在场 / panel cap——校验留采纳时既有 `handoff_*` inbound 兜底（同 `task_propose_decision` 不校验 message id 口径）。
- **采纳后的 `HandoffItem` 与用户直接触发不可区分；茶客不能 propose `handoff_clear`**（P7.4）。`issued_by` 恒 `HANDOFF_ISSUED_BY_USER`、不加新取值（采纳是用户确认动作，语义上就是用户触发）；proposer provenance 仅经 `handoff_delegate` 的 `reason` 前缀保留，review / panel 采纳后不留 proposer 痕（可接受——卡片 meta 行已显「<proposer> 提议」）。`handoff_clear`（清队列）是 destructive 操作，**不开**茶客 propose 入口（同 `/clear task` 不给茶客 propose 入口口径）。propose 永远等用户点，无自动 / 超时采纳。
- **`/tools` `/skills` 走单一共享投影 `TeaGuest.describe_capabilities()`**（2026-05-20）。茶客能力 introspection（注册 tools + 可用 skills + 权限模式）只此一个投影方法，WebSocket `_inbound_list_guest_caps` handler 与 CLI REPL `_print_guest_caps` 共调；**禁止**任一端各拼一份采集逻辑。tools / 可用 skills 是 `TeaGuest.__init__` 时一次注册 / 扫描的**静态**集合（MCP 也在 init、权限模式切换不增删 `agent.tools` 成员），post-init 不变。inbound `list_guest_caps` 白名单严格 `{type, guest}`、handler 归**核心层**（与 `fetch_turn_detail` 同口径——introspection 不属 admin/task/io/settings 任一 slot）；回包 `GUEST_CAPS_INFO` 一次性查询，不进 transcript / 不落盘 / 不挂房间 turn，`schema_version` 不 bump。**查茶客实例必经 `Orchestrator.get_guest(name)`**——它读 orchestrator 私有 `_guests` 活字典，反映运行时增删；**不**读 `RoomSession.guests`（`frozen=True` 的 boot 快照，运行时增删不回写）。`/tools` 与 `/skills` 共用同一 inbound `list_guest_caps`，请求方传 `view`（`"tools"`/`"skills"`），server 规范化后经 `GUEST_CAPS_INFO` 响应**原样回声** —— 前端按响应自带的 `view` 裁剪显示哪段，**不**靠可变全局态对号入座（两条 `/tools`/`/skills` 查询并发时全局态会串台、把 A 的 tools 渲成 skills，codex P2）。`view` 是纯展示回声，server 不解释、只规范化。
- **能力花名册是装配期一次性解析的不可变快照**（P8.2-roster）。`build_room_session` 解析 `roster: dict[guest→summary]`，每位茶客的能力摘要走三级解析——手写 `[[guest]].summary`（room.toml，走 P4 配置闭环四点：config 解析 / `_room_config_to_dict` snapshot / `_render_room_toml` 回写 / 本节不变量）→ `persona_summary` 中央内容寻址缓存（`user_data_root/.chahua/persona-summaries/<hash>.json`，`hash` = persona md sha256、值含 `gen_version`）→ 无。解析结果传给 `Orchestrator` → `ContextRenderer`；运行期增删茶客整体重建 session，故 renderer 持的是**不可变快照**、**不**做运行期增量更新——roster-b 后台 LLM 生成的新摘要**下次重建 session 才生效**（同 session 内不刷）。花名册只进 onboarding 的 `<room>` 块「在场」行（任一茶客有摘要 → bullet 花名册、全员无 → 退回逗号单行），**不**进每轮 `<room_update>`（稳定信息、避免 N×T token 放大）。`clamp_summary`（一行 ≤40 字）被 `<room>` 渲染共用。`build_room_session` **不**改 async、boot **不**阻塞——`schedule_generation` 后台预热有 `get_running_loop()` 守卫（无 loop 跳过）、缓存命中零 LLM 调用，所有失败 WARN 不阻断房间。
- **托管任务会话（MTS）是瞬态运行态，每房间最多 1 个，不落盘**（P8.3；P9 起全局可有多个后台 MTS）。`ManagedSession`（`task_id` / `manager_guest` / `budget`）挂 `Orchestrator._managed_session`，与 `_handoff_queue` 同瞬态语义——不落盘、crash / `reset_room` / ws 断开即清，不跨重启恢复。**P9 起切房不结束 MTS**：旧前台 busy 转后台续跑，MTS 在后台自驱到 budget/task/cap 自然收尾；只有 ws 真正断开（`_serve_one` finally `_aclose_background_runtimes`）才强制结束后台 MTS。`_managed_session is None` 即「无托管」，**不**另存 `enabled` bool（避免「`enabled=False` 但对象还在」的二义态）。只经 `managed_session_start` inbound 开启——无自动 / 超时 / 茶客 propose 开启（MTS 授权茶客在预算内自主烧 token，必须用户显式确认）。`MAX_MANAGED_BUDGET = 20`（入站上限硬护栏）/ `MANAGED_SESSION_DEFAULT_BUDGET = 6`（前端预填）是 `handoff.py` 模块常量、不进 toml。
- **MTS 跑在 handoff drain loop 上，不新开调度路径**（P8.3）。`run_pending_handoff` drain 每轮 turn 跑完调一次 `_advance_managed_session_after_turn(item, sink)`，再照常走既有 peek / `turn_end` / 收尾，既有「5 步」内部顺序一字不动；`_managed_session is None` 时该调用立即返回，非 MTS 房间零行为变化。`_advance` 按「刚跑完的是不是管理者回合」分流：管理者回合不做事（其 delegate / panel 提议已被 hook 在回合内入队）；worker 回合且 `_handoff_queue` 空 → `budget -= 1` + 回调 `enqueue_handoff(delegate(manager))` + emit `managed_session_advanced`。停止守卫 `_managed_session_stop_reason()` 先判（budget → task_closed → cap，谁先命中报谁）。**不**给 Task 加 `plan_items` / 结构化计划字段——MTS 是调度层机制、与计划是否结构化无关（计划仍是 markdown artifact，管理者 `read_file ./task/<plan>.md` 读回续推进）。
- **6 个会 emit 的结束 reason；`manager_finished` 只由 drain 收尾兜底产生**（P8.3）。`managed_session_ended.data.reason ∈ {manager_finished, budget_exhausted, task_closed, cap_reached, user_stopped, user_cancel}`。`manager_finished` 由 `run_pending_handoff` 的 `has_next` 为假处兜底产生，覆盖「管理者复查完没派活 / 调用链续不下去（被指派茶客不在场被 `_advance_to_runnable_handoff` drop、发言抛错等）」——**不**公开 `target_missing` / `error` reason（早期版本列了但与「不单独检测、统一兜到 `manager_finished`」的实现自相矛盾，评审 v2 收敛删去）。前端 `manager_finished` 文案取中性「托管会话结束」。
- **结束 MTS 必清 `_handoff_queue`**（P8.3）。`end_managed_session(sink, reason)` 任意结束路径都清掉待跑 handoff 项 + 重发空队列快照——MTS 内 worker / panel 项是被 hook 自动入队的，若结束只清会话状态不清队列，房间会把已入队的 worker 跑完继续自动说话（被理解成「停止失效」），也会让 `budget_exhausted` / `task_closed` / `cap_reached` 多跑一个已入队 worker（用户设的预算就不再是硬数）。`managed_session_stop` **不**取消当前 in-flight turn（自然跑完——要立即掐断当前发言走既有 `cancel`）；`handoff_clear` / `cancel` 中途介入时一并结束 MTS（reason `user_cancel`）。
- **MTS 内只自动入队管理者的 `handoff_delegate` / `handoff_panel` 提议**（P8.3）。实现是 `ChahuaTransport.set_task_proposal_hook` 注入的 `Orchestrator._intercept_task_proposal`：`emit_chahua` 遇 `TASK_PROPOSAL` 先过 hook，命中（MTS 激活 + 提议来自管理者 + kind 是 delegate / panel）即 `enqueue_handoff` 并**拦下该 envelope 不下发前端**（不渲采纳卡）。非 MTS / 非管理者 / review / decision / status 提议照常渲卡；管理者 `propose_delegate(自己)` 被跳过（WARN + 吞掉，防自循环空转）。`handoff_tools.py` / `proposal_card.js` / `TeaGuest.speak()` 签名**零改动**——`task_proposal_hook` 缺省 `None`、非 MTS 路径多一个 `is None` 判、零行为变化。**不**给管理者开专用 `delegate` 后端工具——用 MTS 内自动入队替代。
- **管理者 MTS 回合注入 `<managed_session>` 临时块**（P8.3）。`_build_winner_blocks` 对「delegate 指向管理者」的项经 `extra_blocks` 注入 `render_managed_session_block(manager, budget)`（`context_renderer.py` 纯函数，复用 P7.2 的 `extra_blocks` 管线）；worker 回合 / 非 MTS delegate 无块。块第 ② 条显式作废 `propose_*` 工具 ack 的「等用户采纳」等待语义——为保 `handoff_tools.py` 零改动不改工具 ack，转而在 prompt 块里纠偏管理者模型的下一步行为（托管期 propose 自动生效，复查后直接 `propose_delegate` 指派下一步、不必交回用户）。
- **MTS 产生的 `HandoffItem` 与用户直接触发不可区分**（P8.3）。`issued_by` 恒 `HANDOFF_ISSUED_BY_USER`（沿用 P7.4——MTS 由用户显式开启，授权范围内的入队语义上就是用户触发）；**不**加 `HandoffItem` 字段、**不**加 `issued_by` 新取值。provenance 仅经 `HandoffItem.reason` 前缀「托管 · <manager> 指派」保留（`reason` 不进茶客 prompt，P7.1 口径延续）。
- **`managed_session_*` 是 hint 型事件，预算与 `max_consecutive_ai_turns` 两者都生效**（P8.3）。三个 envelope `managed_session_started` / `managed_session_advanced` / `managed_session_ended` 不进 transcript、不触发 AI（同 `handoff_*` / `task_*` 口径），新增事件类型不 bump `schema_version`（沿用 P7.4「加值不破坏协商」）。`budget` 计管理者**复查回合**数——worker 完成后把管理者放回队列记 1 次、kickoff 首个管理者回合**不**耗——是用户旋钮；房间级 `max_consecutive_ai_turns` 是硬护栏，MTS 不能越过。两个 inbound `managed_session_start`（四道校验：`task_id` == 当前 active 且非终结态 / `manager_guest` 在场 / `budget` ∈ `1..MAX_MANAGED_BUDGET` / 当前无 MTS）与 `managed_session_stop` 归 handoff slot（与 `_inbound_handoff_*` 同调度层归属）。

### 9.x P9 切房后房间后台续跑

- **`RoomRuntime` 注册表 + `RoomEventRouter` 可变路由 sink**（P9 9.1）。server 从「持 1 个 `self._session`」升级为「持 `self._runtimes: dict[room_id, RoomRuntime]` 注册表 + `self._foreground_id` 前台指针」；`_session` 读点统一走 `_foreground_runtime.session` property。一个 `room_id` 在注册表里最多 1 个 `RoomRuntime`——不允许同房「前台一份 + 后台一份」并存。`RoomEventRouter` 是 per-room 可变路由 sink（本身就是 `EnvelopeSink`）：turn / handoff drain 启动时传的 sink 永远是某个 runtime 的 `router`（稳定对象）、不是裸 ws sink——切房只翻 router 的 `mode`，in-flight turn 调用栈里捕获的还是同一 router 对象、事件路由自动跟着 `mode` 变，无需触碰运行中的 turn。这解决了「sink 是顺调用栈透传的参数、in-flight turn 无法中途换 sink」这个最硬的卡点。in-flight 状态（`inflight_task` / `inflight_kind` 字段）与其生命周期方法（`set_inflight` / `cancel_inflight` / `cancel_and_drain_inflight` / `inflight_alive`）下沉到 `RoomRuntime`；server 侧保留同名 compat property / wrapper（`_inflight_turn_task` / `_inflight_kind` / `_set_inflight` / `_cancel_and_drain_inflight` 等），一律按前台 runtime 取值，旧读点 / 测试夹具不动。
- **切房两阶段（失败原子性）+ 后台 runtime 仅在有活时存在**（P9 9.2）。`_switch_room` 不再 `_cancel_and_drain_inflight`。**阶段一**准备目标 runtime（已在注册表的后台 runtime 直接复用、不在则 `build_room_session` 装配）——目录不存在 / room.toml 坏 / LLM 凭据缺等任何失败都在「未碰旧前台」时 `return`，旧前台 runtime / `_foreground_id` 一字不动；**阶段二**目标就绪后 demote 旧前台（busy → `router.mode=background` 留注册表后台续跑、idle → close 移出）→ 一次性切 `_foreground_id` → 重发快照。后台 turn / handoff drain 跑完，`_run_turn` / `_run_handoff_turn` 的 finally 调 `_maybe_self_destruct_background_runtime`：runtime 仍 `background` 且 in-flight 槽空 → emit `room_background_finished` + close + 移出注册表（后台 runtime「仅在真有 in-flight 活时存在」，闲房不留、资源天然有界）。切回竞态：`_switch_room` 先翻 `mode=foreground`，turn 收尾的自毁判定随即不成立——两者都在事件循环单线程内、各自无 await，「先翻 mode 再走收尾」的顺序即保证正确。清理遍历整个注册表：正常退出走 `async def aclose()` 对全部 runtime cancel+drain+close、`_serve_one` 的 finally 走 `_aclose_background_runtimes()` 清后台留前台（ws 断开后前台 runtime 保留供重连复用）；带 MTS 的 runtime 先 `end_managed_session` 再 cancel drain（§8 拆除顺序），清完即移出 `_runtimes`、重复 cancel/close 同一 runtime 静默放过（幂等）。**同房重建**（加删茶客 / 改 LLM / 权限 / trust）仍走 `_replace_session` + 先 `_cancel_and_drain_inflight`——P9 只改「切到不同房间」一条路径。例外：前台房含 `isolation=global` 茶客时切走前必 `cancel+drain`（其跨房共享 cwd 的 `share/` `task/` 软链会被目标房 `build_room_session` retarget、与后台 turn 撞车），故注册表里的后台 runtime 永不含 global 茶客。
- **后台 router 只放行里程碑事件**（P9 9.3.1）。`RoomEventRouter` `background` 模式按精确白名单 `_BACKGROUND_WHITELIST` 过滤：`turn_start` / `turn_end` / `message_end` / `task_info` / `task_artifact_added` / `managed_session_*` / `room_background_finished` 放行，`message_start` / `message_delta` / `guest_thinking` / `tool_*` 等高频流式一律丢弃。理由：多个后台房并发时全量流式会炸 ws 流量与前端负担；后台发言**内容**不靠这些事件，靠切回时 `room_history` 快照从盘重建（完整无损）。白名单集合与设计文档 §4 表格同源，改一处同步另一处；回归 `tests/test_room_event_router.py`。
- **`emit_room_snapshot` 重投前台房 MTS 快照**（P9 9.3.2，推翻 P8.3「`emit_room_snapshot` 不重投 MTS」）。原不变量的前提是「MTS 不跨断线存活」；P9 让 MTS 能在后台续跑，切回一个「托管中」的后台房间时前端需自给自足重建「托管中」状态条 / 「停止托管」按钮，不能依赖前端缓存早先收过的 `managed_session_started`（只在「MTS 启动时恰在前台」才成立，脆弱）。`emit_room_snapshot` 末尾调 `orchestrator.emit_managed_session_snapshot(sink)`：`_managed_session` 非空 → 补发一帧 `managed_session_started`，`budget` 是**当前剩余**值；无 MTS 空操作。
- **房间列表 `rooms_available` 每房带 `busy` 标志**（P9 9.3.2）。`_rooms_available_with_busy` 给 `discover_rooms` 结果叠加 `busy`：`busy=True` ⟺ 该 `room_id` 在 `_runtimes` 注册表且 runtime `inflight_alive()`。`discover_rooms` 的 `room_id` 与注册表 key 同口径（房间目录名）。前端房间列表「进行中」徽标据此渲染——含切走后转后台续跑的房间（后台 runtime「仅在有活时存在」，故注册表里的后台房几乎恒 `busy`）。
- **`MAX_BACKGROUND_ROOMS` 软上限淘汰最早后台房**（P9 9.4.1）。`server.py` 模块常量 `MAX_BACKGROUND_ROOMS = 5`：后台 runtime「仅在真有 in-flight 活时存在」，并发 session 数 = 1 前台 + N 个真正在跑的后台、N 自然不大；5 对桌面 App 既宽松又不至于失控，要调直接改本常量。`_inbound_switch_room` 在 `_switch_room` 之后调 `_enforce_background_room_limit`：后台 runtime 数超上限即淘汰 `background_since_ms` 最小（最早转入后台）的 runtime——走 9.2 强制拆除路径 `_aclose_one_runtime`（带 MTS 先 `end_managed_session` 再 cancel drain），拆除后补一帧 `room_background_finished`（room_id 用 `room.name`）+ emit info `NOTICE`。`room_background_finished` 放在 `_aclose_one_runtime` **之后**发：强制拆除会 cancel 被淘汰 runtime 的 in-flight turn，被 cancel 的 turn 收尾时 orchestrator 补 `turn_end` + turn wrapper finally 自毁补 `room_background_finished`（两者经后台 router 白名单放行）——本方法若**先**发 `room_background_finished` 前端「进行中」徽标会经历「灭 → 被 `turn_end` 点亮 → 再灭」的可见闪烁，放拆除后发则只「亮 → 灭」，与后台房正常跑完一致；自毁那帧与本方法补发的是同 `room.name` 重复帧，前端 `delete` 幂等无害。**软上限**：超限淘汰 `background_since_ms` 最早项而非拒绝切房（用户切房意图不该被旧后台任务挡住，P9 §11 决策 3）。`background_since_ms` 每次「转入后台」（`_switch_room` 阶段二 demote）写当前 Unix 毫秒、复用的后台 runtime 切回前台时清回 `None`（前台房恒 `None`，否则超限淘汰会把前台房误判成「最早后台房」）。回归 `tests/test_server_switch_room.py`。

### 9.x P10 聊天界面增强（Mermaid / 图片预览 / 产物下载链）

### 9.x P15 桌面登录态自动注入 LLM 配置（用户在 desktop 选模型、零重启即时生效）

### 9.x P8.3/P8.4 托管任务会话（MTS）—— 待机闭环现状版（至 P8.4.11）

> 本节为 CLAUDE.md「托管任务会话（MTS，P8.3 / P8.4）」段的完整快照（2026-07-07 简化时下沉），**与上方 P8.3 时代平铺条目冲突处以本节为准**（如结束 reason：`MANAGER_FINISHED` 已退役 → 5 个）。设计文档见 `docs/P8.3-原生自动推进.md` / `docs/P8.4-MTS 待机闭环.md`。

- **MTS 是瞬态运行态，每房间最多 1 个，不落盘**（P9 起全局可有多个后台 MTS）。crash / `reset_room` / ws 断开即清；切房旧前台 busy 转后台自驱直到自然收尾。只经 `managed_session_start` inbound 开启，无自动 / 超时 / 茶客 propose 开启。
- **断线即结束 MTS（切房不结束）**。`_serve_one` finally 先 `_maybe_end_managed_session(user_cancel)` 再 cancel drain，否则 MTS 既不推进也无人停。`emit_room_snapshot` 重投 MTS：前台房 `_managed_session` 非空时末尾补帧 `managed_session_started`（`budget` 是剩余值）。
- **MTS 跑在 handoff drain loop 上，不新开调度路径**。`run_pending_handoff` 每轮跑完调 `_advance_managed_session_after_turn`（`_managed_session is None` 即返回）再走 5 步。按「刚跑完是否管理者回合」分流：管理者回合不做事（**没派活 = dormant，不是 finished**）；worker 回合且队列空 → `budget-=1` + 回调 `delegate(manager)` + emit `managed_session_advanced`。
- **停止条件 —— 5 个 reason**（`MANAGER_FINISHED` 已退役）：`budget_exhausted` / `task_closed` / `cap_reached` / `user_stopped` / `user_cancel`。终结只能因有界资源或用户显式行为。`task_closed` 触发：关 MTS 任务、采纳 `task_propose_status("done")`、或让 MTS 任务不再 active（`stop_reason()` 含 `active_task_id != ms.task_id` 检查）。
- **drain 收尾队列空 + MTS 活 → 保持 dormant，不终结**。`run_pending_handoff` body `has_next=False` 与 while-break 两处都 `return` 不调 `end_managed_session` —— 管理者没派活 ≠ 事情结束。
- **dormant 复活走 drain 路径 + skip chain（P8.4.7）**。`submit_user_message` 入口当 MTS 活+队列空+manager 在场+不忙时 **pre-enqueue** 一个 manager DELEGATE kickoff + emit `HANDOFF_ENQUEUED` → 既有 drain 消费（`<managed_session>` 块经 `_build_winner_blocks` 注入）→ **跳过** `_run_ai_chain`。**Why**：原「chain 跑完 → re-drain」依赖 manager scoring 胜出+拿块，两者都不成立，dormant 永远卡死。manager 不在场/正忙 → 走常规 chain。chain 后 re-drain（`reset_cap=False`）保留。
- **`managed_session_start` 拒收 bg-run busy manager（P8.4.7/.9）**。`_inbound_managed_session_start` 在 ②（manager 在场）和 ③（budget）间加 ②b：`guest_in_bg_run(manager)` → NOTICE error 拒开。**Why**：kickoff DELEGATE 会被 drain busy-winner 守卫静默 drop，UI 收到 started 却永无 kickoff。**narrow**：只查 bg run（前台/handoff 占用可被抢占，只有 bg run 不可抢占）。
- **MTS proposal intercept：summarizer 不查 manager 自己（P8.4.9）**。`_handoff_item_from_proposal` 在 manager 自己 `speak()` 内跑（busy），item 在 finally 解 busy 后才被消费。「workers 讨论、我汇总」（panel.summarizer=manager）是核心模式 —— summarizer 用 `busy - {manager}` 放行；delegate target=manager / panel panelist=manager 仍按全集 busy 拒。
- **dormant 期间 task 状态变更经 `check_after_task_change(sink)` 主动收尾**。4 个 task inbound 末尾在 `_emit_task_info` 后调一次（dormant 无 turn 触发 `stop_reason()`）。统一经 `Orchestrator.check_managed_session_after_task_change(sink)` 薄转发。
- **结束 MTS 必清 `_handoff_queue`**。`end_managed_session(sink, reason)` 任意路径都清待跑项 + 重发空队列。`managed_session_stop` 不取消当前 turn；`handoff_clear` / `cancel` 中途介入一并结束 MTS（`user_cancel`）。
- **MTS 内只自动入队管理者的 `handoff_delegate` / `handoff_panel` 提议**。`_intercept_task_proposal`（经 `set_task_proposal_hook` 注入）拦下 envelope 不下发前端。非 MTS / 非管理者 / review / decision / status 照常渲卡。
- **管理者 MTS 回合注入 `<managed_session>` 临时块**。`render_managed_session_block(manager, budget)` 经 `extra_blocks` 注入，worker 回合 / 非 MTS delegate 无块。第 ② 条作废 `propose_*` 的「等用户采纳」等待语义；第 ④ 条明确「没下一步就讲完、不强行 propose」是合法收尾。
- **`managed_session_*` 是 hint 型事件**，不进 transcript、不触发 AI、不 bump `schema_version`。`budget` 计管理者复查回合数（kickoff 不耗）；`max_consecutive_ai_turns` 是硬护栏。
- **前端 dormant 子态由三源派生，不发新 envelope**。`managed_session.js` 按 MTS 状态 + handoff 队列长度 + 前台 in-flight 合成按钮文案。点击行为不变（发 `managed_session_stop`）；`turn_start`/`turn_end` 翻转时调 `managedSession.refresh()`。
- **自指派 early swallow（P8.4.11）**。`_intercept_task_proposal` 在调下游前先识别 `kind=handoff_delegate ∧ payload.target == ms.manager_guest` → 直接 swallow + return True。**Why**：`let_speak` 已标 manager busy → 下游全集 busy 校验返 None → 退化「渲卡兜底」→ 用户采纳真 enqueue manager，破坏「自指派不入队」。

### 9.x P11 后台 Agent（bg run / 并行执行）

> 本节为 CLAUDE.md「后台 Agent（P11，bg run / 并行执行）」段的完整快照（2026-07-07 简化时下沉）。设计文档见 `docs/P11-后台 Agent.md`。

- **`active_guest_names` 是 `guest_busy()` 唯一数据源**。runtime 与 orchestrator 的同名 set 是同一个（经 `_attach_runtime_state` 注入）。**add 必先于任何 `await`**：bg run 校验通过即同步 `agent_runs[run_id]=run` + `active_guest_names.add(target)`（先于 `create_task`）；前台/handoff `let_speak` 包 `try: add → finally: discard`。裸构 Orchestrator 时 `active_guest_names is None` 整段跳过。
- **`guest_busy` vs `guest_in_bg_run` 二分（P8.4.9）**。`guest_busy` 读全集=「此刻占用」；`guest_in_bg_run` 只查 `agent_runs`=「不可抢占」。**handoff inbound 准入校验必须用 `guest_in_bg_run`** —— 用 `guest_busy` 会把「前台讲话但可抢占」误判，破坏 cancel+drain 抢占。**drain 自身的 busy-winner 守卫**仍用全集兜底。
- **bg run 占用的茶客不接 `@`、不参与打分**。`find_user_mention` 命中 busy 名整 token 忽略；broadcast winners 过滤 busy；scoring `scorables` / `cooled` 都排除 busy。
- **`busy_alive() = inflight_alive() or has_active_runs() or pending_mts_continuations or has_managed_session()` 仅 P9「runtime 生命周期 / busy 展示」用**（3 处）。**不用于前台 turn 控制** —— `_run_turn` / drain 的 cancel/drain 仍走 `inflight_alive()`。
- **5 步清理（cancel_and_drain_all）race-free**：① 同步 cancel 前台 turn → ② 同步 cancel 全部 `agent_run_tasks` → ③ `await gather(*bg_tasks, return_exceptions=True)` → ④ `await inflight_task` → ⑤ `session.close()`。先同步 cancel 两段再 await drain。带 MTS 先 `end_managed_session(user_cancel)`。
- **bg wrapper finally 6 步（顺序锁死）**：`detect_new_artifacts` → `BatchMessageSink.flush_to(router)` → `agent_runs.pop(run_id)` → emit `AGENT_RUN_{FINISHED,CANCELLED,ERROR}` → `advance_after_bg_completion`（MTS 续命，仅 `mts_managed=True`）→ `active_guest_names.discard` → `_maybe_self_destruct_background_runtime`。terminal envelope 在 propose flush 之后、MTS 续命在 terminal 之后、自毁在 discard 之后。任一 step 抛异常仍保后续。
- **MTS × bg run 续命 —— spawn 时刻快照（P11.2.X）**。`AgentRun.mts_managed` + `mts_manager_at_spawn` 由 `_start_agent_run` 按 `(MTS 活, source==manager)` 冻结，不跟随后续 MTS 状态。`_start_agent_run` 拒 `target==manager`（防 bg 内 propose 污染 MTS 队列）。
- **续命触发只认 `AGENT_RUN_FINISHED`**（cancelled/error 跳过）。`advance_after_bg_completion`：MTS 活 + manager 与冻结值一致 + `stop_reason` 不命中 + budget>0 → `budget-=1` + enqueue `DELEGATE(manager)` + emit `managed_session_advanced`；否则各走对应 `end_managed_session`。
- **续命后按 inflight 分流起 drain**。无 inflight → 起 `_run_handoff_turn`；drain 已跑 → 不动；user turn 在跑 → `add_done_callback` 等 user 跑完再起。`create_task` 失败 → `end_managed_session(user_cancel)`。收尾兜底 MANAGER_FINISHED 触发都加 `_has_pending_mts_bg()` 守卫。
- **budget 语义扩展**：「manager→worker（含 bg）→manager 桥扣 1」—— spawn N 个 bg ≈ 用 N budget；同回合 spawn + propose(worker) 双扣。
- **`_has_pending_mts_bg` orch ↔ runtime 严格 1:1**。经 `_attach_runtime_state` 绑定 —— session 跨 runtime 复用须同步重绑。裸构 orch 默认 `lambda: False`。
- **pre-start cancel race 兜底 sweep**。`create_task(wrapper)` 后立即 cancel 时 wrapper 没进 finally —— `cancel_and_drain_agent_runs` 末尾遍历残留 `agent_runs` discard guest_name 再 clear。**discard 单条 + 最后 clear**（前台/handoff `let_speak` 共写同一 set）。
- **`BatchMessageSink` 白名单 + run_id 注入**。`_DROP` 拒 HANDOFF_* / MANAGED_SESSION_* / AGENT_RUN_*；`_PASS` 只放 NOTICE；其余裹 `_with_run_id`。`TASK_PROPOSAL` 缓冲到 wrapper finally 才 flush（保证 terminal envelope 后于缓冲 propose 到达）。
- **bg run 不污染前台取证：`speak(record_debug=False)`**。wrapper 期间 `self._recorder` 替成 `NOOP_RECORDER`。
- **bg run inbound `agent_run_start` 四道校验**：① `target` 在场；② `task_id` 若给须命中；③ `guest_busy(target)==False`；④ `len(agent_runs) < MAX_AGENT_RUNS_PER_ROOM(=4)`。校验完成 + 两 dict 写入必须先于 `create_task`。
