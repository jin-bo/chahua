# P8.3：原生自动推进 —— 托管任务会话（MTS）

> 目标：让「管理者茶客发起指派 → 被指派茶客执行 → 控制权**自动回到管理者**复查 →
> 管理者再指派下一步」这个闭环**自己转起来**，不必每一步都等用户敲一句话或点一次
> 「采纳」。用户**显式开启**一个有预算上限的「托管任务会话」（Managed Task
> Session，下称 **MTS**），授权管理者茶客在预算内自主推进；用户可随时停止。
>
> P8.3 是**调度层增量**，收敛后的核心只有三件事：① 一个不落盘的会话状态
> `ManagedSession`；② handoff drain loop 每轮 turn 后调一次
> `_advance_managed_session_after_turn()` 续队列 / 收尾；③ 管理者的 `propose_delegate`
> / `propose_panel` 提议在 MTS 内由后端 hook 直接入队。复用 P7 的 drain loop /
> `HandoffItem` / cap / `_run_handoff_turn` wrapper，复用 P7.4 的 propose 工具
> （**工具面零改动**），复用 P5 的 Task 模型。**不改对话原语、不改 Task 数据结构、
> 不引入结构化 `plan_items`、不新开调度路径、不新增管理者专用工具。**

**状态：已落地（2026-05-21，设计经评审收敛 v3）**。上游契约见
[`P8-任务管理 skill 与原生化.md`](P8-任务管理%20skill%20与原生化.md) §2（回合模型约束）
/ §6（P8.3 草案）；handoff 调度层见
[`P7-显式 handoff 与 delegation.md`](P7-显式%20handoff%20与%20delegation.md)（drain loop /
`HandoffItem` / cap / `_run_handoff_turn` wrapper）、
[`P7.3-圆桌 panel.md`](P7.3-圆桌%20panel.md)（`_advance_to_runnable_handoff` 死项 drop +
runtime 重校验）、[`P7.4-茶客 propose handoff.md`](P7.4-茶客%20propose%20handoff.md)

## 0. 本阶段做 / 不做

**做**：

- 瞬态运行态 `ManagedSession`（`task_id` / `manager_guest` / `budget`），挂 Orchestrator，
  单房间最多 1 个，**不落盘**（§3.1）。
- handoff drain loop 每轮 turn 跑完后调一次 `_advance_managed_session_after_turn(item)`：
  worker 回合后把管理者放回队列、管理者回合后判收尾；预算/上限耗尽即结束（§4）。
- 管理者提议自动入队：`emit_chahua(TASK_PROPOSAL)` 处一个 Orchestrator 级 hook，
  捕获管理者的 `handoff_delegate` / `handoff_panel` 提议并直接 `enqueue_handoff`，
  **不发可采纳的 `TASK_PROPOSAL`**（§5）。
- 两个 inbound：`managed_session_start` / `managed_session_stop`；三个 envelope：
  `managed_session_started` / `managed_session_advanced` / `managed_session_ended`（§3）。
- 管理者 MTS 回合注入临时块 `<managed_session>`，复用 P7.2 的 `extra_blocks` 机制（§7）。
- 前端首版：任务面板「托管运行 / 停止托管」按钮 + MTS 状态条（§8）。
- `examples/personas/Maya/skills/task-management/SKILL.md` 补一节「托管会话中的推进口径」（§9 末）。

**不做（评审收敛 / 推后）**：

- **不**给 Task 加 `plan_items` / 结构化计划字段（P8 §3 已否决，§6.1）。
- **不**新开「自动推进」调度路径 —— 复用 handoff drain（§6.2）。
- **不**给管理者开专用 `delegate` 后端工具 —— 用 MTS 内自动入队（§6.3）。
- **不**改 `handoff_tools.py`、**不**改 `proposal_card.js`、**不**改 `TeaGuest.speak()`
  签名 —— 自动入队只动 `transport_bridge.py` + Orchestrator（§5）。
- **不**自动入队管理者的 `propose_review` / `task_propose_decision` /
  `task_propose_status` —— 只自动入队 delegate/panel（§5.2）。
- **不**做 stop 的软停/硬停两套语义 —— `managed_session_stop` 一种行为（§3.3）。
- **不**让 MTS 落盘 / 跨重启恢复（§6.5）；**不**支持单房间多并发 MTS（§6.6）。
- **不**给 `HandoffItem` 加字段 / 加 `issued_by` 新取值（§6.7）。
- **不**做无用户开启的自动 MTS / 茶客 propose 开启 MTS（§6.4）。
- **不**做出错自动复盘重试 —— 出错按收尾路径交回用户（§4.3）。
- **不**在首版做 slash `/manage` —— 推后到 follow-up，避免一次把 CLI / composer 全拖进来（§8.3）。

## 1. 背景：回合模型为什么挡住自动推进

ChaHua 是回合制群聊（P8 §2 / P7.1 不变量）：茶客每次 `speak()` 只跑一个 turn，发言完
控制权回到用户；handoff drain loop（`run_pending_handoff`）跑完队列后以
`turn_end(next="user")` 收尾、不回落 scoring。被指派茶客发言完，控制权回到用户，
**不会自动回到管理者**。

**推论**（P8 §2）：「分析 → 计划 → 指派 → 执行 → 复查 → 调整 → 再指派」闭环**无法由
管理者茶客自主跑完**。缺口在调度层，**不在 Task 数据结构** —— 即使计划仍是 markdown
artifact，管理者也能 `read_file ./task/<plan>.md` 读回继续推进。缺的是一条调度规则：
worker 执行完，控制权**条件性回到管理者**而不是用户。这条规则就是 MTS。

现有 handoff 拼不出来，因为缺两件事：① drain 队列空就停、不会自己续 —— 要有人在队列空
时把管理者放回去（§4）；② 管理者复查完要「再指派」，但 `propose_delegate` 今天渲成
采纳卡等用户点 —— 自动推进要求这一步免采纳（§5）。P8.3 = 这两件事，都装在调度层。

## 2. MTS 生命周期与停止条件

### 2.1 一次托管会话

```
用户：任务面板点「托管运行」→ 选管理者 Maya、预算 6 → 确认
   │ inbound managed_session_start {task_id, manager_guest:"Maya", budget:6}
   ▼
开启   建 ManagedSession ；enqueue_handoff(delegate("Maya"), reason="托管启动")
       emit managed_session_started ；启动 drain（_run_handoff_turn wrapper）
   ▼
管理者回合  Maya 读 Goal / 计划 artifact，调 propose_delegate("阿伟", "先做数据清洗")
            → emit_chahua(TASK_PROPOSAL) 被 hook 拦下 → 直接 enqueue_handoff(delegate("阿伟"))
            → emit handoff_enqueued（进队列预览，不渲采纳卡）
            turn 跑完 → _advance：管理者回合、队列非空 → drain 继续，不交回用户
   ▼
worker 回合  阿伟执行、发言、可落 ./task/ artifact
            turn 跑完 → _advance：worker 回合、队列空、budget>0 → budget 6→5
            → enqueue_handoff(delegate("Maya"), reason="托管复查") + emit managed_session_advanced
   ▼
管理者回合  Maya 在 <recent_messages> 看到阿伟产出，复查
            → 继续派活：propose_delegate("小林", …) → hook 入队 → 回到 worker 回合
            → Goal 达成：task_propose_status("done")（**不自动入队**，渲卡等用户）
              且不再 propose_delegate → 队列空 → drain 收尾 → MTS 结束 manager_finished
   ▼
结束   清 ManagedSession ；emit managed_session_ended {reason}
       drain 照常 turn_end(next="user")，控制权回到用户
```

### 2.2 停止条件 —— 只有 6 个会真正 emit 的 reason

| reason | 触发 | 检测点 |
|---|---|---|
| `manager_finished` | 管理者复查完没再派活、或调用链因任何原因续不下去（被指派茶客已不在场、发言抛错等）→ 队列空，drain 走到收尾 | drain 收尾兜底（§4.2）|
| `budget_exhausted` | `budget` 扣到 0 | `_advance`（§4.1）|
| `task_closed` | `task_id` 对应任务被关闭 / 状态变终结态 / 不存在 | `_advance` |
| `cap_reached` | `_consecutive_ai_turns` 撞 `max_consecutive_ai_turns`（drain 硬安全上限）| `_advance` |
| `user_stopped` | 用户点「停止托管」（`managed_session_stop`）| inbound handler（§3.3）|
| `user_cancel` | 用户「全部取消」（`handoff_clear`）或取消当前 turn（`cancel`）| inbound handler（§3.3）|

> **设计取舍**：早期版本另列 `target_missing` / `error` 两个 reason，与「不单独检测、
> 兜到 `manager_finished`」的实现自相矛盾。收敛后**不公开**这两个 reason ——「调用链
> 续不下去」（target 不在场被 `_advance_to_runnable_handoff` drop、或茶客发言抛错）
> 一律走 drain 收尾兜底归 `manager_finished`。前端 `manager_finished` 文案因此取中性
> 措辞「托管会话结束」，不写「管理者已完成」。

**预算语义**：`budget` = 管理者**复查回合**的最大次数（worker 完成后把管理者放回队列
记 1 次）。kickoff（开启时首个管理者回合）**不耗预算**。它与房间级硬护栏
`max_consecutive_ai_turns`（统计所有连续 AI 回合）**两者都生效，谁先到谁停**。

## 3. 数据契约

### 3.1 `ManagedSession` 运行态（瞬态，不落盘）

```python
# chahua/handoff.py —— 紧挨 HandoffItem / HandoffKind
@dataclass
class ManagedSession:
    """托管任务会话运行态。与 _handoff_queue 同瞬态语义：不落盘、crash 即丢、
    reset_room / 切房即清。单房间最多一个。"""
    task_id: str        # MTS 驱动的任务（= 开启时的 active task）
    manager_guest: str  # 注册的管理者，茶客 name（= speaker_id）
    budget: int         # 剩余复查回合数，每次「worker→管理者」回调扣 1
```

挂 Orchestrator：`self._managed_session: Optional[ManagedSession] = None`。`None` 即
「无托管」—— 用「是否为 `None`」表达开/关，**不**另存 `enabled` bool（避免「`enabled=
False` 但对象还在」的二义态）。`reset_room` / `switch_room` / `clear_room` 把它连同
`_handoff_queue` 一起清。

常量（`handoff.py`）：`MAX_MANAGED_BUDGET = 20`（入站上限硬护栏）/
`MANAGED_SESSION_DEFAULT_BUDGET = 6`（前端弹窗预填）。

### 3.2 上行 inbound（两个新帧）

| 帧 | 字段白名单（**严格**，未知键 → NOTICE error 丢帧）| 校验 |
|---|---|---|
| `managed_session_start` | `{type, task_id, manager_guest, budget}` | ① `task_id` 非空 str 且 == 当前 active task 且任务非终结态；② `manager_guest` 非空 str 且在房间在场（茶客、非 `"user"`）；③ `budget` 是 `1..MAX_MANAGED_BUDGET` 整数；④ 当前**无** MTS 在跑（有则 NOTICE error，不替换 —— 换管理者/预算先 stop 再 start）|
| `managed_session_stop` | `{type}` | 无（无 MTS 时空操作 + NOTICE info）|

`managed_session_start` 校验通过：建 `ManagedSession` → `enqueue_handoff(delegate(
manager_guest), reason="托管启动")` → 走 P7.1 既有 `_enqueue_handoff_and_maybe_start`
（`_inflight_turn_task is None` 才启 `_run_handoff_turn`；有 in-flight 按 `_inflight_kind`
三态处理）→ emit `managed_session_started`。

### 3.3 stop / cancel 语义 —— 一种 stop 行为，不分软硬

| 用户动作 | inbound | 对 MTS | 对 `_handoff_queue` | 对当前 in-flight turn |
|---|---|---|---|---|
| 「停止托管」按钮 | `managed_session_stop` | 结束，`user_stopped` | **清空**（由 `_end_managed_session`，已自动入队但没跑的项不再跑）| **不取消**，自然跑完 |
| 「全部取消」 | `handoff_clear` | 结束，`user_cancel` | 清空（P7.1 既有）| 取消（P7.1 既有）|
| 取消当前 turn | `cancel` | 结束，`user_cancel` | **清空**（MTS 激活时由 `_end_managed_session`；无 MTS 时不动，P7.1 既有）| 取消（P7.1 既有）|

**`managed_session_stop` 必须清队列**：MTS 内 worker/panel 项是被 hook 自动入队的，
若 stop 只清会话状态、不清队列，用户点完「停止托管」房间还会把已入队的 worker 跑完、
继续自动说话 —— 会被理解成「停止失效」。stop handler 直接调
`_end_managed_session("user_stopped")`，由它统一清 `_managed_session` + 清
`_handoff_queue`（§4.2）；当前已在跑的那一个 turn 不取消（要立即掐断当前发言走既有
`cancel`，无需在 stop 里再造一套）。

`handoff_clear` / `cancel` 的 handler 末尾同样追加一步：若 `_managed_session` 非空 →
`_end_managed_session("user_cancel")`（一并清队列）。

### 3.4 下行 envelope（三个新事件类型）

| 事件 | `data` | 时机 |
|---|---|---|
| `managed_session_started` | `{task_id, manager_guest, budget}` | MTS 建立后 |
| `managed_session_advanced` | `{manager_guest, remaining_budget}` | 每次「worker→管理者」回调入队后（UI 倒计时）|
| `managed_session_ended` | `{reason}`（取值见 §2.2）| MTS 结束时，恰好一次 |

`events.py::ChahuaEventType` 加三个枚举值，`events.js` 同步镜像。三个都是 **hint 型**
事件（前端渲状态条 / 系统气泡，不进 transcript、不触发 AI —— 同 `handoff_*` /
`task_*` 口径）。新增的是事件类型，旧前端遇未知 type WARN 后忽略（向前兼容），故
**不 bump `schema_version`**（沿用 P7.4「加值不破坏协商」判断）。

## 4. 执行：`_advance_managed_session_after_turn`

P8.3 **不新开 drain 路径** —— MTS 完全跑在 P7 既有 `run_pending_handoff` drain loop 上。
drain loop 每轮 turn 跑完后、在既有「peek → turn_end → flush → kicks → has_next 收尾」
流程**之前**，多调一次 `_advance_managed_session_after_turn(item)`（`item` = 刚跑完的
`HandoffItem`）。该函数可能往 `_handoff_queue` 续上下一项、或结束 MTS，然后控制流
**照常进入既有的 peek / turn_end / 收尾流程**（既有「5 步」内部顺序一字不动）。
`_managed_session is None` 时该函数立即返回，对非 MTS 房间零行为变化。

### 4.1 `_advance_managed_session_after_turn(item)`

```python
def _advance_managed_session_after_turn(self, item: HandoffItem) -> None:
    ms = self._managed_session
    if ms is None:
        return
    stop = self._managed_session_stop_reason()   # budget / task_closed / cap
    if stop:
        self._end_managed_session(stop)
        return
    just_ran_manager = (item.kind is HandoffKind.DELEGATE
                        and item.target == ms.manager_guest)
    if just_ran_manager:
        # 管理者回合：它本轮的 delegate/panel 提议已被 task_proposal hook 在回合内
        # 直接入队（§5）；这里无需再做事。没派活则队列此刻为空，drain 走到收尾、
        # 由 §4.2 的兜底归为 manager_finished。
        return
    # worker 回合：worker 不会自动入队，队列空即代表「这一棒没有后续」→ 把管理者
    # 放回队列复查。
    if not self._handoff_queue:
        ms.budget -= 1
        self.enqueue_handoff(_delegate_item(ms.manager_guest, reason="托管复查"))
        self._emit_handoff_enqueued()                    # 刷队列预览，与 server handler 同口径
        self._emit_managed_session_advanced(ms)          # {manager_guest, remaining_budget}
```

`_managed_session_stop_reason()` 按 §2.2 顺序返首个命中的 reason 或 `None`：

```python
def _managed_session_stop_reason(self) -> Optional[str]:
    ms = self._managed_session
    if ms is None:                                          return None
    if ms.budget <= 0:                                      return "budget_exhausted"
    task = self._tasks_store.get_task(ms.task_id)
    if task is None or task.status in CLOSED_STATUSES:      return "task_closed"
    if self._consecutive_ai_turns >= self._max_consecutive_ai_turns:
                                                            return "cap_reached"
    return None
```

### 4.2 收尾兜底：drain 退出前结束 MTS

drain loop 收尾返回（`has_next` 为假、即将 `turn_end(next="user")` 后 `return`）那一处，
加一步：

```python
if self._managed_session is not None:
    self._end_managed_session("manager_finished")
```

这是**唯一**产生 `manager_finished` 的地方，覆盖三种「队列空了、MTS 还活着」：①管理者
复查完没派活；②管理者派的活被 `_advance_to_runnable_handoff` 当死项 drop 光（target
不在场等）；③茶客发言抛错（`_run_handoff_turn` wrapper 吞 `CancelledError` / `speak()`
的 `finally` 保 `message_end{error}`，drain 继续到队列空）。`_advance` 已显式结束的
（budget/task/cap）此时 `_managed_session` 已是 `None`，下面 `_end_managed_session` 的
守卫使这里不重复触发。

**`_end_managed_session` —— 结束 MTS 必清待跑队列**：

```python
def _end_managed_session(self, reason: str) -> None:
    if self._managed_session is None:
        return                              # 守卫：任意路径重复调用安全
    self._managed_session = None
    self.clear_handoff_queue()              # 结束 MTS = 不再自动说话：清掉所有待跑项
    self._emit_managed_session_ended(reason)
```

**结束 MTS 必清 `_handoff_queue` 是 P8.3 硬约束**（§9 不变量）。MTS 跑动时队列里的待跑
项几乎都是 hook 自动入队的 worker/panel；MTS 一结束就清掉，保证「停止 / 预算耗尽后
房间不再自动说话」。此规则使 `budget_exhausted` 不会"多跑一个 worker"（§4.3），也让
`managed_session_stop` 的清队列收归一处（§3.3）。代价：MTS 跑动中用户手动 `@某人` /
`/delegate` 插的队，若恰在 MTS 结束时还没跑会被一并清掉 —— 已接受的边角（§12）。

### 4.3 出错与边界

- **茶客发言抛错**：不专门检测、不重试。管理者回合抛错 → 无产出 → 队列空 → §4.2 归
  `manager_finished`；worker 回合抛错 → 队列空 → `_advance` 照常回调管理者复查，管理者
  能在 `<recent_messages>` 看到那条 `error` 气泡、自己决定重派或收尾。
- **管理者派的 worker 不在场 / panel 欠员**：自动入队「宽进」，drain 既有
  `_advance_to_runnable_handoff` 跑前 drop 死项（WARN + 重发队列快照）；drop 光 → §4.2
  归 `manager_finished`。
- **预算 vs cap**：`_managed_session_stop_reason` 先判 budget、再判 cap，谁先命中报谁。
- **`budget_exhausted` 后不多跑**：管理者在「剩余预算 0」的那次复查里仍可能
  `propose_delegate` —— hook 会先把 worker 入队，`_advance` 随后判 `budget_exhausted`
  调 `_end_managed_session`，**连这个还没跑的 worker 一起清掉**。用户设「预算 1 轮」
  就是 1 轮，不会被理解成「再多跑一个 worker」。`task_closed` / `cap_reached` 同理 ——
  结束 MTS 即清队列（§4.2）。

## 5. 管理者提议自动入队

P8 §6 留的核心问题：管理者复查完怎么「再指派」而不逐次等用户采纳。

### 5.1 工具面零改动 + `emit_chahua` 级 hook

管理者**仍调 P7.4 既有的 `propose_delegate` / `propose_panel`** —— `handoff_tools.py`
一字不改，茶客侧没有「我在不在托管会话里」的感知负担。区别只在这条提议落到哪：

- propose 工具照常 `transport.emit_chahua(TASK_PROPOSAL, data)`。
- `ChahuaTransport` 新增一个可选 `task_proposal_hook` 回调，由 Orchestrator 在接线每位
  茶客 transport 时注入（同一个回调，一行装配）。`emit_chahua` 遇 `TASK_PROPOSAL`
  事件先过 hook：**hook 返回 `True` → 该 envelope 不再下发前端**（拦截）；返回 `False`
  → 照 P7.4 既有路径发出，前端渲采纳卡。`task_proposal_hook` 为 `None`（缺省）时行为
  与今天完全一致。
- hook 实现 `Orchestrator._intercept_task_proposal(envelope) -> bool`：

```python
def _intercept_task_proposal(self, env: ChahuaEnvelope) -> bool:
    ms = self._managed_session
    if ms is None:
        return False
    data = env.data
    if data.get("proposer") != ms.manager_guest:
        return False                       # 非管理者提议 → 照常渲卡
    kind = data.get("kind")
    if kind not in (TASK_PROPOSAL_KIND_HANDOFF_DELEGATE,
                    TASK_PROPOSAL_KIND_HANDOFF_PANEL):
        return False                       # review/decision/status → 照常渲卡（§5.2）
    item = _handoff_item_from_proposal(kind, data.get("payload"))
    if item is None:
        return False                       # 形状坏（工具已保证、理论不达）→ 不拦
    if kind == TASK_PROPOSAL_KIND_HANDOFF_DELEGATE and item.target == ms.manager_guest:
        log.warning("MTS 管理者自指派，跳过")
        return True                        # 吞掉空转，不入队不渲卡
    self.enqueue_handoff(item)              # 直接入队，绕开采纳卡
    self._emit_handoff_enqueued()
    return True
```

`_handoff_item_from_proposal` 是个小构造函数（payload → `HandoffItem`）：delegate 取
`target` + `reason`、panel 取 `targets` + `summarizer`；`issued_by` 恒
`HANDOFF_ISSUED_BY_USER`（§6.7）；`reason` 带 `"托管 · <manager> 指派：…"` 前缀留
provenance。

**为什么不发可采纳的 `TASK_PROPOSAL`、也不靠前端抑制卡**：早期版本让 propose 照常 emit
`TASK_PROPOSAL`、再让前端 `proposal_card.js` 按「MTS 激活 + proposer == manager」自己
判「这张卡别渲」。这要前端 MTS 状态与后端严格同步，文档自己都把「不同步 → 用户看到点
不动的卡」列为风险。收敛后：**后端 hook 直接拦截，自动入队的提议根本不下发
`TASK_PROPOSAL`**，前端只收到 `handoff_enqueued`（队列预览刷新）—— 没有「该不该渲卡」
的判断，也没有跨端状态一致性问题。`proposal_card.js` **零改动**。

> propose 工具返回给管理者 LLM 的 ack 文案（P7.4 既有「已提议……等用户采纳」）在 MTS
> 内不再精确，但无害：`<managed_session>` prompt 块（§7）已明确告知管理者「托管期内
> 提议自动生效」。为保 `handoff_tools.py` 零改动，ack 文案不动。

### 5.2 只自动入队 delegate / panel

MTS 内管理者的其它提议**不**自动入队，照常渲采纳卡等用户：

| 管理者提议 | MTS 内 | 为什么 |
|---|---|---|
| `propose_delegate` / `propose_panel` | **自动入队** | 「派下一步活」就是 MTS 闭环本身，用户开启 MTS 即授权 |
| `propose_review` | 渲卡，用户采纳 | 不是推进闭环的动作；review 锚具体 message，让用户确认更稳 |
| `task_propose_decision` | 渲卡，用户采纳 | 决策入库写权限永远在用户（P5 不变量），不因 MTS 放宽 |
| `task_propose_status` | 渲卡，用户采纳 | 关任务/改状态是真决策；管理者用它**收尾**（提议 `done`）正是 §2.1 的优雅退出 —— 卡给用户、MTS 因「没派活、队列空」自然结束，两件事解耦但协同 |

## 6. 关键设计决策（with rationale）

### 6.1 MTS 是调度层机制，与计划是否结构化无关

P8 §3 已否决结构化 `plan_items`。MTS 要的只是「谁是管理者、worker 完成后回调谁、转
几轮、何时停」—— 全是调度层运行态。管理者自己 `read_file ./task/<plan>.md` 读回计划、
用脑子决定下一步派给谁，和非托管模式下做的事一样，只是不必每步等用户续话。
**MTS 落地不依赖、也不推动 `plan_items`。**

### 6.2 复用 handoff drain loop，不新开调度路径

每个 MTS 回合本质就是一次 handoff delegate/panel：管理者回合 = `delegate(manager)`，
worker 回合 = 管理者派的 `delegate(worker)` / `panel`。所以 MTS 不需要自己的执行器 ——
`run_pending_handoff` / `HandoffItem` / cap / `_run_handoff_turn` wrapper / cancel
fixup 全复用，P8.3 只加 `_advance_managed_session_after_turn`（决定「队列空时续不续」）
+ 收尾兜底。新开一条 `run_managed_loop` 会把 cap / wrapper / cancel / 收尾全复制一遍。

### 6.3 不给管理者开专用 `delegate` 工具，用 MTS 内自动入队

候选方案是给管理者一个 `is_read_only=False`、真有调度副作用的后端工具，MTS 内直接
enqueue。否决：它要新写工具、论证「茶客直接驱动调度」如何不破「茶客只能 propose」
不变量、还要处理「非 MTS 时这工具存在但不该用」。自动入队方案下工具面零改动 ——
管理者永远只有 `propose_delegate`，「提议」语义始终成立；「免不免采纳」是**调度层**
根据 MTS 状态的决定，不进茶客认知。「采纳」的执行者从「用户逐次点」变成「用户一次性
开启 MTS 即授权调度层代采纳」，且**有界（预算）、可撤销（随时 stop）**。

### 6.4 MTS 必须用户显式开启，茶客不能 propose 开启

开启 MTS = 授权一段有预算的自主循环，比单次 handoff 重。只能用户经任务面板触发。
不做：无用户动作的自动 MTS、茶客 propose 开启、超时自动开启。理由同 P7.4 §5.5
「propose 永远等用户点」+ P5.1「写权限永远在用户」。茶客能在 MTS 内影响调度（propose
下一步），不能决定「要不要进入/延长 MTS」。

### 6.5 MTS 不落盘，与 `_handoff_queue` 同瞬态语义

`ManagedSession` 不写盘、不跨重启恢复 —— crash / 切房 / 刷新即丢。MTS 是「此刻正在
自动跑」的运行态，不是房间持久属性。重启后房间静止，想继续就再点一次「托管运行」——
比恢复一个半跑的自主循环（要面对预算剩多少、该回调谁等不确定态）语义清楚。任务本身
（goal / 计划 artifact / decisions）都在盘上，重开 MTS 无损。

### 6.6 单房间最多 1 个 MTS

与「单时刻最多 1 active task」（P5 不变量）对齐：MTS 绑定 active task，active task
唯一 → MTS 唯一。`managed_session_start` 在已有 MTS 时直接 NOTICE error 拒绝（不替换 ——
替换要先安全收尾旧 MTS，徒增状态机分支）。换管理者/预算：先 stop 再 start。

### 6.7 MTS 产生的 `HandoffItem` 与用户直接触发不可区分

沿用 P7.4 §5.7：`HandoffItem.issued_by` 恒 `HANDOFF_ISSUED_BY_USER`，**不**为 MTS 加
新取值。MTS item 语义上就是用户授权的（用户开了 MTS）。provenance 走 `reason` 前缀
（`"托管复查"` / `"托管 · <manager> 指派：…"`）保留，足够 debug / 队列预览辨识。

## 7. prompt 装配：管理者 MTS 回合注入 `<managed_session>` 块

管理者在 MTS 回合需知道三件事，否则它会按 P8.1 skill 的「结尾交回用户」口径行事、不
主动续推：① 你在托管会话中，复查后**直接** `propose_delegate` 指派下一步，托管期内
自动生效、无需用户采纳，不要说「请用户决定」；② **若 `propose_delegate` / `propose_panel`
工具返回「已提议……等用户采纳」一类等待语义，在托管会话中请忽略该等待语义 —— 你的
delegate/panel 已自动入队生效，照常继续推进**；③ Goal 达成时用 `task_propose_status
("done")` 收尾（该提议不会自动生效、会给用户确认）；剩余托管预算 N 轮。

第 ② 条专门抵消工具 ack 文案与 MTS 实际行为的不一致：P7.4 的 `propose_*` 工具 ack
写死「等用户采纳」，MTS 内为保 `handoff_tools.py` 零改动不改它 —— 改由
`<managed_session>` 块把那句等待语义**显式作废**。低成本、不动技术面，且直接纠偏
管理者模型的下一步行为（否则它可能误以为要停下等用户）。

落地复用 **P7.2 的 `extra_blocks` 机制**（`build_context_for` 的临时块通道，对
`_render_onboarding` / `_render_incremental` 两条渲染路径同步生效，注入位在
`<speak_instruction>` 之前）：Orchestrator 跑 MTS 管理者回合时构造一个
`<managed_session>` 临时块传入 `extra_blocks`；块内容由 `context_renderer.py` 新增
`_render_managed_session_block(manager, budget)` 纯函数现场合成（措辞固定、`quoteattr`
防注入）。**worker 回合不注入**（worker 只是被普通指派）。非 MTS 回合 `extra_blocks`
不含该块，输出与 P7/P8.2 一致。`<managed_session>` 是临时块（每轮现合成），与
`<current_task>`（永久块）两个独立机制，同 P7.2 口径；不进 scoring prompt。

## 9. 关键不变量（落地时同步追写 CLAUDE.md）

- **MTS 是瞬态运行态，单房间最多 1 个，不落盘**。`ManagedSession`（`task_id` /
  `manager_guest` / `budget`）挂 Orchestrator，与 `_handoff_queue` 同语义：crash / 切房 /
  `reset_room` 即清，不跨重启恢复。`_managed_session is None` 即「无托管」，不另存
  `enabled` bool。
- **MTS 必须用户显式开启，茶客不能 propose 开启**。只经 `managed_session_start`，无
  自动 / 超时 / 茶客 propose 开启。
- **MTS 跑在 handoff drain loop 上，不新开调度路径**。drain 每轮 turn 跑完调一次
  `_advance_managed_session_after_turn(item)`，再照常走既有 peek / turn_end / 收尾，
  既有「5 步」内部顺序一字不动。
- **`_advance` 按「刚跑完的是不是管理者回合」分流**。管理者回合不做事（其 delegate/
  panel 提议已被 hook 在回合内入队）；worker 回合且队列空 → `budget-=1` + 回调
  `delegate(manager)`。停止守卫 `_managed_session_stop_reason()` 先判（budget /
  task_closed / cap）。
- **`manager_finished` 只由 drain 收尾兜底产生**，覆盖「管理者没派活 / 调用链续不下去
  （target 不在场、发言抛错）」；不公开 `target_missing` / `error` reason。
- **MTS 内只自动入队管理者的 `handoff_delegate` / `handoff_panel` 提议**。实现是
  `ChahuaTransport.emit_chahua` 处的 `task_proposal_hook`：hook 命中即直接
  `enqueue_handoff` 并**拦下该 `TASK_PROPOSAL` 不下发前端**（不渲采纳卡）。review /
  decision / status 提议照常渲卡。`handoff_tools.py` / `proposal_card.js` /
  `TeaGuest.speak()` 签名**零改动**。
- **MTS 产生的 `HandoffItem` 与用户直接触发不可区分**。`issued_by` 恒
  `HANDOFF_ISSUED_BY_USER`（沿用 P7.4 §5.7），provenance 仅经 `reason` 前缀保留。
- **结束 MTS 必清 `_handoff_queue`**。`_end_managed_session(reason)` 任意路径
  （budget/task/cap/manager_finished/user_stopped/user_cancel）都清掉待跑 handoff 项 ——
  保证 MTS 结束后房间不再自动说话，也使 `budget_exhausted` / `task_closed` /
  `cap_reached` 不会多跑一个已入队的 worker。`managed_session_stop` 不取消当前 in-flight
  turn（自然跑完）；要立即掐断当前发言走既有 `cancel`。`handoff_clear` / `cancel` 中途
  介入时一并结束 MTS（`user_cancel`）。
- **`managed_session_*` 是 hint 型事件**，不进 transcript、不触发 AI；新增事件类型不
  bump `schema_version`。
- **预算与 `max_consecutive_ai_turns` 两者都生效**。`budget` 计管理者复查回合数
  （kickoff 不耗），是用户旋钮；`max_consecutive_ai_turns` 是硬护栏，MTS 不能越过。

P8.1 SKILL.md 同步补一节「托管会话中的推进口径」：context 出现 `<managed_session>` 块
时，复查后直接 `propose_delegate` 指派下一步（托管期自动生效），不必交回用户；Goal
达成用 `task_propose_status("done")` 收尾。

## 12. 主要风险 & 兜底

| 风险 | 兜底 |
|---|---|
| **MTS 自循环烧 token** | ① `budget` 用户开启时设、`MAX_MANAGED_BUDGET=20` 硬顶；② `max_consecutive_ai_turns` 独立护栏，MTS 不能越；③ `managed_session_stop` 一键停、`cancel` / `handoff_clear` 硬停；④ 状态条实时显剩余预算 |
| 管理者复查完不派活、MTS 卡住 | 管理者回合结束没自动入队 delegate/panel → 队列空 → drain 收尾兜底归 `manager_finished`，绝不空转 |
| 管理者 `propose_delegate(自己)` 空转 | `_intercept_task_proposal` 跳过 `target == manager_guest` 的 delegate（WARN + 吞掉，§5.1）|
| 管理者派的 worker 不在场 / panel 欠员 | 自动入队「宽进」，drain `_advance_to_runnable_handoff` 跑前 drop 死项；drop 光 → `manager_finished` |
| `task_proposal_hook` 改了 `emit_chahua` 引入回归 | hook 缺省 `None`，非 MTS / 非 `TASK_PROPOSAL` 路径多一个 `is None` 判、零行为变化；回归测覆盖「非 MTS 时管理者提议照常 emit `TASK_PROPOSAL`」 |
| 用户点「停止托管」后房间还自动说话 | `_end_managed_session` 清 `_handoff_queue`（§4.2），已入队没跑的 worker 不再跑；当前 in-flight 那一轮跑完即止 |
| 预算耗尽但还多跑一个 worker | `_end_managed_session` 清队列 —— `budget_exhausted` / `task_closed` / `cap_reached` 后队列里没跑的项一并清掉（§4.3），用户设的预算就是硬数 |
| 管理者回合抛错 | `speak()` finally 保 `message_end{error}`；管理者无产出 → 队列空 → `manager_finished` 收尾（§4.3）|
| 用户在 MTS 内手动 `@某人` / `/delegate` 插队 | 插队项 append 进 `_handoff_queue` 照常 drain；其后 `_advance` 仍按「刚跑完的是不是管理者」分流。MTS 结束时若该插队项还没跑，随 `_end_managed_session` 清队列被一并清掉 —— 已接受的边角 |
