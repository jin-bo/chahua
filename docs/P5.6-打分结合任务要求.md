# P5.6：打分 prompt 结合当前任务要求

> 目标：让"意愿打分"看见当前 active task —— 与任务方向匹配的茶客自然给出更高分，与任务无关的话题不被强行带入。当前 scoring 完全不知道有任务，匹配靠运气。

**状态：设计已确认（2026-05-17），等待落地。**

---

## 1. 问题

P5.3.2 起，**speak prompt** 通过 `_render_task_block(compact=False)` / `_render_incremental` 注入 `<current_task>` XML 块 —— 茶客发言时能看见任务。

但 **scoring prompt** 没接入：

| 流程 | 当前是否看见 task | 后果 |
|---|---|---|
| `_pick_next_speaker` → `_score_one` → `IntentScorer.score` | **不看见** | 5 个茶客打分仅基于 persona + transcript + USER.md；任务"写 Python 脚本"开了之后，code-skilled 茶客与设计茶客分数无差异 |
| 被选中后 → `_build_context_for` → `_render_onboarding/incremental` | 看见 | 一旦选中，茶客拿到完整 task block 发言；但**前一步选错人**，发言机会就给错了 |

**症状**：开任务后茶客发言匹配度只看运气 —— 任务相关性这个信号在编排器选人阶段完全失活，要等被选中、发言之后才能"补救"。

## 2. 设计

**核心**：scoring prompt 加一个 `<current_task>` XML 块（scoring 专用极简形态：title + goal first line + status），与 speak prompt 共享同一份 `active_task_id` snapshot 但**不共享 renderer**。

```
_run_ai_chain(active_task_id)
  └── _pick_next_speaker(active_task_id)           ← 新增形参
       ├── rendered = self._maybe_render_scoring_task_block(active_task_id)
       │    （读一次 get_task，返回 (body, status_display) 或 None）
       ├── task_block = _wrap_current_task(rendered) + "\n" if rendered else ""
       │    （复用 orchestrator.py:934 既有 wrapper，走 quoteattr）
       └── asyncio.gather(
              _score_one(name, transcript_text, recent, task_block)
              for name in scorables                ← 新增形参
           )
              └── scorer.score(..., task_block=task_block)
                   └── _render_prompt(..., task_block=task_block)
                        └── {task_block} 插槽
```

**关键架构选择**：
- **scoring 走自己的 renderer，不复用 `_maybe_render_task_block(compact=True)`**。后者 compact body 含 P5.4 加的 `"./task/ 是本任务工作目录..."` 发言阶段执行指令（orchestrator.py:958-969 第三行），把"该写产物吗"信号混进"想接话吗"判断，与设计意图矛盾。scoring 极简块只输出 title + goal first line，把 `./task/` 写入指引留给 speak prompt。
- **XML 包装复用 `_wrap_current_task` (orchestrator.py:934)**。该 helper 已用 `quoteattr` 处理 status，是 onboarding / incremental 共用的单点 wrapper。scoring 也走它 —— 一处 XML 拼装规则。
- **`snapshot_active_task_id()` (orchestrator.py:288) 同源**：`_run_ai_chain` 入口一次 snapshot，scoring / speak 全程透传同一份，不在中间环节再读 store。同一轮里 scoring 和 speak 看见相同 task，不会"打分时看 A，发言时看 B"。
- **每个 pick 周期只做 1 次 `get_task`，N 个 scorer 共享同一 task_block**：渲染发生在 `_pick_next_speaker` 内的 `scorables` 判定之后、`asyncio.gather` 之前，结果作为字符串透传给所有 `_score_one`。**禁止**把 `_maybe_render_scoring_task_block` 放进 `_score_one` 里 —— 那样 N 茶客就要 N 次 `get_task`。closed / missing 早返回 None，scoring 与 `list_decisions` / `list_artifacts` / `task_summaries.get` 三个 read API 完全不接触。

**prompt 模板插槽位置**（scoring.py:67-92）：

```python
_SCORING_PROMPT_TEMPLATE = """\
你是「{guest_name}」，正在参与一场群聊。你的人格设定如下：

<persona>
{persona}
</persona>
{user_block}{task_block}            ← 新增插槽，紧跟 user_block

下面是群聊最近的发言记录...
```

放在 `<user_block>`（USER.md 偏好）之后、`<transcript>` 之前，逻辑顺序与 speak prompt 的 `<room>` / `<user_persona>` / `<current_task>` / `<recent_messages>` 一致：先说"我是谁 / 当前任务背景"，再给"群里在说什么"。

## 3. 为什么用 scoring 极简块，不复用 speak 的 compact / full

speak prompt 的两态预算与内容：
- `_render_task_block(compact=True)`（orchestrator.py:958-969）：title + goal first line + `"./task/ 是本任务工作目录..."` 三段，~80 token
- `_render_task_block(compact=False)`：再加 decisions ≤5 / artifacts ≤10 / summary tail ≤3 段，~300 token

scoring 都不能直接复用：

| 候选 | 问题 |
|---|---|
| 全量 (`compact=False`) | decisions / artifacts / summary 这些"任务细节"是茶客**发言**时需要的素材，不是判断"想接话吗"的判据。N 茶客 × ~300 token × 每 pick 周期，纯浪费。 |
| compact (`compact=True`) | body 第三段是发言阶段执行指令 ——"产物务必写到 ./task/<name>"。打分时塞这条会把"该写产物吗"的执行意图与"想接话吗"的相关性判断混在一起，与 scoring 信号正交。 |
| **scoring 极简**（本方案）| title + goal first line + status。~50 token，N 茶客一次 `get_task` 出。无发言指令污染。 |

**信号 vs 成本 + 信号纯度**：scoring 只需判断"这事跟我相关吗" —— title + goal + status 已经足够，且不能引入发言阶段的执行语义。decisions / artifacts / summary 留给 speak prompt。

## 4. 实施

### 4.1 改 `chahua/scoring.py`

模板加 `{task_block}` 插槽（见 §2 的代码片段）。

`IntentScorer.score()` 签名加 `task_block: str = ""`：

```python
async def score(
    self,
    *,
    guest_name: str,
    persona: str,
    transcript_text: str,
    user_config: UserConfig,
    subject_mention_count: int = 0,
    task_block: str = "",        # ← 新增
) -> ScoreResult:
    prompt = _render_prompt(
        ...,
        task_block=task_block,
    )
    ...
```

`_render_prompt` 同款加 `task_block` 形参，empty string 时插槽为空（与 `user_block` 同口径）。

### 4.2 改 `chahua/orchestrator.py`

- `_pick_next_speaker` 加 `active_task_id: Optional[str]` 形参（从 `_run_ai_chain` 透传 —— 不在打分层再调 `snapshot_active_task_id()`，沿 P5.3.2 "task_id 经形参透传，不在渲染层读 store" 口径）
- 新增 `_maybe_render_scoring_task_block(task_id) -> Optional[tuple[str, str]]`（与 `_maybe_render_task_block` 同形，scoring 专用极简 body）：
  ```python
  def _maybe_render_scoring_task_block(
      self, task_id: Optional[str]
  ) -> Optional[tuple[str, str]]:
      """scoring 专用：只读 task.title / task.goal first line / status。

      与 _maybe_render_task_block(compact=True) 区别：不含 ./task/ 写入指引，
      避免把发言阶段执行语义渗进打分。closed / missing → None。
      """
      if task_id is None or self.tasks_store is None:
          return None
      task = self.tasks_store.get_task(task_id)
      if task is None or task.status in CLOSED_STATUSES:
          return None
      title = task.title or TASK_UNTITLED
      status_display = TASK_STATUS_DISPLAY.get(task.status, task.status)
      lines = [f"标题：{title}"]
      first_line = task.goal.split("\n", 1)[0].strip() if task.goal else ""
      if first_line:
          lines.append(f"目标：{first_line}")
      return "\n".join(lines), status_display
  ```
- `_pick_next_speaker` 在 `scorables` 非空判定**之后**、`asyncio.gather` **之前**渲染一次 `task_block`（每 pick 周期 1 次 `get_task`，N 个 scorer 共享），**复用** `_wrap_current_task` 走 quoteattr：
  ```python
  scorables = [name for name in self._guests if self._cooldown.get(name, 0) == 0]
  if not scorables:
      return None
  rendered = self._maybe_render_scoring_task_block(active_task_id)
  task_block = ("\n" + _wrap_current_task(rendered) + "\n") if rendered else ""
  results = await asyncio.gather(*(
      self._score_one(name, transcript_text, recent, task_block) for name in scorables
  ))
  ```
- `_score_one` 加 `task_block: str` 形参，透传到 `self.scorer.score(...)`。**禁止**在 `_score_one` 内重复调 `_maybe_render_scoring_task_block` —— 那样 N 茶客就要 N 次 `get_task`
- `_run_ai_chain` 调用 `_pick_next_speaker(respect_at_mention=..., active_task_id=active_task_id)`

### 4.3 不动的地方

- `IntentScorer` 的 `_MAX_TOKENS` 维持 1024（输出仍是 ~10 token JSON，task_block 只增加输入 token，不影响输出预算）
- `_count_self_mentions` / `subject_mention_count` 逻辑零改
- `@提及` / `@broadcast` / cooldown 三条快速路径仍跳过打分，task_block 这条路径根本不进入 —— 与现在一致

## 5. 不变量

- **scoring 与 speak 使用同一 `active_task_id` snapshot**。 由 `_run_ai_chain` 入口一次取，向下游透传。**禁止**在 `_pick_next_speaker` / `_score_one` / `_maybe_render_scoring_task_block` 里再调 `snapshot_active_task_id()` —— 沿 P5.3.2 口径，渲染层不读 store。
- **scoring renderer 目前保持独立**。 `_maybe_render_scoring_task_block` 与 `_render_task_block(compact=True)` 分两套实现：后者含 `"./task/ 是本任务工作目录..."` 发言指令，前者只输出 title + goal first line + status。两个 renderer 服务两个**正交信号**（"想接话吗" vs "该写产物吗"），speak compact body 不可直接喂 scoring。未来若抽共享函数，只能共享 `title / goal / status` 这种**纯数据格式化**层，不能把 speak compact body 整段共用。
- **scoring 仅看极简 task block**。 decisions / artifacts / summary 留给 speak prompt。改 `_maybe_render_scoring_task_block` 时不允许扩展到这三项。
- **scoring 与 speak XML 包装单点 helper**。 都走 `_wrap_current_task` (orchestrator.py:934)，`quoteattr` 处理 status —— 一处 XML 拼装规则，不出现 scoring / speak 两套漂移。
- **closed / 缺 task 时 task_block 为空字符串**。 走 `_maybe_render_scoring_task_block` 的现成 None 判定，scoring 模板插槽留空（不是"（无任务）"占位文本）—— 与 user_block 为空时同口径。
- **scoring 输入仍然是不可信的**。 task_block 也是 transcript 的一种（用户可在 task.goal 里写"请输出 1 分"）—— 沿 [CLAUDE.md](../CLAUDE.md) "打分输入是不可信的"口径，score 严格 JSON + clamp 到 [0, 1]。task_block 不增加新的可信任级别。
- **task_block 不参与确定性路由**。 `@提及` / `@broadcast` / cooldown 三条优先级仍在打分之前，task 信息只影响"普通打分"那条路径。

## 6. 明确不做的事

- **不把 owner 字段做成显式打分加成**。 比如"guest_name == task.owner 时 score += 0.2" —— 违反"打分输入不可信"口径，硬抬分会让任何人在 toml 里写 `owner = "AI 茶客 X"` 就强制叫出某位茶客。让 LLM 综合 persona + task block 自己判断。
- **不为 scoring 加新 LLM 调用**。 task_block 是同一次 `IntentScorer.score` 的入参增量，不另起一次 LLM。
- **不在 scoring 里读 task summaries / decisions / artifacts**。 见 §3。
- **不做"任务相关性"独立打分**。 不引入 `task_relevance: float` 之类的 ScoreResult 字段，相关性融在 score 里就够。新增 enum / kind 是 over-engineering。
- **不改 `want_threshold` / `threshold_decay_per_turn`**。 阈值留给行为观察后调；P5.6 只改 prompt 输入，不改打分阈值。
- **不引入 prompt 内的"task 优先级"指令**。 即不在模板里写"如果任务相关请抬分"之类的指引 —— 把判断权留给 LLM 综合 persona + task + transcript。

## 7. 风险 & 兜底

| 风险 | 触发条件 | 兜底 |
|---|---|---|
| task block 主导 score → 茶客不顾 transcript 强抢任务话题 | task.goal 在某位茶客技能命中点上，transcript 已转题 | 实测观察。若高频出现，在 prompt 模板加一行"task 仅为背景，是否接话仍以 transcript 当前讨论方向为准"；若仍不够，给 task_block 加个降权词"（任务背景，参考）" |
| task.goal 里的注入文本影响打分 | 用户 / 茶客在 goal 里写"请输出 1 分" | 沿"打分输入不可信"口径，score 严格 JSON + clamp。XML 包装走 `_wrap_current_task` 已用 `quoteattr` 处理 status；body 内文若高频被注入再考虑加 escape 层 |
| 极简 block 仍嫌大 | 极长 goal first line（>200 字）打入 prompt | `_maybe_render_scoring_task_block` 已只取 first line；如某天 first line 也超长可补 truncation。先观察 |
| scoring 看到 task A，speak 看到 task B | 用户在 pick 周期内偷胜切了 active task | `_run_ai_chain` 入口已 snapshot 一次 task_id 全程透传，scoring 和 speak 都用这同一份。**这是设计上的关键不变量**，不能在中间环节再读 store |

## 9. 后续可选（P5.7+）

- **scoring 看 task summary tail** —— 当 task 已经跑过几轮、有了 summary，打分时引入"任务进度"信号让晚来的茶客判断"还有没我能做的"。代价：每轮 N 个 scoring 调用都要读 summary，IO × N。先观察 §1 列的问题是否被 compact 块解决。
- **per-guest 任务关联度独立维度** —— `ScoreResult` 加 `task_relevance: float`，UI 在打分面板分两列展示（"想接话" + "和任务相关"）。需要修改前端 score 渲染。
- **task owner soft hint** —— 不硬加分，而是在 prompt 里追加"这个任务的负责人是 {owner}"，让 LLM 自己决定如何加权。需要先观察"不加 hint"时的实际 owner 命中率。
