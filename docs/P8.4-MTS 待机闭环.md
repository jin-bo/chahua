# P8.4：MTS 待机闭环 —— `MANAGER_FINISHED` 退役

> 目标：修 P8.3 一个已落地的语义缺陷 —— **管理者一回合没派活就被当成「任务完成」**
> 而强制终结 MTS。实际场景里「再想想」「先停一下」「等用户输入」「正在做 read-only
> 调研后再决定」都会让管理者那一轮不 propose delegate/panel，但 MTS 不应该因此关掉。
>
> P8.4 把「manager 没派活」从**终结信号**改成**待机信号**：MTS 保持活、清空队列、状态
> 条改「待机中」，等用户下一句话经既有 `submit_user_message` 路径自然续上。终结 reason
> 从 6 个收敛到 5 个（删 `manager_finished`），管理者「我已完事」表态走既有路径
> `task_propose_status("done")` → 用户采纳 → `task_closed` 收尾。
>
> P8.4 是**调度层语义修正**，不动数据契约、不动工具面、不新增 envelope 类型。改动集中
> 在两个 helper 方法 + 一处 `submit_user_message` 末尾的 re-drain + 一条 prompt 块；前端
> 状态条加一个「待机」态文案。**不 bump `schema_version`**。

## 1. 背景：`MANAGER_FINISHED` 为什么是错的

P8.3 §4.2 把「drain 收尾 + 队列空 + MTS 活」归为 `manager_finished`，覆盖三种情况：
①管理者复查完没派活；②管理者派的活被 `_advance_to_runnable_handoff` 当死项 drop 光；
③茶客发言抛错。设计 rationale 是「绝不空转 —— 没下一步就当事情结束了」。

但「没派活」与「事情结束」**不等价**。实际跑下来观察到至少 4 个场景：

| 场景 | 管理者实际意图 | 当前行为 | 期望行为 |
|---|---|---|---|
| **思考型回合** | "让我先读一下 X、再想想"（read-only 调研，本轮不派人） | MTS 终结，下次要重新开启 | MTS 保持活，下次自然推进 |
| **暂停型回合** | "先停一下，我观察这个数据再决定"（向用户表达） | MTS 终结 | 待机 |
| **等用户输入** | "这个方向你倾向 A 还是 B？"（问用户） | MTS 终结，用户答完没法续上 | 待机，用户回答即续 |
| **管理者卡壳** | 模型这一轮没产出有效计划（边角，但确实会发生） | MTS 终结 | 待机，用户敲一下「继续」即可恢复 |

只有「调用链续不下去」（worker 不在场 / 发言抛错 → `_advance_to_runnable_handoff` drop
光）算「无法继续」—— 但即便这种情况，**让用户接管比强制结束 MTS 更合理**：用户看到
WARN + 队列预览异常即知道发生了什么，可以手动 `@另一位` 或直接停。

**核心错位**：P8.3 把「不派活」等同于「事情完成」，是因为没设计「待机」这一态。把它
当成完成态导致：（a）用户看到 MTS 莫名结束，要重开；（b）管理者那一轮的真实意图（思
考 / 问用户）被吞掉；（c）勉强避免「管理者一定要派活」反向训练 prompt，又出现「为了
不让 MTS 关掉而硬派活」的诱导。

## 2. 状态机 diff：6 个 reason → 5 个

P8.3 §2.2 列出 6 个 reason，P8.4 删 `manager_finished`：

| reason | P8.3 | P8.4 | 触发 |
|---|---|---|---|
| `manager_finished` | ✅ drain 收尾兜底 + P11.2.X bg 终态兜底 | ❌ **删除** | —— |
| `budget_exhausted` | ✅ `stop_reason()` | ✅ 同 | `budget <= 0` |
| `task_closed` | ✅ `stop_reason()` | ✅ 同（§4.2 扩展）| 任务不存在 / 任务终结态 / **MTS 任务不再 active**（P8.4 新增触发条件，吸收 P8.3 eager USER_CANCEL 覆盖的「切走 active / 开新任务」场景）|
| `cap_reached` | ✅ `stop_reason()` | ✅ 同 | `_consecutive_ai_turns >= max` |
| `user_stopped` | ✅ `managed_session_stop` | ✅ 同 | 用户点「停止托管」 |
| `user_cancel` | ✅ `handoff_clear` / `cancel` | ✅ 同 | 用户「全部取消」/「取消当前」 |

**收敛后语义**：MTS 只能因为「**有界**（budget / cap / task）」或「**用户显式行为**
（stopped / cancel）」结束。「管理者认为完事了」**没有独立 reason 通道** —— 它走任务层
的既有路径：管理者 `task_propose_status("done")` → 渲采纳卡 → 用户点采纳 →
**`close_task` inbound**（终结态走 `close_task`、非终结态才走 `update_task`，前端
`proposal_card.js::buildAcceptInbound` 按 status 分流；server `_inbound_update_task` 显式
拒终结态 `patch.status`，强制走 close）→ MTS `check_after_task_change` helper 命中
`TASK_CLOSED`。这条链 P8.3 §2.1 末尾已描述过（「Goal 达成时用 `task_propose_status("done")`
收尾」），P8.4 把它升格为唯一退出通道。

**前端文案影响**：`formatManagedSessionNotice` 删 `manager_finished` 一条；其它 4 条文案
不变。`task_closed` 文案**扩展成「任务关闭或切换，托管会话结束」**，覆盖三种来源：
（a）用户直接关 MTS 任务；（b）用户采纳管理者 `propose_status("done")` 卡（同 a，
经 `close_task` inbound）；（c）用户开新任务 / 切走 active，让 MTS 任务不再是 active
（P8.4 新增，吸收 P8.3 eager USER_CANCEL 兜底的场景）。

## 3. 改动：删除 `MANAGER_FINISHED` 的全部 emit 点

`MANAGER_FINISHED` 当前有 **两处** emit 点，P8.4 都删除。

### 3.1 drain 收尾兜底（`_orchestrator_handoff_drain.py`）

`:197-217`（drain body 内 `if not has_next` 分支）与 `:226-233`（while-break 退出处补底）
都改为「队列空 + MTS 活时 `return`，不调 `end_managed_session`」。具体：

```python
# P8.3 旧（drain body 内 `if not has_next`）
if (
    orch._mts_ops._managed_session is not None
    and not orch._handoff_queue
    and not orch._has_pending_mts_bg()
):
    orch._mts_ops.end_managed_session(
        sink, reason=MANAGED_SESSION_REASON_MANAGER_FINISHED,
    )
return

# P8.4 新
return     # 不终结 MTS；MTS 保持 dormant 等下次用户消息
```

drain loop 收尾 `turn_end(next="user")` 照常发，控制权回到用户 —— 与 P8.3 流程一致。MTS
是否活、剩余 budget 多少、队列是否为空，**前端从既有三源派生：`handoff_state.js` 队列
镜像（由 `HANDOFF_ENQUEUED` / `HANDOFF_CONSUMED` / `HANDOFF_CLEARED` 三事件共同维护）+
MTS 状态（`managed_session_*`）+ in-flight 状态机（`turn_*`），不需要新事件**（§6 详）。

**`_has_pending_mts_bg()` 守卫一并删除**：P8.3 设它的本意是「有未完成 bg 时安静退出
drain、让 bg 完成回调来 wake，避免误触 `MANAGER_FINISHED`」。P8.4 删了 `MANAGER_FINISHED`
emit 后，无论有没有 pending bg，两个分支都是 `return` —— 守卫等价于 dead code。删的
副作用：bg 完成回调路径 (`advance_after_bg_completion` / `handle_mts_bg_terminal_non_finished`)
**继续保留**，因为它们承担 MTS 续命与 stop_reason 推进，不受本节改动影响。守卫的语义
载体由「drain 收尾不终结 MTS」（§3.1）+「bg 完成回调主动推进 / 不主动终结」（§3.2）
两段共同承担，比内嵌守卫更清晰。

### 3.2 P11.2.X bg 终态兜底（`_server_agent_run.py`）

`handle_mts_bg_terminal_non_finished` `:502-511`（「最后一个 mts_managed bg 以

runtime.session.orchestrator._mts_ops.end_managed_session(

## 4. dormant 复活路径与 task 状态变更检查

### 4.1 `submit_user_message` 末尾 re-drain（带 `reset_cap=False`）

MTS dormant 状态下，用户下一句话 `submit_user_message` 走既有路径：drain（队列空、立即
返回）→ chain。chain 内管理者经 scoring 拿到发言权（MTS 期间管理者**通常**占据高分槽，
**不保证** —— 见下文最后一段），说话过程中可能 `propose_delegate(...)` →
`intercept_task_proposal` hook 命中 → 自动入队 `_handoff_queue`。

**问题**：chain 不知道队列被 hook 喂了东西，它继续按 scoring 选下一位发言者、走完 chain
内既有 cap。`_handoff_queue` 里的 worker delegate 要等下次用户消息触发的 drain 才执行 ——
显然不对，用户期望「自动推进」立即接上。

**Cap 双扣陷阱**：`run_pending_handoff` 当前实现（`_orchestrator_handoff_drain.py:94-96`）
入口无条件 `orch._consecutive_ai_turns = 0`，docstring 显式声明「入口清零计数一次，
drain loop 内不再清零」。如果 re-drain 直接调既有签名，**chain 段累计的轮数会被一笔
勾销**：

```
chain 跑 N 轮（_consecutive_ai_turns = N）
  → 管理者 propose_delegate，hook 入队
chain 自然退出（无足够 scorer / 撞 cap）
re-drain 调 run_pending_handoff → 入口 reset → _consecutive_ai_turns = 0
re-drain 可跑满 max_consecutive_ai_turns 轮
总 AI 轮数 = N + max，远超 cap
```

这违反 P7.1 「`submit_user_message` 是唯一编排两者的入口、总 AI 工作量受单一 cap 约束」
不变量。

**修法**：给 `run_pending_handoff` 加 `reset_cap: bool = True` 形参 **两处签名都改**：
`_orchestrator_handoff_drain.py::HandoffDrainOps.run_pending_handoff`（真实现）+
`orchestrator.py::Orchestrator.run_pending_handoff`（主类薄转发，`:450-454`）—— 后者只
透传新参数即可，遗漏会让 P8.4 re-drain `TypeError`。

```python
# _orchestrator_handoff_drain.py::HandoffDrainOps（真实现）
async def run_pending_handoff(
    self, sink: EnvelopeSink, *, task_id: Optional[str], reset_cap: bool = True,
) -> None:
    orch = self.orch
    if not orch._handoff_queue:
        return
    if reset_cap:
        orch._consecutive_ai_turns = 0
        orch._rounds_without_user_or_mention = 0
    # ... 余下与 P7.1 一致 ...

# orchestrator.py::Orchestrator（主类薄转发，必须同步改签名透传）
async def run_pending_handoff(
    self, sink: EnvelopeSink, *, task_id: Optional[str], reset_cap: bool = True,
) -> None:
    """slot 拆分：薄转发到 HandoffDrainOps。"""
    await self._drain_ops.run_pending_handoff(
        sink, task_id=task_id, reset_cap=reset_cap,
    )
```

```python
# orchestrator.py::submit_user_message —— 末尾
await self.run_pending_handoff(sink, task_id=active_task_id)    # reset_cap=True（既有）
await self._run_ai_chain(sink=sink, active_task_id=active_task_id)
# P8.4 re-drain：chain 内管理者经 hook 自动入队的 delegate，chain 不知道要切回 drain；
# 统一在收尾补一次。reset_cap=False —— chain 段已累计的轮数不被清零，cap 在整条
# submit_user_message 内是单一预算。非 MTS / 队列空时 run_pending_handoff 早 return。
if (
    self._mts_ops.managed_session is not None
    and self._handoff_queue
):
    await self.run_pending_handoff(
        sink, task_id=active_task_id, reset_cap=False,
    )
```

`reset_cap` 默认 `True` —— P7.1 / P8.3 / P11 既有所有调用点（`submit_user_message` 首次
drain、server `_run_handoff_turn` wrapper、bg run 续命起的 drain）行为零变化。新参数
只在 P8.4 re-drain 这一处取 `False`。

**cap 判定规则不改、只增加 reset 开关**：drain loop 内既有「档② 此刻预算占了即 `break`
留队首」（`_orchestrator_handoff_drain.py:108-112`）+ panel 的 `cost > max` 死项 drop
（`:280-290`）全部一字不动；只在「入口要不要清零计数」这一点上多了开关。所以
`HandoffItem` / cap 阈值常量 / `_advance_to_runnable_handoff` / `_run_handoff_turn`
wrapper / cancel fixup **整链零改动**（接触面 §10）。

**第二次 `run_pending_handoff` 是自循环的**：drain loop 每轮 turn 跑完调
`advance_after_turn`，worker 跑完把管理者放回队列、budget 扣 1，直到队列空（dormant 再次
出现）或命中 budget/cap/task 终结。这一次调用就把整段「MTS 复活后的连锁推进」跑透；
P8.3 那套 5 步收尾、cancel、wrapper 全复用，零新逻辑。

**「为什么不让 chain 在管理者发言后立即切到 drain」**：chain 与 drain 分流是 P7.1 核心
不变量（「drain 不回落 scoring」），让 chain 中途切 drain 会破坏「`submit_user_message`
是唯一编排两者的入口」。把 re-drain 放在 `submit_user_message` 收尾、不动 chain 内部，
保持调度层语义清晰。

**chain 内非管理者发言的合法分支**：dormant 期间用户消息若与管理者关联度低，scoring
完全可能让另一位茶客先发言（或干脆没人过阈值），那位茶客**不**走 MTS hook、不入队
delegate。chain 退出后 `_handoff_queue` 仍空，re-drain 的 `if` 条件不命中 → 直接跳过
（`run_pending_handoff` 自身的 `if not queue: return` 也兜得住）。MTS **继续 dormant**
等下一次用户消息。这是合法分支，不是 bug：dormant 复活的入口是 scoring，不是「管理者
必然抢到发言权」。若用户希望管理者必然回应，明显的工程手段是 `@管理者名` 走 P5 既有
mention 路由。

### 4.2 task 状态变更 helper：`check_after_task_change()` + 删 P8.3 eager end

**先删 P8.3 三处 eager `end_managed_session` 块**。`chahua/server_inbound_task.py` 当前
在三个 inbound 早期（`_cancel_and_drain_all_foreground` 之后、mutation 之前）显式调
`end_managed_session(USER_CANCEL / TASK_CLOSED)`：

| 位置 | P8.3 行为 | 为什么 P8.4 必须删 |
|---|---|---|
| `:148-156`（`_inbound_open_task`） | 总是 `USER_CANCEL`（新任务必 ≠ MTS 任务） | dormant MTS 一旦被这条 eager end 杀掉，§4.2 helper 的「占位」就没意义；§4 整段 dormant 复活闭环被旧代码直接抵消 |
| `:316-323`（`_inbound_set_active_task`） | 总是 `USER_CANCEL` | 同上 |
| `:371-385`（`_inbound_close_task`） | 关 MTS 任务 → `TASK_CLOSED`；关别的 → `USER_CANCEL` | 关 MTS 任务由 helper 经 `stop_reason()` 兜住（行为等价）；关别的任务下 P8.3 强行结束 MTS 是过度反应 —— P8.4 让 MTS 仍 dormant 在自己的任务上 |

三处全删，统一改成「`_cancel_and_drain_all_foreground` → mutation → `emit_task_info` →
**最后调 `check_after_task_change(sink)`**」。`_cancel_and_drain_all_foreground` 杀掉
inflight drain 这件事 P8.4 不动 —— 它本就该杀（用户在动 task 状态时让旧 drain 跑完是
不合理的）。差别在于：cancel 之后 MTS **保持活、转 dormant**，而非立即终结。

**`stop_reason()` 同步扩 1 条**：覆盖「MTS 任务不再是 active」这种 P8.3 走 eager
`USER_CANCEL` 兜底的场景。

```python
# _orchestrator_managed_session.py::ManagedSessionOps.stop_reason —— P8.3 既有实现上
# 加 P8.4 新增的 active 不一致检查。属性访问沿用既有 slot 形态：状态在 self.orch 上、
# 不在 slot 本地存副本（slot 是行为聚合，无独立状态）。
def stop_reason(self) -> Optional[str]:
    ms = self._managed_session
    if ms is None:
        return None
    if ms.budget <= 0:
        return MANAGED_SESSION_REASON_BUDGET_EXHAUSTED
    if self.orch.tasks_store is not None:
        task = self.orch.tasks_store.get_task(ms.task_id)
        if task is None or task.status in CLOSED_STATUSES:
            return MANAGED_SESSION_REASON_TASK_CLOSED
        # P8.4 新增：MTS 必须绑定当前 active task —— 用户切走 active 即视为 task_closed。
        # 折叠进既有 task_closed 而非新增 reason，沿用「5 reason 收敛」原则；前端文案
        # 扩展成「任务关闭或切换」覆盖三种来源。tasks_store 为 None 的房间（非任务房）
        # 该分支自然不执行。
        if self.orch.tasks_store.active_task_id != ms.task_id:
            return MANAGED_SESSION_REASON_TASK_CLOSED
    if self.orch._consecutive_ai_turns >= self.orch.config.max_consecutive_ai_turns:
        return MANAGED_SESSION_REASON_CAP_REACHED
    return None
```

新 helper：

```python
# _orchestrator_managed_session.py::ManagedSessionOps
def check_after_task_change(self, sink: EnvelopeSink) -> None:
    """task 状态变更后主动跑一次 stop_reason() 检查。

    dormant 期间 advance_after_turn / advance_after_bg_completion 都不触发，需要在
    task 状态变更（open_task 自动 set_active / update_task 改 status /
    set_active_task / close_task）路径手动调一次，命中即 end_managed_session。

    替代 P8.3 在 server_inbound_task.py 各 handler 早期的 eager end 块（已删）——
    交给 stop_reason 统一判定，未来加新停止条件只改一处。
    """
    if self._managed_session is None:
        return
    stop = self.stop_reason()
    if stop is not None:
        self.end_managed_session(sink, reason=stop)
```

调用点（4 个 task inbound handler `chahua/server_inbound_task.py`）末尾，**`emit_task_info`
之后**：

| handler | 触发哪条 stop_reason |
|---|---|
| `_inbound_open_task` | 自动 `set_active` 到新任务 → `active_task_id != ms.task_id` → `TASK_CLOSED`（P8.4 扩展） |
| `_inbound_update_task` | patch 含 `status` 但非终结态 → 无命中（任务仍 active、仍 open）。占位，未来 update 加新字段时受益 |
| `_inbound_set_active_task` | 切到非 MTS 任务 → `active_task_id != ms.task_id` → `TASK_CLOSED`；切到 MTS 任务（idempotent）→ 无命中 |
| `_inbound_close_task` | 关 MTS 任务 → `task.status in CLOSED_STATUSES` → `TASK_CLOSED`；关别的任务 → 无命中（MTS 在自己任务上 dormant 继续）|
| 采纳 `task_propose_status("done")` 卡片 | `proposal_card.js::buildAcceptInbound` 拼成 `close_task` inbound → 走 `_inbound_close_task` → 已覆盖 |

**P8.4 行为 vs P8.3 行为对照**：

| 场景 | P8.3 | P8.4 |
|---|---|---|
| MTS 活 + 用户开新任务 | eager `USER_CANCEL`，MTS 终结 | helper → `TASK_CLOSED`（MTS 任务不再是 active），MTS 终结 |
| MTS 活 + 用户切 active 到非 MTS 任务 | eager `USER_CANCEL` | helper → `TASK_CLOSED` |
| MTS 活 + 用户关 MTS 任务 | eager `TASK_CLOSED` | helper → `TASK_CLOSED`（等价） |
| MTS 活 + 用户关**非** MTS 任务 | eager `USER_CANCEL` | **helper 无命中，MTS 继续活在自己的任务上**（P8.4 改进） |
| MTS 活 + 用户改非终结 status | eager 不触发（P8.3 update_task 没装 eager end） | helper 无命中（等价） |

唯一行为差异是第 4 行：P8.4 让 MTS 在「用户关了别的任务」时活下来，符合「MTS 终结只
因 5 个明确 reason」语义；P8.3 把它当 USER_CANCEL 是过度反应。前 3 行 reason 名字
（`USER_CANCEL` → `TASK_CLOSED`）变了，行为等价：MTS 终结、清队列、emit `managed_session_ended`。
前端文案表把 `task_closed` 文案扩展成「任务关闭或切换」即可。

**收敛成一个 helper 而非逐点 5 行守卫**：未来加 task 状态变更入口（如假想的
`bulk_update_tasks`）只需调 helper、不会遗漏；helper 内一处改 `stop_reason` 即全路径
生效。`emit_task_info` / `relink_task_dirs` 等附属操作不需调 helper —— 它们是同一 inbound
的下游副作用，helper 调一次即覆盖。

## 5. prompt：告诉管理者「没下一步就讲完就行」

P8.3 §7 的 `<managed_session>` 块第 ② 条作废了 `propose_*` 工具 ack 的「等用户采纳」等待
语义。P8.4 加第 ③ 条，明确「没下一步时不强行 propose」是合法收尾：

```
<managed_session>
你正在「托管任务会话」中（管理者：{manager}，剩余复查预算：{budget} 轮）。

① 复查后**直接** propose_delegate / propose_panel 指派下一步，无需等用户采纳。
② 若 propose_* 工具 ack 含「等用户采纳」一类等待语义，在本会话中**忽略它** ——
   你的提议已自动生效，照常继续推进。
③ **没有可派的下一步**时（如需要再读资料、需要用户输入、Goal 已达成等），
   **直接讲完当前发言并结束本轮**，不要为了维持会话而硬派活。MTS 会自动等
   用户下一句话再续 —— 它不会因为你这一轮没派活而结束。
④ Goal 真正达成时用 task_propose_status("done") 收尾（不自动生效，给用户确认）。
</managed_section>
```

第 ③ 条把「待机是允许的」纳入管理者的认知。`_render_managed_session_block(manager,
budget)` 实现里在 `<managed_session>` 块末尾追加这一段；`quoteattr` 防注入；纯函数无副
作用。`examples/personas/Maya/skills/task-management/SKILL.md` 同步加一节「待机收尾」
（用户读得到的口径源）。

**为什么不让管理者用工具显式声明「待机」**：新增工具 = 新 prompt 训练成本 + 模型在两条
出路（讲完 vs 调工具）之间摇摆。「直接讲完就行」是 LLM 自然行为，把 prompt 改对比把
工具改对成本低得多。这呼应 P8.3 §6.3「用 hook 而非新工具」的决策。

## 6. 前端：状态条加「待机中」态

状态条数据来自三个既有前端模块状态，**不新加 envelope 订阅**：

- **MTS 状态**（活 / budget）：来自 `managed_session_started` / `managed_session_advanced` /
  `managed_session_ended`；
- **队列镜像**（是否空、项数）：来自 `app/renderer/handoff_state.js`，由它已订阅的
  `HANDOFF_ENQUEUED`（整份快照替换）/ `HANDOFF_CONSUMED`（单项 popleft）/
  `HANDOFF_CLEARED`（清空）三事件维护 —— **不要只读 `handoff_enqueued`**，否则 drain
  消费完队首、前端镜像不更新 → 永远不进入「待机」态；
- **in-flight 状态**：前端从 `turn_start` / `turn_end` 维护的状态机读，已由
  `envelope_router.js` 的 `BACKGROUND_MILESTONE_TYPES` 分流过滤好（§6 末段）。

dormant 推导：**MTS 活 + 队列镜像空 + 当前无 in-flight turn**。前端 `managed_session.js`
（或 composer 状态条模块）订阅 `handoff_state` 的 listener、读自身 MTS 状态 + 前台
in-flight 状态合成文案：

| 状态 | 文案 |
|---|---|
| MTS 活 + 队列非空 + in-flight | `托管中 · {manager} 管理 · 剩余 {budget} 轮 · 待跑 {N} 项` |
| MTS 活 + 队列空 + in-flight | `托管中 · 推进中 · 剩余 {budget} 轮` |
| **MTS 活 + 队列空 + 无 in-flight** | **`托管中（待机）· {manager} 管理 · 剩余 {budget} 轮 · 等待用户消息`** |
| MTS 关 | （隐藏状态条）|

第 2 行（队列空 + in-flight）**有意不写发言者身份**：`HANDOFF_CONSUMED` 之后 worker
正在发言时会落到这一行，写「{manager} 发言中」会把 worker 的发言误标为管理者；要把
当前发言者写对，前端得额外订阅 `MESSAGE_START`/`MESSAGE_END` 抓 `speaker_id` —— 引入
新状态机得不偿失。中性文案「推进中」直观表达「MTS 正在跑，等本轮完」，无歧义。

「待机」态加一个浅灰色 dot 或 pause 图标做视觉区分；点击仍可弹「停止托管」按钮。**没有
新 envelope** —— in-flight 状态前端已经从 `turn_start` / `turn_end` 维护。

**前端跨房 in-flight 判定不会受切房 race 影响**：`envelope_router.js:102-110` 已对后台
房间里程碑分流 —— 当 `env.room_id` 非空且与 `foregroundRoomId` 不一致、且 `env.type ∈
BACKGROUND_MILESTONE_TYPES`（含 `turn_*` / `managed_session_*`）时，envelope 走
`roomList.onBackgroundMilestone`，不进主 switch 也不更新前台 in-flight 状态。所以 P8.4
新增的「无 in-flight」推导只读前台房的 `turn_start` / `turn_end` 状态机 —— P9 切房 race
已在 P9 阶段解决，P8.4 不引入新问题。

`managed_session_ended` 文案表删 `manager_finished` 项。`task_closed` 文案**扩展成
「任务关闭或切换，托管会话结束」**，覆盖三种来源（详见 §2 末段）：（a）用户直接关 MTS
任务；（b）用户采纳 `propose_status("done")` 卡走 `close_task`；（c）用户开新任务 / 切走
active 让 MTS 任务不再是 active（P8.4 新增，吸收 P8.3 eager USER_CANCEL）。

## 7. 关键设计决策

### 7.1 为什么不给 dormant 设超时

候选方案：dormant 超过 N 分钟自动 `end_managed_session(idle_timeout)`。否决理由：

- 茶话室是异步聊天范式，用户可能离开几十分钟回来 ——「超时关闭」会把回来的用户摔到
  「MTS 已关」的莫名状态，要重开。
- `budget` / `cap` / `task_closed` 已是三条独立护栏，外加用户「停止托管」一键退出。
  再加超时是引入新状态机分支与新前端文案，收益不抵成本。
- ws 断开会自动清 MTS（既有 P9 不变量），客观上已有「软超时」。

### 7.2 为什么不加 `managed_session_dormant` envelope

候选方案：MTS 进入 dormant 时 emit 一帧 `managed_session_dormant`，给前端一个显式信号。
否决：

- dormant 不是 MTS 的独立状态 —— 它就是「活 + 队列空 + 无 in-flight」的派生态。前端从
  既有三个信号合成即可，多发 envelope 是冗余。
- 「显式信号」诱惑后端在 dormant 进入 / 退出时都发 envelope；进入容易（drain 收尾即发），
  **退出难** —— 退出时机其实是「下次 turn_start」，意味着要把 turn_start 与 dormant 状态
  耦合。不如让前端推导。

### 7.3 为什么不让管理者用 `task_propose_status("done")` 自动入队

候选方案：MTS 内管理者的 `task_propose_status("done")` 也被 intercept hook 自动采纳、
触发 `task_closed` 终结。否决：

- P5 不变量「task / decision 写权限只在用户」是承重契约 —— **关任务是真决策**，不能因
  MTS 放宽。让管理者「自我宣告完事」绕过用户确认是 backdoor，破坏「采纳卡是用户唯一
  授权点」语义。
- 用户点采纳 = 一次额外动作，但这一刻用户确实**应该看到**「管理者认为任务完了，你同意
  吗」—— 它是 MTS 收尾的关键信号，不是要省略的"摩擦"。
- P8.3 §5.2 已明确「只自动入队 delegate / panel」，P8.4 不动这一约束。

### 7.4 为什么把 P11.2.X 兜底也改成 dormant 而不是某种 `bg_failed` reason

候选方案：保留「最后一个 mts bg 失败 + 无后续」的终结路径，但换 reason 名（如
`bg_terminal_no_followup`）。否决：

- 新增 reason = 新前端文案 + 新测试矩阵分支；价值低。
- 这种边角场景下「保持 dormant」语义清晰：用户看到 bg 失败气泡、状态条仍「待机中」，
  自然决定下一步。比硬塞一个新 reason 直觉。
- 与 §3.1 drain 兜底同样删 `MANAGER_FINISHED`，保持「MTS 只因 5 个 reason 之一终结」的
  口径统一。

## 9. 风险 & 兜底

| 风险 | 兜底 |
|---|---|
| **dormant MTS 永远不退出**（用户离开） | ws 断开既有清 MTS 路径（P9）；用户长期离线也不会有新消息触发 chain，MTS 自然挂着不消耗 budget。等同于一个不消耗资源的"已暂停"标签 —— 体验上比"莫名关掉"好 |
| **chain 内管理者派活后 re-drain 又跑很久** | re-drain 调 `run_pending_handoff(..., reset_cap=False)`，不清零 `_consecutive_ai_turns`；chain 段 + re-drain 段共享同一 `max_consecutive_ai_turns` 预算。详见 §4.1 cap 双扣陷阱讨论 |
| **chain 内选的不是管理者，re-drain 空操作 MTS 仍 dormant** | 合法分支（§4.1 末段）。下一次用户消息再试；想强制管理者回应用 `@管理者` mention |
| **管理者真没下一步、prompt 不到位还硬 propose** | `<managed_session>` 块第 ③ 条明确允许「讲完就行」+ SKILL.md 同步；若仍硬 propose，hook 仍自动入队、推进多一轮 —— 不是新行为 |
| **测试断言 `manager_finished` 的旧用例集体红** | 一次性迁移：~8 处 grep 出后改断言为「MTS 仍活 + 队列空」+ 加 `submit_user_message` 续上一轮的回归用例；P8.4.3 commit 单独处理 |
| **前端旧版收到没有 `manager_finished` reason 的房间表现** | `formatManagedSessionNotice` 删项后旧前端理论上不会再收到该 reason；万一收到（部署不同步）走默认中性文案兜底 —— 加一行 `default: "托管会话结束"` |
| **dormant 期间用户改 task 状态、MTS 挂在已关或不再 active 的任务上** | §4.2 helper `check_after_task_change(sink)` 在 4 个 task inbound handler 末尾统一调；按 §4.2 矩阵分流 —— `close_task`（关 MTS 任务）/ `open_task`（自动 set_active 新任务）/ `set_active_task`（切到非 MTS 任务）均命中 `stop_reason()` 扩展条款 → `end_managed_session(task_closed)`；`update_task` 非终结 status 通常无命中（占位，未来 update 加新字段时受益）；`close_task` 关别的任务 → 无命中，MTS 在自己任务上继续 dormant |
