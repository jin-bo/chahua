# P8.7：MTS 预算收尾轮 —— 最后一次管理者复查转收尾模式

> 目标：MTS 因 **`budget_exhausted`** 终结时，用户能拿到一份交接 —— 做完了什么、还剩什么、
> 卡在哪、下一步怎么走 —— 而不是「托管中 · 剩余 N 轮」那条 bar 悄无声息地消失。
>
> **手段：不新增任何回合。** MTS 的最后一次管理者复查**本来就跑在 `budget == 0` 上**
> （worker 回合先 `budget -= 1` 再入队复查，§2），它天然就是收尾轮 —— 只需在那一轮把注入的
> `<managed_session>` 块**换成**收尾块。
>
> P8.7 是**prompt 分流 + proposal 收口**：一个新块 + 一处渲染分支 + 一处 proposal 拦截
> （后者改的是 hook 行为，不只是文案，故不写作「纯 prompt」）。**不加状态字段、不动调度、
> 不动队列、不动 cap 计算、不新增 stop reason / envelope、不改 wire 与前端、
> 不 bump `schema_version`。**

**状态：已落地（2026-08-01，v2 简化稿实现 + v3 复审收敛）**。立项依据见
[`P8.5-codex-goal 机制对照与借鉴.md`](P8.5-codex-goal%20机制对照与借鉴.md) §4.5 + §6 建议 5。
上游契约见 [`P8.3-原生自动推进.md`](P8.3-原生自动推进.md)（MTS 生命周期 / `advance_after_turn`）、
[`P8.4-MTS 待机闭环.md`](P8.4-MTS%20待机闭环.md)（5 reason 收敛 / `<managed_session>` 块）、
[`P8.6-MTS 管理者审计提示.md`](P8.6-MTS%20管理者审计提示.md)（反目标缩水口径，收尾块沿用）、
[`P7-显式 handoff 与 delegation.md`](P7-显式%20handoff%20与%20delegation.md)（`extra_blocks` 注入位）。
被借鉴对象见 agentao 0.4.18 `agentao/cli/input_loop.py::run_goal_continuation` 的
`_wrap_up_prompt` 分支。

> **v1 已废弃**：初稿设计成「在最后一次复查之后**再插入**一个管理者收尾回合」，为此引入
> `ManagedSession.wrapping_up` flag、两处 stop 分流、入队前清队列、cap 余量守卫。评审指出
> 最后一次复查本身已经是 budget==0 的终局回合，插入回合纯属多余 —— 它多烧一次 LLM 调用，
> 并且**那四个守卫全是新设计自己制造的问题**。v2 全部删除，见 §8 修订记录。

## 1. 为什么只给 `budget_exhausted`

P8.4「5 reason 收敛」的五个终结理由里，只有一个是「活干到一半、纯资源到点」：

| stop reason | 收尾 | 理由 |
|---|---|---|
| **`budget_exhausted`** | **有** | 唯一「任务没完、用户没喊停、纯预算到点」的终结，最需要交接 |
| `task_closed` | 无 | 任务已关 / 已切走；closed task 不注入 task 块，收尾也没上下文，且用户刚做完这动作 |
| `cap_reached` | 无 | 硬护栏路径，此时不该再对管理者提任何要求 |
| `user_stopped` / `user_cancel` | 无 | 用户显式喊停 / 断线。「停」就是停 |

被借鉴对象同口径：agentao `run_goal_continuation` 只在 `budget_tripped()` 分支跑
`_wrap_up_prompt`；`update_goal(complete|blocked)`（≈ `task_closed`）与 Ctrl-C
（≈ `user_cancel`）都直接 `break`。

**范围声明（诚实划界）**：本阶段保证的是「**正常预算耗尽路径下，最后一次管理者复查以收尾
模式运行**」。用户停止 / 取消 / 任务变更仍可在任意时刻立即终止 MTS，此时**没有**收尾轮 ——
这是设计意图（上表），不是缺陷。不为此补状态机。

## 2. 机制：`budget <= 0` 的管理者回合就是最后一轮

本阶段的支点是**两条独立命题**，都由既有代码保证、无需新状态。注意它们**不是**一条「双向
严格等价」—— 见 §4 末的边角。

**① 安全性（切换收尾 prompt 永不误伤）**：任何**实际跑起来**的、渲染 `extra_blocks` 时
`ms.budget <= 0` 的管理者回合，**必定是终局回合**。因为管理者回合跑完，`advance_after_turn`
第一件事就是 `stop_reason()`（`_orchestrator_managed_session.py:284`），`budget <= 0` 直接返
`BUDGET_EXHAUSTED` → `end_managed_session`。管理者这一轮就算又派了活，也在
`end_managed_session` 清队列时被丢（既有语义，`test_budget_one_runs_one_worker_then_exhausted`
钉死）。**这条是「换 prompt 安全」的全部依据** —— 不会有 budget≤0 的管理者回合后面还跟着
别的回合。

反向的「所有管理者回合中只有终局那次 budget≤0」同样成立（其余管理者回合 budget 恒 > 0）：
kickoff 有 inbound 校验 `1 <= budget <= MAX_MANAGED_BUDGET`（`server_inbound_handoff.py:470`）；
dormant 复活的 kickoff（P8.4.7）只可能在 budget > 0 时发生 —— 进入 dormant 的那次
`advance_after_turn` 同样先查 `stop_reason()`，budget≤0 早已终结。

**② 覆盖性（正常路径下终局回合确实会被排上）**：`budget` 只在「worker → 管理者」回调处
递减，且**递减后立即入队那一条管理者复查**（前台 `:298-305`，bg `:259-266`）。所以正常
worker / bg 路径上，budget 从 1 掉到 0 的那一步，正好排进这个终局管理者回合。

**②不是全称命题** —— 存在特定队列交错让终局管理者回合排上了却跑不到（§4 末）。届时只是
「这次没有收尾轮」，不会误渲、不会挂死，故本阶段不为它加机制。

**时序（budget=1 全程，零额外回合）**：

```
kickoff: manager turn      budget=1  → <managed_session>（正常块）→ 派 Wei
Wei worker turn            budget=1  → advance: 队列空 → budget-=1 → 0 → 入队 manager 复查
manager 复查 turn          budget=0  → <managed_session_wrapup>（收尾块）   ← 本阶段唯一改动点
  advance_after_turn: stop_reason() = budget_exhausted → end_managed_session
```

对比 v1 的「最后复查 + 额外收尾」两个管理者回合：v2 的管理者回合总数与**现状完全一致**，
只是最后那一轮拿到了不同的 prompt。

## 3. 改动

### 3.1 收尾块（`chahua/context_renderer.py` 新增）

**`manager` 必须走 `quoteattr`**（与 `render_managed_session_block` / `<room>` 等块同口径，
CLAUDE.md「`quoteattr` 防注入」）—— 茶客名是用户可配的自由文本，含 `"` / `<` / `&` 会破坏
XML 属性边界：

```python
    return (
        f"<managed_session_wrapup manager={quoteattr(manager)}>\n"
        ...
    )
```

渲染结果（`manager="Maya"`）：

```text
<managed_session_wrapup manager="Maya">
The review budget for this managed session is exhausted — this is your FINAL turn.
Review what the workers just delivered, then wrap up. Do NOT start new substantive
work, do NOT delegate, and do NOT start background runs — propose_delegate /
propose_panel / spawn_agent_run / spawn_agent_runs are all off-limits this turn. A
propose_delegate / propose_panel here is dropped outright and produces NO approval
card, so do NOT tell the user to approve anything.
Summarize for the user: what was accomplished toward the task goal; what remains,
verified against the FULL task scope (do NOT report a shrunken goal as met); any
blockers; and one concrete next step.
Only if the FULL scope is met, call task_propose_status("done") to close the task
(the proposal goes to the user for confirmation, not auto-applied). Running out of
budget is NOT itself grounds for "done" or for task_propose_status("blocked") — if
the goal is unmet, say so in the summary and leave the task status unchanged.
Always reply in the same language as the conversation (default: Chinese).
</managed_session_wrapup>
```

要点：**"Review what the workers just delivered, then wrap up"** 是必须的 —— 这一轮同时也是
最后一次复查回合，不能写成纯汇总而让管理者忽略刚交付的产物。反目标缩水口径承 P8.6 §2
第 ⑤ 条；语言锚点按 P14 不变量保留。承重语义点（回归钉这几条，不钉整句）：`FINAL turn` /
`do NOT delegate` / `FULL task scope` / 语言锚点。

**替换掉 `<managed_session>` 就得把仍适用的语义带过来**（v3 复审补齐，见 §8）—— 本块
**不是** `<managed_session>` 的子集，四条对应关系逐条列明；漏任一条都在收尾轮留下一个
被替换掉的旧 bullet 的空洞：

| 收尾块条款 | 对应被替换的 bullet | 漏了会怎样 |
|---|---|---|
| 禁 `spawn_agent_run(s)` | ③ 并发走 spawn、**不吃 budget** | 管理者按 ③ 学到的路子在收尾轮起后台 run；spawn **不经 `TASK_PROPOSAL`、swallow 拦不住**，run 活过 MTS，跑完没人复查 |
| 「dropped、NO approval card，别叫用户去点」 | ② 作废 `propose_*` 的「等用户采纳」ack | `propose_*` 工具 ack 恒是「已提议、等采纳」；收尾轮既 swallow 就没卡 → 收尾发言写「请点采纳」，UI 里根本没那张卡 |
| `task_propose_status("done")` 的**动作** | ⑤ 审计 + done 收尾 | 只带前置审计（`FULL task scope`）不带动作 —— 恰好在最可能完工的一轮没人告诉管理者怎么收，任务停在 `doing` |
| 「预算到点 ≠ done ≠ blocked」 | ④ 防过早 blocked 节流 | 本块主动问「有无 blocker」，而 status 提议**不在 swallow 白名单**、会真渲卡 —— 一次性受阻 + 用户采纳即落库 `blocked`，正是 P8.6 要防的 |

### 3.2 渲染分流（`_orchestrator_handoff_drain.py::_build_winner_blocks`）

既有 MTS 档（`:346-354`）内部二选一，判定条件外的一切不动：

```python
        ms = self.orch._mts_ops._managed_session
        if (
            ms is not None
            and item.target == ms.manager_guest
            and winners == [ms.manager_guest]
        ):
            if ms.budget <= 0:
                return [[render_managed_session_wrapup_block(ms.manager_guest)]]
            return [[render_managed_session_block(ms.manager_guest, ms.budget)]]
```

**是替换不是追加**：`<managed_session>` 第 ① 条逐字是「直接调 propose_delegate /
propose_panel」，与收尾指令正面冲突，两块同时注入等于给模型两个相反命令。走独立块也正是
本阶段**不触碰「5 条 bullet / 顺序不变」不变量**的原因。

### 3.3 收尾轮的 proposal：拦截并吞掉

`intercept_task_proposal` 在既有 manager + kind 校验之后加一道（与 P8.4.11 自指派 early
swallow 同位置、同形态）：

```python
        if ms.budget <= 0:
            _log.warning("MTS 预算已耗尽，收尾轮的 %r 提议不入队（%s）", ms.manager_guest, kind)
            return True        # 拦下：不入队、不下发采纳卡
```

**位置承重：必须留在 kind 白名单之后。** swallow 本身不读 `kind`，把它上提到白名单之前
看着像无害简化，实则会把 `task_propose_status("done")` / review / decision 一并吞掉 ——
管理者宣布任务完成、却没有任何采纳卡，任务静默停在原状态。回归钉在
`test_zero_budget_swallow_stays_below_kind_whitelist`（v3 复审补，§6）。

**为什么是 swallow 而不是「降级渲采纳卡」**（v1 的方案，已否决）：采纳卡会在收尾消息还在
流式生成时就出现，用户点「采纳」→ `handoff_delegate` inbound 把项 append 进当前 drain 队列
→ 紧接着收尾轮结束、`end_managed_session` 清队列 → **用户已经点了采纳，handoff 却静默消失**。
收尾 prompt 已经要求管理者给出「一个明确下一步」，用户要继续推进有的是正常入口（直接
`@`、手动 handoff、或重开一次托管），不需要一张注定被清掉的卡。

**代价（v3 复审记账，有意接受）**：swallow 在 `_handoff_item_from_proposal` **之前**，
所以它也吞掉了那些改前会「校验不过 → 退化渲卡」的提议（target 不在场 / target busy /
panel 形状坏）。改前那张卡能活过 `end_managed_session`（是 UI 态不是队列态），用户事后
点采纳会走正常 inbound、要么真跑要么给出明确报错。现在一律只剩一条 server 侧 WARNING。
这是「收尾轮不派活」的直接推论 —— 要保留那条降级路径就得让 swallow 依赖校验结果，等于
把「收尾轮该不该派活」的判断交给「这次派活合不合法」，语义反了。

**与现状的差异**：现在这一轮的管理者提议会被 hook 自动入队、随后被 `end_managed_session`
清掉（净效果相同，但多一次 `handoff_queue` 快照抖动）。改成 swallow 后行为更直白。既有断言
「预算耗尽后管理者最后一轮派的活不多跑」在两种实现下都成立。

## 4. 不变量

- **管理者回合总数与现状一致** —— 本阶段不新增、不删除任何 turn，只换最后一轮的 prompt。
- **收尾模式的判定是纯派生量 `ms.budget <= 0`，不引入状态**（§2 等价论证）。因此不存在
  「flag 忘了清 / 翻两次 / 跨会话泄漏」这类失效面。
- **`<managed_session>` 块零改动**：收尾走独立块，P14 / `docs/INVARIANTS.md` 的
  「5 条 bullet 顺序不变」「第 ② / 第 ③ 条」不变量与 `tests/test_mts_spawn_boundary.py`
  既有断言均**不触发双写**。
- **两块互斥、不共存**：同一回合只注入其中之一（§3.2 是 if/else）。
- **不新增 stop reason / envelope / 配置字段**；`schema_version` 不动；前端零改动 ——
  收尾轮在前端就是一个普通的 handoff turn（`handoff_consumed` + `turn_start` / `turn_end`
  + 消息气泡），bar 在其后正常消失。
- **swallow 的位置承重：必须在 kind 白名单之后**（§3.3），它不读 `kind`。
- **收尾块自带被替换 bullet 的仍适用语义**（§3.1 表）—— 改块时四条对应关系一并复核。
- **终结路径一律不变**：`advance_after_turn` / `advance_after_bg_completion` /
  `check_after_task_change` / server inbound 的 stop / cancel 全部原样。用户停止、取消、
  任务变更仍可**立即**终止 MTS，包括在收尾轮进行中（§1 范围声明）。

**有意不覆盖的边角**（不补，补了就得重新引入插入回合）：

- **budget ≥ 1 时被用户中途停止 / 取消 / 任务变更**：无收尾轮，同 §1 上表与范围声明。
- **「扣到 0 时管理者项前面还压着非管理者项」的队列交错**：前台 worker 路径的
  `budget -= 1` 有 `if not queue` 守卫（`:297`），队列非空时不扣、不入队；但 **bg 路径
  （`advance_after_bg_completion`）没有这道守卫** —— 队列里已有 `worker_X` 时一个 bg 完成，
  仍会 `budget -= 1` 并 append 管理者复查，队列成 `[worker_X, manager]`。drain 先跑
  `worker_X`（budget 已 0，但不是管理者回合，不渲任何 MTS 块），其后 `advance_after_turn`
  命中 `BUDGET_EXHAUSTED` → `end_managed_session` 清队列，**那条管理者项连同收尾轮一起被丢**。
  
  这是 MTS 预算记账的**既有**行为（现在该管理者复查同样被丢，只是没人注意），P8.7 不引入
  也不修复它 —— 修它要动 bg 路径的扣减时机，属独立议题（§7）。
  
  **不要把它和「多 bg deferred callback」竞态混为一谈**：后者（`:248-255` 的 queue-empty
  守卫）队列里残留的那一项**正是管理者 delegate**（`advance_after_bg_completion` 入队的是
  `HandoffItem(kind=DELEGATE, target=ms.manager_guest, ...)`，代码注释里的 `review_bob` 指
  「因 bob 的 bg 完成而触发的复查」，target 是管理者本人）—— 它会以 `budget == 0` 跑起来，
  **正常拿到收尾块**，不漏。

## 7. 后续（未立项，承自 P8.5）

- **wall-clock 预算轴**（P8.5 §4.2）：若立项，收尾判定从 `ms.budget <= 0` 扩成「任一预算轴
  已耗尽」即可，机制原样复用（这也是把判定收在一个派生表达式上的好处）。
- **`cap_reached` 要不要也收尾**：现在不给（§1）。若要给，须先回答「撞 cap 时哪一轮是最后
  一轮」—— cap 路径没有 budget 那样的天然终局回合，多半又要插回合，是独立设计题。
- **blocked ↔ MTS 收尾联动**（P8.5 §4.3 第 2 点）/ **单茶客 goal**（§4.4）：无依赖。

**v3 复审提出、本阶段有意不做**（都要么扩机制、要么改既有设计决定，记在此处备查）：

- **收尾轮宣称「FINAL」时可能还有 bg run 在跑**。管理者按第 ③ 条 spawn 了 N 个后台 run，
  第一个跑完就把 budget 扣到 0 并排上终局复查 —— 收尾块此时宣称 final，其余 run 的产出
  会在 MTS 结束**之后**才落到房间，且 `advance_after_bg_completion` 见 `managed_session
  is None` 直接跳过，没人复查。**「MTS 在 bg run 未完时就结束」是既有行为**（`_has_pending_
  mts_bg` 自 P8.4 退役 `MANAGER_FINISHED` 后已无生产读点），P8.7 只是把它从静默变成了
  一句明说的「final」。要修得让 MTS 在 bg 未完时**延后终结**，是独立设计题。
- **swallow 不覆盖 `handoff_review`**。`propose_review` 在收尾轮仍渲卡，用户在收尾消息
  流式中点采纳同样会被 `end_managed_session` 清掉 —— 与 §3.3 要防的是同一个竞态。但
  review 卡在 MTS 全程都渲（「只自动入队 delegate / panel」是既有不变量），本阶段不动
  白名单口径；要收就该连同「终局回合的所有 handoff 类提议」一起收，是独立议题。
- **swallow 在少数交错下会落到非收尾回合上**。判定是纯派生量 `ms.budget <= 0`，不区分
  「这一轮渲的是收尾块还是别的块」—— 例如队列 `[panel(summarizer=manager), delegate(manager)]`
  时 bg 完成把 budget 扣到 0，管理者作为 panel summarizer 那一轮拿的是 `<panel_summary>`
  却也吃 swallow。修法是给「本轮是不是收尾轮」加状态，正是 v1 被推翻的那条路，不走。
- **收尾块会永久留在管理者 `agent.messages` 里**，下一次 MTS 的 `<managed_session>` 第 ①
  条与它正面矛盾。这是**所有 `extra_blocks` 临时块的共有属性**（`<review_target>` /
  `<panel_context>` / `<managed_session>` 同理），不是 P8.7 引入；要解得给临时块加过期
  语义或注入位收回，属 prompt 装配层的独立议题。
