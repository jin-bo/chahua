## 0. 上游前提：图里的数据从哪来　**\[非本相位职责，但决定本相位是否通电]**

一张 flint 图 = 「一份内联数据 + 一份图规格」。茶话室里这两样的来源是：

```
茶客可用的取数通道 ──▶ 结果行写成 ```flint 块（数据内联）落进它的回复
   ① P17 GuanLan MCP 只读长期记忆（persona mcp.json 裸 url）
   ② persona sidecar mcp.json / [[guest.extra_mcp_servers]] 接的任意 MCP server
   ③ 茶客自身工具（read_file 读 ./task/ 下的 csv / json 产物、shell 跑统计）
        ──▶ P10.2：渲染进程把该块编译渲染成图
```

两条**不属于 P10.2、但必须成立**的前提，先钉死免得实现完发现「通了电没有灯」：

1. **茶客得会写 flint 块。** mermaid / LaTeX 模型本就会写，**flint 是 2026 年的新语言、模型不会自发产出合法块**
   ——这是 P10 / P10.1 没有的一片。故本相位**必须**配一份作者侧 skill（§1「做」的最后一条 + 决策P10.2-9），
   否则渲染器永远等不到它的输入。
2. **数据必须内联落盘，不做「渲染时查库」**（沿决策P4.20-12）。图 = 取数那一刻的**快照**，100% 可从 transcript
   里那段 markdown 重建；渲染进程**永不**发起数据请求。这既是「transcript 是唯一事实来源」在本相位的形态，
   也是不给渲染进程开出网路径的安全前提。刷新数据 = 让茶客重新取一次数、产出新块。

## 1. 本阶段做 / 不做

### 做

- **前端拾取 + 编译 + 渲染**（新模块 `app/renderer/flint_chart.js`，约 400 行，决策P10.2-2）：
  `enhanceFlint(container)` 扫 `container.querySelectorAll('pre > code.language-flint')` → **视口门**（§3.5）→
  `JSON.parse(code.textContent)` → **入口白名单裁剪** → **按气泡宽重编译**（§3.4）→ **出口断言** →
  `echarts.init(…, {renderer:'svg'})` + `setOption` → 用 `<figure class="flint-rendered">` 就地替换那个 `<pre>`。
- **两个 npm 直接依赖 + 钉版 + 动态 `import()` 懒加载**（决策P10.2-1，非 CDN、随 electron-builder 打包、离线可用）：
  - `flint-chart@0.4.1` 的 `dist/echarts/index.js`（531,443 B）——**自包含单文件 ESM**，具名导出 `assembleECharts`；
  - `echarts@6.1.0` 的 `dist/echarts.esm.min.js`（1,121,654 B）——**自包含 ESM 全量构建**，具名导出 `init` 等。
  两者**独立懒加载、并发 `Promise.all`**，无 flint 块的气泡零加载这 1.65 MB。**两个包都已实测可在沙箱渲染进程
  直接 `import()`**（§3.2 —— 这是 P10.1 highlight.js 那个坑的对应验证项，不是抄结论）。
- **安全闸硬编码**（沿决策P4.20-4/-5，§4）：入口只收白名单顶层键 + **拒 `data.url`（只认内联 `data.values`）**
  → flint 生成式编译 → **键域**出口断言（无 `link`/`toolbox`/`dataView`、无 `image`、无 `image://` 符号、
  无带尖括号的字符串 `formatter`、`renderItem` 必须是函数、`graphic` 仅 `type:'text'`、`series` 非空）
  → `renderer:'svg'` + `tooltip.renderMode:'richText'`（tooltip 不走 HTML 通道）。
- **资源闸三条**（沿决策P4.20-6/-18/-20）：块源 > 64 K **字符**、`data.values` > 1000 行、画布**上界**
  （宽 > 1600 / 高 > 1200，或非有限数）→ **不渲染**，保留源码 + 徽标；另读 flint 自己的 `_warnings`，
  见 `code:"overflow"` → 「数据被截断」徽标（**三档文案可分辨**，修法完全不同）。**不静默截断**。
- **★ 按气泡宽重编译 + 绘图区下限**（**茶话室核心新机制一**，决策P10.2-4/-5，§3.4）：气泡 `max-width:75%`
  比观澜的 wiki 栏窄约 40%，直接照搬观澜的「取第一个 `_width ≤ 栏宽` 的档」会把绘图区压到 51–81 px。
  故 ① 渲染前给气泡加 `.has-flint`（`max-width:92%`）**再量宽**；② 收窄档必须同时满足
  `_width ≤ 可用宽` **且** `绘图区 ≥ 160 px`，都不满足就**放弃收窄**、用自然尺寸 + `overflow-x` 横向滚动。
- **★ 视口门 + 实例回收**（**茶话室核心新机制二**，决策P10.2-6/-7，§3.5）：flint + ECharts 是茶话室**第一个
  有状态渲染器**（mermaid / KaTeX / hljs 都是一次性 DOM 变换）。而聊天列表是**无界滚动**、且
  `renderSidebar` 每帧 `room_info` 都 `messagesEl.replaceChildren()` 整列表重建——不管就是
  「每条 room_info 泄漏 N 个 ECharts 实例 + 全量重编译」。故：`IntersectionObserver` 门住首次编译
  （只有真滚到眼前的图才付编译代价）+ 每次 `enhanceContent` 先清扫脱树实例 + 软上限 LRU 回收（回退成源码，
  再进视口会重渲）。
- **优雅降级 + 失败封闭**（沿决策P4.20-10/-15）：运行时加载失败 / JSON 语法错 / 白名单拒绝 / 出口断言不过 /
  flint 抛错 / 超限 / **`init`+`setOption` 抛错** → **`<pre>` 源码原样留存** + 错误徽标。保证它成立的是**顺序**：
  `replaceWith` 是整条链的**最后一步**，全链在 `<pre>` 仍挂在树上时完成；渲染期抛错当场 `dispose` 临时实例。
  **永不空白、零未消毒注入。**
- **茶席主题**（决策P10.2-8，沿决策P4.20-13/-22/-23/-24 的两半分工）：文字与五档轴走 `echarts.init` 第二参主题对象；
  序列色板走**按位替换**（flint 把 ECharts 默认色板硬编码进产物，主题里写 `color` 完全无效）；
  语义色图型（`Waterfall Chart`）整张跳过换色。取值对齐 `chat.css` 既有暖米调色，**单档配色、不预留深浅切换**。
- **配套作者侧 skill `flint-chart-author`**（决策P10.2-9，§0.1 的直接后果）：职责=选图型与编码、必要时聚合、
  生成 / 修复 / 解释 / 校验 flint 规格；**不负责**取数权限、markdown 落在哪、渲染。交付形态走茶话室既有的
  **persona sidecar `skills/`** 通道（`examples/personas/*/skills/` 已有 4 个先例），另说明拷进
  `~/.agentao/skills/` 可对全体茶客生效。**真闸子的阈值必须与渲染器逐条一致**（顶层五键 / 拒 `data.url` /
  ≤1000 行 / 画布上界），否则 skill 会稳定产出被自家闸子拒渲的块。
  **注意「闸子」与「建议」要分清**：skill 里的「对象数组 + 标量单元格」渲染器**并不查**，是作者建议
  （§3.3.1 / 决策P10.2-11）；反过来，skill 曾教的画布**下限**渲染器也不设——两种混淆各出过一次。

### 不做（推后 / 收敛）

- **不**做服务端 / CLI 渲染（沿决策P10.1-9 / P4.20-10）：CLI REPL 回字面 JSON（honest，零信息损失——规格与数据
  都在块里）。**不**把 flint / ECharts 依赖渗进 Python 侧。
- **不**改 transcript / envelope / `schema_version` / 任何 `.py`（纯前端相位）。
- **不**渲染用户气泡里的 flint 块：用户气泡走 `textContent`（`chat_stream.js::makeUserRow`，
  `.bubble-user .text{white-space:pre-wrap}`），本就不过 markdown ——mermaid / 公式 / 代码高亮同样不渲，
  本相位不为 flint 破这个例（honest 残留，明写在此）。系统气泡（`makeSystemRow`）同理不调 `enhanceContent`。
- **不**引第二个渲染后端（Vega-Lite / Chart.js / Plotly）——沿决策P4.20-2：一个后端就够，多一个 = 多一份包体 +
  多一片安全面。**flint 的 npm 包里那四个后端的 dist 必须被打包白名单排除**（§9）。
- **不**做图表交互（`dataZoom` / 点击下钻 / 导出 PNG）：本相位是只读呈现，不是 BI 面板。交互面 = 攻击面 + 状态面。
- **不**做渲染时查库 / 自动刷新 / 实时数据（沿决策P4.20-12，见 §0.2）。
- **不**引 `ResizeObserver` 跟随窗口 / 分栏拖动重排（沿决策P4.20-17）：由 `overflow-x:auto` 兜底，
  下一次重绘（切房 / room_info / 历史重放）按新气泡宽重算——而茶话室的重绘频率**远高于**观澜（§3.5），
  这条兜底比观澜那边更站得住。
- **不**在流式 delta 期间渲（沿 P10 mermaid 不变量）：半截 JSON 必然 `JSON.parse` 失败刷徽标。
  delta 期间显示字面 JSON 源码（honest），`message_end` 才经 `enhanceContent` 渲一次。
- **不**改 CSP（§4.5 论证现有 CSP 已覆盖）、**不**新增 i18n（茶话室单语中文 UI，徽标走
  `data-flint-error` + CSS `::before`，同 `.mermaid-error` precedent）。

**为何后端零改是对的**：flint 块经 marked `fenced_code` 已 emit `<pre><code class="language-flint">转义 JSON</code></pre>`
（与 mermaid 同载体契约）；前端读 `.textContent` 时浏览器自动反转义，**喂给 `JSON.parse` 的是 JSON 文本、不是
HTML**。`marked → DOMPurify` 管线全程不破（`pre`/`code`/`class` 在 `USE_PROFILES.html` 白名单内），
`renderMarkdown` 其余调用方零回归。

**顺带白拿的一条**：flint 块里的 `$` 不会被数学 carrier 扩展吃掉——marked 的 `fenced_code` 是 block-level、
先于 inline tokenizer 吃掉整块，inline 扩展不进围栏内部（P10.1 §7 手测 7 已锁）。故观澜实现期撞到的
「KaTeX auto-render 进 `<svg><text>` 改写坐标轴标签」那条**跨增强器竞态在茶话室由构造免疫**：
茶话室的 KaTeX 只认 marked 产出的 `span.math-tex` carrier，从不做文本节点走查。**明写在此，免得实现时照抄
观澜的 `ignoredClasses` 补丁、以为自己修了个问题。**

### 2.1 注入点是**三处不是四处** —— 任务卡 goal 的富渲染分支是死代码（**纠正 P10.1 的既有过度承诺**）

P10.1 文档（§3.4 / §9）把 `task_panel.js` 的 task goal 列为第四个注入点，本文初稿照抄了。**实测不成立**：

```
task_panel.js:211   if (onPatchTask) { goal.textContent = task.goal; attachInlineEditor(...) }  ← 走这支
task_panel.js:222   else if (task.goal) { goal.innerHTML = renderMarkdown(...); enhanceContent(goal) }  ← 死支
renderer.js:700     createTaskPanel({ …, onPatchTask: (taskId, patch) => {…} })   ← 全仓唯一调用点，必传
task_panel.js:149   renderTaskCard(active)                                        ← 唯一调用点，模块内部
```

`onPatchTask` **恒非空** ⇒ goal 永远走 plaintext contenteditable 分支，`enhanceContent(goal)` 在发布版里
**从未执行过**。这不是 P10.2 引入的——**mermaid / 公式 / 代码高亮在任务卡 goal 里也从来没渲染过**，
P10.1 §7 的手测项 6「任务卡 goal 含公式 / 代码 → 渲染」真跑过就该红。

**本相位的处置：删掉这个承诺，不去补通它。** 理由不是「懒得做」，而是 goal 是个
**`contenteditable` 编辑面**——往里塞一个有状态的 ECharts 实例会和 inline editor 直接打架
（浏览器输入工具会改写 contenteditable 子树，`.math-done` / `data-mermaid-rendered` 这类幂等标记随之失效，

### 3.2 双运行时懒加载（npm ESM）——**须先验证，不能照抄观澜结论**

观澜是 vendored 资产 + 注入 `<script>` / 动态 `import()` 混合姿态；茶话室渲染进程是

Electron 里 import 即抛。故两个新包**逐条实测**（`npm pack` 解包后静态核查）：

| bare import（`from "pkg"`） | **0** | **0** |
| 动态 `import(` | **0** | **0** |

```js
// 懒加载：两个运行时并发、各自单例（沿 P10.1 loadKatex / loadHljs 范式）。
// 失败清 Promise 允许重试 —— 但**光清 Promise 不够**：按 HTML 的 module map 语义，一个失败的
// 动态 import() 会把该 URL 的失败结果留在文档存活期内，重发同一 URL 会立刻再 reject、根本不重取
// （沿决策P4.20-26；mermaid/KaTeX/hljs 没这问题只因它们至今没真失败过重试过）。故重试换 query。
let _rtPromise = null;
let _rtAttempt = 0;
function loadFlintRuntime() {
  if (_rtPromise) return _rtPromise;
  const bust = _rtAttempt ? `?retry=${_rtAttempt}` : "";
  _rtPromise = Promise.all([
    import(`../node_modules/flint-chart/dist/echarts/index.js${bust}`),
    import(`../node_modules/echarts/dist/echarts.esm.min.js${bust}`),
  ])
    .then(([flint, echarts]) => {
      if (typeof flint.assembleECharts !== "function") throw new Error("no assembleECharts");
      if (typeof echarts.init !== "function") throw new Error("no echarts.init");
      return { assemble: flint.assembleECharts, echarts };
    })
    .catch((e) => { _rtPromise = null; _rtAttempt++; throw e; });
  return _rtPromise;
}
```

### 3.3.1 「对象数组 + 标量单元格」是**作者侧建议，不是渲染端闸子**（决策P10.2-11）

skill 的自校验清单要求「`data.values` 是对象数组、每个单元格是标量」，而 `sanitizeFlintInput`
**只查数组 / 行数 / 列名**，不查行与单元格的形状。初稿把这两件事写成了「闸值必须逐条一致」的发布门
——**那是把建议误当成闸子**。本相位的取舍：**保留为作者建议，删掉那条发布门**，理由与代价都写清楚。

**为何不必是安全闸**：单元格的值走的是「JSON → flint 生成式编译 → ECharts 按 option 建 SVG DOM」这条链，
**全程没有字符串→DOM 的解析**，值一律被画进 `<text>`（§4）。一个嵌套对象当单元格，威胁模型上与一个字符串
没有区别。安全性完全由「入口白名单 + 键域出口断言 + `svg`/`richText`」承担，**与单元格类型正交**。

**但代价不是零，得说清楚**——实测六种畸形输入喂 `assembleECharts`（`Bar Chart`，`x:c` / `y:v`）：

| 输入 | flint 行为 | 本相位链路上的下场 |
|---|---|---|
| 正常标量 | `series[0].data=[1,2]` | 正常渲染 |
| **嵌套对象单元格** `v:{n:1}` | **不抛错**，`data=[[0,0,1],[1,0,1]]` | ⚠️ **渲成一张不报错、非空、但错误的图** |
| **嵌套数组单元格** `v:[1,2]` | **不抛错**，`data=[1,1]` | ⚠️ **同上，静默错图** |
| `null` 单元格 | `data=[null,2]` | 正常（图上是个缺口，语义合理） |
| 数组行 `["a",1]` | `data=[]` | 空 series 守门拦下 → 徽标（**安全**） |
| `null` 行 | 抛 `Cannot read properties of null` | catch → 徽标（**安全**） |

⇒ **六种里四种是安全的**（抛错 / 空 series 都被既有守门接住），**两种会静默说谎**：嵌套对象 / 嵌套数组单元格
产出非空但错误的 series，正好**绕过** `assertSafeOption` 的空 series 守门——与决策P4.20-14 想堵死的
「不报错也不降级、默默说谎」是同一类。**明记为已知缺口，不假装没有。**

**为何仍不在本期加闸**：① 它不是安全面（上段）；② 触发它需要作者把一个对象塞进单元格，而 skill 的自校验
清单第 4 条已明写禁止——这是**作者纪律能覆盖**的范围，与「外部数据可能是恶意的」不同（数据是茶客自己
`GROUP BY` 出来再写进块的，不是原样转发的攻击面）；③ 真要加，代价也只有一行——**留作可选加固**：
在列名校验那一圈顺手对**被 `encodings` 引用的列**抽查一次值类型，非
`string|number|boolean|null|undefined` 即 `throw new Error("non-scalar-cell")`（复用既有 catch → 徽标）。
遍历本来就在做，增量近乎为零。**若将来真有人踩到静默错图，直接开这一行即可，不必重新论证。**

⇒ **发布门相应收窄**：skill 与渲染器必须逐条一致的只有**真闸子**——顶层五键 / 拒 `data.url` /
`≤1000` 行 / 画布上界。「对象数组 + 标量单元格」降级为**作者建议**（skill 里照留，措辞不改）。

### 3.4 ★ 按气泡宽重编译 + 绘图区下限（**茶话室核心新机制一**）

**问题**：观澜的 wiki 正文栏实测 377–560 px；茶话室气泡是 `max-width:75%` of 消息栏，而消息栏 =
窗口宽 − 侧栏 200 − 右抽屉 300（打开时）。1280 窗口开任务面板 ≈ 560 px 气泡，1000 窗口开面板 ≈ 375 px。

**实测 flint 的 `canvasSize` 行为**（它是**布局提示不是硬钳位**，请求值与产物 `_width` 恒有一段固定 chrome 开销）：

| 图型 | 自然尺寸 | `grid.left+right` | 请求 400 | 300 | 200 | 120 | 60 | 20 |
|---|---|---|---|---|---|---|---|---|
| Bar Chart | 523×417 | 124 | 454 | 355 | 253 | 175 | **142** | **142** |
| Line Chart（无图例） | 502×525 | 124 | 455 | 355 | 255 | 175 | 115 | 75 |
| Scatter Plot | 500×438 | 124 | 455 | 355 | 255 | 175 | 115 | 75 |
| **Pie Chart** | 400×320 | 0 | 400 | 300 | **280** | **280** | **280** | **280** |
| **Line + color 图例** | 618×525 | **240** | — | — | — | — | — | — |

图例那一行单列，因为它是最坏情况——**开销恒为 +171 px，且 `legend.left` 被烤成绝对像素**：

```
自然：_width=618  legend.left=464  grid={left:86,right:154}
请求 420 → _width=591  legend.left=437  绘图区=351
请求 320 → _width=491  legend.left=337  绘图区=251
请求 240 → _width=411  legend.left=257  绘图区=171
```

⇒ **两条结论，都是茶话室独有的**：

1. **有硬地板。** `Pie Chart` 不管请求多小都是 280 px；带图例的线图最小也在 171 px 开销之上。
   一个 260 px 的气泡**永远**装不下一张饼图——「收不进去」在聊天里是**常态**，不是边角，必须设计进去。
2. **照抄观澜的「取第一个 `_width ≤ 栏宽` 的档」会画出没法读的图。** 375 px 气泡 × 带图例的线图：
   ratio 0.4 那档 `_width=321 ≤ 375` **成立**，于是被采纳——但绘图区只剩 `321−240 = 81 px`，
   6 个 x 刻度 3 条线挤在 81 px 里。观澜那条规则在 377 px 起步的栏里勉强够用，在气泡里不够。

**修法两半**：

```js
// ① 渲染前先把气泡放宽，**再量宽**（决策P10.2-4）。
//    顺序是承重的：getBoundingClientRect() 会强制同步 layout，故加 class 必须在量之前；
//    反过来做（渲完靠 CSS :has(.flint-rendered) 放宽）会按旧的 75% 定尺寸、白白浪费 17% 宽度。
//    非气泡宿主（若将来有）没有 .bubble 祖先 → closest 返回 null，静默跳过。
function widenBubbleFor(code) {
  code.closest(".bubble")?.classList.add("has-flint");   // .bubble.has-flint { max-width: 92% }
}

// ② 收窄档必须同时满足「落进栏」与「绘图区够用」（决策P10.2-5）。
const FLINT_FIT_RATIOS = [1, 0.75, 0.55, 0.4];
const FLINT_MIN_PLOT_W = 160;            // 绘图区下限（px）：低于此就不是一张能读的图

// 绘图区宽度。**`grid` 有三种形态，只认对象会静默失守**（决策P10.2-5，评审实测）：
//   ① 对象   —— 普通笛卡尔图（`{left,right,…}`）
//   ② 数组   —— 用了 column/row 分面时**每个分面一个 grid**（`[{left,top,width,height},…]`）
//   ③ 不存在 —— 非笛卡尔图型（Pie/Treemap/Sunburst/Gauge…），整张画布就是绘图区
// 数组形态里 `g.left`/`g.right` 是 undefined → `||0` 让公式退化成 `plotWidth === _width`，
// 于是**下限对所有分面图恒过**：实测双列分面柱图 avail=375 时 `_width=365`（≤375 ✓）、
// 公式算出 365（≥160 ✓）当场采纳，而**真实的两个分面各只有 146 px**。
// 分面图取**最窄的那个分面**——读者是逐个分面读的，最窄的那个决定这张图能不能读。
const plotWidth = (o) => {
  const g = o.grid;
  if (Array.isArray(g)) {
    const ws = g.map((x) => (x && Number.isFinite(x.width) ? x.width : o._width));
    return ws.length ? Math.min(...ws) : o._width;
  }
  if (g && typeof g === "object") return o._width - (g.left || 0) - (g.right || 0);
  return o._width;                                        // 非笛卡尔：整张画布即绘图区
};

// flint 自己的 overflow 截断（`_warnings`）在收窄过程中**会被我们制造出来**（决策P10.2-5 下半）。
const hasOverflow = (o) => Array.isArray(o._warnings) && o._warnings.some((w) => w && w.code === "overflow");

function assembleFitted(assemble, input, avail) {
  const base = assemble(input);
  if (!avail || !base || typeof base !== "object" || !Number.isFinite(base._width) || base._width <= avail)
    return base;                                          // 天然就落在栏里
  const baseOverflow = hasOverflow(base);                 // base 本来就截断的，不赖收窄
  const ratio = base._height / base._width;
  for (const r of FLINT_FIT_RATIOS) {
    const width = Math.round(avail * r);
    if (width < 1) break;
    let cand;
    try {
      cand = assemble({ ...input, chart_spec: { ...(input.chart_spec || {}), canvasSize: { width, height: Math.max(1, Math.round(width * ratio)) } } });
    } catch { break; }                                    // 收窄走不通就别把一张本来能画的图弄丢
    if (!cand || !Number.isFinite(cand._width)) break;
    // 收窄**只准让图变小，不准让图变少**：base 没截断而候选截断了，说明是这一档把数据挤掉的
    // ——采纳它会让一张本来完好的图挂上「数据被截断」徽标，把作者引向删类别这条错路。
    if (!baseOverflow && hasOverflow(cand)) break;        // 再窄只会更糟，直接收工用 base
    // 绘图区随 _width 单调收缩，故第一个同时满足两条的就是最优档。
    if (cand._width <= avail && plotWidth(cand) >= FLINT_MIN_PLOT_W) return cand;
  }
  return base;   // 宁可横向滚动，也不要一张绘图区被压成条 / 被挤掉数据的图（决策P10.2-5）
}

// 待替换的 <pre> 是块级元素、正好铺满气泡内容区，故它的边框盒宽 == <figure> 换上去会拿到的宽。
// 不量 .bubble 或父容器 clientWidth：那含 padding（气泡是 8px 12px），会高估约 24px。
const columnWidth = (code) => (code.parentElement ? Math.floor(code.parentElement.getBoundingClientRect().width) : 0);
```

**为何是「放弃收窄 + 横向滚动」而不是「继续收窄」或「报错不渲染」**：
- 继续收窄 → 画出一张**看着完整、实则读不了**的图，与决策P4.20-6 拒绝静默截断是同一条红线；
- 报错不渲染 → 用户拿到的是一坨 JSON，比一张要横向滚一下的图差得多，且他**没有可修的东西**
  （气泡宽是宿主决定的，不是规格问题）。
- 滚动条本身是 `.flint-rendered{overflow-x:auto}`，与 `.mermaid-rendered` / `pre` 既有姿态一致，用户已熟悉。

### 3.5 ★ 视口门 + 实例回收（**茶话室核心新机制二**）

**问题**：`renderer.js::renderSidebar` 在**每一帧 `room_info`** 上跑 `messagesEl.replaceChildren()`
（切房 / 重连 / clear / **改头像 / 改设置 / 增删茶客** 都会触发），随后 `room_history` 把
**整份 transcript（数百条）**重放。于是：

- 每条 `room_info` → 所有已渲染 `<figure>` 脱树。ECharts 把实例挂在**自己的全局注册表**上，
  不 `dispose` 就是**每条 room_info 泄漏 N 个实例**（含其事件与定时器）。
  观澜那边只有「切语言 / 切预览模式」两个低频触发点，茶话室这个频率高一个量级。
- 每条 `room_info` → 整份历史里所有 flint 块**全量重编译 + 重 init**。一个有 20 张图的房间，
  改一次头像就要付 20 次编译 + 20 次 `echarts.init` 的代价，其中 19 张在视口外、用户根本看不见。

- **`enhanceFlint` 内部的清扫兜不住全部情形**（决策P10.2-7，评审指出）：清扫只在 `enhanceFlint` 被调用时跑，
  而**用户气泡走 `makeUserRow` → `textContent`、根本不经 `enhanceContent`** ⇒ 切到一个空房间、
  或一个只有用户消息的房间，清扫**一次都不会跑**，上个房间的实例全留着。故必须另配**显式卸载钩子**
  ——这正是仓库既有的做法：图片预览的 `_observedFigures` 也是自己维护一份集合
  （`chat_view.js:590`）并在 `renderSidebar` 里显式 `clearPendingArtifactPreviews()`（`renderer.js:330`）。

**修法三条**：

```js
// ① 视口门（决策P10.2-6）：只有真滚到眼前的块才付编译代价。
//    **懒创建**（决策P10.2-6 下半）：写成顶层 `const _io = new IntersectionObserver(...)` 会让
//    Node 里 `import` 本模块当场抛 ReferenceError —— §7 那批「无需 DOM 的纯函数单测」根本跑不到。
//    root:null（视口）而非某个滚动容器：一个 observer 通吃，不给每个宿主配一个。
//    rootMargin 200px：提前一屏开始渲，滚到时图已在位、不闪。
let _io = null;
const io = () => (_io ||= new IntersectionObserver(onIntersect, { rootMargin: "200px 0px" }));

const _pending = new Set();                      // 已 observe、尚未渲染的 <pre>（卸载时要 unobserve）

function onIntersect(entries) {
  for (const e of entries) {
    const el = e.target;
    if (el.matches("figure.flint-rendered")) {
      el.__flintVisible = e.isIntersecting;      // 已渲好的图：只更新可见性，供 LRU 判断
      if (e.isIntersecting) touch(el);
    } else if (e.isIntersecting) {
      io().unobserve(el); _pending.delete(el);
      renderOneFlintBlock(el, /* wasVisible */ true);   // 待渲的 <pre>：这才开始编译
    }
  }
}

// ② 实例登记簿 + 清扫 + 显式卸载（决策P10.2-7）。
const _charts = new Set();                       // { chart, fig, seq }
const FLINT_MAX_LIVE = 12;                       // 软上限：全部可见时不淘汰
let _seq = 0;
const touch = (fig) => { if (fig.__flintRec) fig.__flintRec.seq = ++_seq; };

function dropChart(rec) {                        // 单点释放：dispose + 解除 observe + 出簿
  try { rec.chart.dispose(); } catch { /* 已 dispose */ }
  if (_io) _io.unobserve(rec.fig);               // **必须解除**，否则 observer 一直持有脱树 figure
  _charts.delete(rec);
}

function sweepFlintCharts() {                    // 每次 enhanceFlint 开头调，**放在早退之前**
  for (const rec of [..._charts]) {
    let dom = null;
    try { dom = rec.chart.getDom && rec.chart.getDom(); } catch { /* 已 dispose */ }
    if (!dom || !dom.isConnected) dropChart(rec);
  }
  for (const pre of [..._pending]) if (!pre.isConnected) { io().unobserve(pre); _pending.delete(pre); }
}

// **显式卸载钩子**：renderer.js::renderSidebar 里紧挨 clearPendingArtifactPreviews() 调一次。
// 与 sweep 的区别：sweep 是「谁脱树清谁」、要靠 enhanceFlint 被调用；这个是无条件全清，
// 切到空房 / 纯用户消息房也一定执行。
export function resetFlintCharts() {
  for (const rec of [..._charts]) dropChart(rec);
  if (_io) { for (const pre of _pending) _io.unobserve(pre); }
  _pending.clear();
}

// ③ 软上限 LRU（决策P10.2-7）：把**最久未见且当前不可见**的一张回退成源码 <pre>
// （源码存在 fig.dataset.flintSrc），并重新交给 observer —— 用户滚回去时它会重渲。
// 回退而非「拒渲」：拒渲会让「滚过一段长历史」永久毒化后面所有图，而回退是自愈的。
//
// **新图必须先标可见再淘汰**（决策P10.2-7，评审指出的自淘汰循环）：新 figure 是从一个**刚相交的**
// <pre> 渲出来的，但 observer 对它的首个回调是**异步**的 —— 在那之前 `__flintVisible` 是 undefined。
// 若其余 12 张恰好都可见，新的这张就成了唯一「不可见」候选，被当场退回源码 → 再次相交 → 再渲 → 循环。
// 故 renderOneFlintBlock 在登记时用 wasVisible 直接把它标成可见，且**淘汰在登记之后**才跑。
function evictIfNeeded() {
  if (_charts.size <= FLINT_MAX_LIVE) return;
  let victim = null;
  for (const rec of _charts)
    if (!rec.fig.__flintVisible && (!victim || rec.seq < victim.seq)) victim = rec;
  if (!victim) return;                           // 全部可见 → 不淘汰（上限是软的）
  const pre = rebuildPreFrom(victim.fig.dataset.flintSrc);   // 回退成源码
  victim.fig.replaceWith(pre);
  dropChart(victim);
  observeFlintBlock(pre);                        // 重新入门，滚回去会自愈
}
```

**为何视口门是对的、而不是过度设计**：它同时解决了三件事——① 编译/init 代价只付给用户看得见的图；
② 活实例数天然被「屏幕能放几张图」界住（每张约 300–400 px 高，一屏 2–3 张 + margin）；
③ **顺序对**：历史重放是从旧到新遍历 DOM，若不加门、又加了个硬上限，会变成「最老的图渲染、最新的图被拒」
——正好和用户想看的相反。LRU 只是给「用户一路滚过 500 条历史」这个尾部情形兜底，
故列为独立薄片（§10 的 P10.2.3），可单独推后；但 **`resetFlintCharts` 卸载钩子属于核心片、不可推后**
（没有它，切房就是稳定泄漏）。

**幂等与竞态**：`<pre>` 渲成 `<figure>` 后原 `code` 已离树，重复调 `enhanceFlint` 不二次渲染；
`await` 期间被重绘的块靠 `code.isConnected` 跳过；重复 `observe` 同一元素是幂等的（DOM 规范保证），
故不必自己排重（但 `_pending` 仍要维护——它的用途是**卸载时能 unobserve**，不是排重）。

## 4. 安全分析

**威胁模型**：茶客经 MCP / 工具取回的外部数据（DB 字段值、GuanLan 页面正文、MCP server 返回）本就是
**不可信输入**（CLAUDE.md「召回内容按不可信数据处理」）。载荷经茶客写进 ` ```flint ` 块，企图在编译 / 渲染链上
取得同源脚本执行（进而调本地 ws / 文件 API），或让渲染进程发起外部请求（数据外发 / 追踪像素）。

**逐层论证「为何挡得住」**（沿决策P4.20-4 的六层，此处只列茶话室这边的落点）：

1. **块内容永远是文本、且只经 `JSON.parse`。** `code.textContent` 是浏览器反转义后的 JSON 文本，
   **从不当 HTML 解析**；**JSON 里没有函数** → ECharts 的 `formatter`/`renderItem` 回调注入面在这条链上
   **天然不存在**。这是选 flint 而非「让 LLM 直接写 ECharts option」的核心安全理由。
2. **入口白名单（不是黑名单）。** 只放行 5 个顶层键、`data` 只保留 `values`。与决策P10.1-5 的 KaTeX
   `trust:false` 同哲学：**白名单铰链**，而不是「全量包做减法」的脆弱黑名单。
3. **flint 是生成式白名单。** 它按 chartType/encodings 从模板生成 option，**不 merge 用户私货**
   （观澜实测三条走私路径产出与干净输入逐键相同）。
4. **键域出口断言**是钉版之外的运行时守门，为**版本漂移**而留——**不是**在补现存漏洞，
   **不要**把它扩写成通用 ECharts option 消毒器（那是决策P10.1-5 已否过一次的 MathJax 式老路）。
5. **渲染产物不含 HTML 通道。** `renderer:'svg'` → 产物是 SVG DOM；`tooltip.renderMode:'richText'` →
   tooltip 作为图元绘制、不走 HTML 字符串拼接（ECharts 历史 XSS 多发于 HTML tooltip + 自定义 formatter）。
6. **失败封闭，且对渲染期失败同样成立。** 靠的是**顺序**：`replaceWith` 是最后一步，
   失败时 `<pre>` 从未离开过 DOM；渲染期抛错当场 `dispose` 临时实例。

**与 P10 mermaid 的一处关键区别，值得单记**：mermaid 产物走**手工 sanitize + `innerHTML` 注入**
（因为 DOMPurify 会清空 `<foreignObject>`）；**flint 产物完全不经 `innerHTML`**——`echarts.init` + `setOption`
是 ECharts 自己按 option 构建 SVG DOM 节点，**没有任何字符串→DOM 的解析步骤**。故本相位**不需要**
mermaid 那道手工 sanitize，也不新增一条「内容→`innerHTML`」注入面。这是三个渲染器里注入面最小的一个。

### 4.5 CSP 无需改动（验证项）

现有 CSP（`index.html:10`）已覆盖，**P10.2 不动一行**：

| CSP 指令 | 现值 | P10.2 需求 | 是否需改 |
|---|---|---|---|
| `script-src` | `'self'` | 动态 `import()` flint / echarts（同源 `node_modules`） | 否（同 mermaid / katex / hljs 已验证） |

## 5. 前端呈现与主题（`chat.css` + 茶席色板）

- **图表容器**（对齐 `.mermaid-rendered`）：

  ```css
  .bubble .text.markdown .flint-rendered {
    margin: 0.5em 0; padding: 8px; background: #fafaf5;
    border: 1px solid #e0d8c4; border-radius: 6px; text-align: center; overflow-x: auto;
  }
  .bubble .text.markdown .flint-rendered svg { max-width: 100%; height: auto; display: inline-block; }
  /* 图表气泡放宽（决策P10.2-4）：由 JS 在**量宽之前**加 class，不用 :has()——后者时序不可控。 */
  .bubble.has-flint { max-width: 92%; }
  ```

  **真正让图落进气泡的不是这条 CSS，而是渲染前的 `assembleFitted`**（决策P10.2-5）：ECharts 把 `<svg>` 以
  `position:absolute` 放进固定尺寸容器 `div`，绝对定位元素的 `max-width:100%` 相对那个 `div` 算、**咬不住它**
  （沿决策P4.20-17 的实测）。这条 CSS 只在「渲染后又缩了窗口 / 拖了分栏」时配合 `overflow-x` 兜底。

- **错误徽标**（对齐 `.mermaid-error`，无 i18n、无 innerHTML）：

  ```css
  .bubble .text.markdown pre.flint-error { border: 1px solid #c66; position: relative; }
  .bubble .text.markdown pre.flint-error::before {
    content: attr(data-flint-error);  /* JS 写三档文案之一，CSS content 只当文本 */
    display: block; margin-bottom: 6px; padding: 2px 6px;
    background: rgba(204,102,102,.15); color: #c66; font-size: 11px; border-radius: 3px;
  }
  ```

  **三档文案必须可分辨**（沿决策P4.20-6/-18/-20），因为修法完全不同：
  `图表渲染失败（已保留源码）` / `数据过大，未渲染（已保留源码）` / `数据超出图表容量、已被截断，未渲染（已保留源码）`
  ——第二档要减**行数**，第三档要减**类别数**，删行对第三档一点用没有。

- **茶席主题两半**（决策P10.2-8，结构沿决策P4.20-13/-22/-23/-24）：

    变体全覆盖、不随上游漂移），只在**颜色键**（`color`/`borderColor`/`shadowColor`/`backgroundColor`/`areaColor`）

## 6. 决策记录

- **\[决策P10.2-1] 两个运行时（flint 编译器 + ECharts）走 npm 直接依赖 + 动态 `import()` 懒加载，
  非观澜的 vendored + 注入 `<script>`。** 茶话室渲染进程本就走 ES module 直引 `node_modules`
  （marked / dompurify / mermaid / katex / hljs 皆然），沿用即可：① **非 CDN**——electron-builder 打进 app、
  离线可用；② **无构建**——直接用 dist 的自包含 ESM；③ **无图块零加载**——`enhanceFlint` 先早退才付这 1.65 MB。
  **代价**：`node_modules` 增 93 MB（echarts 61 M + flint 32 M），但进 asar 的只有**两个文件 1.65 MB**
  ——须靠打包白名单「排除全部 + 重纳一文件」实现（§9，与既有 `@highlightjs/cdn-assets` 同款）。
  **对照**：mermaid 单包解包后就 3 MB+ 且已在船上，量级可接受。**退路**：若不接受，保持字面 JSON
  （决策P4.20-10 的 honest 回退本就常驻）。
- **\[决策P10.2-2] 新开 `app/renderer/flint_chart.js`，不塞进 `chat_view.js`。** 与 P10.1 把三个增强器全塞进
  `chat_view.js` 的做法有意不同：`chat_view.js` 已 804 行，flint 这一坨约 400 行（编译链 + 两个新机制），
  塞进去会让一个「chat / sidebar 视图原语」模块过半是图表编译器。`chat_view.js` 只 `import { enhanceFlint }`
  并在编排器加一行——编排器仍是四类增强的唯一归口（决策P10.1-8 不破）。
- **\[决策P10.2-3] 安全闸 / 资源闸 / 事务式替换 / 出口断言误杀边界**整体沿用观澜决策P4.20-4/-5/-6/-14/-15/-16/-18/
  -20/-25/-26，**同版本同结论、不重新论证**。理由：那套边界是对着**同一份 `flint-chart@0.4.1` dist**
  跑完 37 图型全链扫描 + 真浏览器冒烟 18/18 得出的，茶话室换的是宿主不是被包装物。
  **但两处必须自己验**：① §3.2 的 ESM 自包含性（载体不同）；② §3.4 的窄栏行为（宿主不同）。
  **升级钉版时，观澜 `vendor/README.md` 的复核清单同样适用**——两仓钉同一版本，任一方升级前应互相知会。
- **\[决策P10.2-4] 图表气泡放宽到 `max-width:92%`，且 class 必须在**量宽之前**加。** 气泡 75% 是为「聊天消息」
  调的，一张图不是一句话。放宽 17% 在 375 px 气泡上多出 ~64 px，正好是「带图例的线图能不能保住 160 px
  绘图区」的分水岭。**顺序是承重的**：`getBoundingClientRect()` 强制同步 layout，故加 class 在量之前即可生效；
  若改用 CSS `:has(.flint-rendered)` 在渲染后放宽，尺寸已按旧宽定死、白丢 17%。
  **不放宽到 100%**：气泡还要留出头像 + 尾巴的视觉呼吸，且用户气泡仍是 75%，一边贴边一边不贴很难看。
- **\[决策P10.2-5b] 绘图区口径必须认全 `grid` 的三种形态；且收窄**不准把数据挤掉**。**（评审 + 实测新增，
  两条都是「闸子看起来在守、其实恒过 / 反而伤人」。）
  ① **`grid` 有三种形态**：对象（普通笛卡尔）/ **数组**（用了 `column`/`row` 分面，每分面一个）/
     不存在（Pie、Treemap、Sunburst… 非笛卡尔）。初稿只认对象，数组形态下 `g.left`/`g.right` 是
     `undefined`、`||0` 让公式退化成 `plotWidth === _width` ⇒ **160 px 下限对所有分面图恒过**。
     实测双列分面柱图 avail=375：`_width=365`（≤375 ✓）、公式算 365（≥160 ✓）当场采纳，
     而**真实的两个分面各只有 146 px**。分面取**最窄那个分面**（读者是逐个分面读的），
     非笛卡尔取整张画布。
  ② **收窄会*制造* flint 的 overflow 截断**：同一份数据，自然尺寸 `_warnings=null` / 两个分面都在；
     收到 ratio 0.4 时 flint 直接**丢掉一个分面**并记
     `{code:"overflow", channel:"column", message:"1 of 2 values in '组' were omitted"}`。
     而 `assertNoSilentTruncation` 跑在**收窄后的最终产物**上 ⇒ 一张自然尺寸完全正常的图会被判
     「数据被截断」，徽标还叫作者去减类别——**问题是我的收窄循环造的，却让作者去改他没错的东西**。
     故候选必须与 base 比：`base` 没 overflow 而候选有 ⇒ 立即停止收窄、退回 base（再窄只会更糟）。
     这是决策P4.20-19「能让 flint 自己算的绝不事后改」在**另一个方向**上的同一课——
     我没有事后改产物，但我用参数把它逼到了它自己会丢数据的档位。
- **\[决策P10.2-5] 收窄档须同时满足「`_width ≤ 可用宽`」与「绘图区 ≥ 160 px」；都不满足就放弃收窄、
  用自然尺寸 + 横向滚动。**（**这是观澜决策P4.20-19 在窄宿主下的必要收紧，不是重复。**）

  是一张**看着完整、实则读不了**的图，与决策P4.20-6 拒绝静默截断同一条红线。
  **绘图区随 `_width` 单调收缩**（同一图型内 `grid` 的边距实测恒定），故「第一个同时满足两条的档」
  就是最优档，不必回溯。**硬地板是客观存在的**（`Pie Chart` 恒 ≥ 280 px、带图例线图恒 ≥ 171 px 开销），
  所以「放弃收窄 + 横向滚动」不是异常分支而是**常规分支**，必须当一等路径设计与验收。
- **\[决策P10.2-6] 首次编译由 `IntersectionObserver` 门住（`rootMargin:200px`），且 observer **懒创建**。**
  茶话室的宿主是**无界滚动列表**且 `room_info` 每帧整列表重建 + 全量重放 transcript
  （`renderer.js::renderSidebar` → `messagesEl.replaceChildren()`；改头像 / 改设置 / 增删茶客都会触发）——

  **渲染顺序对**（不加门又加硬上限的话，历史重放会「最老的渲染、最新的被拒」，正好和用户想看的相反）。

## 11. 实现纪要（2026-08-04 落地）

设计稿的判断基本站得住——**四条大机制（安全/资源闸、按气泡宽重编译、视口门 + 两道回收、`.mjs` 拆分）
一条没改**。下面只记**与设计稿不同**或**设计稿没有**的部分，以及落地时重新量出来的数字。

### 11.1 设计稿没有、实现期加的一片：`npm run smoke:flint`

**为何非加不可**：设计稿把「两个 npm 包能不能在 `sandbox:true` 的纯 Chromium ESM 上下文里 `import`」
放在 §3.2 用**静态核查**（`npm pack` 解包 grep）当证据，又把「真渲染」整个推给人手测。
**但 P10.1 那次栽的正是这个形状的坑**：`highlight.js` 的 `es/*` 是重导出 CJS 的 shim，
静态看它是 ESM、node 里因为有 CJS interop 还**假性通过**，只有真 Electron 里 import 才抛。
静态核查能证「没有 bare import / 没有 `require(`」，**证不了「Chromium 的 module loader 真能把它加载起来」**
——那是两件事。而「推给人手测」在一个没有 CI 的仓库里，等价于「跑一次然后消失」。

故落 `app/scripts/flint-smoke/{main.js,smoke.html,smoke.js}`：一个一次性 Electron main 起
**与 `main/index.js` 逐字同款 `webPreferences`** 的窗口，页面挂 **与 `renderer/index.html` 逐字同款 CSP**，
在里面跑真 `enhanceFlint`，把结果打到 stdout 后按失败数退出。**21 项全绿**，覆盖 §7 手测里
1 渲染 / 8 注入 / 9 不误伤 / 11 拒 `data.url` / 12 三档徽标（①④）/ 13 空图守门 / 4 实例回收（①③）；
**评审后又加了 5 条**（⑨–⑬）把「气泡真被撑宽」「`<figure>` 不横向溢出」「失败后 `.has-flint` 被撤掉」
「`#messages` 是 observer 能用的滚动容器」「窄栏收窄后不溢出」从人眼挪进了自动——它们是第 ⑤⑥ 两条
评审缺陷的**反向验证**（撤掉修法这几条必红，实测过，见 §12.3）。

> **这两条「逐字同款」是它有意义的前提**：改主窗口 `webPreferences` 或 `index.html` 的 CSP 时须一并改它，
> 否则冒烟绿而真 app 红。`!scripts/**/*` 已在打包排除里，不进 asar。

**仍然只能人眼的**：窄气泡下「读不读得清」、视口门「有没有少编译」、LRU「滚回去有没有自愈」、
流式「闪不闪」、tooltip hover、Network 面板的懒加载与离线。这些在 §7 里都标了 `[★人眼]`，
**已于 2026-08-04 由维护者整串跑通**（13 项全过）——但它们**不因此退休**：是发版前复跑的脚本，
改渲染端后须重跑（这正是把它们逐条留在 §7 而不是折叠成一行「验收通过」的原因）。

### 11.2 主题与色板落在 `flint_core.mjs` 而非 `flint_chart.js`

设计稿 §10 的 P10.2.2 把 `CHAHUA_FLINT_THEME` + `applyChahuaPalette` 列在 `flint_chart.js` 名下
（§9 落点表倒是列在 `flint_core.mjs`，两处本就打架）。**实现按 `flint_core.mjs` 走**：
主题对象是纯数据、换色是纯函数，都该待在可测那一半——`flint_core.test.mjs` 里
「五档轴必须齐」「`Waterfall Chart` 整张跳过」「恰好叫 `#5470c6` 的类别名不被改写」「cat20 全覆盖」
四条用例正是因此才写得出来。`flint_chart.js` 只 `import` 它、传进 `echarts.init` 第二参。

### 11.3 打包白名单比设计稿多一条

`build.files` 除了设计稿写的两组「排除全部 + 重纳一文件」，还得加 **`"!renderer/**/*.test.mjs"`**——
`renderer/**/*` 会把 `flint_core.test.mjs` 一并卷进 asar（首次 `build:dir` 实测确实进去了）。
一个 import `node:test` 的文件躺在发布包里不会被加载、不构成安全问题，但它是**明确的失误**：
新增测试文件与它所测的模块同目录时，打包白名单要跟着走一步。

核过的结果：asar 里 flint / echarts 相关**只有两个文件**——`echarts/dist/echarts.esm.min.js` +
`flint-chart/dist/echarts/index.js`；无 `echarts/lib/**`、无 `*.map`、无 flint 的
`plotly`/`chartjs`/`vegalite`/`excel`/`gallery`/`test-data` dist。`node_modules` 增 93 MB，asar 增 ~1.65 MB，
与决策P10.2-1 的估算一致。

### 11.4 一处小加固：运行时加载失败时清 `data-flint-observed`

设计稿的 `loadFlintRuntime` 已按决策P4.20-26 用换 query 绕开 module map 的失败缓存，
但 `enhanceFlint` 侧用 `data-flint-observed` 排重 ⇒ **加载失败过的 `<pre>` 再也不会被重新 observe**，
那条重试路径其实到不了。实现里在「运行时加载失败」这一支 `delete pre.dataset.flintObserved`，
让下一次 `enhanceContent` 能真重试。（编译期失败不清——那是确定性失败，重试只会重复刷同一个徽标。）

### 12.1 安全 / 正确性（改了行为）

| 4 | `assembleFitted` 锁死宽高比，**高度变矮**就让 flint 丢行，于是第一档就 break、退回横向滚动 | 同一档再试一次「保住 `base._height`」，仍 overflow 才收工 | 60 类别横向柱图：`{375,370}`→OVF，`{281, base._height}`→336×577 零丢失，一个满足全部验收条件却被静默跳过的档 |

### 12.3 这一轮的一般形态

三条值得记下来，它们比具体的 bug 更耐用：

1. **「闸子恒过」是本相位反复出现的形状**（第 1/2/7 条，加上落地前评审已抓的 `grid` 数组形态）。
   共同结构是：闸子按**一个假定的产物形状**写，而上游的真实形状多一种变体。**写闸子时要问的不是
   「这条能不能拦住坏的」，而是「上游产物有几种形态，我认的是哪一种」。**
2. **「机制看着在，其实没生效」同理**（第 5/6/8/10 条）：`.has-flint` 加了但气泡没被撑开、
   `rootMargin` 传了但 root 错、重试代码写了但不可达。**共同点是没有任何测试真的量过它的效果** ——
   于是这轮给每条都补了一个**能被反向验证**的断言（把修法撤掉、断言必须变红，第 5/6 两条真跑过）。
3. **测试自身也会「看着在测」**（第 12/14 条）：一条被注释满足的正则、一份和产品分了叉的副本。
   判据同上：**把被测的东西弄坏，用例必须红。**
