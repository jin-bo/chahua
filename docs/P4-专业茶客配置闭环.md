## 2. 决定性约定

### 2.1 `model = "<provider>/<model>"` —— 合并为单字段

为了减少配置噪音、与 LiteLLM / OpenRouter / agentao 用户的肌肉记忆一致，**取消单独的 `provider` 字段**。`model` 值里以**第一个 `/`** 作为 provider/model 分隔符：

```toml
model = "openai/gpt-5.4-mini"         # provider="openai",  model="gpt-5.4-mini"
model = "anthropic/claude-opus-4-7"   # provider="anthropic", model="claude-opus-4-7"
model = "openrouter/qwen/qwen3-coder" # provider="openrouter", model="qwen/qwen3-coder"
```

规则：

- **必须含 `/`**。`model = "gpt-5.4"` → `RoomConfigError`（请写 `openai/gpt-5.4`）。强制写明 provider 比"自动按环境变量推断"更可读，也避免与房间默认 provider 隐式耦合。
- **取首个 `/`**：`openrouter/qwen/qwen3-coder` → provider=`openrouter`、model=`qwen/qwen3-coder`（OpenRouter 与 LiteLLM 的 model id 里普遍有 `/`）。
- provider 名在 `_DEFAULT_BASE_URLS` 范围内（openai / deepseek / moonshot / siliconflow / openrouter / ollama …）自带默认 base_url；其它 provider 必须显式 `base_url`，缺即报错（与现状 `_make_llm_client` 一致）。
- 单 `model` 字段同时覆盖 `[scoring]` / `[summary]` / `[[guest]]` 三处。

`base_url` / `api_key_env` 仍作为可选独立字段：

```toml
[[guest]]
model       = "openai/gpt-5.4"
base_url    = "https://my-corp-proxy/v1"      # 可选；缺即按 provider 默认
api_key_env = "CORP_OPENAI_KEY"               # 可选；缺即按 OPENAI_API_KEY
```

### 2.2 API key 不进 toml

仍走环境变量 / `.env`（与 [DESIGN.md §4](DESIGN.md) 末段一致）。toml 里允许的最大让步是 `api_key_env = "MY_VAR"` —— 告诉装配层 "去读哪个变量"。这条门有两个理由：

- **不落明文**：room.toml 经常被 commit / 分享 / 截图，key 进文件就回不来了。
- **打包后多用户共用 user_data**：装配时读环境变量，每个用户的 key 来自各自 shell，互不污染。

UI 表单里 key 字段一律渲染成"环境变量名 + ✓ 已配置 / ✗ 未配置"灰显，不接受明文输入。

### 2.3 LLM 段：整段写或整段不写（"all-or-nothing per section"）

**没有字段级 fallback**。一个 LLM section（`[scoring]` / `[summary]` / `[[guest]]`）要么写 `model`、要么整段不出现；不允许只写 `base_url` 或只写 `api_key_env`。

判定规则：

- section 里出现 `base_url` / `api_key_env` 之一但缺 `model` → `RoomConfigError("[scoring].base_url 不能单独出现，需同写 model")`。
- `model` 写了 → 解析 `LLMSpec(provider, model, base_url=?, api_key_env=?, temperature=?)`；`base_url` 缺则按 provider 默认（如 `openai` → `https://api.openai.com/v1`）；`api_key_env` 缺则按 `<PROVIDER>_API_KEY` 约定。这两条是**默认值**，不是"从别处继承"。

section 级 fallback（"整段缺即怎样"）：

| 缺谁 | 用谁 |
|---|---|
| `[[guest]]` 没出现 LLM 字段 | 房间默认 = `LLMSpec.from_env()` |
| `[scoring]` 整段缺 | 房间默认 |
| `[summary]` 整段缺 | `[scoring]` 的有效 spec（即缺 `[scoring]` 时也是房间默认） |

这条策略的代价：用户想"用 OpenAI 默认 model 但换到自己的 proxy"，必须把 model 也写出来 —— 因为没有"提供 base_url 时自动继承 provider 推断的 model"的隐式行为。**这是有意为之** —— 隐式 overlay 让"为什么这个茶客用了 X model"难以追溯；显式 model 让 UI / `room_info` envelope 一眼能展示"这位茶客在用什么"。

UI 端：[[guest]] 模型选择只有两态（"继承房间默认" / "自定义（model 必填）"）；`[summary]` 选择也只有两态（"复用 `[scoring]`（含房间默认 fallback）" / "单独指定（model 必填）"）。**不存在**"[summary] 跳过 scoring 直接走房间默认"的中间态 —— 那是 power-user 才用得到的边角配置，raw editor 可以表达（写 `[summary]` 段且 model 与房间默认一致），表单不暴露这第三态。

### 2.4 `extra_mcp_servers` 的信任语义

[chahua/trust.py](../chahua/trust.py) 现在按 `persona_rel` 索引信任：persona sidecar 的 `mcp.json` 默认不装载，必须用户在 UI 勾"信任此 persona 的 MCP"才生效。这条规则**只覆盖 persona 来路**，因为 persona 可能从 GitHub 导入，`command` 是任意可执行。

P4 引入的 `[[guest.extra_mcp_servers]]` 是**用户在自己的房间 toml 里手写的**，等价用户意图，**自动信任**，无需进 trust 清单。两份合并喂给 `Agentao`：

- persona sidecar mcp（受 trust 门控）
- 房间级 extra_mcp_servers（无门控）
- 同名时**房间级覆盖** persona（房间级是"这里要这么用"的具体配置）

UI 表单里要写明这条不对称：勾选信任 vs 直接添加，是两种不同语义的入口。

### 2.5 `isolation` 切换不自动迁移记忆

`isolation = "room" | "global"` 决定 `working_directory`：

- `room`（默认）：`<room_dir>/guests/<name>/`
- `global`：`<user_data_root>/guests/<name>/`

切换 isolation 后**旧路径下的 `.agentao/memory.db` 不会自动迁移**。UI 在切换提交前 confirm 一次，文案说明：

> 切换会改变工作目录路径。已有的 `.agentao/memory.db` / `sessions/` 不会自动迁移，你可以保留旧记忆（手动 cp 老路径到新路径），或就此让茶客失忆。

不做自动迁移的理由：单机本地、用户最懂自己的 `.agentao` 干净不干净；做自动迁移要处理"两边都有 db 怎么办"的 ambiguity，复杂度不值。

## 4. Python 后端改造

### 4.1 `chahua/llm_spec.py`（新）

把 `session._make_llm_client()` 的"环境变量 → LLMClient"逻辑抽出来。所有三处来源（房间默认 / `[scoring]` / `[summary]` / `[[guest]]`）共用同一 `LLMSpec` → `build_client(spec)` 出口。

```python
@dataclass(frozen=True)
class LLMSpec:
    provider: str
    model: str
    base_url: Optional[str] = None
    api_key_env: Optional[str] = None
    temperature: Optional[float] = None      # 缺即走 _DEFAULT_TEMPERATURE / LLM_TEMPERATURE

    @classmethod
    def from_env(cls) -> "LLMSpec":
        """复刻现 _make_llm_client 行为：读 LLM_PROVIDER → <PREFIX>_{API_KEY,BASE_URL,MODEL}。
        命令行 / dotenv 是单人单 provider 入口，允许裸 model（无 /）—— 自动拼成
        `<provider>/<model>` 装入 spec。与 toml 路径强制 / 的策略故意不一致。"""

    @classmethod
    def from_toml(cls, data: dict | None, *, label: str) -> Optional["LLMSpec"]:
        """整段缺（data is None / empty）→ None，由调用方决定 fallback。
        data 非空：必含 'model' 字段；§2.3 的 all-or-nothing 校验在这层做：
          - 出现 base_url / api_key_env 但缺 model → RoomConfigError(label).
          - model 缺 '/' → RoomConfigError(label).
          - 未知 provider 且缺 base_url → RoomConfigError(label).
        label 是 '[scoring]' / '[[guest]] 宝总' 等人话定位。"""

def build_client(spec: LLMSpec) -> LLMClient:
    """按 spec 解析 api_key（按 api_key_env 或 <PROVIDER>_API_KEY）+ 构造 LLMClient。
    缺 key 等问题统一 SystemExit（CLI / server 同口径，与现 _make_llm_client 一致）。"""

def split_model_id(value: str) -> tuple[str, str]:
    """'openai/gpt-5.4' → ('openai', 'gpt-5.4')；'openrouter/qwen/qwen3-coder'
    → ('openrouter', 'qwen/qwen3-coder')。无 '/' 抛 ValueError。"""
```

**`_make_llm_client()` 命运**：移除（不保留薄包装）。当前返回 `(client, provider_name)` tuple 的形态在 P4 多 client 后失去意义 —— "一个 provider 字符串"代表不了多茶客异构的事实。改造范围：

| 现有 | 替换为 |
|---|---|
| `chahua/session.py` `_make_llm_client()` | 删 |
| `chahua/session.py` `RoomSession.provider: str` 字段 | 删（无单值可代表） |
| `chahua/server.py:238` 启动日志 `provider：{self._session.provider}` | 改打"房间默认 `{spec.provider}/{spec.model}` · {N} 位茶客（{M} 套自定义模型）"，从 `LLMSpec.from_env()` + per-guest spec 汇总 |
| `tests/conftest.py` / 其它 fixture 引用 `provider` 字段 | grep 跟改，详见 P4.1 验证项 |

不保留薄包装的理由：tuple 返回是历史包袱，留着会让调用方继续按"全房间一个 provider"的心智写代码。一次性挪掉，长期更清。

### 4.2 `chahua/config.py`

字段位移：

- `_DEFERRED_GUEST_KEYS` 移除 `provider` / `base_url` / `model` / `isolation` / `extra_mcp_servers`，保留 `transport`（P5）。
- `_DEFERRED_ROOM_KEYS` 移除 `max_consecutive_ai_turns` / `want_threshold` / `speaker_cooldown_turns` / `onboarding_threshold`。
- `_DEFERRED_TOPLEVEL_SECTIONS` 清空（`scoring` / `summary` 转白名单）。

dataclass 扩展：

```python
@dataclass(frozen=True)
class GuestConfig:
    name: str
    persona_path: Path
    permission: str
    isolation: Literal["room", "global"] = "room"
    llm: Optional[LLMSpec] = None                          # 缺即走房间默认
    # toml 表层是 list[dict]（数组表），config.py 解析时翻译成 dict[name -> cfg]
    # 方便 guest.py 合并 persona sidecar；name 字段被吸收做 key，从 cfg 移除
    extra_mcp_servers: Optional[dict[str, dict]] = None

    def workspace_in(self, room_dir: Path, *, user_data_root: Path) -> Path:
        if self.isolation == "global":
            return user_data_root / "guests" / self.name
        return room_dir / "guests" / self.name

@dataclass(frozen=True)
class RoomConfig:
    # 原字段不动
    orchestrator_overrides: dict[str, Any] = field(default_factory=dict)
    scoring_llm: Optional[LLMSpec] = None
    summary_llm: Optional[LLMSpec] = None
```

校验加固：

- `model` 字段必须能 `split_model_id` —— 没 `/` 直接 `RoomConfigError`，错误信息指 `model = "openai/gpt-5.4"` 示例。
- `isolation` 必须 ∈ `{"room", "global"}`。
- 编排数值字段类型 + 范围（`want_threshold ∈ [0,1]`、`max_consecutive_ai_turns ≥ 1`、`speaker_cooldown_turns ≥ 0`、`onboarding_threshold ≥ 1`）；越界即 `RoomConfigError`。
- **`[[guest.extra_mcp_servers]]` 的 toml ↔ python 转换**：
  - toml 写法是数组表（`[[guest.extra_mcp_servers]]` 重复段），解析为 `list[dict]`。每项必含 `name:str` + `command:str`；`args` 可选但必须 `list[str]`；`env` 可选 `dict[str,str]`。其它键 → `RoomConfigError`（不静默接受未知字段，与 §2 一致）。
  - python 内部转 `dict[name -> {command, args?, env?}]`：方便 `guest.py` 与 persona sidecar `mcp.json` 同名覆盖合并。`name` 字段被吸收做 key 后从 cfg dict 里移除。
  - **同 guest 下重名 → `RoomConfigError`**（强约束）。不取"后者覆盖"，因为 toml 数组表的顺序在 UI mutator → 写盘 → reload 之间不稳定（admin 重写按 dict 顺序），让用户依赖顺序是雷。同名想覆盖 persona sidecar 的，写一个房间级条目就够（合并规则在 `guest.py`，那是 persona vs 房间两段之间的覆盖，单段内不允许）。
  - **UI inbound `update_guest_extra_mcp` 也按 `list[dict]`**：与 toml 形态一致，前端不必关心内部 dict 形态。重名校验在 admin 层做。

### 4.4 `chahua/admin.py`

#### 4.4.1 先泛化 `_rewrite_and_validate`（P4 的承重墙）

现状 [chahua/admin.py:198](../chahua/admin.py) `write_room_toml` 仅接 `name/topic/rules/guests`，[chahua/admin.py:408](../chahua/admin.py) `_rewrite_and_validate` 也只 PUT `new_guests`，其它字段 round-trip 必丢。**P4 任何非 guest-list 改动（编排参数、scoring/summary LLM）都依赖先把这两个函数泛化**。

泛化形态：snapshot 升级为"完整 toml 视图 dict"，mutator 通过 `dataclasses.replace` 或纯函数 patch 出新 snapshot，统一交给 `_rewrite_and_validate(room_dir, snapshot, paths)`。

```python
# 完整快照形态（与 write_room_toml 入参 1:1）
TomlSnapshot = TypedDict("TomlSnapshot", {
    "name": str,
    "topic": str,
    "rules": str,
    "user_md": Optional[str],
    "orchestrator_overrides": dict[str, Any],   # 空 dict = 不写 [room] 编排字段
    "scoring": Optional[dict],                   # None = 不写 [scoring]
    "summary": Optional[dict],                   # None = 不写 [summary]
    "guests": list[dict],                        # 每项含 isolation / llm / extra_mcp_servers
})

def _read_existing_for_mutate(room_dir, paths) -> TomlSnapshot:
    """走 load_room_config + _room_config_to_dict，返回完整快照。"""

def _rewrite_and_validate(room_dir, snapshot: TomlSnapshot, paths) -> RoomConfig:
    """1) write_room_toml(**snapshot) 整段重写
       2) load_room_config 校验
       3) 校验失败 → 用上一次成功 snapshot（FS bytes 也行）回滚 → raise"""

def write_room_toml(room_dir, *, name, topic, rules, user_md=None,
                    orchestrator_overrides=None, scoring=None, summary=None,
                    guests):
    """完整重写。任一 optional 段为 None / 空容器 → 不写那段。"""
```

回滚策略：泛化后 snapshot 是 dict，回滚仍按"上次磁盘 bytes"重写最稳（避免"snapshot 自身被某 mutator patch 错"再写回去）。`update_room_toml`（raw editor）走 bytes-snapshot，结构化 mutator 走 dict-snapshot；两路在 admin 层共享同一个 "write → validate → on-fail rewrite-old-bytes" helper。

#### 4.4.2 mutator 列表

`_room_config_to_dict()` 完整还原所有字段；`_persona_to_relative` 不动。

新增结构化 mutator（每个都拿 snapshot → 改一处 → `_rewrite_and_validate`）：

- `update_guest_llm(paths, room_dir, name, spec_dict | None)` —— None 即"回到房间默认"，删 guest 段下的模型字段。spec_dict 必须满足 §2.3 all-or-nothing 校验（含 model 时其它字段合法、不含 model 时 raise）。
- `update_guest_isolation(paths, room_dir, name, isolation)`。
- `update_guest_extra_mcp(paths, room_dir, name, servers: list[dict])` —— 重名 raise；空 list 即清掉该 guest 的 `[[guest.extra_mcp_servers]]` 全部条目。
- `update_room_orchestrator(paths, room_dir, overrides: dict)` —— 全空 dict 即清掉 `[room]` 下的编排字段。
- `update_room_llm(paths, room_dir, section: "scoring"|"summary", spec_dict | None)` —— None 即删整段；spec_dict 走 §2.3 校验。

`update_room_toml`（raw editor）一字不动 —— power-user 兜底，校验路径自动包含新字段。

**MCP envelope 三字段的语义**：

## 7. 风险点

1. **`model` 缺 `/` 的现存配置**：现状 `room.toml` 都没填 `model`（走环境变量），P4 允许字段时既有房间不受影响。但 `LLM_MODEL` 环境变量 + `_make_llm_client` 用法仍是无 `/` 的裸 model id —— 那条路径是"按 `LLM_PROVIDER` 推断 provider"，与 toml 路径硬拒无 `/` 的设计**故意不一致**。命令行 / dotenv 是单人单 provider，toml 是多茶客可异构，约束不同。
2. **房间级 `extra_mcp_servers` 自动信任 vs persona sidecar 走 trust**：UI 必须写明这条不对称，否则用户会困惑"为什么 persona MCP 要勾、房间级不用勾"。modal 里把两块物理分开 + 不同标签（"persona 自带" / "房间级"）。
3. **`isolation=global` 茶客在不同房间装配**：必须确保不同 `RoomSession` 装配各自的 `TeaGuest` 实例（共享 `working_directory`，但 PermissionEngine / transport / Agentao 实例独立），否则两间房同时跑会撞 transport state。`build_room_session` 现有逻辑天然如此 —— 但要写明这是设计意图，防有人后续做 "global guest singleton" 误优化。
4. **schema round-trip 的注释损失**：[admin.py 模块 docstring](../chahua/admin.py) 已经写明"手工注释 / 字段顺序在重写时无论如何都会丢"。P4 不引入注释保留承诺，文档里继续讲明白"通过 UI 改了房间后 room.toml 会被规范化"。
5. **`api_key_env` 与 provider 的耦合期望**：`api_key_env = "MY_KEY"` 是给"用了非标准 env 变量名"的人留的逃生口。缺这字段时走 `<PROVIDER>_API_KEY` 约定（与 `_make_llm_client` 同口径）。文档里讲明白默认约定 → 用户大多数情况无需写这字段。
6. **测试覆盖**：现有 `tests/test_admin.py` 与 `tests/test_orchestrator_*` 覆盖大部分回归路径；P4 主要加：round-trip 测（snapshot 完整保真）、`split_model_id` 单测、`LLMSpec.from_toml` 校验测（含 §2.3 all-or-nothing 反例）、`isolation` 路径测、`extra_mcp_servers` 重名 raise 测、`update_*_llm` mutator 测、envelope 中三套 MCP 字段的拆分测。
7. **`_make_llm_client()` 移除的连锁影响**：P4.-1 必须 grep 全仓库（含 `tests/` / `app/`）确认无外部依赖。预计命中点：`session.py` 自身、`tests/conftest.py` fixture（若有）、`server.py` 启动日志。`RoomSession.provider` 字段删除同理 —— 没找到现有 envelope / UI 消费者，但要再确认一遍。
