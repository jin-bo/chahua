# P7.4：显式 handoff —— 茶客 propose（提议接力）

> 目标：在 P7.1 / P7.2 / P7.3 已落地的「用户**直接**触发 handoff」之上，补上另一条入口
> ——**茶客 propose、用户采纳**。茶客在发言里可以调工具「提议下一句交给 X」/「提议请 X
> 审范总刚才那段」/「提议拉个圆桌」，UI 把提议渲成「采纳 / 忽略」卡片，**用户点采纳后**
> 才走 P7.1~7.3 既有的 `handoff_*` inbound 入队。
>
> P7.4 是**纯增量、零调度层改动**：复用 P5 早就有的 `TASK_PROPOSAL` envelope + 前端
> `proposal_card.js`「采纳 / 忽略」卡片机制，复用 P7.1~7.3 的 `handoff_delegate` /
> `handoff_review` / `handoff_panel` inbound 及其全部校验。新增面只有**茶客侧的几个
> propose 工具** + **前端卡片的 kind 分支**。server inbound handler、drain loop、各
> inbound 校验、envelope schema 全部一字不动。

**状态：设计中（2026-05-20）**。上游契约见 [`P7-显式 handoff 与 delegation.md`](P7-显式%20handoff%20与%20delegation.md)
§4.1（user only vs AI propose 的结论）/ §3.3（`TASK_PROPOSAL` kind 占位）/ §7（阶段表
P7.4 行）；propose 机制原型见 [`P5-任务房间.md`](P5-任务房间.md) §6.3 / P5.3.4 / P5.3.7
（`task_propose_decision` / `task_propose_open`）。落地拆分见本文 §11。

> **对 P7 上游占位的两处修正**（本文 §5.1 / §5.2 详述）：
> 1. P7 §7 把工具占位叫 `task_propose_handoff`——**改名 `propose_delegate` /
>    `propose_review` / `propose_panel`**，去掉 `task_` 前缀：handoff 是房间级调度、
>    不属于任务域（与「handoff 不收进 Task 工具」评审同口径），工具落 `chahua/handoff_tools.py`
>    而非 `task_tools.py`。
> 2. P7 §3.3 把 propose envelope 占位写成嵌套 `kind:"handoff"` + `payload.kind`——
>    **改成 flat kind**：`TASK_PROPOSAL.data.kind ∈ {decision, open, handoff_delegate,
>    handoff_review, handoff_panel}` 五个平铺值，前端 `proposal_card.js` 单层 switch。

## 0. 本阶段做 / 不做

**做**：

- 新建 `chahua/handoff_tools.py`：三个茶客侧 propose 工具
  - `propose_delegate(target, reason?)` —— 提议「下一句交给 target 发」。
  - `propose_review(reviewer, reviewee)` —— 提议「请 reviewer 审 reviewee 最近一条发言」。
  - `propose_panel(targets, summarizer?)` —— 提议「拉一场 targets 的圆桌」。
  - `register_handoff_tools(agent, *, transport, room)` 工厂；`TeaGuest` 接线。
- `events.py` / `events.js` 加三个 `TASK_PROPOSAL_KIND_HANDOFF_*` 平铺常量。
- 前端 `proposal_card.js`：`renderPayloadPreview` + `buildAcceptInbound` 各加三个
  handoff kind 分支——采纳即拼 P7.1~7.3 既有的 `handoff_*` inbound。
- 茶客 propose 工具 `is_read_only = True`（同 `task_propose_*`——为权限层放行，**非**
  「无副作用」声明：会 emit `TASK_PROPOSAL` envelope）。

**不做**（推后 / 永不做）：

- **不**新增 envelope 类型——复用 `TASK_PROPOSAL`（同 P5.3.7 口径）；**不** bump
  `schema_version`；**不**新增持久化目录 / toml 字段。
- **不**改任何 server inbound handler——采纳走前端拼回 `handoff_*` inbound，
  `_inbound_handoff_delegate` / `_review` / `_panel` 及其**各自既有校验零改动**（§4）。
- **不**开茶客 propose `handoff_clear`——清队列是 destructive 操作，user-only（同
  `/clear task` 不给茶客 propose 入口的口径，§5.6）。
- **不**做 propose 的自动采纳 / 超时采纳 / 默认采纳——提议永远等用户点（§5.5）。
- **不**让 propose 工具校验 target / reviewee 在不在场——校验留给采纳时既有的
  `handoff_*` inbound 校验（§5.4，同 `task_propose_decision` 不校验 message id）。
- **不**给 `HandoffItem` 加新字段 / 新 `issued_by` 取值——采纳后的 item 与用户直接
  触发的**不可区分**，`issued_by` 恒 `"user"`（§5.7）。
- **不**做 slash `/propose`、**不**做茶客 propose set_active_task / open_task 之外的
  task 动作（那些 P5 已有 `task_propose_*`，不在 P7.4）。
- **不**碰 P7.5 `task.owner`。

## 1. 现状速写 —— P5 / P7.1~7.3 留下的复用面

P7.4 几乎不写新机制，全是「把两套老管道接起来」：

| 已落地（P5 / P7.1~7.3） | P7.4 怎么蹭 |
|---|---|
| `TASK_PROPOSAL` envelope（`events.py::ChahuaEventType.TASK_PROPOSAL`）+ `data = {proposer, kind, payload, task_id?}` | **零新增**——handoff 提议复用同一 envelope，只多三个 `kind` 平铺值 |
| `task_tools.py::_TaskProposeBase`：`transport.emit_chahua(TASK_PROPOSAL, {...})` + 返 LLM ack 字符串 | 照抄成 `handoff_tools.py::_ProposeHandoffBase`（同结构、不同 `_kind`）|
| 前端 `proposal_card.js`：`onEnvelope` 渲「采纳 / 忽略」卡 + `(proposer,kind,payload-hash)` 去重 + 切房 reset | `renderPayloadPreview` / `buildAcceptInbound` 各加 3 个 `kind` 分支；去重 / reset / 宿主气泡查找**零改动** |
| `proposal_card.js::buildAcceptInbound`：propose envelope → 既有 inbound（`decision→ADD_DECISION` / `open→OPEN_TASK`）| 加 `handoff_delegate→HANDOFF_DELEGATE` 等三条映射 |
| `handoff_delegate` / `handoff_review` / `handoff_panel` inbound + 各自既有校验（delegate / review / panel 每档校验数不同）| **零改动**——采纳拼出的 inbound 与用户直接触发走同一 schema、同一 handler 路径，校验天然复用 |
| `handoff.py::HandoffItem.issued_by`（默认 `HANDOFF_ISSUED_BY_USER`，docstring 已写明「propose-then-adopt 采纳后仍是 `"user"`」）| **零改动**——P7.4 印证这条 docstring，不加新取值 |
| `Room.message_by_id` / `Room` 消息列表（P7.2 加的线性查找）| `propose_review` 工具用 `room` 把 `reviewee` 名解析成其最近一条 `message_id` |

**最重要的判断**：handoff 提议与「直接触发」在**采纳之后完全同构**——用户点「采纳」
产出的 `handoff_*` inbound 帧，与用户直接点 composer「指派」按钮发的帧走**同一
inbound schema、同一 handler 路径**（delegate 采纳时 `reason` 多带一个 `"<proposer>
提议："` 前缀——这是唯一的*值*差异，字段集 / schema 不变）。
所以 P7.4 不碰 server、不碰 drain、不碰校验，只在「茶客怎么发起提议」和「提议怎么渲成
卡片」两端加代码。这与 P5.3.7「propose 不直接写库、采纳后才入库、server handler 零改动」
是同一条设计线。

## 2. 动作形态：茶客 propose handoff

### 2.1 三种提议，一一对应 P7.1~7.3 的三种 handoff

| 工具 | 茶客意图 | 采纳后走的 inbound |
|---|---|---|
| `propose_delegate(target, reason?)` | 「下一句该让 target 说」 | `handoff_delegate {target, reason?}` |
| `propose_review(reviewer, reviewee)` | 「reviewee 刚那段该让 reviewer 审一下」 | `handoff_review {target, message_id}` |
| `propose_panel(targets, summarizer?)` | 「这个问题该拉 targets 开个圆桌」 | `handoff_panel {targets, summarizer?}` |

### 2.2 一次提议的完整生命周期

```
茶客 C 在发言里调 propose_delegate(target="范总", reason="他更熟水文")
   │
   ├─ 工具 execute() → transport.emit_chahua(TASK_PROPOSAL, {
   │      proposer: "C", kind: "handoff_delegate",
   │      payload: {target: "范总", reason: "他更熟水文"}})
   │  工具返回 ack 字符串给茶客 LLM：「已提议……等用户在 UI 采纳」
   │
   ▼
前端 proposal_card.js.onEnvelope(env)
   ├─ 找宿主气泡（C 当前这条消息的 message_id）
   ├─ 去重指纹 (proposer,kind,payload-hash) 未见过 → 渲卡片
   │     「C 提议（等用户确认）」
   │     「建议下一句交给『范总』」+ 理由「他更熟水文」
   │     [ 采纳 ]  [ 忽略 ]
   │
   ▼
用户点「采纳」
   ├─ buildAcceptInbound → {type:"handoff_delegate", target:"范总",
   │      reason:"C 提议：他更熟水文"}
   ├─ sendInbound(...) → 走 P7.1 既有 _inbound_handoff_delegate
   │      （既有校验：target 非空 str / 在场 / ……）
   └─ 卡片双按钮锁死 + 标「已采纳」；handoff_enqueued 回环刷队列预览
```

茶客点「忽略」分支：`proposal_card.js` 既有逻辑——`card.remove()`，不发任何 inbound。

## 3. 数据契约

### 3.1 `TASK_PROPOSAL.data.kind` 三个平铺新值（`events.py` / `events.js`）

```python
# chahua/events.py —— 紧挨现有两个常量
TASK_PROPOSAL_KIND_DECISION = "decision"          # 已有
TASK_PROPOSAL_KIND_OPEN = "open"                  # 已有
TASK_PROPOSAL_KIND_HANDOFF_DELEGATE = "handoff_delegate"   # P7.4 新增
TASK_PROPOSAL_KIND_HANDOFF_REVIEW   = "handoff_review"     # P7.4 新增
TASK_PROPOSAL_KIND_HANDOFF_PANEL    = "handoff_panel"      # P7.4 新增
```

`events.js::TaskProposalKind` 同步镜像三个值（前端 `proposal_card.js` 已 import 它）。

**为什么 flat 不嵌套**（修正 P7 §3.3 占位）：P7 §3.3 占位写的是
`kind:"handoff"` + `payload:{kind:"delegate"|...}` 两层。但 `proposal_card.js` 的
`renderPayloadPreview(kind, payload)` / `buildAcceptInbound(data)` 都是**对 `data.kind`
单层 switch**；嵌套会逼前端写「先判 handoff 再判 payload.kind」两级 dispatch，且
`payload.kind` 与外层 `kind` 永远联动、是冗余状态。平铺成 `handoff_delegate` 等三个值，
前端 switch 多三个 `case`、零嵌套。kind 值取 `"handoff_delegate"` 与 inbound 帧
`type` **同字面值**——`buildAcceptInbound` 里 `kind` 去掉无前缀即可对上（见 §3.3）。

### 3.2 三种 `payload` 形状

| kind | payload | 字段说明 |
|---|---|---|
| `handoff_delegate` | `{target: str, reason?: str}` | `target` = 被指派茶客名；`reason` = 提议茶客的理由（可缺省）|
| `handoff_review` | `{message_id: str, target: str, reviewee: str, snippet: str}` | `target` = 审阅者；`message_id` = 被审消息（**工具在 propose 时解析**，§3.4）；`reviewee` / `snippet` 仅供卡片预览 |
| `handoff_panel` | `{targets: list[str], summarizer?: str}` | 与 `handoff_panel` inbound 同形 |

`payload` 形状**有意贴近**对应 inbound 的字段集——`buildAcceptInbound` 基本是「换个
`type`、挑几个键」的直译，不做结构转换。`handoff_review.payload` 是唯一带「多余字段」
的（`reviewee` / `snippet` 是卡片预览用，采纳时丢弃）。

### 3.3 采纳映射（`proposal_card.js::buildAcceptInbound` 新增三分支）

```js
// kind 去掉「handoff_」前缀即 inbound 的 type 后缀；逐字段直译。沿用 proposal_card.js
// 既有写法 `typeof x === "string" ? x : ""`，不引入新 helper。
if (data.kind === TaskProposalKind.HANDOFF_DELEGATE) {
  const target = typeof payload.target === "string" ? payload.target : "";
  if (!target) return null;                       // 字段不齐 → 采纳按钮 disabled
  const out = { type: Inbound.HANDOFF_DELEGATE, target };
  // proposer 进 reason 前缀 —— 给 debug record / 队列预览 hover 留 propose 痕迹
  // （HandoffItem 不落盘，reason 是唯一能带 provenance 的字段，§5.7）。
  const why = typeof payload.reason === "string" ? payload.reason : "";
  out.reason = why ? `${data.proposer} 提议：${why}` : `${data.proposer} 提议`;
  return out;
}
if (data.kind === TaskProposalKind.HANDOFF_REVIEW) {
  const target = typeof payload.target === "string" ? payload.target : "";
  const mid = typeof payload.message_id === "string" ? payload.message_id : "";
  if (!target || !mid) return null;
  return { type: Inbound.HANDOFF_REVIEW, target, message_id: mid };
}
if (data.kind === TaskProposalKind.HANDOFF_PANEL) {
  // 坏 targets 一律 return null —— 不 filter「修正」。`["A", 1, "B"]` 不能被静默
  // 改成 `["A","B"]` 当成另一个合法 panel；要么整体合法、要么拒。
  const targets = payload.targets;
  if (!Array.isArray(targets) || targets.length < 2) return null;
  if (!targets.every((x) => typeof x === "string" && x)) return null;
  const out = { type: Inbound.HANDOFF_PANEL, targets };
  if (typeof payload.summarizer === "string" && payload.summarizer) {
    out.summarizer = payload.summarizer;
  }
  return out;
}
```

`buildAcceptInbound` 返 `null` → `proposal_card.js` 既有逻辑把「采纳」按钮渲成
disabled + tooltip（与现有 `decision` 缺 task 时同分支）。**`handoff_review` 不带
`reason`、`handoff_panel` 不带 `reason`**——这两种 inbound 本就没有 `reason` 字段
（`HandoffItem` review/panel 项 `reason` 恒 `None`）；proposer 信息只活在卡片上
（卡片 meta 行「C 提议（等用户确认）」），采纳后不进 item（§5.7）。

### 3.4 `propose_review` 的 message_id 在 propose 时解析（**关键约束**）

P7.2 的 `handoff_review` inbound 要求一个具体 `message_id`，且其三道校验③ 要
`room.message_by_id(message_id)` 命中。但**茶客看不到 message_id**——`room.format_messages`
喂给茶客的 `<recent_messages>` 是 `<message>\n{display} 说：{text}\n</message>`，
**不含 id**。所以茶客无法像用户点气泡那样「指着某条消息」请审。

P7.4 的解法：`propose_review` 工具**只收茶客名**`reviewer` / `reviewee`，由工具在
`execute()` 里用注入的 `room` 把 `reviewee` 解析成「该茶客最近一条发言的 message_id」：

```python
# handoff_tools.py::ProposeReviewTool.execute
msg = self._room.latest_message_by_speaker_id(reviewee)   # 见 §3.5
if msg is None:
    return f"Error: 「{reviewee}」最近没有发言可审，无法提议请审。"
payload = {"target": reviewer, "message_id": msg.message_id,
           "reviewee": reviewee, "snippet": msg.text[:80]}
```

**工具参数口径**：`reviewer` / `reviewee`（以及 `propose_delegate` 的 `target`、
`propose_panel` 的 `targets` / `summarizer`）传的都是**茶客 `name`**——即 `Message.speaker_id`
那个稳定标识，**不是 display name**。茶客 prompt 里看到的 `{display} 说：…` 用的是
display name，但房间成员名册（茶客 `name`）在 onboarding 的 `<room>` 块里给出，茶客据此
填参。工具 description 要写明「传茶客名」。

- 解析发生在 **propose 时**（不是采纳时）——message_id 冻结在「茶客当时看到的那条」，
  即使 reviewee 在用户采纳前又说了新话，被审的仍是茶客本意指的那条（§5.3）。
- MVP **只支持「reviewee 最近一条」**——茶客说「请审范总刚那段」是绝对主场景；
  「审更早的某条」属于用户主场景（用户能看气泡直接点），不为茶客开（§5.3）。
- reviewee 在最近 transcript 里没发过言 → 工具返 `Error:` 字符串，茶客 LLM 收到即知
  这条提议发不出去（不 emit envelope）。

### 3.5 `Room` 加一个 `latest_message_by_speaker_id`

P7.2 已加 `Room.message_by_id`（O(n) 线性、不建索引）。P7.4 加一个对称的：

```python
def latest_message_by_speaker_id(self, speaker_id: str) -> Optional[Message]:
    """按 speaker_id 倒序线性查找最近一条；未命中返 None。
    与 message_by_id 同口径——review 是低频用户/茶客动作，O(n) 够，不建索引。"""
    for m in reversed(self._messages):
        if m.speaker_id == speaker_id:
            return m
    return None
```

**字段名口径**：`Message` 的稳定标识字段是 `speaker_id`（`room.py`——`"user"` 或茶客
`name`，**不存 display_name**）。helper 名与形参都用 `speaker_id`，与 `Message` 字段
对齐；`propose_review` 工具收的 `reviewee` 就是茶客 `name`（= 该茶客的 `speaker_id`），
不是 display name——见 §3.4 工具参数说明。这是 P7.4 在 `Room` 上唯一的新增面，与既有
`message_by_id` 完全同构。

## 4. 执行：采纳即走既有 inbound，server 零改动

P7.4 **没有「执行」一节**——这正是设计的核心。propose 不入队、不碰调度层；用户点
「采纳」后，前端 `sendInbound(buildAcceptInbound(...))` 发出的就是 P7.1~7.3 既有的
`handoff_delegate` / `handoff_review` / `handoff_panel` 帧。之后：

- `_inbound_handoff_*` handler 照跑——含 delegate / review / panel 各自既有的**校验**
  （review 三道 / panel 五道，delegate 走 payload 白名单 + target 在场）。
  茶客 propose 了一个不在场的 target、或 panel 撞了 cap？采纳那一刻被既有校验拦下、
  emit `NOTICE error`，与用户手动发了个非法帧**同路径**。propose 侧不预先校验（§5.4）。
- `enqueue_handoff` / `run_pending_handoff` / `_run_handoff_turn` wrapper / cancel /
  turn 末尾 5 步——**全部一字不动**。
- `handoff_enqueued` 回环刷新前端队列预览小条。

**唯一要确认的回归点**：采纳拼出的 inbound **不得带入该 inbound 白名单之外的字段**
（白名单内的可选字段——如 `handoff_delegate` 的 `reason`——可有可无；字段值也可不同，
如 delegate 的 `reason` 前缀）。三种
inbound 的字段集见 §3.3——`handoff_delegate` 多带 `reason`（合法可选字段）、
`handoff_review` / `handoff_panel` 不带任何 propose-only 字段。`reviewee` / `snippet`
**绝不能**漏进 `handoff_review` inbound（白名单严格 `{type,target,message_id}`，多字段
→ 服务端 NOTICE error 丢帧）——`buildAcceptInbound` 只挑 `{type,target,message_id}` 三键。

## 5. 关键设计决策（with rationale）

### 5.1 工具不叫 `task_propose_handoff`，叫 `propose_delegate/review/panel`，落 `handoff_tools.py`

P7 §7 阶段表把工具占位写成 `task_propose_handoff`。**P7.4 改名**：

- handoff 是**房间级调度通道**，不属于任务域——「handoff 该不该收进 Task 工具」一题
  已评审否决（handoff 在无任务的纯聊天房间也成立、review 锚的是 transcript 消息不是
  artifact）。工具带 `task_` 前缀会重新暗示「handoff ⊆ task」这条被否决的从属关系。
- 既有 `task_propose_decision` / `task_propose_open` 在 `task_tools.py`，确实是任务域。
  P7.4 三个工具落**新模块 `chahua/handoff_tools.py`**，与 `handoff.py`（数据契约）/
  `task_tools.py`（任务工具）三者域清晰：handoff 调度 / 提议工具 / 任务工具。
- 三个工具**一类一个**（不做单个 `propose_handoff(kind, ...)` 多态工具）——三种 kind
  的参数集差异大（`target` vs `reviewer+reviewee` vs `targets+summarizer`），多态工具
  要在一个 JSON schema 里塞条件字段，LLM 易传错组合；一类一个工具、各自干净 schema，
  与 `task_propose_decision` / `task_propose_open` 分两个工具同口径。

### 5.2 复用 `TASK_PROPOSAL` envelope，不新开 `HANDOFF_PROPOSAL`

`TASK_PROPOSAL` 名字带 `TASK`，handoff 提议复用它有轻微命名违和。但：

- P7 §4.1 已定调「propose 复用 `TASK_PROPOSAL` envelope、server handler 零改动」。
- envelope 本质是个通用「提议」管道——`{proposer, kind, payload}` 与任务无耦合。
- 前端 `proposal_card.js` 已围绕 `TASK_PROPOSAL` 把「找宿主气泡 → 渲卡 → 去重 → 采纳/
  忽略」整条做完了。新开 `HANDOFF_PROPOSAL` 要把这套**整体复制一份**，纯重复。
- 卡片挂在「提议茶客的发言气泡」下——handoff 提议同样需要这个挂点（茶客在哪条消息里
  提的议，卡片就跟在哪条下）。复用 = 免费拿到这个行为。

重命名 `TASK_PROPOSAL → PROPOSAL` 会 ripple 到 `events.py` / `events.js` /
`proposal_card.js` / `task_tools.py` + 可能 bump `schema_version`，收益只是名字好看
——不值。**保留 `TASK_PROPOSAL` 名、flat kind 扩值**。

### 5.3 `propose_review` 只能审「reviewee 最近一条」，且在 propose 时冻结

见 §3.4。两条收敛：

- **只审最近一条**：茶客看不见 message_id，没法精确指任意历史消息。「请审 X 刚说的」
  是茶客视角的绝对主场景；「审三条之前那段」是用户视角（用户能滚动、能点气泡），
  P7.2 的气泡「请审…」按钮已经覆盖。为茶客开「审任意历史消息」要么暴露 message_id
  给茶客 prompt（污染 `<recent_messages>` 格式、动 `format_messages` 不变量），要么给
  工具加「第几条」这种脆弱的相对寻址——都不值，**不做**。
- **propose 时冻结 message_id**：若改成「采纳时前端再解析 reviewee→最新消息」，茶客
  提议到用户采纳之间 reviewee 又发了言，被审的就漂移成新消息、偏离茶客本意。工具在
  `execute()` 里当场解析并把具体 `message_id` 写进 payload——审的永远是茶客提议时
  看到的那条。

### 5.4 propose 工具不校验 target / reviewee 在不在场

`propose_delegate("不存在的人")` / `propose_panel(["张三"])`（撞 cap）——工具**不拦**，
照常 emit `TASK_PROPOSAL`。理由：

- 与 `task_propose_decision` 不校验 `supporting_message_ids` 真实性同口径——propose 是
  「提个议」，正确性由**采纳**那一刻的既有 `handoff_*` inbound 校验兜底。
- propose 工具若自带校验，就要在茶客进程里复制一份「谁在场 / cap 多少」的判断逻辑，
  与服务端校验两处维护、易漂移。
- 唯一例外是 `propose_review` 的 `reviewee` 解析——那不是「校验」是「取数」（要拿
  message_id 才能组 payload），reviewee 没发过言时返 `Error:` 是取数失败的自然结果。
- 代价：茶客提了个非法 delegate，用户点采纳才看到 `NOTICE error`。可接受——非法
  propose 本就少见，且用户多半在采纳前就从卡片看出「这人不在房间里」。前端卡片**可选**
  增强：`buildAcceptInbound` 阶段拿 `guests` 名册预判、`target` 不在场就把采纳按钮
  渲 disabled——但这需要 `proposal_card.js` 拿到 guests 列表（当前没有），**推后**，
  不进 P7.4 MVP。

### 5.5 propose 永远等用户点，不自动采纳 / 不超时采纳

提议卡片只有「采纳 / 忽略」两个用户动作，没有「N 秒后自动采纳」「茶客可自己采纳」。
这是 P5.1「写权限永远在用户」+ P7 §4.1「茶客不能静默 delegate/panel，否则 AI 自我
接龙开 50 个 panel 打穿 token」的直接延伸。propose 把「茶客能影响调度」与「茶客能
决定调度」切开——前者开放，后者永远在用户。

### 5.6 不开茶客 propose `handoff_clear`

`handoff_clear`（全部取消 = cancel 当前 + 清队列）是 destructive 操作。不给茶客 propose
入口——与「`/clear task` 不给茶客 propose 入口、清产物比写产物风险更高必须用户主动」
同口径。茶客能提议「加」一项 handoff，不能提议「清空」别人的调度安排。

### 5.7 采纳后的 `HandoffItem` 与用户直接触发不可区分；`issued_by` 恒 `"user"`

`handoff.py::HandoffItem.issued_by` 默认 `HANDOFF_ISSUED_BY_USER`，docstring 早写明
「propose-then-adopt 采纳后入队时仍是用户最终触发，所以恒 `"user"`」。P7.4 印证这条、
不加新取值（不引入 `"proposed"` / proposer 名之类）：

- 「采纳」是用户的确认动作——采纳后的 item 在语义上**就是**用户触发的，与用户点
  composer「指派」按钮无差别。给 `issued_by` 加值会让 drain / debug 到处要分叉判断。
- proposer 的 provenance 去哪了？`HandoffItem` **不落盘**（队列瞬态），唯一能带它的是
  `reason` 字段：`buildAcceptInbound` 给 `handoff_delegate` 的 `reason` 加 `"<proposer>
  提议："` 前缀（§3.3）——debug record 的 `trigger.handoff_item.reason` / 队列预览
  hover 因此能看出「这条是 C 提议、用户采纳的」。
- `handoff_review` / `handoff_panel` 没有 `reason` 字段，采纳后 proposer 不留痕——
  可接受：卡片 meta 行已显「C 提议」，提议本身是会话内可见的；要给 review/panel item
  也加 provenance 得专门加字段，不值。

### 5.8 茶客怎么知道这几个工具的存在与时机

靠**工具 description 措辞**，不新增 prompt 块（不动 `context_renderer` 的 6+1 块结构）。
description 要写清「提议 ≠ 立刻生效，要用户采纳」「仅在确有必要时提议，别每轮都提」
——克制措辞抑制「茶客每轮 propose handoff」的噪声风暴（§10）。与 `task_propose_*` 的
description 同风格（「提议 ≠ 入库——UI 渲染成采纳 / 忽略卡片」）。

## 6. UI 增量

P7.4 前端的**行为逻辑**只动 `app/renderer/proposal_card.js`（加三个 `kind` 分支）；
协议常量 `TaskProposalKind` 同步改 `events.js`（§3.1）——纯常量镜像、无逻辑。

### 6.1 `renderPayloadPreview` —— 三种卡片预览

| kind | 卡片标题 | 卡片正文 |
|---|---|---|
| `handoff_delegate` | 「建议交给『范总』发下一句」 | 理由（`payload.reason`，有才显）|
| `handoff_review` | 「建议请『范总』审阅一条发言」 | reviewee + snippet：「审『汪小姐』：{snippet}…」|
| `handoff_panel` | 「建议发起圆桌」 | 「成员：A、B、C」+「汇总：F」（有 summarizer 才显）|

未知 kind 仍走 `proposal_card.js` 既有的「未知提议类型」兜底分支（dev 期捕错、不静默）。

### 6.2 `buildAcceptInbound` —— 三条采纳映射

见 §3.3。返 `null` 时复用既有「采纳按钮 disabled + tooltip」分支（tooltip 文案：
「字段不齐，无法采纳」）。

### 6.3 卡片 meta / 去重 / 宿主气泡 —— 全部零改动

`proposal_card.js` 的 `dedupKey`（`proposer|kind|payload-hash`）、`onEnvelope` 找宿主
气泡、`reset()` 切房清指纹、采纳后双按钮锁死——**对 handoff kind 自动生效**，不用动。
handoff 提议卡片与 decision/open 提议卡片**视觉一致**（同 `.proposal-card` 样式），
用户对「采纳 / 忽略」的心智统一。

### 6.4 没有新的「发起」UI

P7.4 不在 composer / 侧栏加任何按钮——提议**完全由茶客在发言里调工具发起**，用户侧
只有「卡片上点采纳」。这与 P7.1~7.3 的「用户直接触发」UI（composer「指派」按钮）正交：
两条入口，一条用户主动、一条茶客提议用户批准。

## 7. 关键不变量（落地时同步追写 CLAUDE.md）

- **handoff propose 复用 `TASK_PROPOSAL` envelope + flat kind**。`data.kind ∈ {decision,
  open, handoff_delegate, handoff_review, handoff_panel}` 五个**平铺**值，不嵌套；前端
  `proposal_card.js` 单层 switch。新增 handoff kind 时 `events.py` / `events.js` 两处
  常量同步。**不**新增 envelope 类型、**不** bump `schema_version`。
- **propose 不入队、不碰调度层；采纳才走既有 `handoff_*` inbound**。茶客 propose 工具
  只 emit `TASK_PROPOSAL`；用户点「采纳」由 `proposal_card.js::buildAcceptInbound` 拼回
  P7.1~7.3 既有的 `handoff_delegate` / `handoff_review` / `handoff_panel` inbound，
  **server handler / drain loop / 各 inbound 校验零改动**。采纳拼出的帧与用户直接触发
  schema 同构（字段集一致，值可不同）——`buildAcceptInbound` 只挑该 inbound 白名单内的键，propose-only 字段
  （`reviewee` / `snippet`）绝不漏进 inbound。
- **propose 工具 `is_read_only=True` 是为权限层放行，非「无副作用」声明**。三个
  `propose_*` 工具不写库不落盘，但 emit `TASK_PROPOSAL` envelope——同 `task_propose_*`
  口径（P5.3.4 不变量延伸）。
- **handoff propose 工具落 `chahua/handoff_tools.py`，不带 `task_` 前缀**。handoff 是
  房间级调度、非任务域；工具名 `propose_delegate` / `propose_review` / `propose_panel`。
- **`propose_review` 在 propose 时把 `reviewee` 名解析成具体 `message_id` 并冻结**。
  茶客看不到 message_id，工具用注入的 `room` 取 reviewee 最近一条发言；MVP 只支持
  「最近一条」。reviewee 没发言 → 工具返 `Error:` 字符串、不 emit。
- **采纳后的 `HandoffItem` 与用户直接触发不可区分**。`issued_by` 恒
  `HANDOFF_ISSUED_BY_USER`，不加新取值；proposer provenance 仅经 `handoff_delegate` 的
  `reason` 前缀（`"<proposer> 提议：…"`）保留，review/panel 采纳后不留 proposer 痕。
- **茶客不能 propose `handoff_clear`**。清队列是 destructive、user-only（同 `/clear
  task` 不给茶客 propose 入口）。

## 10. 主要风险 & 兜底

| 风险 | 兜底 |
|---|---|
| **茶客 propose 风暴**——每轮发言都调 `propose_*`，刷一屏卡片 | ① `proposal_card.js` 既有 `(proposer,kind,payload-hash)` 去重——同一提议反复刷只渲一张；② 工具 description 措辞克制（「仅在确有必要时」「提议 ≠ 立刻生效」）；③ 卡片可「忽略」一键移除；④ 真失控时属调 prompt / 加每轮 propose 计数上限的后续事，不在 P7.4 |
| 茶客 propose 不在场的 target | 采纳时既有 inbound 校验 emit `NOTICE error`（§5.4）；卡片预校验推后 |
| 茶客 propose 撞 cap 的 panel | 采纳时 `handoff_panel` 五道校验⑤ emit `NOTICE error` |
| `propose_review` 的 reviewee 没发过言 | 工具返 `Error:` 字符串、不 emit envelope；茶客 LLM 收到即知 |
| propose 到采纳间 reviewee 又发言 | message_id 在 propose 时已冻结（§5.3），审的仍是茶客本意那条 |
| `reviewee` / `snippet` 漏进 `handoff_review` inbound | `buildAcceptInbound` 只挑 `{type,target,message_id}` 三键——**前端目前无 JS 测试体系**，此项作 P7.4.3 的**手测核对项**（§11）；若把 `buildAcceptInbound` 提纯成无 DOM 依赖的纯函数，可后续补一个最小 JS 单测，但不为 P7.4 引入测试框架 |
| 提议卡片宿主气泡被 evict（长会话）| 复用 `proposal_card.js` 既有逻辑——找不到宿主即丢弃且不留指纹（同 decision/open）|
