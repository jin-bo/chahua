## 0. 本阶段做 / 不做

**做**：

- 引入 mermaid 懒加载渲染：`renderMermaidIn(container)` 扫 markdown 输出的
  ` ```mermaid ` 代码块，动态 import mermaid 后 render 成 SVG 嵌进气泡（§5）。
- 引入「气泡 ↔ 产物」关联：`MessageArtifactRegistry` 房间级注册表，落
  `rooms/<id>/message_artifacts.jsonl`；`task_artifact_added` envelope 多带可选字段
  `originated_message_id`（§2 / §3）。
- 前端 `attachArtifactToBubble`：图片走 `<img>` 懒加载预览、其它走 pill 下载链
  （§6）。
- `download_file` inbound 加可选 `purpose ∈ {download, preview}`，envelope
  `file_download` 原样回声；purpose=preview → 前端把 bytes 灌进等待中的 `<img>`，不
  触发 `a.download`（§4）。
- 历史回放（room_history）按 message_id 投影 `originated_artifacts` 列表，刷新 / 切房
  后挂件能还原（§3 / §7）。

**不做（推后 / 收敛）**：

- **不**做 SVG 内嵌预览 —— SVG 可内嵌 `<script>`，走保守的 pill 下载链（§6.3，
  设计选择 C=保守）。
- **不**做协议级 eager 内嵌字节 —— 图片字节统一走 `download_file purpose=preview`
  懒拉，envelope 不膨胀（§4，设计选择 B=纯懒）。
- **不**做任意 markdown 内嵌图床（`![](...)`）—— 只处理「茶客经 `task_write_artifact`
  在任务内写出的产物」。任意 URL 的图片渲染走 `marked` 默认 + CSP 限制（§5.5）。
- **不**改 transcript.jsonl 行结构 —— 产物关联走旁路 jsonl（`message_artifacts.jsonl`，
  §2.2）。
- **不**改 `task_artifact_added` 既有字段；只**加**一个可选字段。`schema_version` 不
  bump（§3）。
- **不**对系统气泡兜底路径回归 —— 命中 `originated_message_id` 时**不**再追居中
  系统气泡（避免「📎 茶客产出：…」与挂件并存的双重提示，§7.3）。
- **不**自动 mark_seen 用户上传的图 —— 用户走 `attach_artifact` 上传路径不经
  `task_write_artifact`，`originated_message_id` 缺省，仍走系统气泡兜底（§7.4）。

## 1. 现状：为什么现在做

P5.4 起，茶客 `task_write_artifact("foo.png", ...)` 写到 `tasks/<active>/artifacts/`
的产物，由 `ArtifactDetector` 在每个 pick 周期末尾扫盘 diff 后 emit
`task_artifact_added`。当前前端的处理（`envelope_router.js`）：

```js
case EventType.TASK_ARTIFACT_ADDED: {
  taskPanel.flashHint(env.type, env.data ?? {});
  appendBubble({ kind: "system", text: "📎 茶客产出：" + data.name });
}
```

也就是说：

- 用户在聊天区看到 `📎 茶客产出：diagram.png`，但**看不到内容** —— 要打开任务面板、
  找到该 artifact、点击触发 `download_file` 把整文件下到本地，才能"看一眼"。
- 茶客气泡里写了 ` ```mermaid graph TD; A-->B ``` ` 这种 markdown 代码块，渲染成 `<pre>`
  纯文本框，需要用户自己复制到 mermaid live editor 才能看。

两件事的痛点同源：**聊天气泡是无产物展示能力的容器**。让聊天区原地能看，是从"工具
对话"走向"工作画布"的最低代价 UX 升级。

落地形态有两个互斥取舍点：

- **图片预览字节走哪**：随 envelope eager 内嵌 base64，还是按需 lazy 拉？eager 让
  envelope 膨胀（一张 500KB 的 PNG 多 ~670KB 帧），但首屏无延迟；lazy 多一个 ws
  round-trip，但协议干净。**P10 选 lazy**（§4）。
- **历史回放是否恢复挂件**：实时 session 才显示，还是刷新 / 切房后也持续在原气泡？
  纯实时方案零持久化代价；历史恢复要新落盘一张映射表。**P10 选恢复**（§2.2，
  设计选择 A=是）。

理由：让用户切回房间后历史仍可见才是稳定的「画布」语义。如果只在实时显示，刷新一次
就退化回普通系统气泡，与"📎 茶客产出"差别不大。

## 2. 后端设计：把 message_id ↔ 产物关联抓出来

### 2.1 关键瓶颈：`ArtifactDetector` 不知道 message_id

`task_write_artifact` 工具调用 → 落盘 → `ArtifactDetector.detect` 在 pick 周期末扫
盘 diff 算 `new_names` → emit `task_artifact_added`。这条链上唯一知道「这个文件是谁
写的」的环节是 `transport_bridge._maybe_record_artifact_path`（在 `task_write_artifact`
工具 `tool_start` 时）。但它和 detect 之间隔着整个 message_end + 多茶客 speak —— 没
有直接通道。

P6.1 的 `debug_recorder` 已经做过类似的事：在 tool_start 时 `record_artifact_path(message_id,
path)` 把映射存进 debug 索引。我们复用相同的拦截点 + 思路，但写到一张专门的注册表，让
detect 阶段能取出。

### 2.2 新模块：`chahua/message_artifacts.py`

```python
@dataclass(frozen=True, slots=True)
class ArtifactRef:
    task_id: str
    name: str
    size: int       # 写入瞬时大小（前端 pill 副文本用；真正下载时 server 重读取最新）
    # rel 不存盘 —— 由 (task_id, name) 派生，与 server 端 _download_file 白名单段形一致

@dataclass
class MessageArtifactRegistry:
    store_path: Optional[Path] = None
    by_message: dict[str, list[ArtifactRef]] = field(default_factory=dict)
    pending: dict[tuple[str, str], str] = field(default_factory=dict)
```

两张表语义清晰：

- **`pending: (task_id, name) → message_id`** —— 流水线缓存。`transport_bridge` 在
  `task_write_artifact` `tool_start` 时 `record_pending`；`ArtifactDetector.detect`
  在 emit envelope 前 `consume_pending` 取 + 删。命不中 → 用户上传 / 跨周期遗留 /
  茶客绕开（目前路径上不存在），envelope 不挂 `originated_message_id`，前端走系统
  气泡兜底。
- **`by_message: message_id → [ArtifactRef]`** —— 加载快照。`__post_init__` 读
  `message_artifacts.jsonl` 重建；`persist` 增量追加。`emit_room_history` 按 message_id
  投影给前端。

### 2.3 落盘：`rooms/<id>/message_artifacts.jsonl`

形态：

```jsonl
{"message_id":"msg_abcd","task_id":"task_123","name":"diagram.png","size":15234}
{"message_id":"msg_efgh","task_id":"task_123","name":"report.md","size":2120}
```

口径与 `transcript.jsonl` / `summary.jsonl` 一致：

- **append-only + 加载跳坏行**：最后一行被截断时跳过、不阻断房间。
- **不 fsync**：单机闲聊 App，每条产物追加 fsync 不值得。
- **入站严格、落盘宽容**：加载时未知字段 warn 后忽略，必需字段缺才跳该条。

`reset_room` 时 `message_artifacts.clear()` 与 `transcript.clear()` 同步截断 —— 否则
`originated_message_id` 会指向已不存在的消息。**`/clear task` 走另一路径**（仅删
`tasks/<id>/artifacts/` 文件），**不动**注册表（这些 message_id 仍在 transcript 里
真实存在，挂件视觉上仍合理）。

### 2.4 装配

`session.py::build_room_session` 中段构造一份 registry，透传给：

```
session.py
  └─ MessageArtifactRegistry(store_path=room_dir/"message_artifacts.jsonl")
       ├─→ _build_guests(..., message_artifacts=registry)
       │     └─ TeaGuest(..., message_artifacts=registry)
       │          └─ ChahuaTransport(..., message_artifacts=registry)
       │               └─ _maybe_record_artifact_path() 调 record_pending
       ├─→ Orchestrator(..., message_artifacts=registry)
       │     └─ ArtifactDetector(..., message_artifacts=registry)
       │          └─ detect() 调 consume_pending + persist
       └─→ RoomSession.message_artifacts （frozen 字段）
             └─ emit_room_history() 调 for_message(message_id)
```

构造参数全部 `Optional[MessageArtifactRegistry] = None` —— 老调用方（925 个测试中
用 `ChahuaTransport(room_id=..., guest_name=...)` 自构的）行为完全不变，仅装配时不带
该参数，detect 路径退化到 envelope 不带 `originated_message_id`，前端系统气泡兜底。

## 3. 协议变化：`task_artifact_added` 多一个可选字段

### 3.1 envelope 形态

**老形态**（不变）：

```json
{
  "type": "task_artifact_added",
  "data": {
    "task_id": "task_123",
    "name": "diagram.png",
    "size": 15234,
    "rel": "tasks/task_123/artifacts/diagram.png",
    "created_by": "guest"
  }
}
```

**新增可选字段**：`data.originated_message_id`，茶客经 `task_write_artifact` 写出
时挂上：

```json
{
  "type": "task_artifact_added",
  "data": {
    "task_id": "task_123",
    "name": "diagram.png",
    "size": 15234,
    "rel": "tasks/task_123/artifacts/diagram.png",
    "created_by": "guest",
    "originated_message_id": "msg_abcd"
  }
}
```

字段语义：「这个产物是消息 `msg_abcd` 流式期间产出的」。**只追加、不改既有字段**；
`schema_version` 不 bump。旧前端忽略未知字段，仍渲老系统气泡。

### 3.2 历史回放：`room_history.messages[i].originated_artifacts`

每条 message 投影时按 message_id 查 registry：

```python
# server_room_snapshot.py::emit_room_history
for m in msgs:
    record = m.to_jsonl_dict()
    refs = message_artifacts.for_message(m.message_id)
    if refs:
        record["originated_artifacts"] = [r.to_payload() for r in refs]
    history.append(record)
```

`ArtifactRef.to_payload()` = `{task_id, name, size, rel}`，与 `task_artifact_added.data`
的相关键同形 —— 前端可用同一个 `attachArtifactToBubble` 入口处理两路径。

空列表的消息**不写键**（与 `Message.to_jsonl_dict` 的 `task_id == None` 不写键同口径），
避免给绝大多数无产物消息塞空数组导致 envelope 膨胀。

## 4. `download_file` 加 purpose 字段

### 4.1 既有路径

`Inbound.DOWNLOAD_FILE {rel}` → server `_inbound_download_file` → 读盘 + base64 →
`FILE_DOWNLOAD {rel, name, size, content_b64}` → 前端 `triggerDownload(Blob)` 强制
`a.download`。

### 4.2 问题

图片预览不能走它 —— 否则用户每渲染一张图，浏览器都被塞一个文件下载。

### 4.3 改动：可选 `purpose` 字段，原样回声

```python
# server_inbound_io.py
async def _inbound_download_file(self, data: dict, sink: EnvelopeSink) -> None:
    raw_rel = data.get("rel")
    rel = raw_rel if isinstance(raw_rel, str) else ""
    raw_purpose = data.get("purpose", "download")
    purpose = raw_purpose if isinstance(raw_purpose, str) and raw_purpose else "download"
    self._download_file(rel=rel, sink=sink, purpose=purpose)
```

server 端读盘逻辑对 `purpose` 取值无差异 —— 仅做 envelope 回声。**无白名单校验**：未知
字符串原样传出，前端按 `purpose === "preview"` 单分支判断，其它一律走 download 兜底。
与「envelope 协议层零硬校验、前端按值分流」同口径。

### 4.4 `_fail_download` 同步带 purpose

失败路径也带 `purpose` 回声 —— preview 路径上的「图占位失败」不应弹下载 alert。
前端 `resolveArtifactPreview` 收到 `{error}` 时把 `<figure>` 标 `.artifact-image-error`
+ 把错误塞进 `<img>.alt`。

## 5. Mermaid 渲染（懒加载）

### 5.1 触发条件

茶客气泡内的 markdown 输出经 `marked.parse` → DOMPurify → `innerHTML`。代码块
` ```mermaid ` 落地为 `<pre><code class="language-mermaid">...</code></pre>`。
`renderMermaidIn(container)` 扫该 selector，命中即触发渲染：

- **唯一入口三处**：`renderGuestText`（history 重放 / appendBubble 全文）、
  `endStreamingMessage` ok 路径 / selection finalize 路径（流式终点）、
  `task_panel.js` 任务卡 goal 渲染（任务面板里也能画 mermaid）。
- **流式 delta 期间禁调** —— 半截的 `graph TD\n  A -->` 会让 mermaid 抛 parse error
  闪烁刷屏。

### 5.2 懒加载

```js
let mermaidPromise = null;
function loadMermaid() {
  if (mermaidPromise) return mermaidPromise;
  mermaidPromise = import("../node_modules/mermaid/dist/mermaid.esm.mjs")
    .then((mod) => { ... m.initialize({ startOnLoad: false, theme: "neutral", securityLevel: "strict" }); return m; })
    .catch((err) => { mermaidPromise = null; throw err; });  // 允许下次重试
  return mermaidPromise;
}
```

- mermaid 解包后约 3MB JS，不用就别 parse —— 第一次撞到 ` ```mermaid ` 块才动态 import，
  之后缓存 Promise 复用。
- 失败一次后清掉 `mermaidPromise` 允许下条消息重试，避免首次网络 / 磁盘瞬时抖动让整
  session 都没图。
- `startOnLoad=false` 不让 mermaid 全页扫 `.mermaid` 类（避免它跟我们的 DOM 抢节点）。
- `securityLevel=strict` 禁 mermaid 配置里的 click 回调跑用户 JS、禁远程 mermaid
  config 加载。
- `theme=neutral` 配茶话室米色 / 浅灰背景。

### 5.3 SVG sanitize：手工剥 + 多层兜底

mermaid render 返 SVG 字符串。DOMPurify 对 `<foreignObject>` 是「safe-by-default 强制
清空内容」—— 而 mermaid v11 节点 label 强制走 `<foreignObject>+HTML`，过 DOMPurify 后
节点文字全没（边 label 因走 `<text>` 幸存）。**手工 sanitize 是唯一保得住 label 的路**：

- 删所有 `<script>`（无论命名空间）。
- 全树清 `on*` 事件属性 + `href` / `xlink:href` / `src` 里的 `javascript:` URL。

安全语义靠多层兜底，**不**靠这一道独撑：

| 层 | 起的作用 |
|---|---|
| mermaid `securityLevel:'strict'` 内部 sanitize | 节点文字本身已被 mermaid 自带 DOMPurify 过滤过 script/on* |
| Electron CSP `script-src 'self'` | 禁所有 inline script 与远程脚本；即使有 `<script>` 漏到 DOM 也跑不起来 |
| 手工 sanitize（这一道） | 补 attribute 级的 on* / javascript: URL（CSP 不管这两个） |

### 5.4 解析路径

SVG 用 `DOMParser('text/html')` parse 而非 `'image/svg+xml'`：

- HTML5 spec 对 `<svg>` 内嵌的 `<foreignObject>` 有特别处理（"foreign content"），切回
  HTML 解析上下文 → foreignObject 子树元素自动归 HTML 命名空间、`<br>` 这种 void
  element 合法（mermaid 在 foreignObject 里就用 `<br>` 做换行）。`'image/svg+xml'`
  严格 XML 模式遇 `<br>` 直接报 mismatch。
- detached document 不加载资源（`<img src>` 不发请求）、不跑脚本。sanitize 跑完才
  `importNode` 进主文档 —— 中间步骤无副作用窗口。

### 5.5 `<pre>` → `<div class="mermaid-rendered">`

成功 → `pre.replaceWith(host)`。失败 → 保留原 `<pre>` + 加 `.mermaid-error` class +
`dataset.mermaidError`，CSS `::before` 把错误显示在源码上方红边框里。

`pre.dataset.mermaidRendered = "1"` 排重：

- 多次进入同一 container 不重启渲染。
- 成功后 pre 已被 replaceWith，下次 `querySelectorAll` 自然找不到。

## 6. 前端：`attachArtifactToBubble`

### 6.1 入口

```js
export function attachArtifactToBubble(bubble, artifact, callbacks) {
  // artifact = {name, rel, size, task_id}
  // callbacks = {onRequestPreview(rel), onRequestDownload(rel)}
  if (shouldRenderInline(artifact.name)) {
    host.appendChild(buildImageNode(artifact, callbacks));
  } else {
    host.appendChild(buildDownloadPill(artifact, callbacks));
  }
}
```

挂在气泡末尾的 `.artifact-attachments` 容器（多个挂件横排）。同 rel 已挂 → 静默跳
（防 live + history 双触发：切回房瞬间 history 重放 + 末尾 live envelope 可能撞同一条）。

### 6.2 图片白名单 + 懒加载（B=纯懒）

```js
const IMAGE_PREVIEW_EXTENSIONS = new Set(["png", "jpg", "jpeg", "gif", "webp"]);
```

`buildImageNode`：

- 创建 `<figure class="artifact-image">` + `<img loading="lazy">` 占位 +
  `<figcaption>{name}</figcaption>`。
- 入队 `pendingPreview.set(rel, [img, ...])`。
- 调 `callbacks.onRequestPreview(rel)` → 前端发 `download_file purpose=preview`
  inbound。

服务端回 `file_download envelope {rel, content_b64, name, purpose:"preview"}` 时
`envelope_router` 调 `resolveArtifactPreview`：

- 查 `pendingPreview.get(rel)`，遍历所有等待中的 `<img>`（同 rel 可能挂多份），按扩展名
  推 mime（png/gif/webp/jpeg）拼 `data:` URL 填 `img.src`。
- 返 `true` → envelope_router 跳 a.download 兜底；返 `false` → 无等待者（用户切走 / 节点
  已 clear），按 download 兜底处理。

点击图片 → `onRequestDownload(rel)` → 浏览器原生下载（用户想保存原图）。

### 6.3 SVG / 其它扩展：pill 下载链（C=保守）

`buildDownloadPill`：

- `<button class="artifact-pill">` 含 `📄 + name + size`，点击触发
  `onRequestDownload(rel)` → 走既有 `download_file purpose=download` 路径，触发
  `a.download`。
- **SVG 强制走这条路径** —— SVG 可内嵌 `<script>`，`<img src="data:image/svg+xml;base64,...">`
  虽然 image context 禁脚本执行，但仍有 CVE 历史。保守做法：不内嵌预览，pill 下载，
  让用户用系统应用打开。

### 6.4 切房 / clear 时清 pending

`pendingPreview` 是模块级 Map。`renderSidebar` 切房 / 清空时
`clearPendingArtifactPreviews()` —— 那些 `<img>` 节点已被 `messagesEl.replaceChildren`
摘走，preview 字节回包来了也无处灌，Map 不清会持续涨。

## 7. envelope 分派 + 历史回放

### 7.1 live：`TASK_ARTIFACT_ADDED` 分流

```js
case EventType.TASK_ARTIFACT_ADDED: {
  const data = env.data ?? {};
  taskPanel.flashHint(env.type, data);  // 面板增量闪烁不变
  const originated = data.originated_message_id;
  if (originated && attachArtifactByMessageId) {
    const ok = attachArtifactByMessageId(originated, {
      name: data.name, rel: data.rel, size: data.size, task_id: data.task_id,
    });
    if (ok) return;  // 命中：不再追居中系统气泡
  }
  // 兜底：用户上传 / 跨周期遗留 / 流式失败丢锚 → 老系统气泡路径
  const text = formatTaskEventNotice(env.type, data);
  if (text) appendBubble({ kind: "system", text });
}
```

`attachArtifactByMessageId(messageId, artifact)` 双查：

1. `inFlight.get(messageId)` —— 流式期间 ChatStream 持引用。
2. `messagesEl.querySelector('li[data-message-id="<...>"]')` —— 流式结束后从 DOM 查。

找到 → `attachArtifactToBubble(bubble, artifact, artifactCallbacks)` 返 true；
找不到 → 返 false，调用方走老系统气泡兜底。

### 7.2 history：每条 message 投影 `originated_artifacts`

`chat_stream.js::renderHistory`：

```js
for (const m of messages) {
  // ... 渲染气泡 ...
  const refs = Array.isArray(m.originated_artifacts) ? m.originated_artifacts : [];
  if (bubble && refs.length > 0) {
    for (const r of refs) attachArtifactToBubble(bubble, r, artifactCallbacks);
  }
}
```

每条独立 `attachArtifactToBubble`、内部按 rel 去重避免双触发（live + history 在切回房
瞬间可能撞同一条）。

### 7.3 不双重提示

命中 `originated_message_id` 时**不**追居中系统气泡 —— 否则用户会看到
「📎 茶客产出：diagram.png」与气泡末尾的内嵌图片并存，重复且割裂。命不中才走系统
气泡兜底。

### 7.4 用户上传仍走系统气泡

用户经 UI `attach_artifact` 上传不经 `task_write_artifact` 工具 → `pending` 无条目 →
detect emit envelope 无 `originated_message_id` → 前端走系统气泡
「📎 用户挂载产物：…」。这是有意为之：用户上传没有"气泡"锚点（用户消息已发完 / 上传
是独立 UI 动作），挂到任意气泡反而误导。

## 8. 不变量增量

CLAUDE.md「关键不变量」节新增以下条目（落到「任务房间」与「事件契约」附近）：

### 任务房间 / artifact 关联

- **`message_artifacts.jsonl` 与 transcript 同生命周期**。`MessageArtifactRegistry`
  per-room、与 `transcript.jsonl` 同位（`rooms/<id>/`）；`reset_room` 同步 clear。
  `/clear task` **不**清注册表（artifact 文件被删但 message_id 仍真实存在于 transcript，
  挂件视觉无害）。
- **`task_artifact_added.data.originated_message_id` 仅由 `task_write_artifact` 工具
  调用路径派生**。`transport_bridge._maybe_record_artifact_path` 是唯一写入点；
  `ArtifactDetector.detect` 是唯一消费点（`consume_pending` 取出 + 持久化）。
  用户上传 / 跨周期遗留 → 字段缺省，前端系统气泡兜底（不变量「artifact 派生表显式
  枚举」同口径，与 P6.1 debug_recorder 派生一致）。
- **`originated_message_id` 是可选字段，envelope schema 不动**。`task_artifact_added`
  既有字段全部保留；新字段缺省（无值）时旧前端忽略未知字段，仍渲老系统气泡 ——
  `schema_version` 不 bump。
- **历史回放投影空列表不写键**。`emit_room_history` 按 message_id 查 registry，空 →
  不写 `originated_artifacts`（同 `task_id == None` 不写键口径），避免给无产物消息塞
  空数组导致 envelope 膨胀。

### 事件契约 / download_file 分流

- **`download_file.purpose` 仅前端分流，server 行为对取值无差异**。inbound 可选
  `purpose ∈ {download, preview}`（默认 download），envelope `file_download` 原样回声；
  无白名单 / 未知字符串原样穿透，前端按 `purpose === "preview"` 单分支判断、其它一律
  按 download 兜底（与「envelope 协议层零硬校验、前端按值分流」同口径）。
- **preview 路径失败也带 purpose 回声**。`_fail_download` 同步带 purpose —— preview
  路径上的「图占位失败」不应弹下载 alert，前端 `resolveArtifactPreview` 把错误塞
  `<img>.alt` + `.artifact-image-error` class。

### 前端 mermaid 渲染

- **mermaid 渲染只在 message_end 全文到位时调一次**。流式 delta 期间禁调 —— 半截
  ` ```mermaid graph TD; A --> ` 会让 mermaid 抛 parse error 闪烁刷屏。`renderMermaidIn`
  入口收敛于 `renderGuestText`（history / appendBubble）/ `endStreamingMessage` 全文
  路径 / `task_panel` goal —— 流式 `appendDelta` 路径不调。
- **mermaid 渲染失败不阻断气泡**。失败保留原 `<pre>` + `.mermaid-error` class +
  `dataset.mermaidError`，CSS `::before` 红边显示错误；下条消息仍可渲。
- **mermaid SVG 走手工 sanitize，不能换 DOMPurify**。DOMPurify 对 `<foreignObject>`
  强制清空内容，mermaid v11 节点 label 走 `<foreignObject>+HTML` 会被剥光。安全语义
  靠 mermaid 自带 sanitize + Electron CSP + 手工剥 on*/javascript: 三层兜底。

### 前端 artifact 挂件

- **挂件渲染按 rel 去重**。`attachArtifactToBubble` 按 `[data-rel="..."]` 查重，
  防 live + history 双触发（切回房瞬间可能 history 重放 + 末尾 live envelope 撞同
  rel）。
- **图片预览懒拉、不 eager 内嵌**。`task_artifact_added` envelope 不带 base64；前端
  渲占位 `<img>` 后发 `download_file purpose=preview`，server 回包后 `resolveArtifactPreview`
  灌字节。同 rel 可能挂多份（用户上传后茶客再写同名），回包一次性填所有等待者。
- **SVG 走 pill 下载链、不内嵌预览**。SVG 可内嵌 `<script>`，保守不渲。其它图片白名单
  `{png, jpg, jpeg, gif, webp}` 走内嵌。
- **切房 / clear 必清 pending preview**。`renderSidebar` 调 `clearPendingArtifactPreviews()`
  —— 否则 messagesEl.replaceChildren 后等待中的 `<img>` 节点已被摘走，preview 字节
  回包无处灌，pending Map 持续涨。

## 11. 已知边角 / 推后

- **同名覆写不重新挂件**：茶客在消息 A 写 `foo.png` → 消息 A 渲挂件；消息 B 再写
  同名 `foo.png` → `record_pending` 覆盖 (task_id, name) 的 message_id 为 B，但
  `ArtifactDetector.detect` 用 `new_names = current - prev` diff，第二次 `foo.png`
  已在 `prev` 中、不 emit envelope —— 消息 B 的气泡不会渲挂件。fix 需要 detect
  额外感知 mtime / hash 才能识别"同名内容已变"。MVP 视为可接受。
- **mark_seen 误绑**：用户上传 `attach_artifact` 后调 `mark_seen(task_id, name)`
  增量 add 到 `seen`，**不**经 `pending`，envelope 不带 `originated_message_id`，前端
  系统气泡兜底 —— 行为正确，但用户上传 hint 与茶客产出 hint 共用 envelope 类型，靠
  `created_by` 字段区分文案。
- **流式失败的气泡挂件**：茶客写盘后 message 在 message_end 前被 cancel / error，
  detect 仍会 emit `task_artifact_added{originated_message_id=失败消息}`。前端找到的
  气泡带 `.error` class，挂件外观正常 —— 用户能下载到那个写过的文件。可接受。
- **真正 push 推送图片字节（"无 round-trip"）**：留作 follow-up。当前懒拉的延迟在
  Electron 内 ws 上可忽略。
