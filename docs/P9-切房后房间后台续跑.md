# P9：切房后房间后台续跑 —— 多 RoomRuntime 与可变路由 sink

> 目标：用户切换房间后，**原房间的 Session 不再被 cancel 丢弃**，正在跑的 turn /
> handoff drain / 托管任务会话（MTS）在后台继续执行到自然完成。切房从「cancel + 替换
> + 关旧房」改为「**仅切前台指针 + 重发快照**」。
>
> P9 是**进程内运行态层的增量**，核心三件事：① server 从「持 1 个 `self._session`」
> 升级为「持多个 `RoomRuntime` 的注册表 + 一个前台指针」；② 引入 **per-room 可变路由
> sink（`RoomEventRouter`）**，解决「sink 是顺调用栈透传的参数、in-flight turn 无法中途
> 换 sink」这个最硬的卡点；③ 后台 runtime「仅在真有 in-flight 活时存在」，turn 跑完即
> 自毁，资源天然有界。**不改对话原语、不改 Task / handoff / MTS 数据结构、不引入跨重启
> 持久化、不新开调度路径。**

**状态：方案研究（草案，未落地）—— 2026-05-21**。上游契约见
[`P7-显式 handoff 与 delegation.md`](P7-显式%20handoff%20与%20delegation.md)（drain loop /
`HandoffItem` / `_run_handoff_turn` wrapper）、
[`P8.3-原生自动推进.md`](P8.3-原生自动推进.md)（MTS / `ManagedSession` / 「断线即结束
MTS」「切房 `_replace_session` 显式 `end_managed_session`」—— 这两条不变量将被 P9 重写）。

## 0. 本阶段做 / 不做

**做**：

- 新增 `RoomRuntime`（封装 `session` + `router` + in-flight 槽）与
  `RoomEventRouter`（per-room 可变路由 sink），见 §2。
- server `self._session` → `self._runtimes: dict[room_id, RoomRuntime]` 注册表 +
  `self._foreground_id` 前台指针，见 §2.2。
- `_switch_room` 重写：切走的房间若 busy 转后台续跑、若 idle 仍 close；不再 cancel，见 §3。
- 后台房间事件里程碑过滤（精确白名单 `turn_start` / `turn_end` / `message_end` /
  `task_info` / `task_artifact_added` / `managed_session_*` / `room_background_finished`
  放行，流式 delta 丢弃），见 §4。
- 后台 turn 跑完自毁 + `room_background_finished` 里程碑事件，见 §5。
- `_serve_one` finally / `ChahuaServer.aclose()` 遍历所有 runtime 清理，见 §5。
- `max_background_rooms` 软上限 + 超限策略，见 §5。
- 前端按 `room_id` 分流 envelope + 房间列表「进行中」徽标，见 §4。

**不做（推后 / 收敛）**：

- **不**做跨 app 重启续跑 —— handoff 队列 / MTS 是声明的瞬态、不落盘（§9）。
- **不**做跨 ws 断连续跑 —— ws 真正断开仍清理全部 runtime（§9）。
- **不**做后台房间逐字流式 —— 后台只推里程碑（§4）。
- **不**做 `cancel_room {room_id}`（取消指定后台房）—— 列为后续增强（§7）。
- **不**改 `orchestrator.py` 调度逻辑、**不**改 `RoomSession` 结构、**不**改
  `handoff_tools.py` / `proposal_card.js` / `TeaGuest.speak()` 签名。
- **不**新增 envelope 类型以外的线协议改动、**不** bump `schema_version`。

## 1. 现状：为什么现在做不到

切房当前是「cancel + 替换 + 丢弃」：`_inbound_switch_room` 先
`await _cancel_and_drain_inflight()` 强杀在跑的 turn，`_switch_room` → `_replace_session`
直接 `old.close()` 关掉旧房所有茶客。四个硬约束：

| 约束 | 位置 | 后果 |
|---|---|---|
| server 单 session | `server.py` `self._session`，`_replace_session` 原子替换后 `old.close()` | 切房即关旧房茶客 |
| 单 in-flight 槽 | `server.py` `_inflight_turn_task` / `_inflight_kind`（一对耦合槽）| 同时只能有一个 turn 在跑 |
| **sink 是调用栈参数** | `submit_user_message(sink=...)` → `_run_ai_chain` → `_let_speak` → `guest.speak` → `transport.bind(sink=...)` 逐级透传 | 一个已在跑的 turn，sink 已被它的调用栈捕获；想把它的事件改投到别处，**无法中途换** |
| 切房显式 cancel | `_inbound_switch_room` 先 `await _cancel_and_drain_inflight()` | 旧房 turn / handoff drain / MTS 全被 cancel 丢弃 |

第三条是关键卡点。哪怕解决了多 session，只要 sink 还是栈参数，后台 turn 的事件就只能投给
「它启动时那个 ws sink」—— 切房后没法改路由。

**落盘天然独立于 sink**：`transcript.jsonl`（`room.append` 同步写）、
`debug/turns.jsonl`（`flush_turn` 同步写）、`tasks/<id>/artifacts/`（`write_artifact`
同步写）都不经 sink。所以后台 turn 的**数据完整性天然成立**，P9 的问题纯粹是「进程内
session 别被关掉」+「事件往哪推」。

## 2. 核心设计：三个新概念

### 2.1 `RoomRuntime` —— 把「一个房间的运行态」打包

新对象封装当前散落在 server 上的 per-room 状态：

```
RoomRuntime:
    room_id: str
    session: RoomSession             # 现有装配产物，保持 frozen 不动
    router:  RoomEventRouter         # 见 §2.3
    inflight_task: Optional[asyncio.Task]
    inflight_kind: Optional["user" | "handoff"]
    background_since_ms: Optional[int]  # 转入后台的时间戳，超限淘汰用，见 §5.3
```

`_inflight_alive` / `_set_inflight` / `_cancel_inflight` / `_cancel_and_drain_inflight`
从 server 方法降级为 `RoomRuntime` 方法。`_run_turn` / `_run_handoff_turn` 包装器改为
「针对某个 runtime」执行。`RoomSession` 本身仍 `frozen=True` 不动 ——`RoomRuntime`
在它外面包一层。

### 2.2 server：多 runtime 注册表 + 前台指针

```
self._runtimes: dict[str, RoomRuntime]   # 所有活着的房间（前台 1 + 后台 N）
self._foreground_id: str                  # ws 当前正在看的房间
```

`self._session` 的所有读点改为 `self._foreground_runtime.session`（可留一个 property
兼容旧调用）。

**关键不变量**：一个 room_id 在注册表里最多 1 个 `RoomRuntime` —— 不允许同一房间
「前台一份 + 后台一份」并存。

### 2.3 `RoomEventRouter` —— 可变路由 sink（本方案的支点）

解决「sink 是栈参数」的办法：**不让 turn 直接拿 ws sink，让它拿一个稳定的 per-room
路由器对象**。

```
RoomEventRouter:
    mode: "foreground" | "background"
    ws_sink: EnvelopeSink            # 当前 ws 连接的真实 sink（连接级）
    __call__(env):                   # 它本身就是一个 EnvelopeSink
        if mode == foreground:  ws_sink(env)                  # 全量透传
        else:                   若 env.type 在后台白名单：ws_sink(env)   # 见 §4
```

- turn 启动时传的 sink 永远是 `runtime.router`（一个稳定对象），不是裸 ws sink。
- 切房 = 把旧 router `mode` 切 `background`、新 router 切 `foreground`。**in-flight
  turn 调用栈里捕获的还是同一个 router 对象**，它的 `mode` 变了，事件路由就自动跟着
  变 —— 无需触碰运行中的 turn。
- 单房间场景下 router 永远 `foreground` = 全量透传，行为与今天**完全一致**（低风险）。

> 区分两类 emit：orchestrator 的 turn 事件走 `runtime.router`；而
> `_emit_room_snapshot` / `_emit_notice` 这类**控制面**事件，由 server 直接用 ws sink
> 发给前台，不走 router。

## 3. 切房新流程

`_inbound_switch_room` 不再 `await _cancel_and_drain_inflight()`。`_switch_room` 重写：

**两阶段顺序（切房失败原子性）**：必须先把目标 runtime 准备好、确认成功，再去动旧
前台。否则若目标房目录不存在 / `build_room_session` 失败 / LLM 凭据缺失，旧前台已被
close 或切 background，用户既到不了新房、也回不到原房。

```
_switch_room(room_id):
  1. room_id == foreground → noop（不变）
  ─ 阶段一：准备目标 runtime（可失败，失败即整体放弃，不碰旧前台）
  2. 目标房间：
       - 已在注册表（之前切走时留下的后台 runtime）→ 复用
       - 不在 → build_room_session 装配新 runtime
       - build 失败（目录不存在 / LLM 凭据缺失等）→ emit NOTICE error，
         _switch_room 直接 return；旧前台原样保持，切房未发生
  ─ 阶段二：目标已就绪，再 demote/close 旧前台
  3. 旧前台 runtime：
       - 若 idle（无 in-flight task）→ close，从注册表移除   ← 等价今天的行为，零开销
       - 若 busy → router.mode = background，留在注册表（后台续跑）
  4. 目标 runtime.router.mode = foreground；self._foreground_id = room_id  ← 一次性切换
  5. _emit_room_snapshot(ws_sink)   # room_info + room_history + task_info（+ MTS 快照，见 §8）
```

要点：

- **切房失败原子性**：阶段一在前、阶段二在后 —— 任何准备失败都在「未碰旧前台」时就
  return，旧前台 runtime / `_foreground_id` 一字未动，用户停在原房。
- **切走 idle 房间仍然 close** —— 后台 runtime「仅在真有活时存在」，闲房不留，资源天然
  有界（见 §5）。
- **room_history 从盘上重建**：切回一个后台房间时，它的 `transcript.jsonl` 已被后台
  turn 实时写进去，快照天然反映后台进度。
- **切回后的流式契约（不是「逐字无缝」）**：切回重发快照后 router 转 `foreground`。若
  切回瞬间后台正有一条 message「已 `message_start`、未 `message_end`」—— 它的
  `message_start` 在后台已被丢弃（§4），前端没有对应的 in-flight 气泡，中途到的
  `message_delta` 会被忽略。契约：**这条进行中的 message 允许只在 `message_end` 一次性
  补齐全文**（前端按 `message_end` 直接渲染完整气泡）；**从下一条 `message_start` 起
  恢复正常逐字流式**。即「切回那一刻正在打字的那条不流式、其后的流式」。
- 切房**不再 cancel**，切房延迟从「等 turn 收尾」降为「装配/快照」，长 turn 期间点切房
  不再卡（顺带修了 `_switch_room` docstring 里吐槽的 UX 问题）。

**与同房重建分流**：加/删茶客、改 LLM/权限/trust 走的是**同房 `_replace_session`
重建** —— 这种情况必须先 `_cancel_and_drain_inflight`（不能在运行的 turn 下重建
session）。P9 只改「切到不同房间」这一条路径，同房重建路径保持 cancel 语义不动。

## 4. 事件路由：前台全量 / 后台里程碑

后台房间若把 `message_delta` / `guest_thinking` / `tool_*` 全量推给 ws，多房并发时 ws
流量与前端负担都炸。`RoomEventRouter` 后台模式只放行**里程碑事件**：

| 事件 | 后台是否推送 | 用途 |
|---|---|---|
| `turn_start` / `turn_end` | ✅ | 房间列表「进行中」徽标、知道何时空闲 |
| `message_end` | ✅ | 后台又产出一条发言（徽标计数 / 提示）|
| `task_info` / `task_artifact_added` | ✅ | 后台任务产物变化 |
| `managed_session_*` | ✅ | 后台 MTS 推进 / 结束 |
| `room_background_finished` | ✅ | 后台 runtime 自毁通知（见 §5）|
| `message_start` / `message_delta` / `guest_thinking` / `tool_*` | ❌ 丢弃 | 高频流式，后台不需逐字 |

后台房间的发言**内容**不靠这些事件 —— 靠切回时的 `room_history` 快照（从盘重建，完整
无损）。前端对后台房间只需维护「忙/闲 + 徽标」，不需后台 DOM。

**前端配合（必须改）**：今天前端默认「收到的 envelope 都属于当前房间」。P9 下
envelope 的 `room_id` 字段（envelope 本就带）成为路由依据 —— 前端收帧先按 `room_id`
分流，非前台房间只更新房间列表徽标。这是前端侧的主要工作量。

> 备选方案：router 后台也全量透传，前端做完整 per-room buffer。服务端更简单，但前端
> 复杂度与 ws 流量都更高。**P9 采用上面的「里程碑过滤」**。

## 5. 生命周期与资源边界

### 5.1 后台 runtime 何时关闭

- **切走时 idle → 立即 close**（§3 第 2 步）。
- **后台 turn 跑完 → 自动 close**：`_run_turn` / `_run_handoff_turn` 的 `finally` 加
  判断 —— 若该 runtime 仍是 `background` 且已 idle（in-flight 槽空、handoff 队列空、无
  MTS），则 emit `room_background_finished` 里程碑、再 close + 移出注册表。
- **进程退出 / ws 断开**：清理必须**遍历整个 `_runtimes`**（今天只处理 `self._session`
  一个 —— 必改点，否则后台房间泄漏）。但 cancel+drain 是 async（要 `await` drain），而
  当前 `ChahuaServer.close()` 是**同步**方法、`server_entry.py` 也同步调用 —— 不能在
  sync `close()` 里 `await`。落地契约：
  - `_serve_one` 的 `finally`（async 上下文）对所有 runtime 做 async
    cancel+drain+close —— 这是正常退出路径。
  - 进程退出新增 `async def aclose()`（遍历所有 runtime 做同样 async 清理），退出流程
    `await server.aclose()`；同步 `close()` 退化为兜底（仅同步 `session.close()`、不
    drain）或直接废弃。
  - **清理必须幂等**：`_serve_one` finally 与 `server_entry.py` 进程退出
    `aclose()` 都会清理全部 runtime —— 退出时可能先断线清一次、再 finally 清一次。
    每个 runtime 清完即从 `_runtimes` 移除，且重复 cancel/close 同一 runtime 不得
    报错（task 已 done 的 cancel、已 close 的 session 再 close 都静默放过）。不需新
    机制，纯实现约束。

### 5.2 切回竞态

用户正好在后台 turn 收尾瞬间切回该房：切回时先把 `mode` 翻成 `foreground`，
`_run_turn` 的 `finally` 里判 `mode == background` 才自毁。翻转与判定都在事件循环单线程
内，「先翻 mode 再走收尾」的顺序即可保证正确，无需锁。需要一条回归测专门覆盖。

### 5.3 资源上界

由于「后台 runtime 仅在有 in-flight 活时存在」，并发 session 数 = 1 前台 + N 个真正在跑
的后台，N 自然不大。加软上限 `max_background_rooms`（server 级常量，**默认 5**）。超限
时切房：**取消最早转入后台的 runtime + emit NOTICE 提示**。

> 取值理由：后台 runtime 闲时无 LLM 调用、只占进程内 agentao 实例的内存，5 个并发对
> 桌面 App 足够宽松又不至于失控；它是软上限、超限即淘汰最早项而非拒绝切房，所以宁可
> 定得稍大。后续要调直接改常量。

「最早」的判定**不做 LRU**，用最小状态：`RoomRuntime` 加一个 `background_since_ms`
字段，每次「转入后台」（§3 阶段二 demote）时写当前时间戳；超限时取
`background_since_ms` 最小者取消。等价做法：`_runtimes` 用 dict，每次转后台时把该项
pop 再 put 回末尾，靠 dict 插入顺序定序。二选一即可，不引入额外 LRU 数据结构。

LLM 并发：两房同时跑 turn = 对 provider 的并发请求翻倍，注意 rate limit；各 session 的
LLM client 独立装配（`build_room_session` 内 `clients_by_spec`），互不串扰。

### 5.4 后台 MTS（托管任务会话）

「未完成的任务后台续跑」最有价值的场景就是 **MTS** —— 它本就是带 budget、自驱
delegate 循环的长任务。MTS 在后台续跑是 P9 的核心收益。代价是要重写 P8.3 的若干不变量
（见 §8）。逐条说明后台 MTS 的行为：

**正常路径（大部分天然成立）**：MTS 跑在 handoff drain loop 上，drain loop 就是那个
in-flight task。切走该房时它 busy → 按 §3 转 `background`、不被 close。于是：

- drain loop 继续：worker 回合、管理者复查回合、`budget--`，直到 `budget_exhausted` /
  `task_closed` / `cap_reached` / `manager_finished` 自然收尾。
- `_intercept_task_proposal` hook（管理者 `delegate` / `panel` 提议自动入队）挂在
  orchestrator 内部、不依赖 sink → **后台照常自动入队**。
- `managed_session_advanced` / `managed_session_ended` 在 §4 后台白名单内 → 仍推给
  ws，前端能给该房徽标显示「托管推进中 / 已结束」。
- MTS 收尾后 drain task 结束 → runtime idle → 自毁 + `room_background_finished`。

**收尾会先后来两帧事件**：MTS 结束发 `managed_session_ended`，紧接着 runtime 自毁发
`room_background_finished`。前端要能区分二者 ——前者「托管任务结束」、后者「后台
runtime 已回收」。

**强制拆除路径必须保住「MTS 存活 ⟺ drain task 在跑」**：P8.3 承重不变量是绝不能出现
「`_managed_session` 对象还在、drain task 已被 cancel」的死调度。P9 下每条强制拆除路径
（ws 断开 / 进程退出遍历清理、`max_background_rooms` 超限取消最早后台房、删除房间）
**都必须先 `end_managed_session` 再 cancel drain，顺序不能反**。`end_managed_session`
会一并清空 `_handoff_queue` —— 保证拆除后不会多跑一个已入队的 worker。

**停止后台 MTS 的入口限制**：`managed_session_stop` inbound 当前白名单 `{type}` 不带
`room_id`，只能停**前台**房间的 MTS。要停后台房的 MTS，用户得先切回去再停。v1 接受此
限制；若前端要在后台房徽标上直接放「停止托管」按钮，需给 `managed_session_stop` 加
`room_id` —— 与 §7 推后的 `cancel_room {room_id}` 同属「房间定址 inbound」，建议一起做。

**资源**：budget 与前台/后台无关，后台 MTS 正常烧预算 + LLM 配额 —— 这正是「自主任务」
的预期用法，但意味着用户不盯着也在花钱。`max_background_rooms`（§5.3）是并发数护栏，
`max_consecutive_ai_turns` 仍是每 orchestrator 的硬护栏。P9 下多个后台房可各自跑 MTS，
互相独立。

## 6. 模块改动清单

| 文件 | 改动 |

## 7. 边界情况

- **切走→切回，turn 仍在跑**：router 转 `foreground`，快照给中间态；切回那一刻正在
  打字的 message 按 §3 流式契约在 `message_end` 一次性补齐，其后的 message 恢复逐字流式。
- **后台 turn 报错**：`_run_turn` 已 swallow + log；finally 自毁照走。
- **后台 MTS 耗尽 budget / 任务关闭**：`managed_session_ended` 作为里程碑推 ws；
  runtime 自毁。
- **`cancel` inbound**：仅作用于**前台** runtime。取消指定后台房需新增
  `cancel_room {room_id}` inbound —— 列为后续增强，P9 不做。
- **`clear_room`**：作用于前台房间（带 in-flight 时仍 cancel 该房）。
- **删除某房间**：若该房有后台 runtime，先走同一强制拆除清理路径（带 MTS 先
  `end_managed_session` → cancel+drain → close，见 §8）再删目录。
- **同房间重复打开**：注册表 room_id 唯一性保证「同房不会前台 + 后台并存」。
- **加/删茶客、改 LLM/权限**：仍是**同房 `_replace_session` 重建**，必须先
  `_cancel_and_drain_inflight`，与切房的「不 cancel」分流（§3）。
- **ws 重连（app reload）**：P9 下 ws 断开仍清掉所有 runtime（含后台）。后台续跑只跨
  「房间切换」，不跨「ws 断连 / app 重启」—— 见 §9。
- **`max_background_rooms` 超限**：cancel 最早后台房 + NOTICE（§5.3）。

## 8. 对现有不变量的影响

落地时 `CLAUDE.md` 关键不变量节 + `docs/DESIGN.md §9` 两处同步。会被 P9 推翻或修订的：

- **「断线即结束 MTS」**（CLAUDE.md「托管任务会话（MTS）」节）：需重表述。P9 下 MTS
  可后台续跑，其结束改由 budget / 任务态 / cap 决定，而非「切房」。**ws 真正断开**时仍
  结束（断线清理全部 runtime）。
- **`_replace_session` 里 `old.orchestrator.end_managed_session(...)`**：切房路径删除
  （改为后台续跑）；仅同房重建路径保留。
- **「`emit_room_snapshot` 不重投 MTS」（新推翻）**：该不变量的理由是「MTS 不跨断线
  存活」，P9 推翻了这个前提 —— MTS 现在能在后台续跑。后果：用户切回一个「托管中」的
  后台房间，`_switch_room` 的 `_emit_room_snapshot` 只发 `room_info` / `room_history` /
  `task_info`，**不发 MTS 状态**，前端「托管中」状态条 / 「停止托管」按钮无法重建。
  **要求**：扩展 `_emit_room_snapshot` —— 前台房间 orchestrator 若 `_managed_session
  is not None`，补发一帧 `managed_session_started`（或等价 MTS 快照）。让切回自给自足，
  不依赖前端按 `room_id` 缓存早先收过的 `managed_session_started`（后者脆弱：只在「MTS
  启动时恰好在前台」才成立）。
- **「MTS 存活 ⟺ drain task 在跑」的耦合不能破**（强化）：P9 新增的强制拆除路径
  （`_serve_one` finally / `ChahuaServer.aclose()` 遍历清理、`max_background_rooms`
  超限取消、删除房间）**必须先 `end_managed_session` 再 cancel drain**，绝不能留下
  「`_managed_session` 还在、drain 已 cancel」的死调度。§6 模块清单里 `aclose()` 的
  「遍历清理」要显式写明此顺序。
- **「MTS 单房间最多 1 个」**：升级为「每房间最多 1 个」，全局可有多个后台 MTS。
- **`_inflight_kind` 三态 + `_cancel_and_drain_inflight` 语义**：从 server 全局降为
  per-runtime。
- **server 测试夹具** `object.__new__(ChahuaServer)`：需补装 `_runtimes` /
  `_foreground_id`。

落盘类不变量（transcript 跳坏行、debug rotation、artifact 检测等）**不受影响** ——
它们本就 per-session、与 sink 无关。

## 11. 已拍板决策

以下四点曾是开放问题，现已收敛为下表决策，正文与 §12 commit checklist 均按此实现 ——
**落地阶段不再重开讨论**。括注里是被否决的备选，仅留作溯源。

1. **ws 真正断开（app 关闭/重启）时**：后台房间**立即全清**（与瞬态契约一致；否决
   「保留一段时间等重连」——需跨断线状态机，复杂度不值）。见 §9。
2. **后台房间事件粒度**：**里程碑精确白名单过滤**（前端轻、ws 流量低；否决「全量
   透传」——前端要做完整 per-room buffer）。见 §4。
3. **`max_background_rooms` 超限策略**：**取消 `background_since_ms` 最早的后台房 +
   NOTICE**（否决「拒绝切房」——用户切房意图不该被旧后台任务挡住）。见 §5.3。
4. **后台 turn 跑完后**：runtime **立即自毁**（资源有界、心智简单；否决「保留若干
   分钟便于快速切回」——引入计时回收、与「后台 runtime 仅在有活时存在」不一致）。
   见 §5.1。
