# P18：消息回溯与历史搜索导出 —— 对齐豆包的两个长期陪伴体验

> 来源：用户提出的两个「豆包式」体验诉求 ——（1）发错消息想**回溯/编辑**让茶客按新文本重生成；（2）长期聊很久，想**按关键词搜历史并跳转到那条**，以及**导出**。
>
> **本文档状态：M1（当前房搜索）+ 回溯（撤回未回复末条）已落地；M1.5 导出小补丁与 M2（全局/正则/跨房搜索）仍为设计。** §7 实施清单反映已落地范围。承重不变量随落地同步进 `CLAUDE.md`「关键不变量」段 + `docs/INVARIANTS.md`（§5 标「待锚定」的两条回溯不变量应在最终合并时落定）。
>
> **一句话定性：搜索/导出是「读」，顺着茶话室 append-only 群聊模型走，便宜；回溯/编辑是「回滚」，逆着走，贵 —— 而贵不在文件格式，在「N 个茶客各持一份烘死的私有记忆」这个群聊根因。**

## Summary —— 结论先行

- **两个需求成本天差地别，且难点定位常被误判**。搜索纯只读、不碰任何承重不变量；「有回复后再回溯」要同时回滚**五套状态**（见 §4.1），而它们现在只能被 `reset_room` 一起全清、无部分回退原语。
- **导出已可用**：`export_room` inbound → `ROOM_EXPORT` envelope → 整房 markdown 走浏览器 Blob 下载、不落盘（`exporter.py` / `server_inbound_io.py`）。用户真正的缺口是**搜索 + 跳转**，不是导出；过滤/元数据只算锦上添花。
- **搜索完全空白但廉价**：现设计刻意把全文检索外包给用户手动 grep jsonl。M1 只需一个只读 `search_room {query, limit?}`（当前房、大小写不敏感子串）+ 前端面板；跳转锚点现成（历史气泡带 `data-message-id`，且当前 `room_history` **一帧全量下发、全量渲染**，命中即在 DOM，跳转 = `scrollIntoView`）。单用户桌面规模线性扫足够，不需索引/分页/正则。全局/跨房/正则放 M2。
- **回溯的根因天花板 = agentao 只有 `clear_history()` 整窗清、没有「rewind 到某 seq」**。豆包是 1 对 1 线性对话（改消息 = 丢一条回复重生成）；茶话室是群聊，被改消息之后的回应已烘进每个响应茶客的私有 `agent.messages`，改盘上 transcript 不回改它们。
- **回溯收窄到唯一安全档**：只做**「撤回*尚无茶客回复*的最后一条用户消息」**。它之后没有任何茶客的 `cursor` / `agent.messages` 碰过 → **主状态只截 transcript 末条、不碰 cursor/记忆**；但 append 后已 `_kick_summarize()` + 空 turn 写过 debug，故**旁路（summary/debug）一致收尾是硬约束、非可选**。这是绕开天花板的唯一干净路径。「局部化 reset_room（有回复后回溯）」与「编辑任意历史消息」**一并明确搁置**。
- **建议三档**：M1 当前房搜索 → M1.5 导出小补丁（元数据/简单时间过滤）→ M2/回溯「撤回未回复的最后一条」；分页、全局搜索、正则、局部 reset 五态、有回复后重编辑全部推后，别把 P18 变成三件大事的合集。

## 1. 需求来源与豆包对照

用户的原始诉求，两点：

1. **回溯**：「你发送了一条信息，但你发现发错了想回溯，可以修改这句话让智能体再重新生成一遍」。
2. **搜索 + 导出**：「我和她肯定会长期聊很久很久，有没有历史记录导出或者搜索的功能」；搜索体验 = 「在历史记录搜索里搜个关键词就跳出对应聊天记录，也可以跳转到那里」。

**关键错配**：豆包是 **1 对 1 线性助手**——一条用户消息 → 一条助手回复 → 一份 LLM 上下文。改你的消息 = 丢掉那条回复、用同一份上下文重生成，干净。茶话室是**微信群模型**（P1 起的核心形态，见 `CLAUDE.md`「项目语义」）：多茶客、可 `@`、茶客之间接话、意愿打分调度。同一个「回溯」动作在群聊里语义完全不同（见 §4）。

## 2. 为什么一个便宜一个贵：架构根因

| 维度 | 搜索 / 导出 | 回溯 / 编辑 |
|---|---|---|
| 操作性质 | **读**（只读快照） | **回滚**（改历史 + 回退状态） |
| 与 append-only 关系 | 顺水（transcript 本就是追加日志，扫它天然合适） | 逆水（要删/改单条，撞 append-only + frozen `Message`） |
| 触碰的承重不变量 | 无 | append-only / 单调 cursor / 多份私有记忆 / 旁路数据关联键 |
| 规模敏感度 | 单用户线性扫足够 | 与规模无关，卡在**记忆一致性**上 |
| 外部依赖 | 无 | 「有回复后回溯」需 agentao 出 rewind 原语（§4.2 天花板） |

**核心洞察：回溯的难点不是「怎么删一行 jsonl」，而是「群里已经有 N 个茶客对你的原话作出了回应，那些回应烘进了各自私有的 LLM 记忆窗口」**。删盘上 transcript 那条，不会让任何茶客「忘掉」它。这是能不能优雅做回溯的天花板，详见 §4.2。

## 3. 需求 A：历史搜索 + 导出（便宜档，建议先做）

用户的真实缺口是**搜索 + 跳转**——导出早已可用。故本档主线是搜索，导出只做小补丁。

### 3.1 搜索（M1 主线）：从零，但只读廉价、当前房即可

现状：**完全空白**，无任何 `search` / `find_message` inbound 或全文索引；forensic 检索被刻意外包给用户手动 grep 盘上 jsonl（`debug_recorder.py` 注释「更老的从盘上 grep，不开翻页协议」）。

**M1 设计（刻意窄：当前房 / 子串 / DOM 跳转，无索引 / 无分页 / 无正则 / 无跨房）**：

- **线协议**：新增一个上行帧 `search_room {query, limit?}`（只搜前台房，不带 `room_id`）。
  - 严格白名单校验，未知键 NOTICE error 丢帧（延续「入站严格」）。
  - 回一个新下行 envelope，`data = {query, results: [{message_id, seq, speaker_id, ts_ms, snippet}], truncated}`。**results 只带 `speaker_id`、不带 display_name**——前端按名册映射显示（与 `emit_room_history` 同口径）。不 bump `schema_version`。
  - **命名约定（照 `room_export` 的先例）**：符号名 SCREAMING、wire value snake_case，且下行走枚举、入站走模块常量——即 `events.py` 加 `ChahuaEventType.SEARCH_RESULTS = "search_results"`；`server.py` 加模块常量 `INBOUND_SEARCH_ROOM = "search_room"`（入站不是枚举，参照现有 `INBOUND_EXPORT_ROOM`）；`app/renderer/events.js` 同步加 `EventType.SEARCH_RESULTS` / `Inbound.SEARCH_ROOM`（前端用 `EventType`/`Inbound` 对象，范本 `ROOM_EXPORT: "room_export"` / `Inbound.EXPORT_ROOM: "export_room"`）。三处 wire 字符串必须一致，别一边 `SEARCH_RESULTS` 一边 `search_results`。
- **后端检索**：扫前台房 `Room._messages`（已在内存），**大小写不敏感子串**匹配即可（不做正则，免 ReDoS + 免协议扩面）。`snippet` = 命中词前后若干字符供列表预览。`limit` 截断 + `truncated` 标志。
  - **规模**：单用户桌面、即便几年每天聊，jsonl 也就几 MB，**线性扫毫秒级**。不建 SQLite FTS / 倒排索引；将来嫌慢再加，且加索引不改线协议。
- **前端面板**：搜索框 → 命中列表（说话人 + 时间 + snippet）→ 点击 `scrollIntoView` 到 `data-message-id` + 高亮。
  - **跳转零障碍**：`emit_room_history` 一帧**全量下发** `Room._messages`（`server_room_snapshot.py:287`），`renderHistory` **全量渲染**（`chat_stream.js:309`），命中消息必已在 DOM，`data-message-id` 现成 → 直接滚过去。**不需要按 seq 回载 / 分页**（当前根本没有分页；`MAX_TURNS_IN_MEMORY=50` 是 debug 面板的裁剪，与聊天历史无关）。

### 3.2 导出（M1.5 小补丁）：保留整房导出，最多补元数据/简单过滤

现状（`server_inbound_io.py` / `exporter.py` / `events.py`，探查所得、point-in-time）：
- inbound `export_room` → `_inbound_export_room` → `_export_room`：`messages_since(0)` 全量 → `exporter.format_room_markdown` → emit `ROOM_EXPORT`（`data={filename, markdown}`）。
- **不落盘**：renderer 端 Blob + `<a download>` 存到用户「下载」。文件名 `茶话室-<房名>-YYYYMMDD-HHMMSS.md`。
- 局限：只有「整房、无过滤」一档；markdown 只写「说话人·时间+正文」，不含 message_id/seq。

**M1.5（可选、小）**：给 `export_room` 加**简单时间段过滤**，或在 markdown 里补 seq/message_id 元数据（便于和搜索结果对齐）。严格白名单校验、envelope 与 `schema_version` 不动。**speaker / task 过滤明确推后**——task 过滤牵扯 UI 状态与语义解释，不进本档。

### 3.3 不变量影响：无

搜索纯只读，不写 transcript / cursor / 记忆，不与 append-only、单调 cursor、多记忆打架。导出小补丁只是给既有只读路径加参数。**A 档不引入任何承重不变量。**

### 3.4 M2（推后）：全局/跨房搜索、正则、跳转回载

- 跨房 `search_all_rooms`（遍历 `discover_rooms()` + 读盘，复用 `read_jsonl_skip_bad`）+ 命中点击 `switch_room` 再滚动。
- 正则匹配（编译失败降级字面量 + 超时/长度护栏）。
- 若将来 `room_history` 改成分页/后向懒拉（`emit_room_history` 注释已留此伏笔），跳转才需要「按 seq 回载上下文」——**届时**才做，不进 M1。

## 4. 需求 B：消息回溯 / 编辑重生成（贵档）

### 4.1 一次回溯要一致回滚的五套状态

「回溯到某条消息、丢弃之后」在群聊里要同时回退五套状态，而它们**现在只能被 `reset_room` 一起「全清」，无任何「部分回退」原语**（探查所得，point-in-time）：

| 状态 | 载体 / 关联键 | 现状 | 回退难点 |
|---|---|---|---|
| 共享群聊记录 | `transcript.jsonl`（`seq`）；`Message` frozen | 严格 append-only，**只有整文件 `room.clear()` truncate，没有按 seq 删/改单条** | 需新增「截断到 seq S-1」写路径 |
| 每茶客读游标 | `cursor.json`（`{guest: last_seen_seq}`） | **单调只增**，`set()` 拒回退，只有 `clear()` 归零 | 需新增「回退某茶客游标」 |
| 每茶客私有 LLM 窗口 | agentao `agent.messages` | 被改消息旧文本**一旦喂过就烘死**，改 transcript 不回改；agentao **只有 `clear_history()` 整窗清、无「截断到某 seq」** | **最硬一环**（§4.2） |
| 增量摘要 | `summary.jsonl`（`[start_seq, end_seq]` 区间） | 改中间消息 → span 覆盖区间语义错位 | 需失效/重算相关 span |
| 旁路取证/挂件 | `message_artifacts.jsonl`（`message_id`）/ `debug/turns.jsonl`（`turn_id`） | 删消息后**直接悬空**；现有代码只在整房 clear 时同步 | 需按键级联失效 |

### 4.2 根因天花板：agentao 无 rewind 原语

群里可能已有 N 个茶客对你的原话作出回应，那些回应烘进了各自私有的 `agent.messages`。你改了原话，就得让这 N 个茶客「忘掉」编辑点之后的记忆重新作答——但：
- 改盘上 transcript **不会**回改任何茶客的 `agent.messages`（两套独立状态，靠 cursor 增量单向喂入）。
- 编辑**不会**自动回退 cursor（单调只增）。
- agentao 侧唯一重置 API 是 `clear_history()`（整窗清空），**没有「truncate 到某条 / rewind 到某 seq」**。

**这是茶话室能不能优雅做回溯的根本天花板。** 现有唯一的粗粒度回滚原语就是 `reset_room`（整房清 transcript + cursor + 全员 `clear_history` + summary + message_artifacts + debug）。

### 4.3 唯一安全档（MVP）：撤回*尚无茶客回复*的最后一条用户消息

**关键收窄**：只在「那条用户消息是 transcript 末尾、且其后没有任何茶客发过言」时允许撤回。这一约束恰好把它挡在 §4.1 五态纠缠**之前**——因为：
- 没有茶客发言 → 没有茶客的 `cursor` 推进到过它。`cursor.set` **只在 speak 成功后**推进到茶客**自己产出**的 seq（`_orchestrator_scoring.py::let_speak`），故没有茶客消息时游标永远不会推进到用户 seq，所有游标都 `<` 这条用户消息的 seq。**注意：打分、以及「无人接话」的空 turn 都不推进 cursor**（打分不碰记忆、空 turn 只写 debug/turns.jsonl）——别把它们误当「看过」。
- 没有茶客发言 → 这条用户文本**从未**作为增量喂进任何茶客的 `agent.messages`（打分不烘记忆——「打分永不吃图/工具」；只有 speak 经 `arun` 才烘）。
- 用户文本消息本身不产 `message_artifacts`。

**所以主状态只需截断 transcript 末条、不碰 cursor / `agent.messages` / `clear_history` / agentao rewind。但 transcript 不是唯一被写的地方**——`submit_user_message` append 后紧跟 `_kick_summarize()`（`orchestrator.py:462+`），且「无人接话」的空 turn 也会 `flush_turn` 写一行 debug/turns.jsonl（`_orchestrator_chain.py:99+`）。故**旁路收尾是回溯 MVP 的硬约束，不是可选补充**：若 `summary`（seq 区间）/ debug（turn）已覆盖被撤 seq，必须同步收尾。**核心原语是「撤回」，编辑 = 撤回 + 把旧文本回填输入框**（UX 糖）。

约束与步骤：
1. **仅房间 idle（无 in-flight）时允许**；正在生成先点「停止」（`cancel` 已存在，半截回复本就不落 transcript）。cancel 后若有茶客已完成发言，则不再满足「尚无回复」→ 退化为「有回复后回溯」，属搁置档（见 §4.4）。
2. **新增「截断 transcript 末条（到 seq S-1）」写路径**——比通用 truncate-to-seq 更窄，只删末条、且断言删的是 `speaker_id == user` 的末条。
3. **旁路一致收尾（硬约束）**：若 `summary` 已有 span 覆盖 seq S → 收尾该 span；若 debug 已写覆盖 seq S 的 turn → 收尾该 turn。`message_artifacts` 对用户文本消息天然为空、无需处理。**cursor / `agent.messages` 一律不动**（前提已保证它们没碰过 S）。
4. 前端：撤回按钮只挂在「最后一条用户气泡且其后无茶客气泡」上；点击发新 inbound `retract_last_user_message`（**无 payload、server 权威**——不带 message_id）。**Why 免 message_id**：本地 echo 用户气泡在落盘前没有 message_id（`renderer.js:803`，同 review 按钮 gotcha），带 id 会让「刚发完立刻撤回」挂不上；改成 server 自查「transcript 末条是 user ∧ 房间 idle」再截断，既让 echo 气泡也能立刻撤回，又天然防「点击瞬间茶客刚接话」竞态（server 复检拒掉、回 NOTICE）。

工程量小、语义可证、不引入任何危险的记忆回滚。正对「刚发出、发现发错、还没人接话，撤回改一下」这个最高频场景。

### 4.4 明确搁置：有回复后回溯 / 编辑任意历史消息

一旦有茶客回复，或要编辑更早的历史消息，就落回 §4.1 的五态一致回退，其中最硬一环（每茶客 `agent.messages` 回退到任意 seq）撞 §4.2 天花板——agentao 只有 `clear_history()` 整窗清，没有 rewind/truncate-to-marker。两条路都**明确搁置**，不在本轮用「`clear_history` 全窗 + 全量重喂」冒充（那会丢编辑点之前的记忆且成本高）：
- **有回复后回溯（原「局部化 reset_room」方案）**：需 transcript 截断 + cursor 回退 + 受影响茶客记忆回退 + summary/artifacts/debug 级联。留待 agentao 出 rewind 原语后再评估。
- **编辑任意历史消息 → 分叉**：更彻底的 branch 语义，规模更大，一并推后。

## 5. 承重不变量（已锚定）

M1 搜索 + 回溯落地时，以下承重约束已写死并同步进 **`CLAUDE.md`「消息回溯与历史搜索（P18）」段 + `docs/INVARIANTS.md`「9.x P18」段**（改不变量两处同步）。此处只留提要，完整表述以那两处为准：

- **[A-搜索] 搜索纯只读、绝不写任何状态**；当前房、`re.escape`+`re.IGNORECASE` 原文子串、无索引/分页/正则；query 长度封顶。M2 跨房读盘复用坏行跳过。
- **[B-回溯] 只允许「撤回*尚无茶客回复*的最后一条用户消息 + 房间 idle」**：server 硬校验「idle（`busy_alive`，含 bg run/MTS）∧ 末条 `speaker_id==user`」，不得放宽。免 message_id、无 payload、严格白名单。
- **[B-回溯] 主状态截 transcript、旁路一致收尾、cursor 与 `agent.messages` 一律不动**；旁路顺序：先 `cancel_pending_summarize` → summary（房间级 + 遍历 store 全量 task）→ debug；summary 收尾包 try/except、snapshot 照常重发。transcript 主体 append-only，撤回是唯一全量重写入口（`write_jsonl_atomic`，先写盘后弹内存）。
- **[B-天花板] 有回复后回溯 / 任意历史编辑依赖 agentao rewind 能力**，未具备前不做、不用「`clear_history` 全窗 + 重喂」冒充。

## 6. 建议路线与优先级

1. **M1 当前房搜索 —— 先做，快赢。** 只读、零不变量风险、单用户线性扫足够。1 个只读 `search_room` inbound + `SEARCH_RESULTS` envelope + 前端搜索面板 + `scrollIntoView` 跳转（历史全在 DOM，无需分页/回载）。
