# P20 茶客调用消耗取证

> 目标：在 P6 调试抽屉里看见**每位茶客每次发言背后的模型调用**——调了几次、每次多久、
> 输入输出各多少 token、命中多少提示缓存、有没有重试、有没有压缩上下文。
>
> **前置**：agentao ≥ 0.5.18（`chore/agentao-0.5.18`）。P6.1 落盘 / P6.2 实时抽屉 /
> P6.3 历史 turn 已落地。
>
> **状态**：已实现（2026-10-31，分支 `feat/p20-llm-call-forensics`）。设计稿经两轮评审修订
> （计量单位 / 截断提示 / finalize 时机 / 汇总完整性）。验收见 §12。

---

## 1. 问题

P6 能回答「谁被选中、为什么、喂了什么 prompt、调了哪些工具、产出了什么」，但回答不了：

| 想问的 | 现在 | 缺口 |
|---|---|---|
| 这轮为什么这么慢？ | 只能看到消息总时长 | 分不清是调用次数多、首 token 慢、重试了还是在压缩上下文 |
| 带技能的茶客缓存到底命中没有？ | 看不到 | agentao 0.5.18 把技能正文移进历史以改善缓存，效果无从验证 |
| 某位茶客为什么比别人贵？ | 看不到 | 输入/输出/推理 token 无记录 |
| 以后开思考深度，推理 token 涨多少？ | 看不到 | 同上 |

agentao 已经在每次模型调用后发 `LLM_CALL_COMPLETED`（含用量）、重试前发 `LLM_RETRY`、
压缩时发 `COMPACTION_STARTED` / `COMPACTION_SETTLED`。chahua 的
`transport_bridge.py::_handle` 目前把它们全部丢弃（见文件末尾的「其余事件…丢弃」注释）。

## 2. 范围

### 做

1. `ChahuaTransport` 接收 `LLM_CALL_COMPLETED` / `LLM_RETRY` / `COMPACTION_SETTLED`，
   按当前 `message_id` 缓存成本条消息的「调用记录」。
2. 消息结束时，同一份记录：
   - 落进 `debug/turns.jsonl` 对应 message 条目（新增字段）；
   - 随 `message_end.data` 下发给前端，供实时抽屉显示。
3. 调试抽屉每条消息下新增「模型调用（N）」小节 + 一行消息合计；turn 头部加一行
   「本轮茶客调用合计」。

### 不做（显式排除，写进 §9 已知缺口）

- **不统计打分与摘要**。`scoring.py` / `summarizer.py` 直接调 `LLMClient`，不经茶客
  transport。界面统一叫「**茶客调用**」，绝不叫「房间消耗」。
- **不统计 agentao 内部的非主循环调用**。上游明确：压缩用的摘要请求走 `llm.chat()`
  而非 `run_llm_call`，**不发** `LLM_CALL_COMPLETED`。压缩只记时长与前后规模，不记 token。
- **不换算费用**。agentao 只给数、不给价（`agentao/llm/_usage.py` 模块注释原话：
  "prices are the host's"）；chahua 也不维护价目表。
- **不做实时提示气泡**（「正在重连…」「正在整理上下文…」）。那是 P20.1，见 §10。
- **不做思考深度配置**。依赖先拆共享 client（`session.py:431-452` 按 `LLMSpec` 复用
  client，打分 / 摘要 / 同配置茶客共用一个对象），另立项。
- **不动 `turns_index` 投影**（索引行 ≤200B 的预算不变）；合计只在详情里算。
- **后台 agent run（P11）不记**：它走 `NOOP_RECORDER`，前台抽屉也不显示它的消息，
  维持现状。

## 3. 上游事件语义（agentao 0.5.18，已核对源码）

### 3.1 `LLM_CALL_COMPLETED`（`agentao/runtime/llm_call.py`）

**计量单位是「一次主循环模型调用」，不是一次 HTTP 请求。** agentao 的
`run_llm_call` 用这个事件包住整个 `LLMClient.chat_stream()`；**重试循环在 `chat_stream` 内部**
（`agentao/llm/client.py` 的 `MAX_RETRY_ATTEMPTS` 循环），所以一次调用内部无论重试几次，
最终只发**一次** `LLM_CALL_COMPLETED`（成功或失败各一次）。由此：

- 「调用次数」= 茶客一次发言里「调模型 → 跑工具」循环的迭代数，**不是** HTTP 请求数；
  HTTP 尝试数 = 1 + 该调用挂的 `retries` 条数（截断时偏小，§4.1）。
- `duration_ms` **包含**所有失败尝试和退避等待，不是单次请求延迟。
- usage 只来自**最终那次响应**；失败尝试的消耗（如果服务商计费）不可见，最终失败时整条 usage 为 `None`。

UI 与文档统一称「**模型调用**」，悬浮说明写明「一次调用可能含多次重试」。取用字段：

| 字段 | 含义 | 缺失口径 |
|---|---|---|
| `status` | `"ok"` / `"error"` | — |
| `duration_ms` | 本次调用总耗时，**含重试与退避** | — |
| `first_token_ms` | 首个正文 token 延迟 | 没出正文 → `None` |
| `first_reasoning_ms` | 首个思考 token 延迟 | 无思考 → `None` |
| `finish_reason` | 结束原因 | 失败 → `None` |
| `finish_reason_reported` | `False` = 上游兜底填的 `"stop"`，非服务商给的 | 失败路径无此键 |
| `prompt_tokens` / `completion_tokens` | 最终响应的输入 / 输出总量（不含失败尝试） | 响应无 usage 或调用失败 → `None` |
| `cache_read_tokens` / `cache_creation_tokens` | **`prompt_tokens` 的组成部分** | 无 usage → `None`；有 usage 但未声明 → `0` |
| `reasoning_tokens` | **`completion_tokens` 的组成部分** | 同上；Anthropic 接口恒 `0`（思考计入输出、无单独计数） |
| `error_class` / `error_message` | 失败时 | 成功 → `None` |

**承重语义**：缓存与推理都是「其中」，**不是额外加项**。合计时只加
`prompt_tokens` 与 `completion_tokens`，缓存 / 推理各自另加、只用于展示「其中多少」。
**`0` 不等于「确认为零」**——上游对「未声明」与「真为 0」都给 `0`，展示层必须承认这一点（§6.3）。

`attempt` 是 agent 级的调用序号（`agent._llm_call_seq`），**不是重试次数**；本设计不使用它。

### 3.2 `LLM_RETRY`（`agentao/llm/client.py`）

在 `chat_stream` 内部、退避等待**之前**发，所以总落在**同一次调用**的 `LLM_CALL_COMPLETED` 之前，
且一次调用可能先后有多条。
字段：`retry`（第几次重试）、`max_retries`、`delay_s`、`reason`。
上游保证重试只发生在尚未输出正文时。

### 3.3 `COMPACTION_SETTLED`（`agentao/compaction/coordinator.py`）

一次压缩尝试的终结事件（`success` / `cancelled` / `failed`；`skipped` 不发）。
字段：`trigger` / `kind` / `reason` / `status` / `pre_msgs` / `post_msgs` /
`pre_tokens_history` / `post_tokens_history`（**不含**系统 prompt 的估算值）/
`duration_ms` / `detail`。

`COMPACTION_STARTED` 本阶段不用（它只服务实时提示，留给 P20.1）。

## 4. 数据模型

### 4.1 消息条目新增字段（`turns.jsonl` → `messages[]`）

```jsonc
{
  "message_id": "msg_…",
  "guest": "阿岚",
  "status": "ok",
  "seq": 42,
  "tool_calls": [ … ],          // 不变
  "artifact_paths": [ … ],      // 不变
  // ── P20 新增 ──
  "llm_calls": [
    {
      "status": "ok",
      "duration_ms": 3120,
      "first_token_ms": 840,
      "first_reasoning_ms": null,
      "finish_reason": "tool_calls",
      "finish_reason_reported": true,
      "prompt_tokens": 18234,
      "completion_tokens": 212,
      "cache_read_tokens": 16384,
      "cache_creation_tokens": 0,
      "reasoning_tokens": 0,
      "retries": [               // 本次调用之前发生的重试；无则省略该键
        {"retry": 1, "max_retries": 3, "delay_s": 1.5, "reason": "rate_limit"}
      ],
      "error_class": null,       // 仅 status=error 时有值；成功时省略该键
      "error_message": null
    }
  ],
  "compactions": [               // 无则省略该键
    {"kind": "full", "trigger": "auto", "reason": "…", "status": "success",
     "pre_msgs": 120, "post_msgs": 14,
     "pre_tokens_history": 98000, "post_tokens_history": 6100,
     "duration_ms": 21000}
  ]
}
```

规则：

- 字段名与上游一致，**原值照抄、不做换算**；未知的上游新键不透传（白名单抽取）。
- `llm_calls` **只由 transport 快照写入**（`record_message_start` 不初始化）。正常发言（含取消 / 失败）的快照必带它，可为 `[]`；快照失败或调用方没传快照 → 缺键 =「无记录」，与实时 `message_end` 一致；
  `compactions` 空则省略。
- **单消息上限**：`llm_calls` 最多 64 条、每条 `retries` 最多 8 条、`compactions` 最多 8 条。
  理由：`max_consecutive_ai_turns` 只限轮次不限单次发言内的工具循环，一次发言 100 次迭代是可能的。
- **截断标志**：三者**任一**超限，超出部分丢弃，并在消息条目上置 `"llm_records_truncated": true`
  （未截断时省略该键）。标志属于快照的一部分（§5），**落盘与 `message_end` 下发同一个值**。
- `error_message` 上游已截到 500 字符；chahua 再截到 300 字符落盘。
- 不 bump `TURNS_SCHEMA_VERSION`（加字段，P6.3 已确立「未知字段忽略」口径）。

### 4.2 `message_end.data` 新增字段

成功 / 取消 / 失败三条路径的 `message_end.data` 都附同一份快照（§5）：
`llm_calls`（始终存在，可为 `[]`）、`compactions`（空则省略）、`llm_records_truncated`（截断时才有）。
内容与 §4.1 落盘的**逐字节相同**（同一个 dict 序列化）。

- 加字段，不 bump envelope `schema_version`。
- **不进 transcript**：transcript 由 `Message` 生成，不读 envelope data（现状如此，保持）。
- 体积：每条调用约 300B，常见发言 1–5 次调用，可忽略；上限 64 条时约 20KB。

## 5. 数据流

```
agentao run_llm_call
   ├─ LLM_RETRY ──────────┐
   ├─ LLM_CALL_COMPLETED ─┤
CompactionCoordinator     │
   └─ COMPACTION_SETTLED ─┤
                          ▼
ChahuaTransport._handle（按当前 message_id 缓存）
   ├─ _pending_retries   ← LLM_RETRY 追加
   ├─ _llm_calls         ← LLM_CALL_COMPLETED：白名单抽取 + 吸收 _pending_retries
   └─ _compactions       ← COMPACTION_SETTLED
                          ▼
ChahuaTransport.finalize_llm_records()  ← 幂等：首次调用生成并冻结快照，之后返回同一份
   ├─ TeaGuest.speak 成功路径：emit message_end 之前调用 → envelope.data
   ├─ TeaGuest._emit_failure（取消 / 失败）：emit 之前调用 → envelope.data
   └─ TeaGuest.speak 外层 finally：再调一次（拿到同一份）→ recorder.record_message_end
```

要点：

- **单一来源**：缓冲只在 transport 里。recorder 与 envelope 读同一份，不各自累计，避免两边对不上。
- **生命周期跟 `partial_text` 一致**：进入 `ChahuaTransport.bind()` 时清零；退出 `bind()` 时**不清**
  （`speak()` 外层 finally 还要读），下次 `bind()` 才清。`bind()` 之外到达的事件（`_message_id is None`）丢弃。不跨消息串。
- **`_pending_retries` 归属**：重试先于对应的 COMPLETED 到达，COMPLETED 时整批吸收并清空。
- **快照 finalize（承重）**：`finalize_llm_records()` 是**唯一**收尾点，幂等：
  1. 首次调用：若 `_pending_retries` 非空（重试后没等到终结事件），追加一条
     `{"status": "cancelled", "retries": [...]}` 占位调用；套用上限与截断标志；**冻结**为快照。
  2. 后续调用：原样返回同一份快照，**不再生成占位**——所以不会重复。
  3. 冻结后到达的 `LLM_*` / `COMPACTION_*` 事件丢弃（debug 日志一行），保证实时与落盘一致。
  4. 进入下一次 `bind()` 时解冻并清空。
- **占位只是兜底**：退避期间被取消，上游通常仍会以 `status="error"` 发出该调用的 COMPLETED
  并吸收挂起的重试；占位只覆盖「没等到终结事件」的情况。真依赖取消测试钉住「不重复记录」（§8 第 12 条）。
- **时序口径**：成功路径 `message_end` 在 `bind()` 内发出，`record_message_end` 在外层 finally；
  两处都调 `finalize_llm_records()`，后者拿到的是前者冻结的快照。若 `room.append` 在 `arun` 成功后抛异常
  （此时没有 `message_end`），finally 的那次调用负责首次 finalize，只落盘。
- 所有新增处理**包 try/except 到底**、只 WARN（与 P6 不变量「debug 不能挂生产路径」同口径）；
  抽取失败的单条事件丢弃，不影响消息流。

## 6. 前端（调试抽屉）

### 6.1 实时与历史统一

- 实时：`debug_panel.js::handleMessageEnd` 从 `env.data` 读 `llm_calls` / `compactions` 存进 message record。
- 历史：`buildHistoricalRecord` 从 `turn.messages[].llm_calls` 读，形态相同。
- 两边都缺字段（P20 之前的老记录）→ 视为「无记录」，**整个小节不渲染**，不报错。

### 6.2 渲染

消息条目 `<details>` 内，在「工具调用」之前加：

```
模型调用（3）  合计 用时 7.4s · 输入 41,203（缓存读 32,768）· 输出 588
  #1 ok   3.1s  首字 0.84s  输入 18,234（缓存读 16,384） 输出 212   tool_calls
  #2 ok   2.0s  首字 0.61s  输入 18,620（缓存读 16,384） 输出 96    tool_calls
  #3 ok   2.3s  首字 0.70s  输入  4,349                  输出 280   stop
     ↻ 重试 1 次（rate_limit，等待 1.5s）
上下文压缩（1）  full · success · 120→14 条 · 21.0s
```

turn 头部（`renderTurn`）在已有摘要下加一行「本轮茶客调用：N 次 · 输入 X · 输出 Y」，
仅当本轮至少一条消息带 `llm_calls` 时出现；完整性提示按 §6.3 叠加。
「N 次」只数有记录的调用（取消占位也计 1 次，因为它代表一次没完成的调用）。

汇总规则全部落在一个纯函数 `summarizeLlmCalls(messages)`：返回
`{calls, input: {sum, complete}, output: {sum, complete}, cacheRead, truncated, missingMessages}`，
渲染层只读它的结果，不在 DOM 代码里另算。

### 6.3 缺失与歧义的显示口径（承重）

| 情况 | 显示 |
|---|---|
| `prompt_tokens` / `completion_tokens` 为 `null` **或缺键**（含取消占位） | 「未提供」 |
| `cache_*` / `reasoning_tokens` 为 `0` | 不显示该括注（上游 `0` 可能是「未声明」，不能写成「缓存 0」误导） |
| `cache_*` / `reasoning_tokens` 为 `null` | 不显示 |
| 合计：**输入、输出分别判断**——某项有任一调用未知 | 该项后缀「（部分未提供）」，只加有值的；全部未知则显示「未提供」，**绝不显示 0** |
| 消息带 `llm_records_truncated` | 消息合计与 turn 合计都加提示「记录已截断，仅统计已记录部分」 |
| turn 内有消息缺 `llm_calls` 键（P20 前的旧记录，或该消息记录失败） | turn 合计加提示「部分消息无记录」 |
| `finish_reason_reported === false` | finish_reason 后加「（未报告）」 |
| `status === "error"` | 行标红，显示 `error_class`，`error_message` 进 `title` 悬浮 |

**合计绝不把缓存或推理再加进输入 / 输出**（§3.1 承重语义）。

数字格式化（千分位、秒）走纯函数，放进可被 `node:test` 覆盖的 `.mjs`（沿 P10.2 `flint_core.mjs` 先例），
DOM 拼装留在 `debug_render.js`。

## 7. 承重不变量（落地后同步进 `CLAUDE.md` + `docs/INVARIANTS.md`）

1. **统计范围 = 茶客 transport 上的主循环调用；计量单位是一次 `chat_stream`（含内部重试），不是 HTTP 请求**。打分、摘要、agentao 内部压缩摘要、后台 run 不计；
   UI 文案只用「茶客调用」。
2. **缓存 / 推理是「其中」不是加项**；合计只加 `prompt_tokens` / `completion_tokens`。
3. **上游 `0` 不当确认零展示**；`null` 与缺键都算未知，显示「未提供」。合计时输入、输出**各自**判断完整性，
   截断与旧记录混合都要显式提示，**部分数据绝不显示成完整合计**。不换算费用。
4. **单一缓冲在 transport，经幂等 `finalize_llm_records()` 冻结成快照**；`message_end` 与 recorder 用同一份快照，
   finalize 只在首次调用时生成取消占位；冻结后到达的事件丢弃；进 `bind()` 解冻清零，无 `message_id` 的事件丢弃。
5. **`llm_calls` 只由快照写入，缺键 = 无记录**（旧记录 / 快照失败），前端标「部分消息无记录」；不 bump 任何 `schema_version`。
6. **白名单抽取 + 单消息上限**，上游新增键不自动透传。
7. **记录失败永不影响发言**（try/except + WARN）。

## 8. 测试（先写失败用例）

后端（`tests/test_p20_llm_call_forensics.py`）：

1. 一次发言两次调用 → `turns.jsonl` 该消息 `llm_calls` 两条、字段照抄。
2. `LLM_RETRY` ×2 后 `LLM_CALL_COMPLETED` → 两条重试挂在该调用的 `retries` 上。
3. 取消发生在退避期间 → 占位 `{"status": "cancelled", "retries": [...]}`。
4. 失败调用 → `status=error` + `error_class`，`error_message` 截断到 300。
5. `COMPACTION_SETTLED` → `compactions` 一条；`skipped`（上游不发）无条目。
6. 跨消息不串：上一条消息的事件不出现在下一条；`bind()` 退出后到达的事件丢弃。
7. 上限与截断：65 次调用 → 64 条 + `llm_records_truncated=true`；单调用 9 次重试、9 次压缩各自也触发该标志；
   `message_end.data` 带同一标志。
8. `message_end.data` 三条路径（ok / cancelled / error）都带 `llm_calls`，且与落盘内容相同（同一快照）。
   finalize 幂等：连调两次只有一条取消占位；冻结后再到的 `LLM_CALL_COMPLETED` 不进快照。
9. 未知上游键不透传。
10. recorder 抛异常 → 发言照常完成（沿 P6 既有 recorder 失败用例写法）。
11. **真依赖契约**：沿 P19 的真 `Agentao` + 本地假 OpenAI SSE 端点，在 SSE 末帧带 `usage`
    （含 `prompt_tokens_details.cached_tokens`），断言端到端落盘值正确——防上游改字段名时替身全绿。
    同一夹具让端点先回一次可重试错误再成功：断言**只有一条**调用、挂一条 `retries`、`duration_ms` 覆盖退避。
12. **真依赖取消**：端点持续回可重试错误，在退避期间取消发言；断言落盘与 `message_end` 一致、
    该调用**只记一次**（要么上游的 error COMPLETED 吸收了重试，要么一条占位，不能两者都有）。

前端（`node:test`，`summarizeLlmCalls` + 格式化纯函数）：`null` / 缺键 / `0` 的显示；输入、输出完整性分别判断
（例：输入全有、输出缺一条）；全部未知显示「未提供」而非 0；截断提示；新旧消息混合的「部分消息无记录」；
缓存与推理不重复相加。

## 9. 已知缺口

- 打分 / 摘要的消耗不可见（可后续给 `scoring.py` / `summarizer.py` 读 `response.usage` 自记）。
- 压缩本身的 token 不可见（上游不发）。
- 一次调用内失败尝试的消耗不可见：usage 只来自最终响应，HTTP 尝试数只能从 `retries` 条数推断（截断时偏小）。
- Anthropic 接口下推理 token 恒为 0（上游口径）。
- 取消后晚到的事件可能混进同茶客下一条消息：agentao 取消时最多等 5s 清理，超时旧回合后台续跑（见 `docs/INVARIANTS.md §9.x P20`）。
- 只能看单轮；跨轮 / 跨茶客汇总（例如「本房今天每位茶客的输入总量」）不做。
