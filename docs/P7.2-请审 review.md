# P7.2：显式 handoff —— review（请审）

> 目标：在 P7.1 已落地的「确定性发言指派通道」之上，加入第二个动作 **review（请审）**——
> 用户在某条**已落 transcript** 的发言气泡上点「请审…」，选一位茶客 B，B 下一轮被指派
> 对那条发言给出审阅意见（通过 / 打回 / 修改建议）。
>
> P7.2 是 P7.1 的**最小增量**：复用 drain loop / `_run_handoff_turn` wrapper / cancel /
> cap / envelope 全套承重墙，**唯一新增面是消息级 prompt 注入**——给被指派茶客的
> context 多挂一段 `<review_target>` 临时块，块内只有被审消息原文 + 审阅指引。

**状态：设计中（2026-05-19，已按评审收敛）**。上游契约见
[`P7-显式 handoff 与 delegation.md`](P7-显式%20handoff%20与%20delegation.md) §2.2 / §3 / §4.5 / §4.6；
P7.1 落地见同文件 §12 表（`57040fb` 起）。落地拆分见本文 §11。

> **评审收敛（2026-05-19）**：初稿的「`<review_target>` 附任务产物清单」「右键复制
> message id」「用户刚发的本地 echo 也能立即请审」三项被判过度设计 / 落不稳，已删 / 推后。
> P7.2 收敛为纯粹的「消息级 prompt 注入」，技术路线更短。详见 §5.5。

## 0. 本阶段做 / 不做

**做**：

- `HandoffKind` 加 `REVIEW` 一档；`HandoffItem` 加 `review_message_id` 字段。
- inbound `handoff_review`（只接 `message_id`，即 `scope=message` 唯一档）。
- `ContextRenderer.build_context_for` 加 `extra_blocks` 参数；onboarding / incremental
  两条渲染路径都接，注入位统一在 `<speak_instruction>` 之前。
- `run_pending_handoff` drain loop 按 `item.kind` 分流：review 项现场合成 `<review_target>`
  块（**只含被审消息原文 + 审阅指引**）、经 `extra_blocks` 喂给被指派茶客。
- debug `VALID_SCORING_PATHS` 加 `handoff_review`。
- `Room.message_by_id` 查找。
- UI：消息气泡「请审…」按钮（**只挂在带 `message_id` 的气泡上**）+ 茶客选择菜单；
  队列预览 review 项标注；调试抽屉 `handoff_review` 徽标。

**不做**（推后 / 永不做）：

- **不开** `scope=last` / `scope=task` / slash `@msg_id`（§5.1）。
- **不在 `<review_target>` 里附任务产物清单**（评审收敛，§5.5）——任务上下文已由
  `<current_task>` 块提供；老消息所属任务的产物以后有明确需求再单独加。
- **不做右键「复制 message id」**（评审收敛，§5.5）——「请审…」按钮本身就是消息锚
  入口，slash `@msg_id` 既不开，就没有「手输 message id」的场景。
- **不支持请审「刚发出、尚无 `message_id` 的本地 echo 用户消息」**（评审收敛，§5.3）。
- **不**新增 envelope 类型——`handoff_enqueued` / `handoff_consumed` / `handoff_cleared`
  P7.1 已全加，review 复用。
- **不**做「B 审完自动回 A 修订」的接力链（§9）——review 是单轮一次性动作。
- **不**碰 panel（P7.3）/ AI propose（P7.4）/ `task.owner`（P7.5）。
- **不** bump `schema_version`、**不**新增持久化目录 / toml 字段。

## 1. 现状速写 —— P7.1 留下的复用面

| P7.1 已落地 | P7.2 怎么蹭 |
|---|---|
| `chahua/handoff.py`：`HandoffKind` enum（仅 `DELEGATE`）+ `HandoffItem` frozen dataclass | 加 `REVIEW` 枚举值 + `review_message_id` 字段；`to_dict()` 多带一字段 |
| `Orchestrator.run_pending_handoff` drain loop（delegate 写死 `scoring_path` / `cost=1` / `winners=[target]`） | drain loop 按 `item.kind` 分流；review 与 delegate **同样**单目标 / `cost=1` / `winners=[target]`，差异只在 `scoring_path` + `extra_blocks` |
| `_run_handoff_turn` wrapper（cancel-safe + 同槽清 `_inflight_*`） | **零改动**复用 |
| `_inbound_handoff_delegate` / `_inbound_handoff_clear` + `_inflight_kind` 三态 | 加平级 `_inbound_handoff_review`，抢占 / 启动 wrapper 逻辑照搬 delegate |
| envelope `HANDOFF_ENQUEUED` / `HANDOFF_CONSUMED` / `HANDOFF_CLEARED` | **零新增**——review 项走同样三个 envelope |
| debug `VALID_SCORING_PATHS` + `SCORING_PATH_HANDOFF_DELEGATE` | 加 `SCORING_PATH_HANDOFF_REVIEW` 一条 + 白名单一行 |
| `_let_speak(guest, *, turn_id, sink, task_id)` | 加可选 `extra_blocks` 形参（P7 §3.4 评审反馈预留：「真需要 extra_blocks 再给 `_let_speak` 加形参」） |
| `ContextRenderer` 固定块结构 + `wrap_current_task` helper | 加 `extra_blocks` 参数转发；`<review_target>` 块由 orchestrator 现场合成 |

**最重要的判断**：review 与 delegate 在调度层**完全同构**——都是单点 winner、`cost=1`、
跳过打分、本轮独占、完成后不回落 scoring。两者**唯一**差异是被指派茶客看到的 prompt
多一段 `<review_target>`。所以 P7.2 不动 drain loop 的控制流（cap / cancel / turn 末尾
5 步），只在「合成 winner 的 context」这一步插一个 `kind` 分支。

## 2. 动作形态：review（请审）

```
用户触发：UI 上点某条已落 transcript 的发言气泡的「请审…」按钮 → 选目标茶客 B
AI propose：P7.4 才开 —— 茶客调 task_propose_handoff(kind="review", target="B", message_id=...)
```

- **效果**：B 在下一个确定性 turn 里被强制发言（跳过打分、本轮独占），prompt 里多挂一段
  `<review_target>`，块内含被审消息原文 + 审阅指引。B 发言完 → 队列空 → emit
  `turn_end(next="user")`，**不回落 scoring**（与 delegate 同口径）。
- **被审消息 = 任意带 `message_id` 的历史消息**（茶客发言 / 用户发言皆可）——不限于最近
  窗口。`<review_target>` 把被审消息 body **内联**进 prompt，正是为了覆盖「审 50 轮前
  那条」的场景（那条早已滑出 `<recent_messages>` / `<room_update>` 窗口）。
- **「请审…」按钮只挂在带 `message_id` 的气泡上**（§5.3）：茶客发言的气泡恒有
  `message_id`（`message_start` envelope 带）；用户发言**刚发出时**是前端本地 echo、
  **没有** `message_id`，要等切房 / 刷新后由 `room_history` 重建才带上。所以「用户刚发
  的那条立即请审」做不到，这是可接受的边角——用户要审自己的话，切房回来即可。
- **handler 行为**与 delegate 完全一致（依 in-flight 类型条件性抢占，见 §3.4）：
  in-flight 是 user-turn → cancel + 入队 + 启 drain；是 handoff drain → 只 append 队尾；
  无 in-flight → 入队 + 启 drain。
- **review 不带 `reason`**：inbound 协议只有 `{type, target, message_id}`（§3.2）。
  delegate 的「内部备注」是因为 delegate 不带任何「要 A 做什么」的语义锚，需要给用户
  一个回看抓手；review 的语义锚就是「审这条消息」，message_id 已经把意图说清，不再加
  自由文本备注（少一个字段、少一处白名单、少一处 UI）。

## 3. 数据契约

### 3.1 `HandoffKind` / `HandoffItem` 增量

`chahua/handoff.py`：

```python
class HandoffKind(str, Enum):
    DELEGATE = "delegate"
    REVIEW = "review"            # ← P7.2 新增

@dataclass(frozen=True, slots=True)
class HandoffItem:
    kind: HandoffKind
    target: Optional[str] = None
    issued_by: str = HANDOFF_ISSUED_BY_USER
    reason: Optional[str] = None
    review_message_id: Optional[str] = None   # ← P7.2 新增；review 专用
    created_at_ms: int = field(default_factory=now_ms)

    def to_dict(self) -> dict:
        return {
            "kind": self.kind.value,
            "target": self.target,
            "issued_by": self.issued_by,
            "reason": self.reason,
            "review_message_id": self.review_message_id,   # ← 同步加
            "created_at_ms": self.created_at_ms,
        }
```

- `review_message_id` 排在 `reason` 之后、`created_at_ms`（带 `default_factory`）之前——
  全字段都有默认值，顺序不影响构造，但跟 [`P7`](P7-显式%20handoff%20与%20delegation.md) §3.1
  最终形态契约的字段顺序对齐。
- delegate 项 `review_message_id` 恒 `None`；review 项 `target` + `review_message_id`
  都非空、`reason` 恒 `None`。**不做 dataclass 级互斥校验**——构造点只有 inbound handler
  一处，按 kind 显式传值即可，加 `__post_init__` 交叉校验属过度设计（与 P7.1 `HandoffItem`
  不校验同口径）。
- **panel 字段（`targets` / `panel_group_id`）仍不加**——P7.3 再扩。

### 3.2 inbound 协议（user → server）

```jsonc
{ "type": "handoff_review", "target": "B", "message_id": "msg_..." }
```

- **白名单严格**：`_HANDOFF_REVIEW_ALLOWED = {"type", "target", "message_id"}`；未知字段
  → NOTICE error + 丢帧（同 `room.toml` / `open_task` / `handoff_delegate` 口径）。
- **三道校验**（任一失败 → NOTICE error + 不入队）：
  1. `target` 是非空 str。
  2. `target in orchestrator.guest_names`（茶客在场）。
  3. `message_id` 是非空 str **且** `room.message_by_id(message_id)` 命中——拒掉
     stale / 伪造的 message_id。**这道校验同时是 §4.1「drain 时被审消息保证存在」不变量
     的工程基础**：inbound 已确认消息存在，加上 `clear_room` 会清空 `_handoff_queue`，
     review 项不可能跨「消息消失」存活。
- **只接 `message_id`，不解析 `scope` 字段**（§5.1）。未来若开 `scope=task` 等档，
  另开 inbound `type`，不在本帧加 `scope` 字段。

### 3.3 envelope（server → user）—— 零新增

review 项走 P7.1 已有的三个 envelope，**不加新类型**：

| 事件 | review 项的语义 |
|---|---|
| `handoff_enqueued` | `data.queue` 含 review 项的 `to_dict()`（带 `kind:"review"` + `review_message_id`），前端整体替换 `handoffQueueState` |
| `handoff_consumed` | drain loop pop review 项、`turn_start` 之后 emit；顶层 `turn_id`，`data.item` 是 review 项 dict |
| `handoff_cleared` | `handoff_clear` 丢弃含 review 的队列项时，`items_dropped` 列出 |

`TASK_INFO` 不收 handoff 队列（P7.1 不变量延续）；`schema_version` 不动（老前端忽略
`item.kind=="review"` 这种未知 enum 值不报错，只是不渲染 review 专属标注）。

### 3.4 抢占 / 启动 —— 照搬 delegate

`_inbound_handoff_review` 的抢占与启动逻辑与 `_inbound_handoff_delegate` **逐行同构**：

```
校验 target / message_id
  → task = self._inflight_turn_task
  → stale = task is not None and (task.done() or task.cancelling())
  → if self._inflight_kind == INFLIGHT_KIND_USER or stale:
        await self._cancel_and_drain_inflight()
  → item = HandoffItem(kind=REVIEW, target=..., review_message_id=...)
  → snapshot = orchestrator.enqueue_handoff(item)
  → emit HANDOFF_ENQUEUED {queue: [...]}
  → if self._inflight_turn_task is None:
        _set_inflight(create_task(_run_handoff_turn(...)), INFLIGHT_KIND_HANDOFF)
```

差异**只有** `HandoffItem` 构造的字段。抢占语义（user-turn 抢、handoff drain 不抢只
append、stale slot 抢）一字不改——这是 P7.1 §4.4 / 反向评审 v3-#1 的承重墙，review
不重新论证。

### 3.5 debug 落盘

- `chahua/debug_recorder.py` 加 `SCORING_PATH_HANDOFF_REVIEW = "handoff_review"` 常量
  + `VALID_SCORING_PATHS` frozenset 加一条。
- drain loop 对 review 项 `record_scoring(scoring_path="handoff_review", ...)`；
  `start_turn` 的 `trigger={"kind":"handoff","handoff_item": item.to_dict()}` 已自动带
  `review_message_id`（`to_dict()` 输出全字段），**不扩 recorder API**。
- `turn_start` envelope `data.scoring_path == "handoff_review"`——前端调试抽屉据此渲徽标。

## 4. 执行：drain loop 按 kind 分流

### 4.1 `run_pending_handoff` 的改动面

P7.1 的 drain loop body 对 delegate 写死了三个值（`winners` / `scoring_path` /
不传 `extra_blocks`）。P7.2 在 pop 出 `item` 之后、`start_turn` 之前插一个 `kind`
分支，算出 `scoring_path` 与 `extra_blocks` 两个值：

```python
item = self._handoff_queue.popleft()
# P7.1 已有的「target 不在场就跳过」校验保留（跨 turn 残留项可能因 remove_guest 失效）。
if item.target is None or item.target not in self._guests:
    _log.warning("handoff item target unavailable; dropping: %r", item)
    continue

if item.kind is HandoffKind.REVIEW:
    scoring_path = SCORING_PATH_HANDOFF_REVIEW
    extra_blocks = [self._render_review_block(item)]
else:                       # HandoffKind.DELEGATE
    scoring_path = SCORING_PATH_HANDOFF_DELEGATE
    extra_blocks = None

winners = [item.target]     # review / delegate 都是单目标
```

- `winners` / `cost`（恒 1）/ turn 末尾 5 步 / cancel fixup —— **全部不动**。review 与
  delegate 在调度层同构，分支只覆盖 `scoring_path` 与 `extra_blocks` 两个值。
- `_let_speak` 调用从 `_let_speak(name, turn_id=..., sink=..., task_id=...)` 改成多传
  一个 `extra_blocks=extra_blocks`（delegate 传 `None`，行为不变）。
- **不为 review 单设「被审消息消失」防御分支**（评审收敛，§5.5）：inbound 已校验消息
  存在，`clear_room` / `reset_room` 会清 `_handoff_queue`（P7.1 不变量），review 项不
  可能跨「消息消失」存活——`_render_review_block` 因此**保证**能查到被审消息，不返回
  `None`、drain loop 不为它加 `continue` 分支。若 `message_by_id` 真返回 `None`，那是
  bug（违反上述不变量），`_render_review_block` 内一句 `assert` 兜底即可，**不**走「静默
  popleft 丢项」——那样会让前端 `handoff_consumed` / 队列快照对不上。

### 4.2 `<review_target>` 块合成

被审消息原文 + 审阅指引，由 orchestrator 在 pick 时现场合成（P7 §4.6：「临时块由
orchestrator 根据 `HandoffItem` 现场合成，渲染器纯转发」）。**收敛后块内不含任何任务
产物清单**——只是「审这一条消息」。

`Orchestrator._render_review_block(item: HandoffItem) -> str`：

1. `msg = self.room.message_by_id(item.review_message_id)`；
   `assert msg is not None`（§4.1 不变量：drain 时保证命中）。
2. `message_xml = format_messages([msg], self._display_map())`——**复用 `format_messages`**，
   保证被审消息的 `<message>` 包装与茶客平时看到的消息边界完全一致（CLAUDE.md
   `format_messages` 不变量）。
3. 拼成 `<review_target>` 块返回。审阅指引文案是模块常量 `_REVIEW_INSTRUCTION`。

块形态（最终喂给 LLM 的字符串）：

```xml
<review_target>
请你审阅下面这条发言：

<message>
汪小姐 说：……（被审消息原文）……
</message>

请给出你的审阅意见：可以是「通过」「打回」或具体修改建议，并说明理由。
</review_target>
```

- **`<review_target>` 是临时块、无 XML 属性**——不需要 `quoteattr`（被审消息 body 已被
  `<message>` 包装隔离；reviewer 身份由 `<speak_instruction>` 表达，不进本块属性）。
- **块内不含产物清单**（评审收敛，§5.5）：transcript `Message` 没有 artifact 绑定字段，
  「这条消息产出的 artifacts」根本无从谈起；而「该消息所属任务的 artifacts 全集」是
  任务级上下文——这个上下文 `<current_task>` 块**已经**在提供，再在 `<review_target>`
  里塞一份既重复、又要解释「可能与这条不相关」、还稀释「审这一条」的焦点。所以
  `_render_review_block` **不调** `tasks_store.list_artifacts`、不接 `task_id`。
- **被审消息可能同时出现在 `<recent_messages>` / `<room_update>` 里**（它就在 transcript
  中）——茶客会看到同一条消息两次。**接受这个重复**：`<review_target>` 是「审这一条」的
  聚焦指针，`<recent_messages>` 是环境上下文，语义不同；不做跨块去重（去重要 diff 两个
  块的内容、复杂度不值，且被审消息常常已滑出窗口、根本不重复）。

### 4.3 被审消息查找：`Room.message_by_id`

`chahua/room.py` 现有 `_messages: list[Message]` 按 seq 升序密集排列，**无 message_id
索引**。P7.2 加一个查找方法：

```python
def message_by_id(self, message_id: str) -> Optional[Message]:
    """按 message_id 线性查找。review 是低频用户动作，O(n) 一次可接受。"""
    for m in self._messages:
        if m.message_id == message_id:
            return m
    return None
```

- **用线性扫描、不建 dict 索引**：review 是用户手点「请审…」触发的低频动作（一次房间
  会话里个位数次），O(n) 扫一遍 transcript 的成本远低于「维护一个 `_by_message_id`
  dict、在 `append` / `clear` / `load` 三处同步」的冗余状态成本。CLAUDE.md「不加冗余
  状态」口径——能 derive 的就不缓存。
- 查找发生在两处：① inbound handler 校验 message_id 存在（`None` → NOTICE error）；
  ② drain 时 `_render_review_block` 取被审消息 body（按 §4.1 不变量保证命中）。
  两处都 O(n) 一次，都不在热路径。

### 4.4 cancel / cap / wrapper —— 零改动复用

- review turn 跑期间被 cancel（用户点停止 / `handoff_clear`）：走 P7.1 既有的
  `_cancel_fixup_and_flush`——`<review_target>` 块只是 prompt 的一部分，cancel 路径
  不感知块内容，`message_end status=cancelled` + `turn_end(cancelled)` + `flush_turn`
  全部照旧。
- cap：review 项 `cost=1`，与 delegate 同；`_consecutive_ai_turns + 1 > max` 撞顶则
  不 pop、队首留到下次用户触发。
- `_run_handoff_turn` wrapper：swallow `CancelledError`、finally 同槽清 `_inflight_*`——
  **一行不改**。

## 5. 关键设计决策（with rationale）

### 5.1 scope 只支持 `message`

- **只开 `scope=message`**：用户强制从「消息气泡 → 请审…」按钮进入，自带 message_id。
- **不开 `scope=last`**：「刚那条」歧义太大——跨 turn 怎么算？被审消息正好是 user 怎么办？
  误触发风险与测试面都不值。
- **不开 `scope=task`**：「全任务过一遍」语义重，会把一长串 artifacts / decisions 拉进
  prompt；先用消息粒度走通，等用户场景明确再说。
- **不开 slash `@msg_id`**：UI「请审…」按钮已覆盖所有合法 message_id 场景，手输
  message_id 没有真实用户场景——这条同时是「不做右键复制 message id」的根据（§5.5）。

### 5.2 `extra_blocks` 注入：onboarding / incremental 两条路径都接

- `ContextRenderer.build_context_for` 加 `extra_blocks: list[str] | None = None` 参数，
  `_render_onboarding` / `_render_incremental` **两条路径都接**，注入位**统一在
  `<speak_instruction>` 之前**（`<current_task>` / `<order_hint>` 之后）。
- **为什么两条都接**：首次被 review 指派的茶客若此前没在房间发过言 / 长间隔回归，会走
  **onboarding** 分支；只接 incremental 会让这位茶客看不到 `<review_target>`、行为分裂成
  「普通发言」。P7 原文「不进 onboarding」是错的，§4.6 已修正。
- **临时块 vs 永久块是两个独立机制**：
  - `<current_task>` / `<order_hint>` 是「有任务时永远注入」，由 `_render_*` 内部按
    `task_id` 是否非空决定——**不走 `extra_blocks`**。
  - `<review_target>`（及 P7.3 的 `<panel_context>`）是「本轮临时指派」，由 orchestrator
    现场合成、经 `extra_blocks` 传入。渲染器**不认识**这些块的语义，纯转发、纯保序。
- **注入顺序**：`extra_blocks` 列表内顺序即输出顺序，调用方（orchestrator）保证顺序，
  渲染器不重排。P7.2 只会传单元素列表（一个 `<review_target>`）。

### 5.3 「请审…」入口只挂在带 `message_id` 的气泡上

- 现状：用户发言的气泡是**前端本地 echo**——`submit` 时前端立即 `appendBubble(..., kind:
  "user")` 渲一个气泡、但**没有** `message_id`（服务端不回 user envelope，message_id 直到
  下次 `room_history` 重建才补上）；茶客发言的气泡走 `message_start` envelope，**恒带**
  `message_id`。
- **设计**：「请审…」按钮**纯按 `data-message-id` 是否存在**决定显隐——不特判 user /
  茶客。自然结果：茶客发言随时可请审；用户发言要等切房 / 刷新后（`room_history` 重建）
  才可请审。
- **为什么不让后端给本地 echo 回环一个 id**：那要么改「user 消息不回 envelope」的既有
  口径（牵动 local-echo 全链路），要么前端维护「echo 气泡 ↔ 服务端 message_id」的回填
  映射——为「刚发的那条想立刻请审」这个边角场景拉一条新链路，不值。承认这个边角、用
  `data-message-id` 一道门槛挡掉，是最短路径。

### 5.4 review 是单轮一次性，不做接力链

- B 审完即结束（队列空 → `next="user"`）。**不**自动把审阅意见回灌给原作者 A、**不**
  自动让 A 修订。要 A 改，用户再 delegate 给 A 即可。
- **为什么不做自动接力**：「B 审 → A 改 → B 复审 → …」是一个 workflow，属于 P8「任务剧本」
  范畴（见 P7 主文档 §9）。P7.2 的 review 故意保持单粒度，与 delegate 一样「一个动作 =
  一个 turn」，避免两个机制功能重叠、避免在 P7 阶段引入「调度器跑剧本」的复杂度。

### 5.5 评审收敛：删掉的三项 + 理由

初稿被评审判为过度设计 / 落不稳的三项，P7.2 一律删 / 推后：

| 删 / 推后 | 理由 |
|---|---|
| `<review_target>` 附任务产物清单 | 引入 `tasks_store.list_artifacts` + 额外渲染 + 额外测试 + 「可能不相关」的解释负担；任务上下文 `<current_task>` 块已提供，重复且稀释「审这一条」的焦点。老消息所属任务产物以后有**明确需求**再单独加 |
| 右键「复制 message id」 | 与现有右键「标为决策」入口撞，且现有右键菜单在无 active task 时直接报错返回；slash `@msg_id` 既不开（§5.1），就没有「手输 message id」场景——这条 UI 无消费方 |
| 请审刚发出、尚无 `message_id` 的本地 echo 用户消息 | 见 §5.3——为边角场景拉新链路不值，用 `data-message-id` 门槛挡掉 |

收敛后 P7.2 = 纯粹的「消息级 prompt 注入」：被审消息原文进 `<review_target>`、喂给
被指派茶客，没有任何旁路的任务上下文 / 调试 UI / echo 回填。

### 5.6 复用 `format_messages` 渲被审消息

- `<review_target>` 内的被审消息 body 走 `format_messages([msg], display_map)`，输出
  `<message>\n{display} 说：{text}\n</message>`——与茶客在 `<recent_messages>` /
  `<room_update>` / 打分 transcript 里看到的消息边界**完全一致**。
- **理由**：CLAUDE.md `format_messages` 不变量——所有喂 prompt 的消息走同一包装；被审
  消息若另起一套渲染，茶客 LLM 会在「这是一条消息」的 tokenization 边界上看到不一致。

## 6. UI 增量

### 6.1 消息气泡「请审…」按钮（P7.2 新增）

## 7. 关键不变量（落地时同步追写 CLAUDE.md）

- **review 与 delegate 共用调度层、差异只在 prompt 注入**。`run_pending_handoff` drain
  loop 对 review / delegate 走同一套 cap / cancel / turn 末尾 5 步 / `_run_handoff_turn`
  wrapper；`item.kind` 分支只覆盖 `scoring_path` 与 `extra_blocks` 两个值，winners /
  cost / 控制流一字不动。改 drain loop 时**不允许**为 review 单开一条平行 drain 路径。
- **review 只支持 `scope=message`**。inbound `handoff_review` 只接 `message_id`、不解析
  `scope` 字段；`last` / `task` / slash `@msg_id` 都不开。未来开新档另起 inbound `type`。
- **`extra_blocks` 临时块两条渲染路径都接、注入位在 `<speak_instruction>` 之前**。
  `ContextRenderer.build_context_for` 的 `extra_blocks` 参数对 onboarding 与 incremental
  两条路径同步生效；渲染器纯转发不重排、不认识块语义。临时块（`<review_target>`）与
  永久块（`<current_task>` / `<order_hint>`）是两个独立机制——后者由 `_render_*` 内部按
  `task_id` 决定，**不走 `extra_blocks`**。
- **`<review_target>` 只含被审消息原文 + 审阅指引，不附任何任务产物清单**。任务级上下文
  由 `<current_task>` 块统一提供；`_render_review_block` 不接 `task_id`、不调
  `tasks_store.list_artifacts`（评审收敛，§5.5）。
- **「请审…」入口只挂在带 `message_id` 的气泡上**。按钮显隐纯由 `data-message-id` 是否
  存在决定，不特判 user / 茶客。茶客发言气泡恒有 message_id；用户本地 echo 气泡没有，
  要等 `room_history` 重建——「请审刚发出的用户消息」是被接受的边角缺口（§5.3）。
- **drain 时被审消息保证存在，`_render_review_block` 不设 `None` 分支**。inbound 已校验
  `message_id` 命中 + `clear_room` / `reset_room` 清 `_handoff_queue`，review 项不可能
  跨「消息消失」存活；`_render_review_block` 查不到即违反不变量（bug），用 `assert` 兜，
  **不**走「静默 popleft 丢项」（会让前端 `handoff_consumed` / 队列快照对不上）。
- **复用 `format_messages` 渲被审消息**。`<review_target>` 内被审消息走 `format_messages`
  的 `<message>` 包装，与茶客平时看到的消息边界一致（CLAUDE.md `format_messages`
  不变量延伸）。

## 8. 明确不做的事

- **不做 review 接力链**（B 审 → A 自动改 → B 自动复审）。属于 P8 任务剧本，见 §5.4。
- **不做 `scope=last` / `scope=task` / slash `@msg_id`**（§5.1）。
- **不在 `<review_target>` 附任务产物清单**（§5.5）。
- **不做右键「复制 message id」**（§5.5）。
- **不支持请审尚无 `message_id` 的本地 echo 用户消息**（§5.3）。
- **不新增 envelope 类型 / 不 bump `schema_version` / 不新增持久化目录 / 不新增 toml 字段**。
- **不做 AI propose review**（`task_propose_handoff`）——P7.4 统一开 propose 家族。
- **不把被审消息从 `<recent_messages>` 里去重**（§4.2）。
- **不做「审阅结果结构化」**（通过 / 打回 当成 enum 落库）——review 产出就是 B 的一条
  普通群聊发言，进 transcript 即可；结构化是 P8 workflow 的事。

## 10. 主要风险 & 兜底

| 风险 | 兜底 |
|---|---|
| 用户审一条很老的消息，被审 body 巨长撑爆 prompt | `<review_target>` 只放**单条**被审消息——单条消息体量有限。真出现超长单条消息是 transcript 本身的问题，不在 review 层兜 |
| 用户对同一条消息连点「请审…」给不同茶客 | 每点一次入一项；drain 串行逐项跑（B 审完 C 再审）——符合「队列」语义，不去重 |
| review 的茶客 LLM crash / 超时 | 与普通 speak 失败同口径——`message_end status=error`，drain 队列后续项继续 |
| 老前端收到 `item.kind=="review"` | `schema_version` 不动；老前端忽略未知 kind，只是不渲染 review 专属标注，不报错 |
| 用户想请审刚发出的自己那条消息 | 本地 echo 无 `message_id`、按钮不显（§5.3）——接受的边角缺口，切房回来即可审 |
