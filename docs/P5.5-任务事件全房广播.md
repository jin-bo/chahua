## 1. 问题

P5.1 ~ P5.4 把任务房间的"持久化 + UI"两端拉齐了，但**编排侧（orchestrator）几乎是旁路状态**：

| 事件链路 | 当前实现 | 缺口 |
|---|---|---|
| 用户点"开任务"按钮 → server `_inbound_open_task` | emit `TASK_OPEN` hint + `TASK_INFO` 权威快照 | 茶客 prompt 不带"任务被开了"这条事实，下次发言基于过期上下文 |
| 用户点"关任务" → `_inbound_close_task` | emit `TASK_CLOSE` + `TASK_INFO` | 茶客不知道任务完成，可能还在追老话题；该有的小结 / 庆祝 / 复盘发言不发生 |
| 茶客写 `./task/<name>` → `_kick_detect_new_artifacts` (orchestrator.py:858) | emit `TASK_ARTIFACT_ADDED` hint | 其他茶客没被通知有新产物，可能重复劳动 |
| 用户记决策 → `_inbound_add_decision` | emit `TASK_DECISION_ADDED` hint | 茶客后续讨论可能重复已决事项 |

**根因**：task 事件只到 envelope（前端 UI 看得见），不进 transcript（茶客的 LLM prompt 看不见）。同时 orchestrator 的"意愿打分主循环"仅由 `submit_user_message` 触发，task inbound 不 kick scoring → 即便信息进了 prompt，也要等下一条真用户消息才轮到茶客发言。

## 2. 设计：合成一条 user 消息

**核心一句话**：每个 task inbound handler 末尾，合成一句以 "user" 身份说的话，复用现有 `submit_user_message` 路径。

```
[用户在 UI 点"开任务"按钮]
    ↓
server._inbound_open_task
    ├── 落盘 task.json / state.json
    ├── emit TASK_OPEN hint
    ├── emit TASK_INFO 权威快照
    └── server._kick_synthesized_user_message(   ← 新增
            "📋 用户开启任务【报告.md】 · 目标：周五前出初稿",
            sink, task_id=task.id,
        )
            ↓
        _cancel_and_drain_inflight()
            ↓
        _inflight_turn_task = create_task(
            _run_turn(synthesized_text, sink, task_id=...)
        )
            ↓
        orchestrator.submit_user_message(...)
            ├── room.append(USER_SPEAKER_ID, text, task_id=...)
            │   —— 进 transcript.jsonl，茶客 LLM 可见
            │   —— 不 emit user envelope（orchestrator.py:307 注：用户消息
            │     依赖前端 local echo 显示，非事件回放）
            └── _run_ai_chain  ← 打分循环自然触发
```

**语义解释**：用户在 UI 上点"开任务"按钮 = 用户行为；紧跟一句合成的"📋 用户开启任务【X】"逻辑上等同于用户用按钮代替了打字。茶客视角：刚刚用户说了句话，按平常的打分流程响应即可。

**重要边界**：`submit_user_message` 不 emit user envelope，真用户消息靠前端本地 echo 显示气泡；**合成消息没有 echo 路径，本次会话内不进聊天气泡**。它的两条保证是：
1. 进 `transcript.jsonl`（茶客下一轮 prompt 看得见）
2. 触发 orchestrator scoring 循环（茶客可能因此发言）

切房 / 刷新后从 `room_history` 重建时会带上这条 user 消息显示成气泡 —— 接受这个"重启后才可见"的口径，不为合成路径补 user envelope。

## 3. 为什么不引入 system 类型？

考虑过且**已否决**的方案：给 `Message` 加 `kind="system"`、新增 `append_system_note` API、`format_messages` 加分支、新 envelope kind / `<system_note>` XML 包、新 `_run_system_turn`。

| 维度 | 引入 system 类型 | 合成 user 消息（本方案） |
|---|---|---|
| `Message` 数据模型 | 加 `kind` 字段 + loader 兼容 | 零改 |
| `format_messages` 渲染 | 加 system 分支 | 零改（`用户 说：📋 ...`） |
| Envelope schema | 新 kind 或加 `participant="system"` | 零改（合成消息不走 user envelope —— 与真用户消息同口径） |
| Scoring 接入 | 新 `_kick_orchestrator_after_system_event` + `_run_system_turn` | 零改（`submit_user_message` 自带 kick） |
| Prompt 渲染 | 茶客看到"〔系统〕..." | 茶客看到"用户 说：📋 ..." |
| 前端实时聊天气泡 | 需要按 kind 走特殊气泡 + 新 envelope | **本次会话不显示**（无 echo）；切房 / 刷新后从 `room_history` 重建出现，挂"用户"头像 |

**代价**：合成消息本会话内只活在 transcript / 茶客 prompt 里，前端聊天流不出现；切房或刷新后才补上"用户"头像气泡。**收益**：代码改动约是 system-type 方案的 1/10，MVP 当晚可落地。前端已有 task hint / `TASK_INFO` 实时显示，用户操作有反馈，不靠这条合成消息撑 UX。

## 4. 实施

### 4.1 新 helper：`server._kick_synthesized_user_message`

新增位置：`chahua/server.py`，紧邻 `_inbound_user_message` (server.py:749) 与 `_run_turn` (server.py:637)。

`sink` 由调用方（task handler）直接透传 —— 它本来就是 `_handle_inbound(data, sink)` 链路上下来的当前连接 emitter（在 `_serve_one` 里是 `sink: EnvelopeSink = lambda env: outbound.put_nowait(env.to_dict())`, server.py:331），helper 不自己造 emitter。

```python
async def _kick_synthesized_user_message(
    self,
    text: str,
    sink: EnvelopeSink,
    *,
    task_id: Optional[str],
) -> None:
    """系统侧合成的"用户消息"。语义：UI 上按钮操作 = 用户行为，紧跟一句话。

    与 _inbound_user_message 的差异：
    - text 由 server 端构造（emoji 前缀 + 任务摘要），不来自 ws 帧
    - 串行口径：先 _cancel_and_drain_inflight 再创建新 turn，与 add_guest /
      set_active_task 同口径 —— 任何改变房间状态的用户操作都重启 in-flight turn
    """
    await self._cancel_and_drain_inflight()
    self._inflight_turn_task = asyncio.create_task(
        self._run_turn(text, sink, task_id=task_id),
    )
```

### 4.3 茶客侧 artifact 自动归集

`orchestrator._kick_detect_new_artifacts` (orchestrator.py:858) 当前只 emit `TASK_ARTIFACT_ADDED` hint 与 `TASK_INFO` 快照。增量加一条合成消息 —— 但**这条不能走 `submit_user_message`**（已在 in-flight turn 里，会和自己冲突）。

**采用：只 `room.append` 一条 user 消息，不另 kick turn**

- 茶客侧 artifact 检测发生在 `_run_ai_chain` 的 pick 周期**末尾**；**若 AI 链还有后续 pick，自然在下一轮被消费；若本轮已到 `max_consecutive_ai_turns` 上限、链条收尾，则这条新 transcript 行留到下一次用户消息（或合成 user 消息）触发新的 AI 链时再进 prompt**。两种情况都不丢，只是延迟不同。
- 实现：直接 `self.room.append(USER_SPEAKER_ID, text, task_id=active_task_id)`（见 `chahua/room.py:161`），不走 `submit_user_message`
- 文案：**泛化、不追踪作者** —— `📎 茶客产出：a.md, b.png`。当前扫描只知道"目录里冒出新文件"，并不知道哪位茶客写的（`created_by=ARTIFACT_CREATED_BY_GUEST` 是个全集标签，不是茶客名，见 orchestrator.py:904）。把多个新文件合并到一条避免连发刷屏。

**不做跨组件 dedupe**：用户走 UI `attach_artifact` 上传后，下一次 `_kick_detect_new_artifacts` 仍会把这些文件当成"新"重新 append 一条 `📎 茶客产出：...`。沿用 orchestrator.py:870-873 的既有口径 —— "不在两个组件间加 sync 通道避免耦合"，**接受 transcript 上同一文件可能出现两行**（`📎 用户挂载产物：x` + `📎 茶客产出：x`）。前端 `task_info` 已是权威，茶客 prompt 多看一行无大碍。

## 5. 不变量

- **task event 合成消息走 `speaker_id="user"`，不引入新 speaker 类型**。
- **合成消息不 emit user envelope**。与真用户消息口径一致（`submit_user_message` 不 emit，靠前端 local echo 显示）；合成路径无 echo，本会话内**不进聊天气泡**，切房 / 刷新后从 `room_history` 重建时才出现。代码层不需要为此做额外事，保持简单。
- **合成消息与真用户消息共用 `_inflight_turn_task` slot**。 task handler 走 `_cancel_and_drain_inflight + create_task(_run_turn)` 与 `_inbound_user_message` 完全同路径，并发模型同 add_guest / set_active_task。
- **茶客侧 artifact 检测不重启 turn**。 `_kick_detect_new_artifacts` 仅 `self.room.append(USER_SPEAKER_ID, ...)` 直写 transcript：若 AI 链还有后续 pick，自然在下一轮被消费；若本轮已到 `max_consecutive_ai_turns` 上限、链条收尾，则留到下一次用户 / 合成消息触发新的 AI 链再进 prompt（详见 §4.3）。**不调** `submit_user_message`（已在 in-flight turn 里会自冲突）。
- **set_active_task 不发合成消息**。 纯 UI 焦点切换，transcript 不该多一行；茶客对 active 切换的感知通过下一次 prompt 注入的 `<current_task>` XML 块（onboarding / incremental 两路径都覆盖）天然完成。
- **update_task 不发合成消息（P5.5 范围）**。要做 old/new diff 才能挑出实质变更，复杂度不值；推到 §9 后续。
- **artifact 合成文案不追踪作者**。 `_kick_detect_new_artifacts` 只知"目录冒出新文件"，不知道哪位茶客写的；统一泛化"📎 茶客产出：..."。不为此引入跨组件作者追踪。
- **不做跨组件 artifact dedupe**。 沿 orchestrator.py:870-873 既有口径，接受用户 UI 上传 + 后续扫描 = transcript 两行（详见 §4.3）。
- **文案在 `chahua/task_event_text.py` 单点维护**。 不允许 handler 内 inline 拼字符串。

## 6. 明确不做的事

- **不引入 `Message.kind` 字段** —— 维持 speaker_id 单字段语义。
- **不为合成消息补 user envelope** —— 真用户消息也不 emit；合成路径不破例。代价是本会话内不显示气泡（详见 §5），接受。
- **不引入 `<system_note>` XML 块或新 envelope kind** —— 现有 `format_messages` 直接复用。
- **不做 transcript 视觉美化** —— 切房 / 刷新后挂"用户"头像的 emoji 前缀消息丑但能用；前端 sniff emoji 前缀渲染成横线是独立 PR（§9）。
- **不做 `update_task` 广播** —— 要 diff old/new 太复杂；推到 §9。
- **不做合成消息频率控制 / debounce** —— 唯一可能高频的 `_kick_detect_new_artifacts` 已通过"同周期多文件合并一条"压住。其它都是用户主动操作，天然不连发。
- **不做合成消息的"撤回 / 编辑"**。 transcript append-only 口径不变。
- **不追踪 artifact 作者**。 文案泛化 `📎 茶客产出：...`，不写哪位茶客（详见 §4.3）。
- **不让茶客主动合成"广播消息"**。 写权限只在用户（沿 P5.3.4 / P5.3.7 propose 不直接写库口径）；茶客侧只有"自己写的产物被扫到 → 合成泛化通报"这种被动出现。
- **不做跨组件 artifact dedupe**（详见 §4.3 / §5）。

## 7. 主要风险 & 兜底

| 风险 | 触发条件 | 兜底 |
|---|---|---|
| 茶客把合成消息当真用户消息回复（"用户为啥用第三人称提到自己？"） | LLM 误解 emoji 前缀 | 实测大多数模型能从 emoji + 句式 + `<current_task>` 上下文推断这是元描述。若发现高频误解，在 `<speak_instruction>` 里加一行"用户消息以 📋 / ✅ / 📎 等 emoji 开头时为 UI 操作回执，可视作上下文不直接回应" |
| 用户连续点多个 task 按钮 → 多次 `_cancel_and_drain_inflight` 让茶客一直被打断说不完话 | 用户 UI 上 5 秒内开 3 个任务 | 接受 —— 现实场景极少；与 add_guest 连按相同代价。若实测痛，加 100ms debounce 到 `_kick_synthesized_user_message` |
| 茶客对每个 task 事件都尝试发言 → 任务密集房间刷屏 | 一天 50+ 个 task 操作 | scoring 阈值 (`want_threshold=0.45`) 已经过滤；若不够，可对合成消息加 `scoring_dampen=0.7` 系数（先观察再加） |
| 用户上传与扫描扫到的 artifact 在 transcript 上重复成两行 | 用户 UI 上传后下一轮 pick 周期 | **接受**，沿 orchestrator.py:870-873 既有口径，不加 dedupe 通道（详见 §4.3） |
| 合成消息在本会话内不出现在聊天气泡 | 所有合成消息（合成消息不 emit user envelope） | **接受** —— 前端已有 task hint / `TASK_INFO` 卡片显示 UI 反馈，不靠这条；切房 / 刷新后从 `room_history` 重建会补上 |

- **本会话内聊天气泡**：若需要合成消息也实时显示气泡，给 `submit_user_message` 加可选 `emit_user_envelope=True` 参数；为合成路径补一帧 `MESSAGE_END(speaker_id="user", seq=...)`。代价是真用户消息和合成消息要分别打开关；先观察用户对"只在切房后看见"的接受度再决定。
- **前端样式**：sniff emoji 前缀（📋/✅/✗/📎/📌）渲染成横线分隔条，去掉"用户"头像 —— 纯前端 PR。
- **茶客 propose 的全局广播**：当前 `task_propose_decision` / `task_propose_open` 只 emit `TASK_PROPOSAL` envelope 给前端渲染采纳卡；若希望其它茶客也能看见提议并讨论，可在 propose 工具内追加 `room.append(<茶客名>, text="（提议）...")` —— 但这违反"茶客对 task 的写操作要走采纳"口径，需重新讨论是否值得开口子。**P5.5 不做**。
- **合成消息可读性**：长 `goal` (>80字) 在合成文案里截断成首行 + "..."；完整 goal 已经在 `<current_task>` XML 块里，重复给茶客不增信息。
