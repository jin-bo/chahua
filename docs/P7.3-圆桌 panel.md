# P7.3：显式 handoff —— panel（圆桌）

> 目标：在 P7.1 已落地的「确定性发言指派通道」之上，加入第三个动作 **panel（圆桌）**——
> 用户多选 N 位茶客（可选再指定一位汇总者 F），这 N 位 + F 在**同一个 turn 内串行**各发
> 一次：N 位先给平行观点，F 最后发一条 consolidate。绕开「单 turn 只 1~2 个 speak」的
> 打分上限。
>
> P7.3 与 P7.1/P7.2 的差别：review 与 delegate 在调度层**完全同构**（单目标 `cost=1`），
> P7.2 因此「控制流一字不动」。**panel 不同构**——它是**多目标**（`winners=list(targets)
> [+summarizer]` / `cost=N(+1)`），drain loop 的 `cost` / `winners` / `next_cost` 三处必须
> 开 `kind` 分支。但 panel **仍不开新 drain 路径、仍是队列里的一个自描述 item**：复用同一
> 个 `run_pending_handoff` while 循环、同一套 cap / cancel / turn 末尾 5 步 / wrapper。

**状态：设计稿 v2（2026-05-20，按评审收敛重写）**。上游契约见
[`P7-显式 handoff 与 delegation.md`](P7-显式%20handoff%20与%20delegation.md) §2.3 / §3.1 / §3.4 /
§4.2 / §4.6 / §7；P7.1 落地见同文件 §12 表，P7.2 落地见
[`P7.2-请审 review.md`](P7.2-请审%20review.md)。落地拆分见本文 §11。

> **v1 → v2 收敛（2026-05-20 评审）**：v1 草案沿 P7 §2.3 把 summarizer 设计成**独立入队的
> 第二个 `HandoffItem`**，靠 `panel_group_id` 与 panel item 关联。评审指出这条路线有三个
> 连带问题：① 「panel + summarizer 同一次 drain 跑完」的承诺不成立（cap 数学没法把跨 turn
> 已消耗的轮数算进去）；② panel 的 target 被运行时过滤光时会留下「孤儿 summarizer」去汇总
> 一场不存在的圆桌；③ `panel_group_id` 从「展示分组字段」被迫升格成「调度语义字段」，制造
> 出「相邻 + 同组 + 前项必须真跑过」这条跨两项的隐式不变量。**v2 把 summarizer 收进 panel
> item 自身**（`HandoffItem.summarizer` 字段）、且让它在**同一个 turn** 内作为最后一位
> speaker —— 一个自描述 item、一个 turn、一次 cap 决策，三个问题同时消失。详见 §5.3。

## 0. 本阶段做 / 不做

**做**：

- `HandoffKind` 加 `PANEL` 一档；`HandoffItem` 加 `targets: tuple[str, ...]` +
  `summarizer: Optional[str]` 两字段；`to_dict()` 同步（`targets` 元组转 list）。
- `handoff.py` 加 `MAX_PANEL_TARGETS = 4` 模块常量。
- inbound `handoff_panel`（`{type, targets, summarizer?}`）：白名单严格 + 五道校验 +
  **cap 数学**（panel turn 的 `N(+1)` 轮 ≤ `max_consecutive_ai_turns`）。**单 item 入队**，
  `_enqueue_handoff_and_maybe_start` 签名不动。
- `run_pending_handoff` drain loop 加 `kind` 分支：panel → `winners=list(targets)
  [+summarizer]` / `cost=len(winners)` / `scoring_path=handoff_panel` / 逐 winner 算
  `extra_blocks`（panelist 给 `<panel_context>`、summarizer 给 `<panel_summary_request>`）。
- `Orchestrator._render_panel_block`（列圆桌成员 + 平行发言指引）+ 模块常量
  `_PANEL_SUMMARY_BLOCK`。
- debug `VALID_SCORING_PATHS` 加 `handoff_panel`。
- UI（最小闭环）：茶客侧栏多选「圆桌」模式 + panel 配置 popover（summarizer 下拉）；队列
  预览能显示 panel 项。**客户端 cap 预校验 + 调试抽屉徽标推到 polish commit**（§6 / §11）。

**不做**（推后 / 永不做）：

- **不真并行**（不同时 emit N 个 `message_start`）——串行执行 + UI 标注「并行讨论中」，
  prompt 注入「平行意见」提示缓解先发言污染（§5.2 / P7 §4.2）。
- **不**把 summarizer 拆成独立入队的第二个 `HandoffItem`（v1 路线，评审否决，§5.3）——
  summarizer 是 panel item 的一个字段，跑在同一个 turn 里。
- **不**引入 `panel_group_id` / `Sequence[HandoffItem]` 入队 / 前端相邻分组（v1 的连带
  复杂度，§5.3 全部删除）。
- **不**把 panel 拆成 N 个 turn——panel 是**一个** item、跑**一个** turn、N(+1) 个
  message（§5.1）。
- **不开 `[panel]` toml 段**——`MAX_PANEL_TARGETS = 4` 是模块常量；`default_summarizer` /
  `parallel_prompt_hint` 开关都不开（§5.6）。
- **不**新增 envelope 类型——`handoff_enqueued` / `handoff_consumed` / `handoff_cleared`
  P7.1 已全加，panel 复用；**不** bump `schema_version`。
- **不**做 AI propose panel（`task_propose_handoff`）——P7.4 统一开 propose 家族。
- **不**做「圆桌完 → 自动接力」之类 workflow——属 P8 任务剧本。
- **不**新增持久化目录 / 不让队列落盘（与 P7.1 同口径，瞬态、crash 即丢）。

## 1. 现状速写 —— P7.1 / P7.2 留下的复用面

| P7.1 / P7.2 已落地 | P7.3 怎么蹭 |
|---|---|

| `_let_speak(guest, *, turn_id, sink, task_id, extra_blocks)` | **零改动**复用——P7.2 已加 `extra_blocks` 形参 |
| `_inbound_handoff_delegate` / `_inbound_handoff_review` + `_enqueue_handoff_and_maybe_start` 共享尾段 | 加平级 `_inbound_handoff_panel`；`_enqueue_handoff_and_maybe_start` **签名不动**（panel 仍是单 item 入队，§3.5） |
| envelope `HANDOFF_ENQUEUED` / `HANDOFF_CONSUMED` / `HANDOFF_CLEARED` | **零新增**——panel 项走同样三个 |
| debug `VALID_SCORING_PATHS` + `SCORING_PATH_HANDOFF_{DELEGATE,REVIEW}` | 加 `SCORING_PATH_HANDOFF_PANEL` 一条 + 白名单一行 |
| `_render_review_block` 现场合成临时块的范式 | `_render_panel_block` 照搬范式（读 `item` + `_display_map`，纯转发） |
| 前端 `handoff_state.js` / `handoff_queue_bar.js` / `handoff_popover.js` | 队列预览加 panel 项渲染（**单项渲染**，无分组）；新增「圆桌」多选模式 + panel 配置 popover |

**最重要的判断**：P7.2 的 review 与 delegate 同构，所以 P7.2 能宣称「winners / cost /
控制流一字不动」。**P7.3 的 panel 打破这个对称**——一个 panel item 对应 N(+1) 次 speak，
`cost`、`winners`、turn 末尾 peek 的 `next_cost` 三处都要认 `kind`。但 panel **仍是队列里
一个普通的、自描述的 item**：drain loop 一次 pop、跑一个 turn、turn 边界 / cap / cancel /
wrapper 全部复用。`for name in winners` 串行循环 P7.1 早就写成「遍历 winners」形态，
delegate / review 只是恰好 `len(winners)==1`——panel 把它真正用到 N(+1)。

## 2. 动作形态：panel（圆桌）

```
用户触发：UI 茶客侧栏「圆桌」多选模式 → 勾 N 位茶客 + 可选 summarizer 下拉 → 发起圆桌
        / 聊天框 /panel @C @D @E --summarizer=@F   （slash 形式留作未来，P7.3 只做 UI）
AI propose：P7.4 才开 —— 茶客自己拉圆桌的成本/收益不对称
```

- **效果**：N 位指定茶客 + 可选 summarizer F 在**同一个 turn** 内**串行**各发一次——N 位
  先依次给平行观点，F 最后发一条 consolidate。整轮跑完 → 队列空（或下一项）→ 等用户。
- **panel = 一个 `HandoffItem`，跑一个 turn**：
  - `HandoffItem.targets` 持 N 个 panelist 名（元组）；`HandoffItem.summarizer` 持可选的
    汇总者名。
  - drain loop pop 出后 `winners = list(targets) + ([summarizer] if summarizer else [])`，
    在**一个 `turn_id`** 下串行 speak `len(winners)` 次。
  - 对应 debug 抽屉里**一条** turn（含 N(+1) 个 message，最后一个是汇总）、一次
    `turn_start` / 一次 `turn_end`。**不拆 N 项、不拆 N 个 turn**（§5.1）。
- **summarizer 在同一个 turn 里作为最后一位 speaker**（v2 收敛，§5.3）：它不是独立 turn、
  不是独立队列项，就是 `winners[-1]`。它 speak 时 N 位 panelist 的发言已串行 append 进
  transcript，summarizer 的 context 自然包含——`<panel_summary_request>` 块只需告诉它
  「请汇总刚才这轮圆桌」。
- **串行不是真并行**（§5.2 / P7 §4.2）：N(+1) 位在一个 turn 里依次 speak，先发言的会进
  transcript、后发言的茶客 onboarding/incremental context 里**看得见**前者。所以「平行」
  在执行层是假的——用 `<panel_context>` 块的 prompt 提示缓解（「独立给出你的观点、不必
  附和或复述」），UI 标注「并行讨论中」让用户知道这是**逻辑**并行。
- **panel turn 是原子的**：N 位 panelist + summarizer 在同一个 turn / 同一个队列 item /
  同一次 cap 决策里——要么整轮跑（含汇总），要么整项留在队首等下次用户触发。**不存在**
  「panel 跑了、summarizer 被推迟」的中间态（这正是 v1 双 item 路线的硬伤，§5.3）。
- **handler 抢占行为**与 delegate / review 一致（§3.5）：in-flight 是 user-turn → cancel +
  入队 + 启 drain；是 handoff drain → 只 append（一项）、不抢占；无 in-flight → 入队 +
  启 drain。
- **panel 不带 `reason`**：inbound 协议只有 `{type, targets, summarizer?}`。与 review 同
  理——「拉这几位开圆桌」语义自洽，targets 已把意图说清，不再加自由文本备注。

## 3. 数据契约

### 3.1 `HandoffKind` / `HandoffItem` 增量

`chahua/handoff.py`：

```python
class HandoffKind(str, Enum):
    DELEGATE = "delegate"
    REVIEW = "review"
    PANEL = "panel"              # ← P7.3 新增

MAX_PANEL_TARGETS = 4
"""panel 一项的 panelist 数硬上限（P7.3 起步阶段模块常量，不进 toml，§5.6）。
不含 summarizer——summarizer 是第 N+1 位，cap 数学单独把它算进 turn 预算（§3.3）。"""

@dataclass(frozen=True, slots=True)
class HandoffItem:
    kind: HandoffKind
    target: Optional[str] = None              # delegate / review 单目标
    targets: Optional[tuple[str, ...]] = None # ← P7.3 新增；panel 的 panelist 名（≥2）
    summarizer: Optional[str] = None          # ← P7.3 新增；panel 的可选汇总者
    issued_by: str = HANDOFF_ISSUED_BY_USER
    reason: Optional[str] = None
    review_message_id: Optional[str] = None
    created_at_ms: int = field(default_factory=now_ms)

    def to_dict(self) -> dict:
        return {
            "kind": self.kind.value,
            "target": self.target,
            "targets": list(self.targets) if self.targets is not None else None,
            "summarizer": self.summarizer,
            "issued_by": self.issued_by,
            "reason": self.reason,
            "review_message_id": self.review_message_id,
            "created_at_ms": self.created_at_ms,
        }
```

- **`targets` 用 `tuple` 不用 `list`**（P7 §3.1 评审反馈 v7-#4）：`dataclass(frozen=True)`
  只锁字段重绑、不锁内部容器；用 `list` 即便 frozen，外部 caller 仍能 `item.targets.append(...)`
  改掉队列里的 targets。`to_dict()` 时再转 `list` 给 envelope / JSON。
- **`summarizer` 是 panel item 自己的字段**（v2 收敛，§5.3）——一个 panel item 完整自描述
  「哪 N 位 + 谁汇总」，drain loop 不必跨两个队列项拼语义。**没有 `panel_group_id`**。
- **各 kind 的字段口径**（构造点只有 inbound handler 一处，**不做** dataclass 级互斥校验，
  与 P7.1/P7.2 同口径）：
  - `delegate`：`target` 非空；`targets` / `summarizer` / `review_message_id` 恒 `None`。
  - `review`：`target` + `review_message_id` 非空；`reason` 恒 `None`。
  - `panel`：`targets`（≥2 项）非空；`summarizer` 可空可非空；`target` / `review_message_id`
    / `reason` 恒 `None`。

### 3.2 inbound 协议（user → server）

```jsonc
{ "type": "handoff_panel", "targets": ["C", "D", "E"], "summarizer": "F" }
// summarizer 可缺省：
{ "type": "handoff_panel", "targets": ["C", "D"] }
```

- **白名单严格**：`_HANDOFF_PANEL_ALLOWED = {"type", "targets", "summarizer"}`；未知字段
  → NOTICE error + 丢帧（同 `room.toml` / `open_task` / `handoff_delegate` 口径）。

### 3.3 五道校验（任一失败 → NOTICE error + 不入队）

1. **`targets` 是 list**，每项是非空 str。
2. **`len(targets) ≥ 2`**——panel 至少两人。单人「圆桌」语义为零、且等价 delegate，应当用
   `/delegate`；inbound 直接拒，不静默降级。
3. **`targets` 去重后仍 == 原长**（无重复），且每项 `in orchestrator.guest_names`（在场）。
4. **`summarizer` 若存在**：非空 str、在场、且 `summarizer not in targets`——summarizer 的
   语义是「汇总**别人**的圆桌发言」，自己既是 panelist 又是 summarizer 会让
   `<panel_summary_request>`「请汇总刚才几位的发言」自指、语义混乱。
5. **cap 数学**——panel turn 的总 speak 轮数不得超 `max_consecutive_ai_turns`：

   ```python
   max_ai = orchestrator.config.max_consecutive_ai_turns
   has_summ = 1 if summarizer else 0
   cap = min(MAX_PANEL_TARGETS, max_ai - has_summ)
   if len(targets) > cap:
       → NOTICE error：「圆桌人数 N 超出上限 cap（受 max_consecutive_ai_turns
         与 MAX_PANEL_TARGETS=4 约束）；请减少茶客或去掉汇总者」
   ```

   - panel turn 的 `cost = len(targets) + has_summ`；要让它**有可能**跑起来，必须
     `cost ≤ max_ai`，即 `len(targets) ≤ max_ai - has_summ`。叠加 token 上限
     `len(targets) ≤ MAX_PANEL_TARGETS`，合并即上式。
   - 有 summarizer 且 `max_ai ≤ 1` → `cap ≤ 0` → 任何 `len(targets) ≥ 2` 都被拒：
     此配置下 panel+summarizer 组合天然禁用（P7 §2.3）。
   - 无 summarizer 且 `max_ai == 1` → `cap = min(4, 1) = 1` → `len(targets) ≥ 2` 被拒：
     panel 至少 2 人、至少要 2 轮预算，`max_ai=1` 跑不下，拒得对。
   - **这道校验是「能不能跑」的静态判断**（与 `room.toml` 抓 typo「错配置宁可炸」同口径）：
     用户配了一个无论如何跑不动的圆桌，当场 NOTICE error 告诉他。**「现在跑得动吗」是 drain
     loop 的 while-entry cap 检查负责**（§4.1）——那里拿 live 的 `_consecutive_ai_turns`
     与 `cost` 比；inbound 校验不预测运行时计数。
   - 因为 panel + summarizer 是**同一个 item、同一个 turn、一次 cap 决策**（§5.3），不存在
     v1「panel 跑了 summarizer 被推迟」的中间态——cap 检查通过即整轮跑，不通过即整项等。

### 3.4 envelope（server → user）—— 零新增

panel 项走 P7.1 已有的三个 envelope，**不加新类型**：

| 事件 | panel 的语义 |
|---|---|
| `handoff_enqueued` | `data.queue` 含 panel item 的 `to_dict()`（带 `kind:"panel"` / `targets` / `summarizer`）；前端整体替换 `handoffQueueState`，把这一项渲成「圆桌：C、D、E → 汇总:F」一条 |
| `handoff_consumed` | drain loop pop panel item、`turn_start` 之后 emit；顶层 `turn_id`，`data.item` 是 panel item dict（`targets` 已是 list） |
| `handoff_cleared` | `handoff_clear` 丢弃 panel 项时，`items_dropped` 列出该项 |

`schema_version` 不动——老前端忽略 `item.kind=="panel"` 这种未知 enum 值、忽略 `targets` /
`summarizer` 未知字段，不报错，只是不渲染 panel 专属文案。

### 3.5 抢占 / 启动 —— 照搬 delegate / review，单 item 入队

`_inbound_handoff_panel` 校验通过后构造**一个** `HandoffItem`：

```python
item = HandoffItem(
    kind=HandoffKind.PANEL,
    targets=tuple(targets),
    summarizer=summarizer,            # None or str
)
await self._enqueue_handoff_and_maybe_start(item, sink)   # ← 签名不动
```

- **panel 是单 item 入队**——`_enqueue_handoff_and_maybe_start(item, sink)` 的 P7.2 签名
  **一字不改**。v1 曾要把它改成接 `Sequence[HandoffItem]`（因为要一次入 panel + summarizer
  两项），v2 收进单 item 后这条改动连同 `panel_group_id` / 原子双入队一并删掉（§5.3）。
- 抢占语义（`_inflight_kind == "user"` → cancel 抢占；`== "handoff"` → 只 append 队尾；
  `is None` → 不需 cancel）与 delegate / review **逐行同构**，不重新论证。

### 3.6 debug 落盘

- `chahua/debug_recorder.py` 加 `SCORING_PATH_HANDOFF_PANEL = "handoff_panel"` 常量 +
  `VALID_SCORING_PATHS` frozenset 加一条。
- panel turn `record_scoring(scoring_path="handoff_panel", winners=winners, ...)`——
  `winners` 是 N(+1) 个名字（含 summarizer），`results` 是 N(+1) 个 `ScoreResult`。
- **整个 panel turn（含 summarizer 那一发）的 `scoring_path` 都是 `handoff_panel`**——
  summarizer 是这个 turn 的最后一位 speaker，不是独立 turn，不另算 `handoff_delegate`。
  （这是 v2 比 v1 更简单的一处：v1 summarizer 是独立 delegate turn，要解释「summarizer
  turn 的 scoring_path 为何是 delegate」；v2 没有这个分叉。）
- `start_turn` 的 `trigger={"kind":"handoff","handoff_item": item.to_dict()}` 自动带
  `targets` / `summarizer`，**不扩 recorder API**。
- `turn_start` envelope `data.scoring_path == "handoff_panel"`——前端调试抽屉据此渲徽标。

## 4. 执行：drain loop 的 `kind` 三路分流

### 4.1 `run_pending_handoff` 的改动面

P7.2 的 drain loop 在 pop 出 `item` 之后只用 `item.kind` 算 `scoring_path` + `extra_blocks`
两个值（review vs delegate），`cost` / `winners` / `next_cost` 全写死 delegate 形态。
P7.3 把这三处也开 `kind` 分支。把分支收进一个纯函数 `_resolve_handoff_render(item)`：

```python
def _resolve_handoff_render(
    self, item: HandoffItem,
) -> tuple[list[str], str, list[Optional[list[str]]]]:
    """按 item.kind 算 (winners, scoring_path, winner_blocks)。
    winner_blocks 与 winners **等长对齐**——drain loop 的 speak 循环 zip 两者，
    逐 winner 取自己的 extra_blocks。delegate / review 单 winner、单块；panel
    的 panelist 取 <panel_context>、summarizer 取 <panel_summary_request>。
    纯函数——不 emit、不 await、不读 store 之外的状态。"""
    if item.kind is HandoffKind.PANEL:
        assert item.targets is not None
        panel_block = self._render_panel_block(item)
        winners = list(item.targets)
        winner_blocks: list[Optional[list[str]]] = [[panel_block]] * len(winners)
        if item.summarizer is not None:
            winners.append(item.summarizer)
            winner_blocks.append([_PANEL_SUMMARY_BLOCK])
        return winners, SCORING_PATH_HANDOFF_PANEL, winner_blocks
    if item.kind is HandoffKind.REVIEW:
        return ([item.target], SCORING_PATH_HANDOFF_REVIEW,
                [[self._render_review_block(item)]])
    return [item.target], SCORING_PATH_HANDOFF_DELEGATE, [None]   # DELEGATE
```

drain loop body 改动：

```python
item = self._handoff_queue[0]
# cost 用声明值——panel = panelist 数 + 有无 summarizer。
cost = (len(item.targets) + (item.summarizer is not None)
        if item.kind is HandoffKind.PANEL else 1)
# 两档 cap 检查（§4.1.1）——次序不能反：
# ① cost 已超过 max 本身 → 此项永远跑不动 → pop + drop + WARN（不能 break，
#    否则永久挡住队首）。
if cost > self.config.max_consecutive_ai_turns:
    _log.warning("handoff item cost %d exceeds max_consecutive_ai_turns=%d; "
                 "dropping: %r", cost, self.config.max_consecutive_ai_turns, item)
    self._handoff_queue.popleft()
    continue
# ② 没超 max 本身、只是此刻 _consecutive_ai_turns 占了预算 → break、留队首，
#    下次用户触发 + drain 入口清零后能跑。
if self._consecutive_ai_turns + cost > self.config.max_consecutive_ai_turns:
    break
self._handoff_queue.popleft()

winners, scoring_path, winner_blocks = self._resolve_handoff_render(item)
# winners 与 winner_blocks 必须等长——漏配会让下面 zip 静默截断 speaker。
assert len(winners) == len(winner_blocks)
# 跨 turn 残留项再校验在场（用户后续 remove_guest 可能让 winner 失效）。
# winners 与 winner_blocks 等长，必须**同步过滤**。
kept = [(w, b) for w, b in zip(winners, winner_blocks)
        if w is not None and w in self._guests]
winners = [w for w, _ in kept]
winner_blocks = [b for _, b in kept]
if self._panel_underfilled(item, winners):   # §4.4 —— panel 有效人数 < 2 → 整项丢弃
    _log.warning("panel item underfilled after revalidation; dropping: %r", item)
    continue
if not winners:                              # delegate / review 单 target 失效
    _log.warning("handoff item target unavailable; dropping: %r", item)
    continue
# ... start_turn / record_scoring(winners=winners) / _emit_turn(TURN_START)
#     / _emit_handoff_consumed ...
try:
    for name, blocks in zip(winners, winner_blocks):   # panel = N(+1) 次串行 speak
        await self._let_speak(name, turn_id=turn_id, sink=sink,
                              task_id=task_id, extra_blocks=blocks)
        self._consecutive_ai_turns += 1
except asyncio.CancelledError:
    self._cancel_fixup_and_flush(sink, turn_id=turn_id)
    raise
# ... turn 末尾 5 步（peek next_cost / turn_end / flush / hooks / return）...
```

- **`cost` / `winners` / `next_cost` 三处认 `kind`**——这是 P7.3 与 P7.2「控制流一字不动」
  的本质差别。但 `for ... in winners` 串行循环、turn 边界、cancel fixup、turn 末尾 5 步
  **全部不动**——panel 只是让 `len(winners)` 从 1 变成 N(+1)，并把单一 `extra_blocks`
  换成与 winners 等长的 `winner_blocks` 列表 zip 进循环。
- **`winner_blocks` 与 `winners` 等长对齐**——这是 panel「panelist 与 summarizer 拿不同
  prompt 块」的承重点。delegate / review 是 `[None]` / `[[block]]` 单元素，行为与 P7.2
  完全一致（zip 单元素 = 原来的单值）。
- **panel 的 N(+1) 次 speak 在同一 `turn_id` 下**：`new_turn_id()` 一次、`start_turn`
  一次、`record_scoring` 一次（winners=N(+1) 个）、`_emit_turn(TURN_START)` 一次、N(+1) 个
  `message_start`/`message_end`、`_emit_turn(TURN_END)` 一次、`flush_turn` 一次。
- **`cost` 用声明值**（`len(targets) + has_summ`，不因 §4.4 runtime 过滤而变）：while-entry
  cap 检查偏保守可接受——过滤掉失效 winner 后实际 speak 数 ≤ cost，`_consecutive_ai_turns`
  按实际 `+1` 累加，计数始终准确。`next_cost` peek 同口径。
- **panel turn 原子**：§4.1.1 的两档 cap 检查通过即 pop + 整轮跑（含 summarizer）；档 ②
  不通过即不 pop、队首留着。**没有「panel 跑一半、summarizer 留到下次」的可能**——它们在
  同一个 `for` 循环、同一个 turn 里。
- **`winner_blocks` 与 `winners` 等长是承重契约**：`_resolve_handoff_render` 返回后立刻
  `assert len(winners) == len(winner_blocks)`。两者由同一函数构造、本应天然等长，但 zip
  对长度不等会**静默截断**——未来改 `_resolve_handoff_render`（比如 panel 加一种 speaker）
  一旦漏配块，没有 assert 会变成「少 speak 一个 winner」的隐性 bug。一行 assert 比换更
  复杂的数据结构（如 `list[tuple[str, blocks]]`）划算。

#### 4.1.1 两档 cap 检查 —— 「永远跑不动」与「此刻跑不动」分开处理

`while` 入口对队首项的 cap 检查**分两档**，次序不能反：

- **档 ①「`cost > max_consecutive_ai_turns`」→ pop + drop + WARN + `continue`**。此项的
  `cost` 比 `max` 本身还大，无论 `_consecutive_ai_turns` 是多少（哪怕 drain 入口已清零）
  都跑不动——它是**死项**。典型成因：panel 入队后用户把 `max_consecutive_ai_turns` 调低到
  小于该 panel 的 `cost`（inbound §3.3 的 cap 数学是入队**那一刻**的校验，挡不住事后改
  配置）。**必须 pop 丢弃**——若走档 ② 的 `break`，死项会永久卡在队首、把后面所有队列项
  一起挡死，且「等下次用户触发」也救不了（下次 drain 入口清零后 `0 + cost > max` 仍成立）。
- **档 ②「`_consecutive_ai_turns + cost > max`」（且未命中档 ①）→ `break`、留队首**。此项
  本身能跑（`cost ≤ max`），只是此刻预算被前面的 AI 轮占了——留在队首，下次用户触发 +
  drain 入口清零后自然能跑。这是 P7.1 既有的「cap 撞顶不 pop」语义。
- 档 ① 对 delegate / review（`cost==1`）几乎不会命中（除非 `max_consecutive_ai_turns` 被
  配成 0——`config.py` 应拒，但 drain 这层 defensive 也能吃下）。它实际是 panel 专属的
  兜底：panel 的 `cost` 可达 5（4 panelist + summarizer），最容易撞「事后调低 max」。
- **不引入队列重算 / cost 迁移**——死项就地 drop 是最小修法，与 §4.4 「panel 欠员就地
  丢弃」同口径（队列项失效就 drop + WARN，不做复杂补救）。

### 4.2 `<panel_context>` 块合成

N 位 panelist **共享同一个** `<panel_context>` 块（`_resolve_handoff_render` 里算一次、
`[[panel_block]] * N` 复制给每位 panelist）。块由 `_render_panel_block(item)` 现场合成：

```python
def _render_panel_block(self, item: HandoffItem) -> str:
    """P7.3：合成 panel 的 <panel_context> 临时块。
    列出本轮圆桌全体 panelist + 平行发言指引。N 位 panelist 共享同一块。
    **不列 summarizer**——summarizer 不是 panelist，它拿 <panel_summary_request>。"""
    assert item.targets is not None
    dmap = self._display_map()
    names = "、".join(dmap.get(t, t) for t in item.targets)
    return (
        "<panel_context>\n"
        f"本轮是一次圆桌平行讨论，参与的茶客是：{names}。\n"
        "请你独立给出自己的观点，不必附和、也不必复述其他茶客已经说过的内容；\n"
        "如果你与前面发言的茶客看法不同，直接说出分歧。这是一次平行表态，"
        "不是接龙。\n"
        "</panel_context>"
    )
```

- **块对全体 panelist 共享**（不 per-panelist 定制）——文案写成位置无关（第一个 / 第 N 个
  panelist 读到同一句都通顺）。不写「除你以外是 X、Y」之类排他名单，列全体更简单。
- **`<panel_context>` 无 XML 属性**——临时块，被指派茶客身份由 `<speak_instruction>` 表达。
- **串行执行下后发言 panelist 会在 `<recent_messages>` / `<room_update>` 里看到前者**——
  这是串行的固有现象（§5.2）。`<panel_context>` 的「不必复述」正为此写。

### 4.3 `<panel_summary_request>` 块 —— summarizer 专属

summarizer 是 `winners[-1]`，`_resolve_handoff_render` 给它配 `[_PANEL_SUMMARY_BLOCK]`。
这是个**模块常量**（不含 per-item 数据）：

```python
_PANEL_SUMMARY_BLOCK = (
    "<panel_summary_request>\n"
    "房间刚结束一轮圆桌平行讨论——多位茶客各自发表了一条独立观点。\n"
    "请你把最近这几条圆桌发言汇总成一条简洁的综述：提炼共识、点出分歧、"
    "列出仍待决定的问题。\n"
    "不要逐条复述，要给出结构化的归纳。\n"
    "</panel_summary_request>"
)
```

- **块是常量、不需要 targets**：summarizer speak 时 N 位 panelist 的发言已串行 append 进
  transcript、紧贴 summarizer 这一发之前，summarizer 的 `<recent_messages>` /
  `<room_update>` 自然包含。块只需告诉它「刚才那轮是圆桌、请汇总」，不必再点名 X/Y/Z。
- summarizer 与 panelist 同在一个 turn——它不是独立 turn、不是独立队列项，`scoring_path`
  随整个 panel turn 是 `handoff_panel`（§3.6）。

### 4.4 panel 运行时人数过滤：欠员即整项丢弃

panel 项入队后、轮到 drain 前，用户可能 `remove_guest` 删掉某位 panelist / summarizer。
§4.1 的同步过滤把失效 winner 从 `winners` / `winner_blocks` 里剔掉。过滤后：

```python
def _panel_underfilled(self, item: HandoffItem, kept_winners: list[str]) -> bool:
    """panel 项过滤后有效 panelist（不含 summarizer）< 2 → 判欠员。"""
    if item.kind is not HandoffKind.PANEL:
        return False
    summ = item.summarizer
    kept_panelists = [w for w in kept_winners if w != summ]
    return len(kept_panelists) < 2
```

- **有效 panelist < 2 → 丢弃整个 panel 项**（含 summarizer，因为 summarizer 是同一 item 的
  字段，不是独立队列项——**不会留下孤儿 summarizer**）。理由：圆桌的最小语义是「≥2 人平行
  表态」；只剩 1 人就不是圆桌，让 summarizer 去汇总一场「1 人圆桌」语义错乱。整项丢弃 +
  WARN，干净可预测。
- **有效 panelist ≥ 2 但 summarizer 失效**：summarizer 已被 §4.1 的同步过滤剔出 winners，
  panel 照常跑 N 位、只是没有汇总那一发——可接受的降级（用户删了汇总者，就不汇总）。
- 这是 v2 相对 v1 的关键修复：v1 summarizer 是独立队列项，panel 项被丢弃时 summarizer 项
  仍滞留队列、下一轮去汇总一场不存在的圆桌（评审 #2 的「孤儿 summarizer」）。v2 summarizer
  是 panel item 的字段，与 panel 同生共死，孤儿问题在数据模型层就不存在（§5.3）。

### 4.5 cancel / wrapper —— 零改动复用

- **panel turn 跑到一半被 cancel**（用户点停止 / `handoff_clear`）：走 P7.2 既有的
  `_cancel_fixup_and_flush`。已 speak 完的茶客 message 正常落 `status=ok`，正在 speak 的
  那位 `status=cancelled`，尚未轮到的（包括还没说的 panelist / summarizer）**不会**有
  message——`turn_end(cancelled)` + `flush_turn` 照旧。panel 的多 message 对 cancel 路径
  透明（cancel 不感知 `winners` 长度）。
- `_run_handoff_turn` wrapper、`_inflight_kind` 三态、`_enqueue_handoff_and_maybe_start`
  的抢占判断——**一行不改**。

## 5. 关键设计决策（with rationale）

### 5.1 panel = 一个 HandoffItem，跑一个 turn

- panel item 持 `targets` + `summarizer`，drain loop 一次 pop、`winners=list(targets)
  [+summarizer]`、一个 `turn_id` 下串行 speak N(+1) 次。
- **不拆成 N 个 delegate item**：拆了就是 N 个 while 迭代 / N 个 `turn_id` / debug 抽屉
  N 条独立 turn——「这 N 位是同一轮圆桌」的语义在数据层彻底消失。一个 turn 含 N(+1) 个
  message 正好复用 P6 既有的 turn 语义（打分路径下一个 turn 本就能有 1~2 个 winner，panel
  只是把上限抬到 N(+1)）。
- **代价**：drain loop 的 `cost` / `winners` / `next_cost` 要认 `kind`（§4.1）——这是
  panel 比 review 多出来的增量。但 `for name in winners` 串行循环 P7.1 早已是「遍历
  winners」形态，N>1 不需要新循环。

### 5.2 串行执行 + UI 标注「并行讨论中」，不真并行

- **真并行**（同时给 N 个茶客 emit `message_start`）的三个坏处（P7 §4.2）：① 真并行写
  transcript → message 顺序乱；② 隔离 transcript（各看各的）→ 互相听不见 → 退化成 N 个
  独立提问；③ 共享 transcript 但乱序 → 后说的内容先进 prompt、因果颠倒。
- **结论**：串行执行——N(+1) 位依次 speak，先发言的进 transcript、后发言的看得见。「并行」
  只在 UI 标注（「并行讨论中…」）和**逻辑语义**上成立。
- **串行的弱点**：先发言的茶客会影响后发言的认知。**用 prompt 缓解**：`<panel_context>`
  块明说「这是平行表态不是接龙，独立给你自己的观点，不必附和或复述」。不完美，但工程零
  冲突、回放与 transcript 顺序一致——接受这个 trade-off（P7 §10 风险表已认）。

### 5.3 收敛：summarizer 收进 panel item，删掉双 item / panel_group_id（v1 → v2）

**v1 草案**（沿 P7 §2.3）：summarizer 是**独立入队的第二个 `HandoffItem`**（`kind=delegate`），
靠 `panel_group_id` 与 panel item 关联，inbound「原子入队两项」。

**v1 的三个连带问题**（2026-05-20 评审，全部采纳）：

| 问题 | v1 为什么坏 |
|---|---|
| **cap 承诺不成立** | v1 宣称「panel + summarizer 同一次 drain 跑完」，但 inbound 的 cap 数学只校验 `N(+1) ≤ max_ai`，**算不进** drain 入口时 `_consecutive_ai_turns` 已被前面的队列项消耗掉的轮数。例：`max_ai=4`，队列前面已有 1 个 delegate 跑掉 1 轮，再 append 3 人 panel + summarizer——panel（cost 3）跑得动、summarizer（独立项 cost 1）撞 cap 被推迟。「自动汇总」承诺破产。 |
| **孤儿 summarizer** | panel 的 panelist 被 `remove_guest` 删到 < 2 人时，drain 丢弃 panel item，但**独立入队的 summarizer delegate 仍滞留队列**，下一轮收到 `<panel_summary_request>` 去汇总一场不存在的圆桌。 |
| **`panel_group_id` 过度耦合** | P7 §3.1 本把 `panel_group_id` 定位成「仅前端展示分组」。v1 为识别 summarizer 把它升格成**调度语义字段**，制造出「相邻 + 同组 + 前项必须真跑过」这条跨两个队列项的隐式不变量——上面两个问题都是这条不变量的并发症。 |

**v2 收敛**：`summarizer` 是 **panel item 自己的一个字段**，summarizer 在**同一个 turn** 里
作为 `winners[-1]` speak。一个自描述 item、一个 turn、一次 cap 决策：

- **cap 承诺真成立**：panel + summarizer 是**一个** item，`cost = len(targets) + has_summ`，
  while-entry cap 检查拿 **live** 的 `_consecutive_ai_turns` 与 `cost` 比（§4.1）。撞 cap →
  整项不 pop、留队首等下次用户触发；不撞 → 整轮跑（含汇总）。**没有「panel 跑了 summarizer
  没跑」的中间态**——它们在同一个 `for` 循环里，物理上不可分。
- **没有孤儿**：summarizer 是 panel item 的字段，§4.4 判 panel 欠员丢弃整项时 summarizer
  随之消失，数据模型层就不可能留孤儿。
- **没有 `panel_group_id`**：item 自描述，`to_dict()` 直接带 `targets` + `summarizer`，前端
  队列预览**单项渲染**「圆桌：C、D、E → 汇总:F」，不需要相邻分组逻辑。`Sequence[HandoffItem]`
  入队、原子双入队、`_enqueue_handoff_and_maybe_start` 改签名——v1 的这些连带改动**全部
  删掉**。
- **代价 / 取舍**：v2 让 summarizer 与 panelist **同处一个 turn**（debug 抽屉里是一条 turn
  的最后一个 message），而 P7 §2.3 原设想 summarizer 跑「另一个 turn」。**这是对 P7 §2.3
  的一处明确修订**：把 summarizer 收进同一个 turn 才能让「panel+summarizer」成为单一原子
  调度单元——这正是干掉前两个问题的关键。代价是 debug 里 summarizer 不是独立可折叠的 turn
  （只是 panel turn 的末条 message）——可接受，「一轮圆桌 = N 条平行观点 + 1 条汇总」本就
  是一个连贯的语义单元。落地时在 CLAUDE.md / P7 §2.3 / §3.1 同步追写本修订。
- 评审还给了「P7.3 干脆先不做自动 summarizer，用户手动 delegate 汇总」的备选。v2 不采纳
  这条**只是因为收进 item 后自动 summarizer 已不再是复杂度来源**——它就是 `winners` 多挂
  一个名字 + 末位换一个 prompt 块。复杂度（双 item / group_id / 跨 drain cap）已被连根拔除，
  功能可以留。

### 5.4 `MAX_PANEL_TARGETS` 与 `max_consecutive_ai_turns` 双重约束

- **两个上限管两件事**：`MAX_PANEL_TARGETS=4` 管「单 turn token 成本」（panelist 数）；
  `max_consecutive_ai_turns` 管「AI 连续发言不夺走用户的麦」。
- panel turn 的 panelist 实际上限 = `min(MAX_PANEL_TARGETS, max_consecutive_ai_turns -
  has_summarizer)`（§3.3）。两个约束取**小**——既不让单轮太贵，也不让一个 turn 占太多轮。
- inbound 校验拒「无论如何跑不动」的 panel；drain while-entry cap 检查管「此刻跑不跑得动」。
  两者口径见 §3.3 末段。

### 5.5 不开 `[panel]` toml

- `MAX_PANEL_TARGETS = 4` 是 `handoff.py` 模块常量。
- **不开 `[panel]` toml 段**——`default_summarizer`（房间预设汇总者）/ `parallel_prompt_hint`
  （关 `<panel_context>` 提示的开关）都不做。
- **理由**：开 toml 段要走 P4 four-touch checklist（`config.py::PanelConfig` → `session.py`
  透传 → `admin_toml.py::_render_room_toml` round-trip → CLAUDE.md 不变量延伸）+ admin UI +
  round-trip 测试面。在用户实际抱怨「4 不够」/「每次手选 summarizer 烦」之前，这套成本不值。
  与 P7 §3.5 / §7 同口径——等用户诉求出现再走 checklist 加段。

## 7. 关键不变量（落地时同步追写 CLAUDE.md）

- **panel = 一个自描述 `HandoffItem`、跑一个 turn**。`HandoffItem` 持 `targets` +
  `summarizer` 两字段完整描述一场圆桌；drain loop 一次 pop、一个 `turn_id` 下串行 speak
  `len(targets)(+1)` 次，对应 debug 抽屉一条 turn 含 N(+1) 个 message（末条是汇总）。
  **不拆 N 项 / 不拆 N 个 turn**（§5.1）。
- **summarizer 是 panel item 的字段，跑在同一个 turn 里、是 `winners[-1]`**（§5.3）。
  **不**把 summarizer 拆成独立入队的第二个 `HandoffItem`、**不**引入 `panel_group_id`。
  这样 panel + summarizer 是单一原子调度单元：一次 cap 决策、要么整轮跑要么整项等，不存在
  「panel 跑了 summarizer 被推迟」的中间态，也不会留「孤儿 summarizer」。
- **panel 串行执行，「并行」只是 UI 标注 + prompt 提示**（§5.2）。N(+1) 位依次 speak，
  后发言的茶客在 `<recent_messages>` 里看得见前者；`<panel_context>` 块用「平行表态不是
  接龙」缓解先发言污染。不做真并行 emit。
- **drain loop 的 `kind` 三路分流只覆盖 `winners` / `cost` / `scoring_path` /
  `winner_blocks` 四个值**（§4.1）。`_resolve_handoff_render(item)` 纯函数单点维护，
  返回与 `winners` **等长对齐**的 `winner_blocks`；`for name, blocks in zip(...)` 串行
  循环 / turn 边界 / cancel fixup / turn 末尾 5 步 / wrapper **一字不动**。**不允许**为
  panel 单开平行 drain 路径。
- **panel 的 `cost = len(targets) + (summarizer 有无)`，while-entry cap 检查分两档**
  （§4.1.1）。档 ①「`cost > max_consecutive_ai_turns`」→ 此项永远跑不动（死项，典型成因：
  panel 入队后用户调低 `max`）→ **pop + drop + WARN**，禁止 `break`（会永久挡住队首 +
  挡死后续队列）；档 ②「`_consecutive_ai_turns + cost > max`」→ 此刻预算不够 → `break`、
  留队首等下次用户触发。次序不能反。cost 用声明值（不因 §4.4 runtime 过滤而变），偏保守
  可接受；`next_cost` peek 同口径。panel turn 原子——cap 通过即整轮跑、不通过即按档处理。
- **`winner_blocks` 与 `winners` 等长是承重契约**（§4.1）。`_resolve_handoff_render` 返回
  后立刻 `assert len(winners) == len(winner_blocks)`——speak 循环 `zip` 两者，长度不等会
  静默截断 speaker；未来改 `_resolve_handoff_render` 漏配块时 assert 当场炸而非埋成隐性
  「少发一个 winner」bug。
- **panel 运行时欠员即整项丢弃**（§4.4）。drain 前同步过滤失效的 winner（`winners` 与
  `winner_blocks` 等长同步剔除）；过滤后**有效 panelist < 2 → 丢弃整个 panel 项**（含
  summarizer，因 summarizer 是同 item 字段，**不会留孤儿**）。summarizer 单独失效但
  panelist ≥ 2 → panel 照跑、无汇总（可接受降级）。
- **panel turn 的 `scoring_path` 全程是 `handoff_panel`**（§3.6），含 summarizer 那一发
  ——summarizer 是这个 turn 的末位 speaker、不是独立 turn。
- **inbound `handoff_panel` 五道校验 + cap 数学**（§3.3）。白名单严格 `{type, targets,
  summarizer}`；`targets` ≥2 项 / 无重复 / 全在场；`summarizer` 在场且不在 `targets`；
  `len(targets) > min(MAX_PANEL_TARGETS, max_consecutive_ai_turns - has_summarizer)` →
  NOTICE error 丢帧。cap 校验是「能不能跑」的静态判断，「此刻跑不跑得动」由 drain
  while-entry cap 检查负责。`MAX_PANEL_TARGETS=4` 是模块常量、不进 toml。
- **`HandoffItem.targets` 用 `tuple`**（§3.1）。`frozen` dataclass 不锁内部容器；`list`
  会被外部 caller 改掉队列里的 targets。`to_dict()` 转 list 给 envelope。
- **`<panel_context>` 对 N 位 panelist 共享、`<panel_summary_request>` 是模块常量**
  （§4.2 / §4.3）。panel 块由 `_render_panel_block` 现场合成（列 panelist、不列
  summarizer）；summary 块无 per-item 数据。两块都走 P7.2 的 `extra_blocks` 管线，注入位
  `<speak_instruction>` 之前。

## 8. 明确不做的事

- **不真并行**（§5.2）——串行执行 + UI 标注。
- **不拆 panel 成 N 个 item / N 个 turn**（§5.1）。
- **不把 summarizer 拆成独立队列项 / 不引入 `panel_group_id`**（§5.3，v1 路线评审否决）。

- **不做 panel 结果接力**（「圆桌完 → 自动请审 → 自动改」）——属 P8 任务剧本。
- **不新增 envelope 类型 / 不 bump `schema_version` / 不新增持久化目录**。
- **不让队列落盘**——与 P7.1 同口径，瞬态、crash 即丢、用户重发即可。
- **不把 panel 的 N 条发言从后发言茶客的 `<recent_messages>` 去重**——串行下它们本就在
  transcript 里，去重无意义。

## 10. 主要风险 & 兜底

| 风险 | 兜底 |
|---|---|
| 4 人 panel + summarizer 把 prompt token / 时延堆高 | `MAX_PANEL_TARGETS=4` 硬上限 + cap 数学双重约束（§3.3 / §5.4）；串行执行单条 message 体量有限 |
| panel 后说的茶客被前面茶客污染（「平行」是假的） | `<panel_context>` 块 prompt 提示「平行表态不是接龙」；UI 标注「并行讨论中」让用户知道是逻辑并行；接受 trade-off（§5.2） |
| 用户配 `max_consecutive_ai_turns=1` 还想开 4 人 panel + 汇总 | inbound cap 数学 → `cap ≤ 0` → NOTICE error 丢帧，提示减人或去汇总者（§3.3） |
| panel 入队后用户把 `max_consecutive_ai_turns` 调低到 < 该 panel 的 cost | inbound 校验是入队那一刻的、挡不住事后改配置。drain while-entry **档 ① cap 检查**：`cost > max` → pop + drop + WARN（不 break），死项就地丢弃、不永久挡队首（§4.1.1） |
| panel 某 panelist 在入队后被 `remove_guest` 删掉 | drain 同步过滤失效 winner；有效 panelist ≥ 2 → 用剩余跑；< 2 → 丢弃整个 panel 项（含 summarizer，无孤儿，§4.4） |
| panel 的 summarizer 被 `remove_guest` 删掉 | summarizer 被同步过滤剔出 winners → panel 照跑 N 位、无汇总那一发（可接受降级，§4.4） |
| summarizer 与某 panelist 是同一人 | inbound 第 4 道校验 `summarizer not in targets` → NOTICE error（§3.3） |
| panel turn 跑到第 2 个茶客时被 cancel | `_cancel_fixup_and_flush`：已说完的 `status=ok`、正在说的 `status=cancelled`、没轮到的（含 summarizer）无 message；`turn_end(cancelled)` + `flush_turn` 照旧（§4.5） |
| panel summarizer 茶客 LLM crash / 超时 | 与普通 speak 失败同口径——`message_end status=error`；它是 turn 末位 speaker，failure 不影响已说完的 panelist message |
| 老前端收到 `item.kind=="panel"` / `targets` / `summarizer` | `schema_version` 不动；老前端忽略未知 kind / 未知字段，不渲染 panel 文案但不报错 |
| 用户连发多个 panel 把队列堆高 | 与 P7.1 同口径——不设队列软上限；真出现「队列堆几十项」反馈再走 P4 checklist 加 `[handoff].max_queue_len` |
