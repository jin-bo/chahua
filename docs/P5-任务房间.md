# P5：从「群聊」升级到「任务房间」

> 目标：在不破坏「聊天是主界面」的前提下，把房间从纯聊天容器升级为**带任务的工作容器**：一个房间可以有多个任务，每个任务有目标 / 状态 / 负责人 / 产物文件 / 决策记录；右侧（或下方）面板能看到"正在产出什么"。

**状态：设计中（2026-05-16）**。本文为方案草案；落地拆分见 §7。

---

## 1. 现状速写 & 关键观察

| 现有 | 与"任务房间"的关系 |
|---|---|
| `Room` + `transcript.jsonl`（flat 流） | 任务**附加**在它之上，不取代 |
| `summary.jsonl`（房间级增量摘要） | 与"任务级摘要"共存，分目录 |
| `share/`（用户上传共享目录）+ `upload.js` | artifact 的搬运基础设施已就位 |
| `[[guest]].cwd` 受 `isolation = room \| global` 决定 | 茶客自动产出归到 task 目录 = 改 cwd 语义，**不在 P5.1 做** |
| `ChahuaEnvelope.schema_version=1` | 新加 `data.task_id` 字段无须 bump；新事件 type 走"未知 type 前端 WARN 跳过"的兼容口径 |

**最重要的判断**：聊天仍是线性主流，task **不分裂消息树**，只是给消息打 tag。Slack thread 那种"消息分裂到子流"会破坏茶客之间"听见对方"的语义（打分上下文取最近 K 条 → 分裂后 K 条不再连续），代价远大于收益。

## 2. 核心模型（四个新概念）

```
Room ─┬─ Task[]               # 一个房间多个任务，串行的"活跃任务"语义
      ├─ transcript.jsonl     # 仍是一条线，每条多一个 optional task_id 字段
      └─ summary.jsonl        # 房间级摘要不动

Task ─┬─ task.json            # 元数据：title/goal/status/owner/created_at
      ├─ decisions.jsonl      # append-only：被"采纳"的决策（指向 message_ids）
      ├─ artifacts/           # 任务产物文件目录
      ├─ events.jsonl         # P5.2 起：状态/负责人/title 变更历史
      └─ summary.jsonl        # P5.2 起：任务级增量摘要
```

### 2.1 Task 数据契约

```python
@dataclass(frozen=True)
class Task:
    id: str                  # task_<10字节 hex>，同 message_id / turn_id 一根
    title: str               # ≤ 60 字
    goal: str                # markdown，多行
    status: Literal["open", "in_progress", "blocked", "done", "abandoned"]
    owner: Optional[str]     # speaker_id（user 或茶客名）；None = 全员
    created_at_ms: int
    updated_at_ms: int
    closed_at_ms: Optional[int]
```

### 2.2 Thread 不是新实体

"同属一个 task_id 的消息"= 一条 thread，UI 上是个 filter 视图，不另存。

### 2.3 Decision

```jsonc
{ "decision_id": "dec_...", "task_id": "task_...",
  "supporting_message_ids": ["msg_...", "msg_..."],
  "summary": "<≤200 字一句话>",
  "marked_by": "user",  // P5.1 仅用户能采纳
  "ts_ms": ... }
```

### 2.4 Artifact

不是新数据库实体，**就是 `tasks/<task_id>/artifacts/` 目录下的文件**。索引在文件系统本身。

## 3. 落盘布局

```
rooms/<room-id>/
├── room.toml               # 不变
├── transcript.jsonl        # +task_id 字段（可缺 = 房间级闲聊，向后兼容）
├── summary.jsonl           # 房间级，不变
├── cursor.json             # 不变
├── guests/                 # 不变
└── tasks/                  # 新
    ├── state.json          # {active_task_id?}，覆写式 tmp+rename；空房间允许缺
    └── <task_id>/
        ├── task.json       # 覆写式 tmp+rename，全量元数据
        ├── decisions.jsonl
        ├── artifacts/      # 文件
        ├── events.jsonl    # P5.2 起；P5.1 没有 status / owner / title 变更
        └── summary.jsonl   # P5.2 起；P5.1 不写任务级摘要
```

**为什么没有 `_index.jsonl`**：单房间任务数大概率个位数到十几个，启动时直接扫 `tasks/*/task.json` 拼列表足够；省一个"真源 + 索引一致性"的小坑。等真撞到性能问题再加。

**为什么单独留 `state.json`**：`active_task_id` 是消息归属的核心状态，必须跨重启 / reconnect / 切房存活，否则用户消息会悄悄落回"房间级闲聊"。它与任务列表无关，独立一个覆写文件比塞进 cursor.json / 散到 task.json 都干净（一个任务被另一个 user action 设为非 active 不该改它自己的 task.json）。

**为什么 task.json 用覆写而非 append**：title / status 是频繁更新的元数据，append-only 历史价值低；状态历史 P5.2 起交给 events.jsonl 存。这与现有 cursor.json 同口径。

## 4. 事件协议增量

### 4.1 Envelope `data.task_id`（顶层不动）

`message_start` / `message_end` 的 `data` 多一个可选 `task_id`。前端按这个分流到任务面板。**schema_version 不 bump** —— 老前端忽略未知 data 字段不出错。

### 4.2 新增 event types

**P5.1**：

| type | 时机 | data |
|---|---|---|
| `task_info` | ws 连上 / 切房 / **active 变化**时重发 | `{tasks: [...], active_task_id?}` |
| `task_open` | 用户开任务 | full task.json |
| `task_update` | title / goal 变更（**P5.1 不含 owner / status**；owner 在 P5.1 锁定为创建时值） | diff |
| `task_decision_added` | 决策入库 | decision 全量 |
| `task_artifact_added` | artifact 入目录（上传 / 手动绑） | `{task_id, name, size, rel}` |

P5.1 不为 "active 切换" 单独定义事件 —— `task_open` 后 server 立刻重发整份 `task_info`，前端按 `active_task_id` 字段更新指针。少一个事件少一个 race 面。

**事件分工：`task_info` 是权威快照，其它是 hint**。`task_info` 永远代表 server 端当前真状态；`task_open` / `task_update` / `task_decision_added` / `task_artifact_added` 只用于局部反馈（toast / 动画 / 高亮增量项），不进任务状态本身。前端任务状态以最近一次 `task_info` 为准。这条契约让 P5.1 实现者不必纠结"task_open 与 task_info 同帧发是不是双重广播"——是，且故意。

**P5.2 追加**：

| type | 时机 | data |
|---|---|---|
| `task_close` | done / abandoned | `{task_id, status, closed_at_ms}` |
| `task_update`（扩展） | owner / status 进入 patch 范围 | 同上但 patch 可含 owner / status |

### 4.3 Inbound（前端 → 服务端）

**P5.1**：

```
open_task         {title, goal, owner?}                      # owner 仅在创建时可设
update_task       {task_id, patch: {title?/goal?}}           # P5.1 仅改 title / goal
attach_artifact   {task_id, share_rel}                       # copy 不 move
add_decision      {task_id, supporting_message_ids, summary}
```

P5.1 故意**不提供** `set_active_task` 与 `close_task`，且 `open_task` 在房间已有任意任务时直接拒绝（详见 §7.1 "一房间最多 1 个任务" 实现项）—— 要么没任务、要么有那一个任务，不留切换 / 隐身 / 清空中间态。这是为了把"切 active 时 turn 在跑怎么办"/"已关闭任务怎么渲染"/"用户找不回旧任务"三个面完整压到 P5.2。

**P5.2 追加**：

```
set_active_task   {task_id | null}
close_task        {task_id, status: "done"|"abandoned"}
# update_task 的 patch 在 P5.2 扩展为也能改 owner / status
```

**`attach_artifact` 是 copy 不是 move**：share/ 是房间公共桌面，茶客 cwd 路径、历史消息里引用的 `share_rel`、同一文件可能挂多个任务 —— 移动都会断引用。MVP 一律走拷贝（茶客视角 share/ 永远在原位）；后续如有"清理 share/" 需求再单独提供 GC 入口，不与 attach 耦合。

### 4.4 用户 / 茶客消息的归属

- 用户消息：**P5.1 inbound 不带 task_id**；server 端在 append transcript 时按当前 `state.json.active_task_id` 自动打 tag。前端没切换 UI 也就没有"想发到任务 X 但 server 是任务 Y"的意图分歧，省一个校对面。P5.2 加切换 UI 后再评估是否让前端 inbound 带意图字段。
- 茶客消息：`orchestrator` 在 `turn_start` 时记 `active_task_id`，本轮 `message_*` envelope 都打这个 tag
- `active_task_id` 落 `rooms/<id>/tasks/state.json`，**server 端是真源**；变化时 server 重发整份 `task_info` envelope（不发增量），前端只镜像不投票
- **P5.1 单房间最多 1 个任务**（见 §7.1 限制条款）；P5.2 起才允许多任务共存，仍维持"同一时刻 0 或 1 个 active"

## 6. 怎么把 task 信息 / artifact 共享给茶客

三通道，三阶段铺开。各通道在各阶段的状态：

- **P5.1**：三通道全空 —— 茶客对 task 零感知，只通过聊天上下文间接知道用户在做什么；artifacts 不在茶客 cwd 范围
- **P5.2**：通道 2 首次出现 **只读** `./task/` 链接（茶客能"看到"当前任务产物文件），但 prompt / tool 仍不感知 task 概念
- **P5.3**：通道 1 先启用（PR 1）、通道 3 后续闭环（PR 2~3） —— 茶客真正"长出 task 视野"，分 PR ship 不做 all-or-nothing
- **P5.4**：通道 2 升级到读写（自动归集茶客产出）；或者直接把 cwd 切到 task artifacts/

### 6.1 通道 1：prompt 注入（task info → 茶客 LLM 视野）— P5.3 启用

只在 `active_task_id` 非空时启用。在 onboarding 末段（rules 之后、最近原文之前）插一块：

```
当前任务：<title>
目标：<goal>
状态：<status>，负责人：<display_name | "全员">
近期决策（最近 5 条）：
- <decision_summary_1>
- <decision_summary_2>
当前产物清单（不嵌内容）：
- README.md (2.3 KB, 2026-05-16 14:23)
- plan.md   (1.1 KB, 2026-05-16 13:50)
- demo.png  (87 KB,  2026-05-16 13:21)
```

**不**把 artifact 文件内容嵌进 prompt —— 大文件爆上下文；让茶客按需走通道 2 / 通道 3 拿。

**已 closed task 的消息**：onboarding 阶段不喂原文，只把 task 的最终 summary 当一句历史摘要喂进"近期梗概"块。

**owner 加权**：见 PR 4 / 可延后到 P5.4（§13 P5.3.9），主路径不动打分。

**实现接缝**（仅 §7.3 / §13 commit 时落代码，规约层放在此处便于和 §6.2 / §6.3 对照）：

- **两态注入，两条路径都接入**：
  - onboarding（`orchestrator._render_onboarding()`，`chahua/orchestrator.py:627-660`）在 "近期梗概" 段之后、"最近原文" 段之前插**完整块**（title / goal / status / owner display / 近期决策 / artifact 清单 / task summary 末 K 段）。
  - incremental（`_render_incremental()`，`chahua/orchestrator.py:662-675`）在 body 行之后、`_speak_instruction` 之前插 **compact 块**（仅 1-3 行：`当前任务：<title>` + `目标：<goal 首行>` + `产物可从 ./task/ 读取`）。
  - 评审反馈背景：`_build_context_for` 触发 onboarding 仅当 `last_seen == 0` 或 `len(increment) > onboarding_threshold`（`orchestrator.py:623`）——开任务后**连续短轮对话几乎全走 incremental**，"只 onboarding 注入"会让 P5.3 在大多数回合失效，必须 incremental 也注入。
- **task_id 经形参透传，render 拆"取数 / 渲染"两层**（避免 active 切换 race，也方便单测）：`_build_context_for(guest_name, *, task_id: Optional[str])` 签名扩；`_run_turn` 入口已 snapshot 的 `active_task_id`（P5.1.8 已立）原路传到 build_context。**取数**在 `_build_context_for` 内分两步：先 `tasks_store.get_task(task_id)`，task 不存在 / 终结态（done / abandoned）直接不注入、不再触碰其余三个 read API；存活才调 `list_decisions(task_id)` / `list_artifacts(task_id)` / `task_summaries.get(task_id)` 拿全 decisions / artifacts / summary_tail。**渲染**调纯函数 `_render_task_block(task, decisions, artifacts, summary_tail, *, compact: bool) -> str`——纯函数不读 store / 不接 self / 不背状态分支，方便单测拼字符串；compact=True 走 1-3 行 compact 块，False 走完整块。拼 prompt 时 active 被切到 Y，本轮仍按 snapshot 的 X 渲染，与 message_* envelope 同源。
- **房间级 `近期梗概` 不动**：之前方案"active 非空切到 task summary"会丢人设互动 / 跨任务决策，破坏茶话室"群聊"的承重感。改为：房间级 `summarizer.summaries` 渲染逻辑零改动；task summary 末 K=3 段作为 task block **内部一小段**"任务近期进展"出场（与"近期决策"区分——决策是用户显式打的，task summary 是 LLM 增量生成的）。无 task summary → 该小段省略。
- 数据来源已在 P5.2 就位：`session.tasks_store.get_task(task_id)` / `list_decisions(task_id)` / `list_artifacts(task_id)` 三个读 API 在 `chahua/tasks_store.py:301/309/332`；task summary 走 `task_summaries.get(task_id).summaries`（`chahua/summarizer.py:367`，P5.2.12 已落盘 per-task summary.jsonl + cursor）。
- prompt 预算：full 块 ≤300 token（decisions ≤5 × 200 字 ≈ 200 token；artifacts ≤10 行 ≈ 50 token；title/goal/task summary 末 3 段 ≤100 token）；compact 块 ≤80 token。**超额时优先保 title/goal**，decisions / artifacts / summary tail 各自截到 3 / 5 / 1 条。
- closed task（status ∈ {`done`, `abandoned`}）不注入：`_build_context_for` 取数后判终结态直接跳过渲染、不调 `_render_task_block`（纯函数不承担分支判断）。closed task 的房间级"近期梗概"出场规则见 §6.1 上文（"已 closed task 的消息"段），与 P5.3 的 task block 分两条线，互不重复。

**scoring 加权实现接缝**：评审反馈后，该项整体挪到 **PR 4 / 延后**（§13 P5.3.9）——主路径不需要碰打分行为 / envelope.scores wire 数据 / 前端可视化。规约仍立："scoring transcript 不读 task 块"沿用 §8 invariant #4（把 task 块塞进打分 prompt 等于给"请输出 1 分"开第二条注入路径）；具体落点与单测见 §13 P5.3.9。

### 6.2 通道 2：文件系统（茶客读 artifact）

| 阶段 | 茶客视角 | 实现 |
|---|---|---|
| **P5.1** | **没有直接路径** | `attach_artifact` 是 copy，share/ 副本仍在原位；茶客继续通过 `./share/<file>` 读原始文件。artifacts/ 在 P5.1 仅给 UI / 持久化用，不进茶客 cwd |
| **P5.2** | `./task/<file>` **只读** | 每个 guest workspace 下放 `./task/` 软链指向 `rooms/<id>/tasks/<active_id>/artifacts/`；active 切换时重链。**只读** —— 茶客能 `ls` / `cat` 但不能 write |
| **P5.4 远期** | 读写 + 自动归集 | 二选一：① 升级 `./task/` 为 read-write 且 server 端监听 / tool wrapper 拦截 write，合成 `task_artifact_added`；② 直接把 guest cwd 切到 `tasks/<id>/artifacts/`，废软链。两条路都要重设 isolation 语义，与 `[[guest]].isolation` 现有口径合并评估 |

**为什么 P5.2 选只读、把"自动归集 write"延后**：read-write 引入两套实现方向（文件系统 watch vs tool wrapper 拦截），都要面对"agentao 写工具的 cwd 边界 + symlink 是否被穿透 + 写到一半 active 被切"三类边界情况。P5.2 只做"茶客能看到产物"已经覆盖"@汪小姐你看下 README 里第 3 节"这种核心用例；自动归集留 P5.4 一次做对。

**P5.2 软链的平台兜底**：POSIX 用 symlink；Windows 用 junction（目录链，无需管理员权限）。`./task/` 名字与 `./share/` 对仗 —— 见名知是任务级桌面。

**只读怎么落地**：`./task/` 解析到 task artifacts/ 路径在 guest workspace cwd 子树**之外**，沿用 agentao 既有 `workspace-write` 权限模式 —— 写工具按 cwd 边界拒绝外部路径即天然只读，不需要额外路径白名单。`full-access` 模式的茶客仍能写但不合成 `task_artifact_added` —— 这种茶客本就有越界写权限，"产物归任务"的语义在 P5.2 不保证。

**active 切换时**：先解 `./task/` 软链再重建。P5.2 切 active 必须先 cancel 当前 turn（沿用 P3.3 cancel 状态机），cancel 完才动软链 —— 避免茶客 read 读到一半路径被切。

### 6.3 通道 3：工具调用（茶客主动查询 / 提议）— P5.3 起

新增几个 task-aware tool 给 agentao 注册：

| 工具 | 行为 |
|---|---|
| `task_list_artifacts()` | 拿当前 active task 的产物清单（重发 §6.1 的格式）—— 茶客中途想查时不必等下次 onboarding 注入 |
| `task_propose_decision(summary, supporting_message_ids?)` | 提议一条决策，UI 渲染成"采纳"按钮等用户点 |
| `task_propose_open(title, goal)` | 提议开新任务，同样 UI 采纳后才入库 |

**走"提议"不走"直接写"**，沿用 §8 invariant #3：写权限永远在用户，茶客不能静默开任务 / 记决策。"采纳"按钮是 UI 把茶客的 propose 转译回 inbound `add_decision` / `open_task` 的薄包装。

**实现接缝**：

- agentao tool 注册接口：`agent.tools.register(tool)`（in-process Python，无须走 MCP），见 `.venv/lib/python3.12/site-packages/agentao/tooling/registry.py:36`（`register_builtin_tools(agent)` 是同款用法的示范）。tool 实例继承 `agentao.tools.Tool`（sync，`execute(**kwargs) -> str`）或 `AsyncToolBase`（async，`async_execute(...)`），实现 `name` / `description` / `parameters`（JSON Schema），可选 `is_read_only = True` 让 read-only / workspace-write 模式不拦。
- **`is_read_only=True` 的语义边界**（三个 task 工具都设 True，但要避免误解为"无副作用"）：`list_artifacts` 是真无副作用 read-only；`propose_decision` / `propose_open` 不直接写 task store / 不落盘，但**会 emit envelope**（`TASK_PROPOSAL`）—— 这里 `is_read_only=True` 是为了避免 agentao 的权限层把"提议事件"当成写操作拦截，**不是声称工具无副作用**。真正的"写入"由用户采纳后走既有 `ADD_DECISION` / `OPEN_TASK` inbound（沿用 §8 invariant #3：写权限永远在用户）。
- 装配落点：`chahua/task_tools.py` 暴露工厂 `register_task_tools(agent, *, tasks_store, transport) -> None`，内部 `agent.tools.register(...)` × 3；`TeaGuest.__init__()`（`chahua/guest.py:92-152`）在 `apply_permission_mode(self.agent, permission)` 之后（line 152）**一行调用** `register_task_tools(self.agent, tasks_store=tasks_store, transport=self._transport)`。`TeaGuest.__init__` 签名加 `tasks_store: TasksStore` 形参；装配端 `chahua/session.py:_build_guests` 一处改签名传入 store。propose 工具的 transport 通过工厂参数显式注入（让工具类不直接依赖 `TeaGuest`），便于单测。
- **为什么用工厂而非把工具类塞进 guest.py**：`TeaGuest` 当前职责已是 `Agentao` / MCP / permission / transport bind / `speak()` 生命周期，把三个 task tool 的 schema + execute 逻辑 + proposal envelope 全塞进去会让它变成"装配 + 业务工具 + UI 事件"的混合体。但也不要过度设计成 `TaskToolRegistry` / plugin 系统——三个工具类 + 一个工厂函数就够（评审反馈）。
- proposal envelope 直接走 transport.emit_chahua（不经 SDK `_handle`）：propose 工具在 `agent.arun()` 内由 LLM 调用，那时 `TeaGuest.speak()` 已 `with self._transport.bind(...)`（`chahua/guest.py:186-188`），sink / turn_id / message_id / task_id 都有效。工具 `execute()` 内直接 `self._transport.emit_chahua(ChahuaEventType.TASK_PROPOSAL, {...})` 推 envelope；不需要新增 agentao 事件类型，不需要改 `transport_bridge._handle`。
- `ChahuaEventType.TASK_PROPOSAL` 加进 `chahua/events.py`；envelope.data 形状：

  ```jsonc
  {
    "task_id": "<当前 active 或 null>",
    "proposer": "<guest_name>",
    "kind": "decision" | "open",
    "payload": {                                  // kind=decision
      "summary": "...",
      "supporting_message_ids": ["msg_..."]?
    } | {                                          // kind=open
      "title": "...",
      "goal": "..."
    }
  }
  ```

  `task_id` 取 `self._transport._task_id`（bind 时已 snapshot），与 message_* envelope 同源——"老任务的 propose 错挂到新 active"在协议层就不可能。
- 工具返回值（喂回 LLM 的 string）：`task_list_artifacts` 返 markdown 清单（同 §6.1 注入格式，茶客可中途按需取）；`task_propose_decision` / `task_propose_open` 返 `"已提议「<summary 截 60 字>」，等用户在 UI 采纳后入库。"`——让 LLM 明白 propose ≠ 入库，避免它反复刷 propose。
- 采纳回环：前端收到 `TASK_PROPOSAL` envelope，渲染"采纳 / 忽略"卡片。点"采纳"按 `kind` 分发——`decision` → 拼 `Inbound.ADD_DECISION` 帧发回 server（`server_inbound_task._inbound_add_decision`，`chahua/server_inbound_task.py:430` 已就位）；`open` → 拼 `Inbound.OPEN_TASK` 帧（`_inbound_open_task`，`server_inbound_task.py:126`）。**server 完全复用既有 handler**，不开新 inbound。点"忽略" / 刷新前端 = 本地丢弃，不持久化（session-local）。
- 工具滥用兜底：服务端不强限 propose 频次（增加复杂度也防不住偏执 LLM 刷工具）；前端按 `(proposer, kind, payload-hash)` 去重折叠，连发相同 propose 只渲染一张；新建 `app/renderer/proposal_card.js` 维护 session-local set。

## 8. 关键不变量（沿 [CLAUDE.md](../CLAUDE.md) 口径）

1. **入站严格、落盘宽容**：
   - 入站 inbound payload（`open_task` / `update_task` / `add_decision` 等）字段白名单严格，未知键直接报错 + emit NOTICE 给前端 —— 等价 `room.toml` 抓 typo 的口径，**保护数据不被前端瞎写**。
   - `task.json` / `decisions.jsonl` / `events.jsonl` 加载时**未知字段 warn 后忽略**，必需字段缺失才跳坏该条 —— 等价 `transcript.jsonl` 跳坏行口径，**保护跨版本向前兼容**（新版本 schema 加字段不让老版本启动炸）。两条规则有意不对称。
2. **`transcript.jsonl` 加字段不破坏向后兼容**：缺 task_id = 房间级；加载跳坏行规则不变
3. **artifact / decision / task 的写权限只在用户**：茶客通过协议标签提议，UI 渲染成按钮等用户点确认；不允许茶客静默开任务 / 记决策（防 AI 自我接龙生成 50 个任务）
4. **API key / 秘密永不进 task.json 也不进 envelope**（沿用现有口径）
5. **`task_id` 只活在 `envelope.data`**，envelope 顶层字段不动，schema_version 不 bump
6. **单房间同时 0 或 1 个 active_task**：心智成本必须低于"打开多个聊天窗口"
7. **task 目录删除 = 硬删除**：和 room 删一致，不留 trash

## 9. 明确不做的事

- 不做任务依赖图 / 甘特 / 看板 —— Linear 的活
- 不做任务级权限隔离（哪位茶客只能看哪个任务）—— 复杂度爆炸
- 不做跨房间任务 —— 房间永远是任务的容器
- 不自动从聊天里 NLP 挖掘任务 —— 误报污染数据；用户必须显式
- 不引入消息线程分裂（Slack-style sub-thread）—— 破坏茶客打分的最近上下文连续性
