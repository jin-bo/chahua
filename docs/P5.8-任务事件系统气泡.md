# P5.8：任务事件改为系统气泡

> 目标：把 task 状态变更从“伪装成用户发言”改成“房间状态通知”。任务事件不再插入 `speaker_id="user"` 消息、不进入 `transcript.jsonl`、不自动触发 orchestrator scoring；前端收到 task event 后在聊天区追加一条居中的系统气泡。

**状态：已实现（2026-05-21）。** 本文是 P5.5 的后续修订，覆盖 `open_task` / `close_task` / `add_decision` / `attach_artifact` / `clear_task_artifacts` / 茶客自动归集产物六类任务事件。

---

## 1. 背景

P5.5 的核心做法是：任务事件末尾合成一条 `speaker_id="user"` 消息，写入 transcript 并启动一轮 `_run_turn`。这让茶客能立刻看到“用户开启任务 / 记了决策 / 挂了产物”，但也引入了三个明显问题：

| 问题 | 具体表现 |
|---|---|
| 污染 transcript | 历史里出现用户没真正说过的话，且挂用户头像 |
| 错误触发 AI | 任务 UI 操作会 cancel 当前 turn 并触发 scoring，可能导致无意接话 |
| 语义混淆 | “任务状态通知”被建模成“用户发言”，后续 review / decision 锚定时会把系统事件当消息 |

P5.3 之后茶客已经通过 `<current_task>`、decisions、artifacts、task summary 看到任务状态。任务事件不必再依赖 transcript 作为唯一传播通道。

**核心取舍（刻意为之）**：P5.5 的两个毛病——「污染 transcript」与「错误触发 AI」——是可以分开修的（可以做到「触发 scoring 但不写 transcript」）。P5.8 选择**两个都砍**：task event 既不进 transcript、也不再触发任何 AI 轮次。代价是开任务 / 记决策 / 挂产物不再「唤醒」房间——从 task 操作到用户下一条消息之间，茶客完全静默。这是 P5.8 最重要的行为变化：task 仍是任务房间的核心动作，但「开任务」本身不再让茶客接话。理由是 P5.5 的自动触发常导致无意接话（任务 UI 操作 cancel 当前 turn 又起 scoring），不如让用户用显式动作（见 §7）决定何时让茶客介入。

## 2. 新口径

**核心一句话**：task event 是 UI 通知，不是对话消息。

```
用户操作 / 茶客产物检测
    ↓
server 更新 task store / artifacts
    ↓
emit TASK_* hint + TASK_INFO 权威快照
    ↓
frontend:
    taskState / taskPanel 正常更新
    chat stream append system bubble
```

不再发生：

- 不调用 `_kick_synthesized_user_message`
- 不调用 `_run_turn`
- 不 `room.append(USER_SPEAKER_ID, ...)`
- 不新增 transcript 行
- 不创建 message_id
- 不触发 review / decision 支持消息选择

系统气泡是当前客户端 UI 的瞬时反馈，和 `/help`、`/tools`、`/skills` 同类：刷新 / 切房后不从 transcript 重建。

## 3. 事件覆盖

| 来源 | envelope（`TASK_ARTIFACTS_CLEARED` 为新增，见 §4.3） | 系统气泡文案 | 是否进 transcript | 是否触发 AI |
|---|---|---|---|---|
| `open_task` | `TASK_OPEN` + `TASK_INFO` | `📋 用户开启任务【{title}】 · 目标：{goal}` | 否 | 否 |
| `close_task` | `TASK_CLOSE`(+`title`) + `TASK_INFO` | `✅ 任务【{title}】已完成` / `✗ 任务【{title}】已放弃` | 否 | 否 |
| `add_decision` | `TASK_DECISION_ADDED` + `TASK_INFO` | `📌 决策：{summary}` | 否 | 否 |
| `attach_artifact` | `TASK_ARTIFACT_ADDED` + `TASK_INFO` | `📎 用户挂载产物：{name}` | 否 | 否 |
| `clear_task_artifacts` | `TASK_ARTIFACTS_CLEARED` + `TASK_INFO` | `🗑️ 用户清空了任务【{title}】的产物（{count} 个文件）` | 否 | 否 |
| 茶客自动归集 | `TASK_ARTIFACT_ADDED` + `TASK_INFO` | `📎 茶客产出：{name}`（逐文件一条） | 否 | 否 |

> **`TASK_CLOSE` 需补 `title`**：现有 `TASK_CLOSE` envelope 的 `data` 只有 `{task_id, status, closed_at_ms}`，不含 `title`。系统气泡文案要 `任务【{title}】`，所以本设计要求后端给 `TASK_CLOSE` 的 `data` 补 `title` 字段（与 `TASK_OPEN` 走 `task.to_jsonl_dict()` 带全量字段同口径）。详见 §5.5。
>
> **茶客自动归集逐文件一条气泡**：`ArtifactDetector.detect` 对同一检测周期的多个新文件**逐文件** emit `TASK_ARTIFACT_ADDED`，前端因此渲染 N 条单名气泡（`📎 茶客产出：{name}`），不是一条拼接 `{name1}, {name2}, ...`。多文件合并留给 §11 可选项。

`update_task` 仍不发系统气泡。原因同 P5.5：需要 old/new diff 才能判断是不是有实质变更，先不扩大范围。

`set_active_task` 仍不发系统气泡。它是纯 UI 焦点切换，不是新事实。

## 4. 协议设计

### 4.1 不新增系统消息实体

不在 `Room.Message` 增加 `kind="system"`，也不新增 `transcript.jsonl` 行类型。系统气泡是前端对 task envelope 的本地渲染结果。

理由：

- transcript 保持“参与者真实发言”语义
- `format_messages` / summarizer / scoring 不需要识别系统消息
- 不需要处理系统消息的 message_id、review、decision 支持锚定
- 刷新后系统气泡消失是可接受的 UI 通知语义

### 4.2 复用现有 task envelope

优先复用已有 `TASK_OPEN` / `TASK_CLOSE` / `TASK_DECISION_ADDED` / `TASK_ARTIFACT_ADDED` / `TASK_INFO`，不新增 `TASK_EVENT_NOTICE`。

前端在 `handleEnvelope` 里处理 task hint 时做两件事：

```js
taskPanel.flashHint(env.type, env.data ?? {});
appendBubble({ kind: "system", text: formatTaskEventNotice(env.type, env.data ?? {}) });
```

其中 `TASK_INFO` 默认不显示气泡，因为它是权威快照，连接 / 切房 / reconnect 都会下发。唯一例外是 `clear_task_artifacts`：当前只有 `TASK_INFO`，没有独立 hint。为避免从泛型 `TASK_INFO` 猜测 diff，本设计新增一个轻量 hint。

### 4.3 新增 `task_artifacts_cleared` hint

为 `/clear task` 增加一个 task hint envelope：

```python
ChahuaEventType.TASK_ARTIFACTS_CLEARED = "task_artifacts_cleared"
```

data:

```json
{
  "task_id": "task_xxx",
  "title": "评审 PR-123",
  "count": 3,
  "names": ["a.md", "b.md", "c.md"]
}
```

顺序：

1. `tasks_store.clear_artifacts(task_id)`
2. `artifact_detector.forget(task_id)`
3. emit `TASK_ARTIFACTS_CLEARED`
4. emit `TASK_INFO`

前端收到 `TASK_ARTIFACTS_CLEARED` 显示系统气泡；`TASK_INFO` 只更新状态。

## 5. 后端实施

### 5.1 删除合成 user turn 入口

`server_inbound_task.py` 移除以下调用：

- `_inbound_open_task` 末尾的 `_kick_synthesized_user_message(open_task_text(...))`
- `_inbound_close_task` 末尾的 `_kick_synthesized_user_message(close_task_text(...))`
- `_inbound_attach_artifact` 末尾的 `_kick_synthesized_user_message(attach_artifact_text(...))`
- `_inbound_add_decision` 末尾的 `_kick_synthesized_user_message(add_decision_text(...))`
- `_inbound_clear_task_artifacts` 末尾的 `_kick_synthesized_user_message(clear_artifacts_text(...))`

保留 task store 写入、audit event、`TASK_*` hint、`TASK_INFO` 快照、`relink_task_dirs` 等现有状态逻辑。

### 5.2 删除 `_kick_synthesized_user_message`

已核实全仓只有 §5.1 那 5 处 task handler 调用 `ChahuaServer._kick_synthesized_user_message`，无其它使用方。§5.1 移除这 5 处后，**直接删除该 helper**。

不保留 legacy helper：保留一个「系统侧合成 user 消息」入口只会被后续改动误用回老路子，与 P5.8「task event 不是对话消息」的口径冲突。目标状态是这个入口在代码里彻底不存在。

### 5.3 茶客自动归集不再 append transcript

`ArtifactDetector.detect` 当前在 `new_names` 非空时：

```python
self.room.append(USER_SPEAKER_ID, detect_artifacts_text(sorted(new_names)), task_id=active_task_id)
```

改为只 emit `TASK_ARTIFACT_ADDED` 和 `TASK_INFO`。系统气泡由前端根据 `TASK_ARTIFACT_ADDED.data.created_by` 渲染：

- `created_by == "user"` → `📎 用户挂载产物：{name}`（`MARKED_BY_USER == "user"`）
- `created_by == "guest"` → `📎 茶客产出：{name}`（`ARTIFACT_CREATED_BY_GUEST == "guest"`）

同一检测周期多个新文件时，后端仍会 emit 多条 `TASK_ARTIFACT_ADDED`。前端可以先按单文件显示；若实测刷屏，再在前端做同 microtask / 100ms 窗口合并。

删掉 `room.append` 后，`artifact_detector.py` 里 `USER_SPEAKER_ID` 与 `detect_artifacts_text` 两个 import 变成未使用，一并清理。

**同 turn 内的可见性变化**：删 `room.append` 后，茶客在一个 AI 链里中途写 `./task/<x>`，**同链后续发言的茶客**不再以 transcript 消息形式看到「茶客产出 X」。但产物本身仍在 `tasks/<active>/artifacts/`，下一轮 prompt 重渲 `<current_task>` 的 artifacts 列表时照常出现——上下文不丢，只是「事件感」没了。可接受。

### 5.4 用户上传产物的重复 + 错误归因（必须处理）

`_inbound_attach_artifact` emit 的 `TASK_ARTIFACT_ADDED` 带 `created_by = MARKED_BY_USER`。但 `ArtifactDetector` 的 `seen` 缓存**不会被 `attach_artifact` 同步**（见 `artifact_detector.py` 类 docstring、CLAUDE.md P5.4 不变量）。因此用户给 **active 任务**上传产物后，下一次有 turn 跑时 `detect()` 会把同一文件当作 `new_names` 再 emit 一次 `TASK_ARTIFACT_ADDED`，且 `detect()` 对 `new_names` **无条件**打 `created_by = ARTIFACT_CREATED_BY_GUEST`。

P5.4 把这条重复标为「接受」——**前提是 hint 不可见**。P5.8 把每条 `TASK_ARTIFACT_ADDED` 渲成可见系统气泡后，这个重复会变成用户可见的 bug，而且作者认错：

```
📎 用户挂载产物：x.md      ← _inbound_attach_artifact emit
📎 茶客产出：x.md          ← 下一个 turn 的 detect() 重发，且 created_by=guest
```

**修法**：`_inbound_attach_artifact` 拷贝文件入 `tasks/<id>/artifacts/` 后，把新文件名同步进 detector 的 `seen` 缓存。`ArtifactDetector` 已有 `forget(task_id)` 这一类显式入口，照此加一个**单数签名**的 `mark_seen(task_id, name)` 方法（唯一调用方 `_inbound_attach_artifact` 一次只 attach 一个文件，不需要批量 API），避免调用方直接戳私属性 `seen[...]`。

**语义必须是增量 add，不能替换整组 `seen`**：实现写死成

```python
def mark_seen(self, task_id: str, name: str) -> None:
    self.seen.setdefault(task_id, set()).add(name)
```

如果实现成 `self.seen[task_id] = {name}`，会把该任务已有的 `seen` 集合整组覆盖掉，下一次 `detect()` 就把那些旧 artifact 重新当成 guest 新产物再发一轮气泡。

`attach_artifact` 可挂到非 active 任务，但 `mark_seen` 对任意 task_id 都安全；`detect()` 只扫 active 任务，所以重复实际只在「挂到 active 任务」时发生，`mark_seen` 一并覆盖即可。

### 5.5 `TASK_CLOSE` envelope 补 `title`

现有 `TASK_CLOSE` 的 `data` 只有 `{task_id, status, closed_at_ms}`，**不含 `title`**；而系统气泡文案需要 `任务【{title}】已完成`。后端给 `_emit_task_envelope(type=TASK_CLOSE, ...)` 的 `data` 补一个 `title` 字段（取被关任务的 `task.title`）。

选「后端补字段」而非「前端从 `taskState` 反查」：与 `TASK_OPEN` 走 `task.to_jsonl_dict()` 自带全量字段同口径，前端 formatter 不必依赖「hint 早于 `TASK_INFO`、此刻 `taskState` 仍持旧快照」这种时序假设。`schema_version` 不 bump——给现有 envelope 的 `data` 加可选字段，老前端忽略未知字段不出错。

### 5.6 删除 `task_event_text.py`

已核实全仓 import `task_event_text` 仅 `server_inbound_task.py` / `artifact_detector.py` / `tests/test_task_event_text.py` 三处，CLI REPL 不消费 task 事件文案。§5.1 / §5.3 删掉前两个调用点后，这些函数在 Python 侧**没有任何运行时使用方**。

因此 **直接删除 `chahua/task_event_text.py` 与 `tests/test_task_event_text.py`**。任务事件通知文案的唯一来源是前端 `formatTaskEventNotice`（§6.1）。

不保留为「Python 侧规格副本」：那会制造 Python / JS 双文案源，还要额外维护一致性测试，而 P5.8 之后 Python 侧根本不渲染这些文案，副本无运行时价值。

如果将来要做 §11 的 `notice_text`（hint data 直接带文案、彻底消除双写），届时再在后端按需引入文案构造，不必为此预留本模块。

## 6. 前端实施

### 6.1 新 formatter

在 `app/renderer/renderer.js` 或独立 `task_event_notice.js` 增加：

```js
function formatTaskEventNotice(type, data) {
  switch (type) {
    case EventType.TASK_OPEN:
      return `📋 用户开启任务【${data.title || TASK_UNTITLED}】${data.goal ? ` · 目标：${firstLine(data.goal)}` : ""}`;
    case EventType.TASK_CLOSE: {
      // data.title 由后端补字段提供（§5.5）。
      const closedTitle = data.title || TASK_UNTITLED;
      return data.status === "done"
        ? `✅ 任务【${closedTitle}】已完成`
        : `✗ 任务【${closedTitle}】已放弃`;
    }
    case EventType.TASK_DECISION_ADDED:
      return `📌 决策：${data.summary || ""}`;
    case EventType.TASK_ARTIFACT_ADDED:
      return data.created_by === "guest"
        ? `📎 茶客产出：${data.name || ""}`
        : `📎 用户挂载产物：${data.name || ""}`;
    case EventType.TASK_ARTIFACTS_CLEARED:
      return `🗑️ 用户清空了任务【${data.title || TASK_UNTITLED}】的产物（${data.count || 0} 个文件）`;
    default:
      return "";
  }
}
```

长 `goal` 只取首行并截断到 80 字以内。系统气泡不要塞完整 goal，完整内容已经在任务面板里。

### 6.2 task hint 分支追加系统气泡

当前 task hint 分支只 flash：

```js
case EventType.TASK_OPEN:
case EventType.TASK_UPDATE:
case EventType.TASK_DECISION_ADDED:
case EventType.TASK_ARTIFACT_ADDED:
case EventType.TASK_CLOSE:
  taskPanel.flashHint(env.type, env.data ?? {});
  return;
```

改为：

```js
case EventType.TASK_OPEN:
case EventType.TASK_DECISION_ADDED:
case EventType.TASK_ARTIFACT_ADDED:
case EventType.TASK_CLOSE: {
  taskPanel.flashHint(env.type, env.data ?? {});
  const text = formatTaskEventNotice(env.type, env.data ?? {});
  if (text) appendBubble({ kind: "system", text });
  return;
}
case EventType.TASK_ARTIFACTS_CLEARED: {
  // 只为系统气泡而来：状态推进由紧随其后的 TASK_INFO 完成，
  // 不接 taskPanel.flashHint（清空动作不需要增量项高亮）。
  const text = formatTaskEventNotice(env.type, env.data ?? {});
  if (text) appendBubble({ kind: "system", text });
  return;
}
case EventType.TASK_UPDATE:
  taskPanel.flashHint(env.type, env.data ?? {});
  return;
```

`TASK_ARTIFACTS_CLEARED` 单独成一支：它没有可高亮的「新增项」，状态推进全靠紧随的 `TASK_INFO`，唯一价值就是系统气泡，因此不调 `taskPanel.flashHint`。

`TASK_UPDATE` 不显示气泡，避免用户编辑标题时聊天流被刷。

### 6.3 历史回放不补系统气泡

`chat_stream.renderHistory(messages)` 不变。系统气泡不进 transcript，因此刷新 / 切房后不会重建。

这是刻意选择：任务面板是任务状态的持久视图，系统气泡只是“刚发生”的反馈。

## 7. UX 规则

- 系统气泡居中，沿用 `.bubble-system`
- 不显示头像、speaker、message id
- 不挂复制按钮和“请审”按钮
- 不出现在右键“标为决策”的支持消息列表里
- 不参与 task filter 的消息列表语义
- 不在 room export markdown 里出现
- 不触发 unread / handoff / scoring

如果用户希望茶客讨论任务事件，应使用显式动作：

- “指派下一句” / handoff delegate
- “请审”某条真实消息
- 直接发一条用户消息，例如“请大家根据刚挂的产物继续评审”

## 9. 迁移与兼容

已有房间里 P5.5 曾写入 transcript 的合成 user 消息不迁移、不删除。

理由：

- transcript 是 append-only 历史
- 删除旧行会影响 summary / cursor / debug turn 索引
- 老消息数量有限，保留成本低

新版本只保证未来 task 事件不再追加这类消息。

**已知可见不一致**：升级后的老房间里，P5.5 时代写入的合成 user 消息刷新 / 切房后仍会作为用户气泡重建出现，而 P5.8 之后的新 task 事件不再重建——同一房间历史里两种行为并存。这是用户可见的（不只是技术成本），但老消息数量有限、且属一次性历史残留，接受不处理。
