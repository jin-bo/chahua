# P20.1 茶客实时状态提示

> 状态：已实现（分支 `feat/p20.1-live-hints`），验收记录见 §8
> 前置：P20（`docs/P20-茶客调用消耗取证.md`）—— transport 已在接 `LLM_RETRY` / `LLM_CALL_COMPLETED` / `COMPACTION_SETTLED`。

## 1. 问题

茶客回复时，现在聊天区只有一个闪烁光标。两种情况下光标会长时间不动，看起来像卡死：

- **重试退避**：上游限流 / 5xx，agentao 在一次 `chat_stream` 内部按 Retry-After 退避重试，可能等几秒到几十秒。
- **上下文压缩**：历史过长时 agentao 调一次摘要模型做 full compaction，最长约一分钟（agentao 注释 #491：就是为了让 UI 说「compacting」而不是「thinking」才加的 `COMPACTION_STARTED`）。

P20 只把这些事后记进调试抽屉，进行中的用户看不到。

## 2. 目标 / 非目标

目标：进行中的茶客气泡上显示一行临时提示，状态结束即消失。

- 重试：`正在重连…（第 1/4 次）`，悬停显示原因（如 `status=429`）。
- 压缩：`正在整理上下文…`

非目标：

- 不落盘、不进 transcript、不进调试记录（P20 已有事后记录）。
- 不做倒计时（退避时长只是计划值，倒计时到 0 却仍在等反而误导）。
- CLI 不显示（流式文本中间插状态行会打乱输出；CLI 本来就静默 thinking / tool）。
- 不覆盖打分 / 摘要 / 后台 run（与 P20 范围一致：只有茶客 transport）。
- `GUEST_THINKING` 前端显示是另一件事，本期不碰。

## 3. 协议

新增 envelope 类型 `guest_status`（hint 型，不 bump `schema_version`）。挂当前 `bind()` 的 turn_id / message_id / guest_name。

```jsonc
// 重试
{"state": "retrying", "retry": 1, "max_retries": 4, "delay_s": 1.62, "reason": "status=503"}
// 压缩（只有 full 压缩会发 COMPACTION_STARTED，另两种毫秒级完成）
{"state": "compacting"}
// 清除
{"state": "idle"}
```

retry / max_retries / delay_s / reason 走 P20 同一套白名单 + 类型清洗（`_llm_call_records._extract`），缺键就不写。

## 4. 后端：状态机（`ChahuaTransport`）

transport 持 `_live_status: Optional[dict]`（最近一次发出的非 idle 状态），`bind()` 进入时清空。只在 bind 内（`_message_id is not None`）发。

| agentao 事件 | 动作 |
|---|---|
| `LLM_RETRY` | 发 `retrying`（每次重试都发，序号刷新） |
| `COMPACTION_STARTED` | 发 `compacting` |
| `LLM_CALL_COMPLETED` | 若 `_live_status` 是 retrying → 发 `idle` |
| `COMPACTION_SETTLED` | 若 `_live_status` 是 compacting → 发 `idle` |

- `idle` 只在当前有对应状态时才发，平时零额外帧。
- P20 记录照旧：这几个事件先喂 `_llm_records`，再走状态机；两者失败互不影响，状态发送失败只 WARN。
- 不在 transport 侧处理 `message_end`：前端在气泡收尾时无条件清提示（见 §5），后端不必补 `idle`。

**切回房间**：`inflight_snapshot()` 带上 `live_status`，`_emit_inflight_message` 在 `message_start` + `message_delta` 之后补发一帧 `guest_status`，让切回时正在退避 / 压缩的气泡立刻有提示。

**后台**：后台房 router 白名单与 bg run `BatchMessageSink` 都是默认丢弃，`guest_status` 不加入 —— 后台不需要实时提示。bg run 侧显式列进 `_DROP` 以示有意。

## 5. 前端

- 纯逻辑 `app/renderer/live_status_core.mjs::describeLiveStatus(data) → {text, title} | null`（node:test 覆盖）。
- `chat_view.js::setLiveHint(bubble, hint|null)`：在气泡内维护一个 `.live-hint` 节点（与 `.status-tail` 分开 —— 后者是终态尾巴，不能被实时提示覆盖或清掉）。
- `chat_stream.js`：
  - `applyLiveStatus(env)`：按 message_id 找 in-flight 气泡；找不到（未建流式气泡）就忽略。
  - 收到 `message_delta` 有文本 → 清 retrying 提示（重试成功后文本已经开始流，不必等 `LLM_CALL_COMPLETED`）。compacting 期间不会有 delta，不受影响。
  - `endStreamingMessage` / `closeInFlightOnDisconnect` → 无条件清提示。
- `envelope_router.js` 加 `GUEST_STATUS` 分支；调试抽屉不消费。

## 6. 不变量

- **`guest_status` 是纯 UI hint**：不落盘、不进 transcript / debug、不影响消息状态；`message_end.status` 仍是边界 truth。
- **气泡收尾前端无条件清提示**，不依赖后端补 `idle`（取消 / 出错 / 断线都可能丢 idle）。
- **后台不发**：不加入后台房白名单，bg run sink 显式 drop。

## 7. 测试

- transport：retry → retrying 帧字段清洗；COMPLETED 后 idle；无 retry 的 COMPLETED 不发 idle；compaction started → settled；bind 外不发；新 bind 清状态；`inflight_snapshot` 带 live_status。
- snapshot：切回时补发 guest_status。
- bg run sink：guest_status 被丢弃。
- 真 agentao 契约：用 P20 的假 SSE（`fail_script`）跑一次，断言收到 retrying → idle 且先于 message_end。
- 前端：`live_status_core.test.mjs`。
- 桌面壳：假 SSE 端点注入一次 429 + Retry-After，肉眼确认提示出现并消失。
