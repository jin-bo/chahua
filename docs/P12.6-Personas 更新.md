# P12.6：Personas 更新 —— 记录来源 + 已安装页 + 检查/更新

> 给「导入 persona」补上一条生命周期：导入时**记录来源**（本地路径 / GitHub），在导入 modal 里加一个**「已安装」页**列出受管 persona，并支持**检查更新 → 单个更新 / 全部更新**。把 persona 从「一次性拷进来的死资产」升级成「可追踪来源、可同步上游」的受管包 —— 与 npm `package.json` 锁来源、`npm outdated` / `npm update` 同款心智。

## 现状与痛点

导入链路（`chahua/persona_import.py`）：本地 `import_from_folder` / GitHub `import_from_github` → 采集 files → manifest dry-run → `_write_files` 拷到 `user_data_root/chahua/personas/<Name>/`。`_validate_target` **故意拒绝覆盖**（目标已存在 → `PersonaImportError`）。

痛点：

- **来源即丢**。拷完文件后，「这个 persona 从哪来的」彻底失忆 —— 磁盘上只剩 `<Name>/` 目录，没有 GitHub URL / 本地路径的任何痕迹。
- **无法更新**。上游作者修了 prompt / 加了 skill，用户唯一的办法是「手动删掉本地目录 → 重新走一遍导入」。而导入又拒绝覆盖，得先删再导，两步且易错。
- **看不见装了什么**。导入 modal 只有「导入」一个动作，没有任何「已安装清单」视图 —— 用户装了哪些、各自什么来源、有没有新版，全靠自己记。
- **改不动现有拒覆盖语义**。`_validate_target` + `_write_files` 的 `mkdir(exist_ok=False)` 是承重护栏（防静默清掉用户改过的 persona），更新必须走一条**显式的、带原子替换**的新路径，不能简单放开覆盖。

## 设计概览

三件事，分别落在「记录」「展示」「同步」三层：

1. **记录来源**：导入成功后，在 persona 目录写一份 chahua 私有 sidecar `.chahua-source.json`（provenance）。记 source_type / 原始 URL 或路径 / GitHub commit sha / 内容哈希 / 时间戳。这是**消费侧安装元数据**，不进作者的 `persona.toml`（那是可分发清单，会被更新覆盖）。
2. **已安装页**：导入 modal 加 tab 切换（「导入」/「已安装」）。「已安装」页经新 inbound `list_installed_personas` 拉取 `user_data_root` 下**所有 dir-form persona**（内置 flat-form 不进列表），渲染每行：名字 / 头像 / 来源 / 状态 / 「更新」/「删除」按钮，顶部「检查更新」「全部更新」。**有 provenance 的可检查/更新；缺/坏 provenance 的标「来源未知 · 不可更新」，仍可删除**。**按需拉取，不塞进高频的 `room_info`**。
3. **检查 + 更新**：
   - **检查**（`check_persona_updates`）：GitHub 走 commits API 比 commit sha（1 req/persona，便宜）；本地文件夹走重新遍历源目录算内容哈希比对。结果经 `personas_installed` envelope 回填每行状态。
   - **更新**（`update_persona {name}`）：按 provenance 重新采集 → manifest dry-run → **原子替换**目录 → 重写 provenance。「全部更新」由前端对 `update_available` 行串行发 `update_persona`（复用单条路径、给逐行反馈，同上传串行循环口径）。
4. **删除**（`delete_persona {name}`）：从「已安装」行直接删整个 persona 目录（destructive，前端 `confirm()` 二次确认）。只删 `user_data_root` 下的 dir-form 目录，删完重发 `personas_installed`（该行消失）+ `room_info`（picker 刷新）。

## 承重不变量

- **provenance 是消费侧安装元数据，住 `.chahua-source.json`，绝不进 `persona.toml`**。`persona.toml` 是作者的可分发清单（严格白名单、更新时会被上游覆盖）；来源 / commit sha / 安装时间是「装它的人」的本地事实。两者生命周期相反（manifest 跟上游走、provenance 跟本地装机走），混在一起更新就会自毁记录。**Why**：与 npm `package.json`（声明）vs `package-lock.json` / `node_modules/.package-lock`（安装事实）同款分层。
- **`.chahua-source.json` 永不被当作 persona 包内容采集**。加入 `_SKIP_NAMES` —— `_collect_local_files` / GitHub walker / installed-dir 哈希遍历**三处**都跳过它。**Why**：① 它是 chahua 内部元数据，不该跟着包被「再导出/再导入」漂走（防 A 装的 persona 带着 A 的来源记录被 B 导入）；② 它由 importer 在 `_write_files` **之后**单独写，更新时**先于**替换重算，永远是新鲜值，绝不能被旧文件覆盖。
- **provenance `schema_version` 必填、当前唯一合法值 = 1，缺/坏 → 该 persona 仍列在「已安装」页但标「来源未知」、`status="source_unavailable"`、不可更新，不报错、不阻断**。读 provenance 是唯一允许 `try/except + WARN + 降级` 的路径（与 `discover_personas` 容错同档）——坏 provenance 不该让 persona 从列表消失，只是去掉「更新」能力、保留「删除」。**Why**：provenance 是增强、不是承重；它坏了用户仍能用 / 删 / 重导该 persona。**注意此处与 `persona.toml` 的 fail-fast 口径有意相反**（manifest 坏在消费路径要冒泡，provenance 坏只降级）。
- **更新 = 全量替换 + 原子 swap，绝不原地改写**。写新内容到临时目录 `personas/.<Name>.update-<pid>/` → manifest dry-run 通过 → `rename(target → .<Name>.bak-<pid>)` → `rename(tmp → target)` → 成功删 bak / 任一步失败 restore bak。**Why**：沿用 `_write_files` 「失败 rmtree 回滚」哲学，但更新的目标**已存在**，必须保证「替换中途被 kill / manifest 校验失败」时旧版完好无损 —— 半个 persona 比旧 persona 危险得多。
- **更新前做本地改动检测；本地已改 → 默认拒，须 `update_persona{force:true}` 才覆盖**。安装时存内容哈希；更新前重算**已安装目录**当前哈希，≠ 存档 → `local_modified=true`。`update_persona` 无 `force` 且 `local_modified` → `PersonaImportError("本地已修改，强制更新会丢弃改动")` 拒绝；`force:true` 才走原子替换。前端「更新」按钮在 `local_modified` 行先 `confirm()` 再发 `force:true`（destructive）。**Why**：服务端必须能区分「普通更新」与「用户已确认丢弃本地改动」——单靠前端 confirm 不够（wscat / 旧前端可绕过），`force` 把决定权钉在 inbound。哈希一处计算、三处复用（安装记录 / 本地改动检测 / 文件夹源 diff）。
- **更新不影响在跑的房间，新内容下次 session 重建才生效**。替换 persona 文件不动任何已构造的 `TeaGuest`（system prompt 在 session build 时读进内存、skills 已 copytree、MCP 已装）。与 P12「作者更新 manifest 不自动重 inflate」同语义：想让新版 persona 生效，删除该茶客重新加入 / 重启房间。**Why**：mid-session 替换磁盘文件天然安全（无人 mmap），把「何时生效」交给既有的 session 重建边界，不引入热重载复杂度。
- **`persona.toml` 的 `version` 是纯展示字段，绝不参与 `status` 判定**。「变没变」永远只由 commit SHA（github）/ content_hash（folder）说了算；`version` 仅渲到 UI（`installed_version` / `latest_version` 并列）给用户肉眼对比。**内容变了一律 `update_available`，即使上游版本号更低（降级）也照样提示** —— 改不改交给用户看版本号自己定。**Why**：版本号依赖作者自觉维护，社区包大量不带 / 不勤 bump；让它参与判定会**漏掉真实变更**（尤其安全/bug 修复）。**不做 `_cmp_version` 比较、不做降级特判** —— 任何「version 改写 status」都是回归。**`latest_version` 取数失败（404/网络/解析/缺字段）也只是 `latest_version=null` + detail 提示，绝不改 status** —— 展示用版本号取不到是 UI 缺失，不是更新判定出错。`version` 是 `persona.toml` 新增**可选**字段，加它**不** bump manifest `schema_version`（与 P12「加字段不 bump」一致）。
- **`list_installed_personas` / `check_persona_updates` 是按需的，绝不进 `room_info`**。provenance 读盘 + 网络检查只在用户打开「已安装」页 / 点「检查更新」时发生。`room_info`（高频、每次房间快照都发）只继续带 `personas_available`（picker 用，无 provenance）。**Why**：把网络 IO / 多文件读盘从热路径剔出去；picker 不需要来源信息。
- **网络型操作走 `asyncio.to_thread`，不阻塞 WS 事件循环**。`check_persona_updates`（GitHub commits API）/ `update_persona`（GitHub 全量重拉）的同步 urllib 调用包进 `to_thread`。**Why**：「检查全部」可能串十几个 GitHub 请求，跑在 handler 里会冻住整个 sidecar（现有 `import_*` 同步阻塞是既有 wart，本步新路径不复制该问题，并在迁移段标注 import 可后续一并迁）。
- **「已安装」列表 = `user_data_root` 下所有 dir-form persona；provenance 只 gate「检查/更新」，不 gate「列出/删除」**。内置 flat-form（app_root ship 自带）**不进列表**（只读 app_root 动不了、也无「上游」概念）。`user_data_root` 下的 dir-form 无论有无 provenance 都列出、都可删；只有带可用 provenance 的才有「更新」。**Why**：① 列出全部让 pre-P12.6 老导入（无 provenance）、provenance 损坏的包都能被看到 / 删除，不会从 UI 消失变成孤儿；② 把「能不能更新」与「在不在列表」解耦，避免「坏一个 json 整个 persona 失踪」。
- **删除只 `rmtree` 一个 `user_data_root` 下的 persona 目录，路径强校验防穿越**。`name` 经 `sanitize_fs_name` + 解析后 `relative_to(user_data_root/chahua/personas)` 校验、且必须 `is_dir()`；app_root / 列表外的路径一律拒。**Why**：删除是 destructive 且 `name` 来自前端，必须像 `download_file` 一样把 traversal 钉死在入口。
- **删除不影响在跑的房间，引用该 persona 的房间下次 session 重建才会因路径缺失报错**。同更新：已构造的 `TeaGuest` 不受磁盘删除影响；但引用该 persona 的房间 `room.toml` 在下次重建时 `persona` 路径 miss → 加载报错。本步**不**主动扫所有房间 toml 拦截删除 —— 前端 `confirm()` 文案提示「正被房间引用时需先移除该茶客」，把判断交给用户。**Why**：跨房扫描 toml 重且 picker 无现成数据；与「更新不 re-inflate」同款「交给既有 session 重建边界」哲学，不引入全局引用计数。
- **5 个新事件不 bump `schema_version`**。`list_installed_personas` / `check_persona_updates` / `update_persona` / `delete_persona` 四个 inbound + `personas_installed` 下行 envelope 沿用「旧前端忽略未知 type」口径。**Why**：与 P11 AGENT_RUN_* / P8.4 MANAGED_SESSION_* 同款增量加法。

## 文件格式：`.chahua-source.json`

写在 `user_data_root/chahua/personas/<Name>/.chahua-source.json`。`schema_version` 锚版本兼容（与 `.chahua-seeded` 幂等标记同属 chahua 私有 dotfile 家族）。

**这是一份新的 per-persona sidecar，无现成文件可复用。** 现有配置文件都不合适：① `persona.toml` 是作者的可分发清单（严格白名单 + 更新被上游覆盖），承重不变量已定不能掺消费侧数据；② `room.toml` 是房间配置，与 persona 安装无关；③ 最接近的是 `<user_data_root>/.chahua-trusted-mcp.json`（trust.py，**集中式** JSON、key=persona_rel）—— 它证明「per-persona 消费侧状态」有先例，但它是为 **MCP 信任**这一独立关切、且**集中存**。provenance 选 **per-dir sidecar 而非集中注册表**的理由：**随 persona 目录共存亡**（`delete_persona` 的 `rmtree` 顺带删掉，无孤儿条目要清理、无「注册表 vs 磁盘」对账）+ 原子 swap 时跟着目录一起换。代价是多一种 dotfile 约定 —— 但 `.chahua-seeded` 已立此例。

GitHub 来源：

```json
{
  "schema_version": 1,
  "name": "Yvonne",
  "source_type": "github",
  "source_url": "https://github.com/owner/repo/tree/main/personas/Yvonne",
  "github": {
    "owner": "owner",
    "repo": "repo",
    "ref": "main",
    "path": "personas/Yvonne",
    "commit_sha": "a1b2c3d4..."
  },
  "content_hash": "sha256:...",
  "version": "1.2.0",
  "imported_at": "2026-05-27T10:00:00Z",
  "updated_at": "2026-05-27T10:00:00Z"
}
```

- `ref`：用户给的分支（`tree/<branch>/...`）或 `null`（仓库根 / 未指定 → 走 default branch）。原样存，更新时用同 ref 再查。
- `commit_sha`：导入时刻该 `path` 的最新 commit sha（commits API 取）。**「变没变」的权威锚点**。
- `version`：导入时刻 `persona.toml` 里的 `version`（可选；包没声明 → `null`）。**纯展示字段**，仅渲到 UI 给用户肉眼对比，**不参与 `status` 判定**（见「更新检测策略」）。
- `source_url`：原始 URL，给前端展示用（「来源：GitHub · owner/repo」）。

本地文件夹来源：

```json
{
  "schema_version": 1,
  "name": "Yvonne",
  "source_type": "folder",
  "source_url": "/Users/me/dev/personas/Yvonne",
  "source_path": "/Users/me/dev/personas/Yvonne",
  "content_hash": "sha256:...",
  "version": "1.2.0",
  "imported_at": "2026-05-27T10:00:00Z",
  "updated_at": "2026-05-27T10:00:00Z"
}
```

- `content_hash`：导入时所有采集文件（不含 `.chahua-source.json`）的规范化哈希。文件夹源 diff + 本地改动检测共用。

`content_hash` 规范：`sha256(`，对 `sorted(files, key=relpath)` 逐项喂 `relpath + "\0" + sha256(bytes).hexdigest() + "\n"`，前缀 `"sha256:"`。relpath 用 `/` 归一（跨平台稳定）。

`version` 来自作者在 `persona.toml` 声明的新增**可选**字段（缺则全程 `null`、退化纯内容信号）：

```toml
schema_version = 1
display_name = "伊冯"
version = "1.2.0"        # 可选；作者发布新版时 bump
summary = "..."
```

## 更新检测策略

**status 唯一由内容信号定，version 纯展示**：commit SHA（github）/ content_hash（folder）判**「变没变」**，是 `status` 的**唯一**判据；`persona.toml` 的 `version` **只**渲到 UI 给人看（「本地 v1.2.0 · 上游 v1.3.0」），**绝不改写 `status`**。**Why**：包可能不声明 version、或作者改了内容忘 bump，让 version 参与判定会**漏掉真实变更**（尤其安全/bug 修复）。内容信号说「变了」就一定 `update_available`，哪怕上游版本号更低（疑似降级）也照样提示 —— 改不改由用户看着两个版本号自己决定。

| 来源 | 检查（cheap） | 更新（heavy） |
|---|---|---|
| GitHub | commits API `GET /repos/{o}/{r}/commits?path={path}&per_page=1[&sha={ref}]` 取 `[0].sha`，== 存档 → `up_to_date`（**1 req**，**不**取 version）；≠ 存档 → `update_available` + **尽力**再取一次上游 `persona.toml` 读 `version` 填 `latest_version`（第 2 req，**仅在确有变化时**，纯展示，失败不影响 status —— 见下） | 全量重拉 contents（同导入）→ 校验 → 原子替换 → 重存 commit_sha + content_hash + version |
| 本地文件夹 | 源目录存在 → 重走 `_collect_local_files` 算 content_hash + 顺手读源 `persona.toml` version（重走时免费）；≠ 存档 → `update_available` + 填 `latest_version`；源目录不在 → `source_unavailable`（**纯本地，无网络**） | 重走采集 → 校验 → 原子替换 → 重存 content_hash + version |

**version 是纯展示字段，不参与任何判定**：`installed_version`（已装，list 即有）与 `latest_version`（上游，仅 check 检到变化时填）并列渲染让用户肉眼对比，**没有 `_cmp_version` 比较逻辑、没有降级特判、不影响 status**。任一侧缺 version → 该侧不显、退化成纯「有更新 / 最新」文案。不引 `packaging`、不解析 semver（非目标）。

**`latest_version` 取数是尽力而为，失败绝不波及 status**：内容信号已判定 `update_available` 之后才去取上游 version；这一步（github 单取 `persona.toml`）若 404 / 网络错 / 解析失败 / manifest 缺 `version` 字段 —— 一律 **`status` 保持 `update_available`、`latest_version=null`、`detail` 追一句「上游版本信息不可用」**，**不**降级成 `error` / `source_unavailable`。**Why**：内容信号才是更新判据，「展示用的版本号没取到」是纯 UI 缺失，让它改写 status 会把「确有更新」误报成错误、破坏「version 不影响判定」不变量。实现上：version 取数包独立 try/except，与「定 status 的内容信号检查」完全隔离。

每行**两个正交维度**：`status`（上游状态，单值枚举）+ `local_modified`（本地是否被改，bool）。两者独立，前端组合渲染文案 —— 避免「本地改了且上游也更新了」时一个 `status` 字段表达不下。`installed_version` / `latest_version` 是第三类**纯展示**附加字段，不进状态判定。

`status`（上游状态枚举）：

- `unknown`：**仅**「有可用 provenance 但还没检查」（list 初拉）。缺/坏 provenance **不**用此值 —— 见 `source_unavailable`。
- `up_to_date`：检查过，与上游一致。
- `update_available`：检查到上游更新。
- `source_unavailable`：无法更新的统一终态 —— **缺/坏 provenance**（list 初拉即定）、或检查时文件夹源已删 / 移走 / GitHub 404。`detail` 带具体原因（「来源未知」/「源目录不存在」/「仓库或路径不存在」）。
- `error`：检查时 GitHub 403 rate-limit / 网络错等**临时**失败（重试可能恢复，区别于 `source_unavailable` 的稳定不可更新），文案带原因。

`local_modified`（bool）：已安装目录当前哈希 ≠ 存档哈希（本地被改过）。与 `status` 正交 —— `update_available + local_modified=true` = 「本地改了且上游也更新了」，前端合并文案、更新前强确认「将丢弃本地改动」并发 `force:true`。无 provenance（无存档哈希）时 `local_modified` 恒 `false`（无从判断）。

## 模块改动

### `chahua/persona_manifest.py`（新增 `version` 字段）

- `_ALLOWED_TOP_KEYS` 加 `"version"`；`PersonaManifest` dataclass 加 `version: Optional[str]`；`_parse_dict` 走 `_opt_str(data, "version", ...)`（缺/空 → `None`，非 str → `PersonaManifestError`）。**不** bump `SCHEMA_VERSION`（加字段不 bump，破坏性才 bump —— P12 既定）。
- **不加任何版本比较器**（无 `_cmp_version`）—— version 纯展示，不比较（承重不变量）。

### `chahua/persona_import.py`（采集复用 + provenance + 更新入口）

抽出共享、加更新路径：

- 新 `@dataclass(frozen=True) PersonaSource`（= provenance 内存形态，含 `version: Optional[str]`）+ `read_source(persona_dir) -> Optional[PersonaSource]`（坏/缺 → WARN+None）+ `write_source(persona_dir, source)`（`write_json_atomic`）。
- `_content_hash(files) -> str`（上文规范）。
- 新 `_version_from_files(files) -> Optional[str]`：从采集到的 files 里挑根级 `persona.toml`、`parse_persona_manifest_bytes` 后取 `.version`（缺 manifest / 缺字段 → `None`）。import / update / github-check 复用。
- 重构 import：`import_from_folder` / `import_from_github` 末尾，`_write_files` 之后 `write_source(...)`（含 `version=_version_from_files(files)`）。GitHub 侧加 `_gh_latest_commit_sha(owner, repo, ref, path)`（commits API）+ `_gh_fetch_one_file(owner, repo, ref, path)`（check 时单取上游 `persona.toml` 读 version）。
- 把「按 source 采集 files」抽成 `_collect_from_source(source) -> list[tuple[str,bytes]]`（folder → `_collect_local_files`；github → `_fetch_github_dir`），import 与 update 共用。
- 新 `update_persona(paths, name, *, force=False) -> UpdatedPersona`：读 provenance（无 → `PersonaImportError("不是导入的 persona / 无来源记录")`）→ **本地改动检测：已安装哈希 ≠ 存档且 `not force` → `PersonaImportError("本地已修改，强制更新会丢弃改动")`** → `_collect_from_source` → `_validate_manifest_pre_write` → `_install_files(target, files, replace=True)`（原子 swap）→ 重算并 `write_source`（含新 `version`）。
- 新 `check_persona_update(paths, name) -> UpdateStatus`：读 provenance → **内容信号**（github 比 commit sha / folder 比 hash）**唯一**定 `status`（变了 → `update_available`，含降级；没变 → `up_to_date`）→ 变了才取上游 version 填 `latest_version`（github 单取 `persona.toml`；folder 重走时顺手；**纯展示、不比较、不改 status**）→ 加 installed-dir 本地改动检测 → 返 `status` + `local_modified` + `installed_version` + `latest_version` + `detail`。**version 取数独立 try/except**：404 / 网络 / 解析失败 / 缺字段 → `latest_version=null` + detail 追「上游版本信息不可用」，`status` 不动（绝不退 `error` / `source_unavailable`）。
- 新 `delete_persona(paths, name) -> None`：`sanitize_fs_name(name)` → 解析 `user_data_root/chahua/personas/<name>` → `relative_to` 校验落在 personas 根内且 `is_dir()` → `shutil.rmtree`。越界 / 非目录 / 不存在 → `PersonaImportError`（含可读原因）。
- `_install_files`：抽 `_write_files` 的写盘核心，参数化 `replace`。`replace=False` 走现有 `mkdir(exist_ok=False)`；`replace=True` 走 tmp dir → swap → restore-on-fail。
- `_SKIP_NAMES` 加 `".chahua-source.json"`。

## 线协议

上行（新增 4 个 `type`）：

- `{type: "list_installed_personas"}` —— 无 payload。
- `{type: "check_persona_updates", name?: string}` —— `name` 缺省 = 检查全部。
- `{type: "update_persona", name: string, force?: boolean}` —— 更新单个；`force` 缺省 `false`，本地已改时须 `true` 才覆盖（前端 confirm 后置 true）。
- `{type: "delete_persona", name: string}` —— 删除单个（destructive，前端已 confirm）。

下行（新增 1 个 envelope）：

- `personas_installed` —— `data.personas = [{name, persona, avatar_data_uri, summary, source_type, source_url, status, local_modified, installed_version, latest_version, detail}, ...]`。`status` 是上游状态枚举、`local_modified` 是 bool（两维正交，见「更新检测策略」）；`installed_version`（已装版本，list 即有，可 null）、`latest_version`（上游版本，仅 `check` 检到变化时填，否则 null）给前端**并列纯展示**（不比较、不影响 status）。`list` / `check` / `update` / `delete` 后均回这一帧（权威全量，前端整批覆盖渲染，同 `room_info.personas_available` 口径）。

更新成功/失败仍走既有 `notice`（info/error）给用户可读反馈。

## 非目标（明确不做）

- **删除时主动扫所有房间 toml 拦截「正被引用」** —— 删除允许进行，前端 `confirm()` 文案提示即可；不做全局引用计数（重且 picker 无现成数据，交给既有 session 重建边界）。
- **私有仓 / token 鉴权 GitHub 更新** —— 沿用导入的匿名 60 req/h 限制。
- **保留本地改动的三方合并** —— 更新是全量替换；本地改动检测只用于**警告**，不做 merge。要保改动请先备份。
- **自动后台检查更新 / 启动时检查** —— 检查只在用户显式点「检查更新」时跑（省网络 + 不惊扰）。
- **版本比较 / 完整 semver / changelog** —— `version` 本步**只读取 + 并列展示**（`installed_version` / `latest_version`），**不**做任何比较（无 `_cmp_version`）、**不**解析 semver、**不**影响 `status`、**不**渲染 changelog。「变没变」始终由 commit sha / content_hash 这一权威内容信号定（见承重不变量）。「按版本号判断新旧 / 拦降级」如有需要留后续小迭代。
- **`room.toml` 自动 re-inflate manifest defaults** —— 与 P12 一致，更新 persona 文件不重写已加入房间茶客的配置；新默认下次加入才生效。
- **把 import 的同步阻塞也迁到 `to_thread`** —— 本步只让**新**路径走 `to_thread`；既有 `import_*` 阻塞是独立 wart，可后续一并迁（留 breadcrumb）。

## 风险与缓解

- **替换中途崩 → 半个 persona**：原子 swap（tmp → 校验 → rename old→bak → rename tmp→target → del bak），任一步失败 restore bak。测试钉「manifest 校验失败时旧版完好 + 无残留」。
- **无声清掉用户本地改动**：安装/更新存 content_hash，更新前比已安装目录哈希；`local_modified` 走二次确认。
- **GitHub rate-limit（检查全部时放大 N 倍）**：检查用 commits API 1 req/persona（不是全量重拉）；撞 403 该行标 `error` 含「匿名 60 次/小时」文案，其余行不受影响。
- **provenance 跟着包漂走**：`.chahua-source.json` 进 `_SKIP_NAMES`，采集三处都跳；它只由 importer 在本地新鲜写。测试钉「源目录含该文件时不被采集」。
- **网络阻塞冻 UI**：check/update 走 `asyncio.to_thread`。
- **provenance 坏导致 persona 消失**：读 provenance 是容错档（WARN+None），坏只降级「不可更新」，persona 仍在列表/picker。

- 从 GitHub 导入一个 persona → 目录下生成 `.chahua-source.json`（含 commit_sha）；从本地文件夹导入 → 含 source_path + content_hash。
