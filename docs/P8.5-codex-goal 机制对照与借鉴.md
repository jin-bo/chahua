## 1. 核心结论

**「能否用 `/goal` 做 ChaHua 任务调度」的答案是：核心机制无需移植 —— 移植即重造 MTS。**
两者是同一类机制（host 拥有的、预算有界的续跑 loop + 写权限三分），ChaHua 这套早已落地。

一处**核心反差**先讲清，免得把对照读偏（再强调见 §3 末）：`/goal` 的定义性行为是「**停
不下来**」—— thread idle 就强制起新 turn，直到 complete/blocked/budget/用户（被评估文档
TL;DR / §5）。ChaHua MTS 在 manager idle 时做的是**相反**的事：进入 **dormant**、等用户
下一句（P8.4 §1 整章主旨）。所以**在「无用户输入下自主持续」这条 `/goal` 的定义性轴上，
是 `/goal` 更激进，MTS 有意选择不那么激进** —— MTS **不是「更弱的 /goal」，是不同的续跑
策略**（dormant-on-idle vs force-continue-on-idle）。其余维度（多 agent 编排、P9 后台
续跑、P11 bg-run 续命、P8.4 待机闭环）MTS 更完善。

值得一提：被评估文档 §10–11 的 agentao 候选设计落到一条架构结论 ——「goal」不该进
harness core，是 **host 的产品概念**，由 drive-turn / inject-context / inject-tools 三个
通用原语组装、host 拥有 outer loop 与终结判定 —— **正是 ChaHua P8.3 早已落地的口径**
（P8.3 §0「调度层增量、不改对话原语、复用 drain loop / `HandoffItem` / cap，工具面零
改动」）。但二者**并非独立趋同**：ChaHua 本身就是 agentao 的 host，候选设计也是为 agentao
host、基于同一套原语写的；这是**同一基底上两个 host 都落到 host-owns-loop**、互为佐证，
而非各自独立撞到同一边界。

所以本文的产出不是「移植计划」，而是**从 `/goal` 拆解里提炼 MTS 当前缺的 5 个设计点**
（§4，按性价比排序；§4.5 为 v4 对照已发布实现后追加）+ **明确不借鉴的 3 项**（§5）。

## 2. codex `/goal` 是什么（自包含速览）

> 详见被评估文档 §1–9，此处只留对照所需的最小骨架，供未读原文者自包含理解。

codex `/goal` 是**单 agent 长任务自动续跑机制**，以可插拔扩展（`codex-rs/ext/goal/`）
实现，核心是一个持久化的 `ThreadGoal`（per-thread、SQLite、六态机
`Active | Paused | Blocked | UsageLimited | BudgetLimited | Complete`），由三柱驱动：

1. **agent 工具**：`get_goal` / `create_goal` / `update_goal` —— agent **只能**把 goal
   标 `complete` 或 `blocked`（且 `blocked` 须「同一阻塞条件连续 ≥3 个 goal 回合」才合法，
   重 prompt engineering 防 agent 钻空子）。
2. **steering 注入**：每轮把隐藏的 continuation 模板注入为一条 `ResponseItem`；objective
   被当**不可信数据** XML 转义、包 `<untrusted_objective>`。其中 `continuation.md` 的核心
   目的是**对抗 agent 把目标缩成最容易通过的子任务**。
3. **auto-drive loop**：`on_thread_idle → continue_if_idle → try_start_turn_if_idle`——
   thread 一空闲且 goal 仍 Active，扩展**自动起一个新 turn** 注入 continuation。这是「agent
   停不下来」的引擎。

外加一层**accounting**：按 token / wall-clock 增量记账，耗尽自动翻 `BudgetLimited` 并
**mid-turn** 注入 wrap-up steering。写权限三分：**user**（create/pause/resume/clear/edit）、
**agent**（仅 complete/blocked）、**system**（budget/usage limit）。

**agentao 候选设计（§10–11）的关键决策（2026-06-23 maintainer）**：token budget out of
scope，只用 time / turn-count；goal 是**纯 host 侧 outer loop**（`while goal.active:
agent.chat(continuation)`），harness Layer 1 **无需改动**（三原语已存在）；agent 写口只留
一个注入工具 `update_goal(complete|blocked)`，**不给 `create_goal`**（goal 由用户 `/goal
<objective>` 创建）。

### 2.1 v4 更新：候选设计已落地（agentao 0.4.18）

上段的「候选设计」到 0.4.18 已是**已发布实现**，落在三个文件：

| 模块 | 内容 |
|---|---|
| `agentao/cli/goal_state.py` | `GoalState`（`objective` + 预算 + 用量）、`GoalStatus` **五态**机 `active / paused / complete / blocked / limit_reached`，落 `.agentao/goal.json` |
| `agentao/tools/goal.py` | `UpdateGoalTool` —— enum 仅 `{complete, blocked}`，active-only 守卫；`is_read_only=True`（好让 analysis-only goal 也能自标完成，不被 read-only 模式挡住） |
| `agentao/cli/input_loop.py` | `run_goal_continuation` —— host 侧 `while goal.is_active:` 外循环；`_continuation_prompt` / `_wrap_up_prompt` 两个模板；`commands/goal.py` 提供 `/goal show|clear|pause|resume|edit|budget` |

**实现相对设计有两处收敛，均印证本文原判断**：

- **六态 → 五态**：codex 的 `UsageLimited` + `BudgetLimited` 合成单一 `limit_reached`
  （`goal_state.py` 模块 docstring 明写）。
- **token budget 确实被丢掉**：同 docstring —— "Drops codex's `token_budget` /
  `tokens_used` (time/turn budgets only)"。§5 第 1 行的「agentao 自己已决定 out of
  scope」由实现坐实。默认 `--turns 25` / `--for 120m`，`--unbounded` 退出默认上限；
  help 文案逐字写着 "first to trip wins; `--turns` is NOT `max_iterations`" —— §4.2
  设计的 first-to-trip-wins 也照做了。

**一条对 ChaHua 的硬事实（§3 末那条架构结论的实测确认）**：`/goal` 落在 `agentao/cli/`，
`UpdateGoalTool` 是 `run_goal_continuation` 期间临时 `add_tool` 注入的（其 docstring 明写
"NOT registered in `agent.py::_register_tools()`"）。ChaHua 走 `Agentao.arun()` SDK 路径，
**拿不到任何一部分** —— `grep -rn 'update_goal|goal.json|run_goal_continuation|GoalState'
chahua/ app/renderer/` **零命中**。两套 goal 平行存在、互不知情，可借的仍只有设计点。

一条架构事实需先讲清：被评估文档 §11 的「Layer 1 harness 无需改动、goal 是纯 host 侧
loop」意味着 —— **即便 agentao 把 `/goal` 实现成它自己 CLI host 的功能，ChaHua（agentao
的另一个 host）也拿不到任何免费提升**，仍得自己写 host 侧续跑 loop。而那个 loop ChaHua
已经写了，就是 MTS。所以「接入 agentao `/goal`」没有可借的**实现**，只有可借的**设计点**
（§4）。

**§3 末 · idle 反差再强调**（§1 已提，因它最容易把对照读偏）：把 MTS 当「多 agent 版
/goal」是对的，但别因此以为 MTS 在**所有**轴上都 ⊇ /goal —— 恰恰在 /goal 的看家本领
「无人催也不停」上，MTS 反向选择了 dormant（P8.4 §1）。要在 ChaHua 复刻「停不下来」需
另立设计，且与 P8.4 的待机哲学直接冲突，未必想要。这条不是缺口，是**有意的策略分叉**。

## 4. 值得借鉴的 delta（按性价比排序）

### 4.1 反「目标缩水」的 continuation 审计提示 —— 最便宜、最值得

codex 的 `continuation.md`（文档 §4）核心目的是**对抗 agent 把目标缩成最容易通过的
子任务**（原文「Do not substitute a narrower, safer, smaller solution because it is
more likely to pass current tests」），并要求「完成」在逐条核验前一律视为**未证实**。

ChaHua 的 `<managed_session>` 块（`context_renderer.py:107-122`，函数
`render_managed_session_block`）当前是 **5 条 bullet**：① 直接 `propose_delegate` /
`propose_panel`；② 忽略 `propose_*` ack 的「等用户采纳」语义；③ 并发用
`spawn_agent_runs`（别拿 `propose_panel` 当并发工具，panel 串行 drain）；④ 没下一步就
讲完、进入 dormant；⑤ Goal 达成用 `task_propose_status("done")` 收尾。**它有派活 /
ack 纠偏 / bg 并发 / idle / done，唯独缺 completion-fidelity / anti-shrinking 审计**——
对一个自主驱动多步任务的 manager，「我是真做完了，还是只做完了简单的部分」恰好是头号
失效模式。

**借鉴形态（注意承重不变量，别低估改动面）**：`context_renderer.py:99-102` 的 docstring
把「块**第 ② 条**作废 `propose_*` 等待语义」钉成 CLAUDE.md MTS 不变量，并要求「P14 后
**5 条 bullet 顺序保持不变**」；`tests/test_mts_spawn_boundary.py::test_managed_session_block_mentions_spawn_agent_runs`
还按「**第 ③ 条**」引用 spawn bullet。所以**不能简单「加第 6 条 bullet」**（破坏「5 条 +
顺序不变」不变量），也不能插在中间（移位 ② / ③ 锚点）。两条合规路径：

- **首选（不改条数）**：把 anti-shrinking 并进现有第 ⑤ 条「Goal met?」——例如
  `Goal met only after verifying the full task scope (do NOT shrink the goal to an
  easier-to-pass subset); then call task_propose_status("done") ...`。条数仍 5、② / ③
  锚点不动、现有断言全绿，只需**新增**一条「块含 anti-shrinking 文案」断言。
- **次选（真要独立第 6 条）**：必须同步更新 `context_renderer.py:99-102` docstring 的
  不变量措辞 + **两处不变量正本**（CLAUDE.md MTS 段 **与 `docs/INVARIANTS.md:133`** ——
  P14「`<managed_session>` 块 5 条 bullet 顺序不变」，按「改不变量两处同步」规矩双写）的
  「块第 ② / 第 ③ 条」条目编号 + `tests/test_mts_spawn_boundary.py` 对「第 ③ 条」的引用
  断言。改动面明显更大。

两条都仍是**纯 prompt**（不动逻辑、不 bump `schema_version`），但**只有首选配得上「最小
patch」**。落地接触面（首选）：`render_managed_session_block` 第 ⑤ 条文案 + 一条渲染
断言 + `examples/personas/Maya/skills/task-management/SKILL.md` 口径同步。按 P8.4 §5
「prompt 改对比工具改对成本低」的同一判断，这仍是 4 项里唯一「现在就能做」的。

**一处取舍（别把首选说成与 codex 等价）**：codex `continuation.md` 的 anti-shrinking 是
**贯穿每轮的保真指令**；并进第 ⑤ 条「Goal met?」语义偏向**完成闸门**（"做完没"），而非
"别在干活途中缩目标"。块虽每轮都注入（5 条 bullet 每轮都在 manager 眼前），但措辞挂在
done-check 下，模型更可能只在收尾时套用。要 codex 级保真度，该挂一条**始终生效**的独立
bullet（→ 反而偏次选）。结论：MVP 取首选够用，但它是「**更便宜、覆盖更窄**」，不是等价。

### 4.2 wall-clock 时间预算轴

MTS budget 只有 turn-count（`ManagedSession.budget` = manager 复查回合数）。文档
§11.1-B 的精到之处：`--for <duration>` 计**累计活跃 wall-clock、排除 pause 时间**，与
turn-count「first-to-trip-wins」，且刻意把时间默认调到 turn-cap 之上以免互相遮蔽。

**缺口（精确划界，别夸大失控）**：MTS 已有**两道 turn 数护栏** —— `cap_reached`
（`max_consecutive_ai_turns`，`_orchestrator_managed_session.py:143`）+ 每个 turn 内部
agentao `max_iterations`。所以失控**不是**「turn 数无界」，而是 **「turn 数有界、单 turn
墙钟无界」**：一个 worker 跑慢 `pytest` / `uv sync` / web-fetch 是**一个** turn，
turn-count 完全不约束它的墙钟。`--for <duration>` 正好补这条独立轴。

**ChaHua 特有的注意点**（决定它不是显然该建）：

- turn 是流式且可后台跑（P9），墙钟在后台房语义更模糊；
- MTS 现在只在 turn 之间（`advance_after_turn` 的 `stop_reason()`）查终结。**v4 修订**：
  原文写「要让时间预算及时生效**需**配 mid-turn 检查」（codex 走 `inject_active_turn_steering`
  在 budget 耗尽时 mid-turn 注入 wrap-up）—— 这条**说过头了**。agentao 0.4.18 实现选了
  **loop 顶部 pre-check**（`input_loop.py::run_goal_continuation` 每轮开头 `budget_tripped()`），
  即 mid-turn 是**及时性（timeliness）的可选升级，不是时间预算的前提**。代价说清楚：
  between-turn 粒度下，超支最多溢出**一个** turn（一个跑 30 分钟的 worker turn 不会被
  打断），而这恰好是 §4.2 划界的那个「单 turn 墙钟无界」缺口 —— **粗粒度时间预算收窄
  它但不消灭它**。ChaHua 的 `stop_reason()` 位置与 agentao 的 pre-check 天然同构，走
  粗粒度可完全不碰 mid-turn；
- 加时间轴 = 给 `ManagedSession` 加字段 + `stop_reason()` 加一条 + 配置闭环（参 P8.3 的
  `budget` 闭环纪律），是真功能而非小 patch。

**评估结论**：待评估、非立项。若立项，按「`budget`（turn）/ `time_budget`（wall-clock）
first-to-trip-wins」做，沿用 P8.4「5 reason 收敛」把它折进 `budget_exhausted` 还是新增
reason 需另议。

### 4.3 `blocked` 的防过早放弃审计（terminal 概念 ChaHua 已有）

**先纠正一个易犯的误判**：ChaHua **早就有 `blocked`**。`task.py:32` 的 7 态含 `blocked`、
`task.py:56` display `"blocked"`、前端 `events.js::TASK_STATUS_OPTIONS` 也有；manager 现在
就能 `task_propose_status("blocked", reason=…)` —— 工具描述（`task_tools.py:280`）逐字写
着 "blocked when stuck"。所以 §3 表里 codex `update_goal(complete/blocked)` 的二分，ChaHua
**两侧都覆盖**（done + blocked），不是缺口。

**真正缺的两点（窄得多）**：

1. **防过早放弃的审计节流**：codex 要求 `blocked` 须「同一阻塞 ≥3 连续回合才合法」
   （文档 §3 / §11.1-E.1，防 agent 一卡就撂挑子）。ChaHua 的 `task_propose_status` 对
   `blocked` **无**这层节流，manager 可能一遇阻碍就 propose blocked。**纯 prompt 级**借鉴，
   可与 §4.1 合进同一个 `<managed_session>` 块改动。
2. **`blocked` 与 MTS 收尾解耦**：`blocked` 是**非终结**态（`tasks_store.py:63`，
   `CLOSED_STATUSES` 只 done/abandoned），故采纳 blocked 走 `update_task`、任务仍 active →
   MTS `stop_reason()` **不收尾**、继续 dormant。是否要让「采纳 blocked → MTS 暂停 / 收尾」
   是个**待评估的语义选择**，**不是**「加第 6 个 reason」（blocked 本就非终结，与 P8.4
   「5 reason 收敛」不冲突）。

**评估结论**：第 1 点（≥3 回合审计）可随 §4.1 顺手做；第 2 点（blocked↔MTS 联动）待有
实际需求再定。原稿「ChaHua 没有 blocked 终态」的判断作废。

### 4.4 单茶客 goal —— 与 MTS 高度重叠的一个特例形态

`/goal` 本质是**单 agent** 续跑；MTS 是它的**多 agent 版**。ChaHua 没有「单茶客自主续跑」
这个形态 —— P11 的 bg run 经核是**单 turn**（`_server_agent_run.py:358` 一次 `guest.speak()`），
不是续跑 loop。

**别把它说成全新机制**：单茶客 goal 在概念上很可能就是 **MTS 的退化特例**（manager 即唯一
参与者、worker 集为空），或 **「bg run 外面套一个续跑 loop」**（注意是**新加** loop，不是
"复用"现成 loop —— bg run 本身不循环）。所以它的价值不在"新颖"，在"**用更轻的形态覆盖 MTS
杀鸡用牛刀的场景**"（一个茶客啃一个长目标、不需要 manager/worker 编排）。

需要回答的设计问题：续跑挂前台 turn 还是 bg run？终结判定复用 `stop_reason()` 还是单独一
套？做成独立机制还是「MTS 单人特例」？**待评估，非立项** —— 若产品确有"单人长任务"诉求
才值得开。

### 4.5 budget 撞顶的收尾轮（v4 追加，对照已发布实现新发现）

**现状（写于 v4 立项时；P8.7 已落地，本段描述的是改前状态）**：MTS budget 耗尽后
**直接消失**。`stop_reason()` 命中 `budget <= 0` 返
`budget_exhausted`（`_orchestrator_managed_session.py:131`），调用方 `end_managed_session`
清 `_managed_session` + 清 `_handoff_queue` + emit `managed_session_ended` —— 没有任何
总结轮。用户侧观感：「托管中 · 剩余 N 轮 · 点击停止」那条 bar 悄悄没了，要知道跑到哪了
得自己往回翻聊天记录拼。

**agentao 的做法**（`input_loop.py::run_goal_continuation`）：loop 顶部 pre-check →
`mark_limit_reached()` → 跑**恰好一轮** `_wrap_up_prompt` → `break`。模板逐字是
"Do not start new substantive work. Summarize the progress made toward this goal, list
the remaining work or blockers, and give the user a clear next step."

**为什么这条独立于 §4.2 值得单列**：它**不依赖时间预算**，挂在既有 turn-count budget 上
就能做（§4.2 的 mid-turn 讨论把它一并埋掉了，见 §4.2 v4 修订）。而且在 P8.4「5 reason
收敛」的五个 reason 里，`budget_exhausted` 是**唯一「活干到一半、纯资源到点」**的那个：
`task_closed` 是任务真结束（用户已知情）、`user_stopped` / `user_cancel` 是用户自己按的
（用户在场）、`cap_reached` 是罕见护栏。**恰恰最需要交接的那一个，现在最沉默。**

**落地形态（v4 初稿草案已被 P8.7 评审推翻，保留作对照）**：v4 写的是「`stop_reason()` 命中
`budget_exhausted` 时不立即 end，而是**再 enqueue 一条** manager DELEGATE 注入 wrap-up
指令，跑完再 end」，并列了四个坑（收尾轮不得再扣 budget / 不得再派活 / 与 `cap_reached`
交互 / 不新增 reason）。

**这个形态是过度设计**。P8.7 评审指出：既有 worker 回合是**先 `budget -= 1` 再入队管理者
复查**（`_orchestrator_managed_session.py:298`），所以**最后一次管理者复查本来就跑在
`budget == 0` 上，它天然就是终局回合** —— 只需把那一轮注入的块换成收尾块，**一个回合都不用
加**。四个坑里有三个（瞬态 flag / 清队列 / cap 余量守卫）**是「插入回合」这个选择自己制造
的问题**，不是需求本身的复杂度；随插入回合一并消失。

**评估结论**：**已落地 → [`P8.7-MTS 预算收尾轮.md`](P8.7-MTS%20预算收尾轮.md)**（v2 简化稿，
2026-08-01）。最终形态是 prompt 分流 + proposal 收口：新块 +
`_build_winner_blocks` 里一处 `budget <= 0` 二选一 +
`intercept_task_proposal` 一处 swallow；不加状态字段、不动调度 / 队列 / cap，测试 3 条且
不改任何既有断言。**本节的教训值得记**：对照一个「host 侧 while 循环」的实现时，容易连它的
*控制流形态*（跑完一轮再 break）一起搬过来；而 ChaHua 的 drain loop 已经把那一轮**排好了**，
只差 prompt。
